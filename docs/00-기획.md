# DDD 학습 교재 제작 기획서

## 1. 목적과 대상 독자

**목적**: DDD(Domain-Driven Design)를 처음 배우는 개발자가 혼자 읽으면서 학습할 수 있는
HTML 교재를 만든다. 블로그 글 모음이 아니라 **한 권의 책**처럼 앞장이 뒷장의 토대가 되는 구조.

**대상 독자 (나 자신)**
- 프로그래밍은 할 수 있다. Python 코드를 읽는 데 어려움이 없다.
- **DDD를 모른다.** Entity, Aggregate, Bounded Context 같은 단어를 들어본 적이 없거나 뜻을 모른다.
- **소프트웨어 아키텍처를 처음 공부한다.** 계층형 아키텍처, 헥사고날, 의존성 역전 같은 개념도
  전제하지 않는다. 필요한 지점에서 그때그때 설명해야 한다.
- 실무에서 쓸 수 있는 판단력을 원한다. 용어 암기가 아니라 "내 프로젝트에 이걸 쓸까 말까"를
  스스로 판단할 수 있는 상태가 목표.

**독자가 전제하지 않아도 되는 것**: DDD 용어, 아키텍처 패턴, ORM 심화 지식, 이벤트 기반 시스템 경험.
**독자가 전제해도 되는 것**: Python 문법(클래스, 데코레이터, 타입 힌트), 관계형 DB와 SQL 기초,
HTTP API를 만들어 본 경험.

## 2. 학습 목표 (교재를 다 읽은 뒤 할 수 있어야 하는 것)

1. 트랜잭션 스크립트로 짠 코드의 문제를 지적하고, 도메인 모델로 옮기는 리팩터링을 할 수 있다.
2. 주어진 요구사항에서 Entity / Value Object를 구분하고, Aggregate 경계를 근거와 함께 그을 수 있다.
3. 불변식(invariant)을 코드로 강제하는 애그리게이트를 Python으로 작성할 수 있다.
4. Repository와 Application Service를 분리해 유스케이스를 조립할 수 있고, 트랜잭션 경계를 설명할 수 있다.
5. 도메인 이벤트로 애그리게이트 간 결합을 낮추고, 결과적 일관성의 대가를 설명할 수 있다.
6. 하나의 시스템을 Bounded Context로 쪼개고, Context Map으로 관계(ACL·공유 커널·순응자 등)를 표현할 수 있다.
7. **DDD를 쓰지 말아야 할 상황을 판단할 수 있다.** (이게 빠지면 교재가 실패다)

## 3. 관통 도메인 시나리오 — "한빛몰"

모든 장의 예제는 **하나의 가상 회사**를 계속 파고든다. 장마다 도메인이 바뀌면 앞장의 코드가
뒷장에서 쓸모없어지고, 독자는 매번 새 도메인을 이해하는 데 힘을 쓴다.

### 3.1 회사 개요

**한빛몰**: 생활용품·식품을 파는 온라인 쇼핑몰. 외주 물류(3PL)를 쓰지 않고 **자체 물류창고**를
운영한다. 창고에는 로케이션(랙 위치)이 있고, 같은 상품(SKU)이 여러 로케이션에 나뉘어 보관된다.
식품을 팔기 때문에 **유통기한**이 있고, 먼저 들어온 재고를 먼저 내보내야 한다.

이 설정을 고른 이유: 재고 할당·부분 출고·취소/환불·유통기한처럼 **불변식과 동시성 문제가 자연스럽게
발생하는** 도메인이라, DDD 개념을 "왜 필요한지"로 설명할 수 있다. 억지 예제(도서관 대출, 은행 계좌
이체)를 만들지 않아도 된다.

### 3.2 Bounded Context (초안 — 9장에서 독자와 함께 다시 도출한다)

| 컨텍스트 | 책임 | 핵심 관심사 |
|---|---|---|
| **카탈로그** (Catalog) | 상품 정보, 판매가, 카테고리, 판매 상태 | "무엇을 파는가" |
| **주문** (Ordering) | 주문 접수, 주문 변경/취소, 주문 금액 계산 | "고객이 무엇을 사기로 했는가" |
| **재고** (Inventory) | SKU별 실물/가용 재고, 입고 배치, 재고 할당 | "지금 팔 수 있는 수량이 몇인가" |
| **창고** (Warehouse) | 로케이션, 피킹 지시, 실사(재고 조정) | "물건이 창고 어디에 있는가" |
| **배송** (Shipping) | 출고, 송장, 택배사 연동, 배송 추적 | "언제 어떻게 고객에게 가는가" |
| **결제** (Payment) | PG 연동, 승인/취소/부분 환불 | "돈을 받았는가" |
| **회원** (Membership) | 회원 등급, 배송지 주소록 | "누가 사는가" |

교재 초반(1~8장)은 **주문 + 재고**에 집중한다. 창고·배송·결제는 9장 이후 컨텍스트를 나누는
장에서 본격적으로 등장한다. 회원/카탈로그는 조연.

### 3.3 핵심 애그리게이트와 불변식

이 표가 교재 전체의 기준선이다. 각 장은 여기에 정의된 불변식을 코드로 만들어 간다.

**`Order` (주문) — 주문 컨텍스트**
- 구성: 루트 `Order`, 내부 엔티티 `OrderLine`, 값 객체 `Money`, `Address`, `Quantity`, `OrderNumber`
- 불변식:
  - I1. 주문 라인이 최소 1개 있어야 한다.
  - I2. 주문 총액 = Σ(라인 소계) − 할인액 + 배송비. 항상 성립해야 한다.
  - I3. 라인 수량은 1 이상이다.
  - I4. `결제완료` 이후에는 라인을 추가/삭제/수량변경할 수 없다.
  - I5. 주문 취소는 `출고시작` 전까지만 가능하다. 그 이후는 "반품" 이라는 다른 개념이다.
  - I6. 주문 시점의 상품명·판매가는 **스냅샷으로 복사**한다. 카탈로그에서 가격이 바뀌어도
        과거 주문 금액은 변하지 않는다. (→ 6장 "주문은 왜 Product를 참조하지 않는가")
- 상태: `생성됨 → 결제대기 → 결제완료 → 출고준비 → 출고됨 → 배송완료` / (`취소됨`)

**`InventoryItem` (SKU 재고) — 재고 컨텍스트**
- 구성: 루트 `InventoryItem`(SKU 단위), 내부 엔티티 `StockBatch`(입고 배치: 입고일·유통기한·수량)
- 불변식:
  - I7. 가용수량 = 실물수량 − 예약수량. 항상 성립.
  - I8. 예약수량 ≤ 실물수량. (초과 예약 불가)
  - I9. 어떤 수량도 음수가 될 수 없다.
  - I10. 할당은 유통기한이 가장 이른 배치에서 먼저 빠진다(FEFO). 유통기한이 지난 배치에는
        할당할 수 없다.
- 이 애그리게이트가 **동시성 예제의 주인공**이다. (동시에 두 주문이 마지막 1개를 잡으면?)

**`PickingOrder` (피킹 지시서) — 창고 컨텍스트**
- 구성: 루트 `PickingOrder`, 내부 `PickingLine`(SKU, 로케이션, 지시수량, 피킹수량)
- 불변식:
  - I11. 모든 라인이 피킹 완료되기 전에는 출고 처리할 수 없다.
  - I12. 피킹수량 ≤ 지시수량.
  - I13. 결번 처리(로케이션에 물건이 없음)된 라인은 다른 로케이션으로 재지시해야 한다.

**`Payment` (결제) — 결제 컨텍스트**
- 불변식: I14. 환불 누계 ≤ 승인 금액. I15. 승인되지 않은 결제는 환불할 수 없다.

**`Product` (상품) — 카탈로그 컨텍스트**
- 불변식: I16. 판매가 ≥ 0. I17. `판매중지` 상품은 신규 주문에 담을 수 없다(기존 주문은 유효).

### 3.4 도메인 이벤트 (7장 이후 사용)

`주문됨(OrderPlaced)` · `재고할당됨(StockAllocated)` · `재고부족(OutOfStock)` ·
`결제승인됨(PaymentApproved)` · `피킹지시생성됨(PickingOrderIssued)` · `출고됨(Shipped)` ·
`주문취소됨(OrderCancelled)` · `재고조정됨(StockAdjusted)`

### 3.5 컨텍스트 간 관계 (10장에서 다룸)

- 주문 → 재고: 고객/공급자(Customer-Supplier). 주문이 "할당해달라"고 요청한다.
- 주문 → 결제(외부 PG): **순응자(Conformist) + ACL**. PG의 이상한 응답 코드를 우리 언어로 번역.
- 카탈로그 → 주문: 스냅샷 복사(위 I6). 공유 커널을 쓰지 **않는** 선택의 근거를 설명.
- 창고 → 배송: 출고 이벤트로 연결(결과적 일관성).
- 배송 → 외부 택배사: ACL.

### 3.6 유비쿼터스 언어 초안 (8장에서 확장, 부록에 용어집)

| 용어 | 뜻 | 혼동하기 쉬운 것 |
|---|---|---|
| SKU | 재고 관리 최소 단위 | "상품"은 카탈로그 개념, SKU는 재고 개념 |
| 할당(Allocation) | 특정 주문을 위해 재고를 잡아두는 것 | 실물이 움직인 게 아니다 |
| 피킹(Picking) | 창고에서 물건을 꺼내는 작업 | 출고(Shipping)의 전 단계 |
| 결번 | 지시된 로케이션에 물건이 없는 상황 | 재고 부족과 다르다 |
| 출고 | 물건이 창고를 떠남 | 배송완료와 다르다 |
| FEFO | 유통기한 이른 것 먼저 출고 | FIFO(입고 순)와 다르다 |

## 4. 교재의 형태 — 결정 사항

### 4.1 페이지네이션: "장(chapter) → 화면(screen)" 방식으로 간다

**결정**: 장마다 HTML 파일 1개. 한 장은 여러 개의 **화면(screen)** 으로 나뉘고,
이전/다음 버튼과 ←/→ 키로 넘긴다. 화면 번호 표시(`7 / 12`), 진행률 바, 좌측 목차 사이드바.

**왜 A4 고정 높이 진짜 페이지네이션을 안 하는가**: 콘텐츠를 고정 높이 박스에 리플로우하려면
JS로 높이를 측정해 자동 분할해야 하는데, 코드 블록·다이어그램·표가 페이지 경계에서 잘리는 문제를
계속 손봐야 한다. 학습 교재의 본질(내용)이 아니라 레이아웃 엔진을 만드는 일에 시간이 간다.
**화면 단위는 저자가 의미 단위로 직접 끊기 때문에** 오히려 읽기 흐름이 좋다.
인쇄용 CSS(`@media print`)는 나중에 선택적으로 붙인다. — 이 결정은 다시 논의하지 않는다.

### 4.2 파일 구조

```
docs/
  index.html            표지 + 전체 목차 + 학습 트랙 안내
  ch01.html ~ chNN.html 각 장 (내용은 HTML에 인라인)
  glossary.html         용어집 (부록)
  assets/
    book.css            공통 스타일 (라이트/다크)
    book.js             화면 넘김, 진행률, 퀴즈 채점, 진도 저장, 코드 하이라이팅
```

### 4.3 `file://` 로 열리는 것을 전제한 기술 제약

이 파일들은 git에 커밋되고, **로컬에서 파일을 더블클릭해서 열린다.** 웹서버가 없다.
따라서:

- **`fetch()` 로 로컬 .md/.json 을 읽지 않는다.** Chrome의 `file://` CORS 정책에 막힌다.
  → 모든 본문은 각 장 HTML에 인라인으로 넣는다.
- **`<script type="module">` 을 쓰지 않는다.** 같은 이유로 막힌다. 일반 `<script src>` 는 된다.
- **CDN 의존 금지.** 오프라인/사내망에서도 열려야 한다. 외부 라이브러리를 쓰지 않는다.
- **코드 하이라이팅**: highlight.js 같은 걸 CDN에서 받지 않고, `book.js` 안에 Python 전용
  간단 하이라이터(키워드/문자열/주석/데코레이터/숫자 정규식 수준, 약 40줄)를 직접 넣는다.
- **Pyodide(브라우저 Python 실행)는 쓰지 않는다.** 수 MB를 네트워크로 받아야 하고,
  아키텍처를 처음 배우는 독자에게 "코드를 브라우저에서 돌려보는 것"보다
  **잘 하이라이팅된 코드 + 잘 만든 퀴즈**가 학습 효과가 크다. 코드를 직접 돌려보고 싶으면
  에디터에 복사해서 돌리는 게 낫다.
- **진도 저장은 `localStorage`**. `file://` 에서도 동작하지만 브라우저/시크릿모드에 따라
  실패할 수 있으므로 try/catch로 감싸고, 없어도 교재는 정상 동작해야 한다.

### 4.4 인터랙티브 요소 (넣을 것만)

1. **화면 넘김** — 버튼 + ←/→ 키 + 진행률 바.
2. **장 끝 퀴즈** — 객관식/OX. 정답 확인 시 **왜 그런지 해설**이 펼쳐진다. 해설이 본문의 일부다.
3. **Before/After 코드 탭** — "나쁜 코드 / 리팩터링 결과"를 탭으로 전환해 같은 자리에서 비교.
4. **접히는 상자** — "더 깊이" (심화 내용, 처음 읽을 때는 건너뛰어도 됨), "흔한 오해".
5. **용어 툴팁** — 유비쿼터스 언어 용어에 밑줄, 마우스 올리면 뜻이 뜬다.
6. **진도 체크** — 읽은 장에 체크 표시(localStorage).
7. **다이어그램** — 인라인 SVG로 직접 그린다(라이브러리 없음). 애그리게이트 경계, 컨텍스트 맵,
   계층 구조, 이벤트 흐름.

넣지 않을 것: 브라우저 코드 실행, 서버 필요한 기능, 로그인, 검색 엔진(장 수가 적어 목차로 충분).

### 4.5 예제 코드 방침

- 기본 언어는 **Python**. 타입 힌트와 `@dataclass` 를 쓴다. 프레임워크 의존 최소화.
- ORM이 필요한 부분은 SQLAlchemy를 예로 들되, **매핑 코드는 개념 설명에 필요한 만큼만** 보여준다.
- 코드는 장을 넘어가며 **누적**된다. 3장의 `Order` 를 5장에서 확장하는 식.
  "앞장에서 만든 것" 을 화면 하나로 요약해 상기시켜 준다.
- 실행 가능한 프로젝트 코드(`examples/` 디렉터리, pytest)는 **이번 범위에 넣지 않는다.**
  교재를 다 쓴 뒤 필요하면 별도로 추가한다.

## 5. 서술 방침

- **개념 → 이름 순서.** 문제 상황과 코드를 먼저 보여주고, 그것에 붙은 이름을 나중에 알려준다.
  ("이렇게 값 자체로 동등성을 판단하는 객체를 값 객체(Value Object)라고 부른다.")
- **1장은 나쁜 코드로 시작한다.** 뚱뚱한 서비스 함수와 빈혈 모델(anemic model)을 먼저 보고
  "이게 왜 아픈가"를 느낀 뒤에 해법을 배운다.
- 매 장 끝: **핵심 요약 3~5줄 + 퀴즈 + "직접 해보기" 과제 1개.**
- 원전 표기: Evans 책(Blue Book), Vernon 책(Red Book/IDDD), 『만들면서 배우는 클린 아키텍처』,
  『파이썬으로 살펴보는 아키텍처 패턴』(cosmic python)에서 온 개념은 출처를 밝힌다.
  독자가 다음 책으로 넘어갈 때 길잡이가 된다.
- 반대 의견도 쓴다. "애그리게이트는 작게" 같은 규칙이 언제 틀리는지, DDD가 과한 프로젝트는 어떤
  프로젝트인지 명시한다.

## 6. 분량 목표

- 장 수: **15장** (0장 포함) + 용어집 부록
- 장당 화면: 6~14 화면 → 전체 약 170 화면
- 장당 독자 학습 시간: 1.0~2.5시간 (읽기 + 퀴즈 + 직접 해보기)
- **총 예상 학습 시간: 약 30시간** (선택 장 제외 시 28.5시간)

구체적인 장 목록과 장별 시간, 학습 트랙(하루 몇 시간 × 몇 주)은 `01-커리큘럼.md` 에서 정한다.

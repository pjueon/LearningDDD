왜 DDD인가
잘 돌아가는 나쁜 코드

DDD를 배우는 가장 빠른 길은 DDD가 없는 코드에서 직접 아파보는 것입니다. 이 장에서는 패턴을 하나도 배우지 않습니다. 대신 한빛몰의 초기 코드를 읽고, 요구사항 세 개를 차례로 끼워 넣으면서 그 코드가 어떻게 썩는지 관찰합니다.

이 장의 진행

  1. 한빛몰의 "주문하기" 요구사항을 읽습니다.
  2. 그 요구사항을 가장 자연스러운 방식으로 구현한 코드를 봅니다. 이 코드는 잘 돌아갑니다.
  3. 현실적인 요구사항 변경 세 개를 순서대로 반영합니다.
  4. 6개월 뒤의 코드를 놓고 정확히 무엇이 아픈지 진단합니다.
  5. 이 상태에 붙은 이름(트랜잭션 스크립트, 빈혈 도메인 모델)을 배웁니다.
  6. 그리고 이 방식이 정답인 경우도 확인합니다.

중요한 태도

앞으로 볼 코드를 비웃지 마세요. 이 코드는 실력 없는 사람이 쓴 코드가 아닙니다. 요구사항을 가장 짧은 경로로 정확히 구현한, 성실한 코드입니다. 문제는 코드 실력이 아니라 코드가 자라는 방향에 있습니다. 그 방향을 볼 수 있게 되는 것이 이 장의 목표입니다.

요구사항: "주문하기"

주문팀 은수가 개발팀에 넘긴 첫 요구사항입니다. 한빛몰 서비스 오픈을 앞둔 시점입니다.

주문하기

고객이 상품과 수량을 골라 주문하면, 재고를 확인하고 결제를 진행한 뒤 주문을 확정한다.

  1. 주문에는 상품이 하나 이상 담겨야 한다.
  2. 판매 중지된 상품은 주문할 수 없다.
  3. 재고가 부족하면 주문을 받지 않는다.
  4. 재고는 유통기한이 이른 것부터 잡는다.
  5. 주문 금액은 (상품 가격 × 수량)의 합이고, 3만 원 미만이면 배송비 3,000원을 더한다.
  6. 결제가 실패하면 주문 전체를 취소한다. 재고도 원상복구해야 한다.
  7. 주문이 확정되면 고객에게 확인 메일을 보내고, 창고 슬랙 채널에 알린다.
  8. 주문 시점의 상품명과 가격을 그대로 보관한다. 나중에 상품 가격이 바뀌어도 과거 주문 금액은 변하지 않아야 한다.

요구사항 여덟 개. 애매한 것도 없고, 이상한 것도 없습니다. 읽으면 바로 코드가 떠오릅니다. 실제로 개발팀은 이걸 이틀 만에 만들어 배포했습니다.

잠깐 — 8번 요구사항이 눈에 걸렸다면

"주문 시점의 상품명과 가격을 보관한다"는 조항은 데이터베이스 정규화를 배운 사람에게는 거슬립니다. 상품 테이블을 참조하면 되는데 왜 값을 복사할까요? 이 조항이 이 교재에서 가장 여러 번 다시 등장하는 요구사항입니다. 6장에서 정면으로 다룹니다.

# ordering/views.py — 한빛몰 v1def place_order(request):
    body = json.loads(request.body)
    customer_id = body["customer_id"]
    items = body["items"]                    # [{"product_id": 12, "qty": 2}, ...]
    address = body["address"]

    if not items:
        return JsonResponse({"error": "주문할 상품이 없습니다"}, status=400)

    conn = db.connect()
    tx = conn.begin()
    try:
        order_id = conn.execute(
            "INSERT INTO orders (customer_id, status, zipcode, road, "
            "detail, receiver, phone, total) "
            "VALUES (%s, '결제대기', %s, %s, %s, %s, %s, 0) RETURNING id",
            (customer_id, address["zipcode"], address["road"], address["detail"],
             address["receiver"], address["phone"]),
        ).scalar()

        total = 0
        for item in items:
            product = conn.execute(
                "SELECT * FROM products WHERE id = %s", (item["product_id"],)
            ).one()
            if product["status"] != "판매중":
                raise ValueError(f"{product['name']}은 판매 중지된 상품입니다")

            available = conn.execute(
                "SELECT COALESCE(SUM(quantity - reserved), 0) FROM stock_batches "
                "WHERE product_id = %s", (item["product_id"],)
            ).scalar()
            if available < item["qty"]:
                raise ValueError(f"{product['name']} 재고가 부족합니다")

            # 유통기한이 이른 배치부터 예약한다
            remain = item["qty"]
            batches = conn.execute(
                "SELECT * FROM stock_batches WHERE product_id = %s ORDER BY expires_on",
                (item["product_id"],)
            ).all()
            for b in batches:
                if remain == 0:
                    break
                take = min(b["quantity"] - b["reserved"], remain)
                conn.execute(
                    "UPDATE stock_batches SET reserved = reserved + %s WHERE id = %s",
                    (take, b["id"]),
                )
                remain -= take

            line_total = product["price"] * item["qty"]
            total += line_total
            conn.execute(
                "INSERT INTO order_lines (order_id, product_id, product_name, "
                "unit_price, qty, line_total) "
                "VALUES (%s, %s, %s, %s, %s, %s)",
                (order_id, product["id"], product["name"], product["price"],
                 item["qty"], line_total),
            )

        # 3만원 미만이면 배송비 3,000원
        if total < 30000:
            total += 3000

        conn.execute("UPDATE orders SET total = %s WHERE id = %s", (total, order_id))

        pg = pg_client.approve(customer_id=customer_id, amount=total, order_id=order_id)
        if pg["resultCode"] != "0000":
            raise ValueError("결제 실패: " + pg["resultMsg"])

        conn.execute(
            "UPDATE orders SET status = '결제완료', pg_tid = %s WHERE id = %s",
            (pg["tid"], order_id),
        )
        tx.commit()
    except Exception as e:
        tx.rollback()
        return JsonResponse({"error": str(e)}, status=400)

    mailer.send(customer_id, "주문이 접수되었습니다", render_order_mail(order_id))
    slack.notify("#창고", f"신규 주문 {order_id}")
    return JsonResponse({"order_id": order_id})

이 코드는 잘 돌아간다

이 대목을 건너뛰면 이 장을 잘못 읽게 됩니다. 위 코드의 장점을 먼저 인정하고 갑시다.

이 코드가 좋은 이유

  • 읽는 순서 = 벌어지는 순서. 위에서 아래로 읽으면 무슨 일이 일어나는지 알 수 있습니다. 추적할 파일이 하나입니다.
  • 이틀 만에 나왔습니다. 클래스 설계 회의도, 추상화 논쟁도 없었습니다.
  • 테스트가 통과했습니다. 정상 주문, 재고 부족, 판매 중지, 결제 실패 — 네 가지 경로를 모두 테스트했고 다 통과합니다.
  • 실제로 잘 팔립니다. 오픈 첫 달 주문 2만 건을 이 코드가 처리했습니다.

DDD를 이야기하는 글들은 이런 코드를 "안티패턴"이라 부르며 시작합니다. 그건 절반만 맞습니다. 이 코드의 진짜 문제는 지금 보이지 않습니다. 문제는 시간과 함께 옵니다.

이제 실제로 벌어진 요구사항 변경 세 개를 순서대로 반영해 보겠습니다. 각 변경은 그 자체로는 아주 합리적이고, 크지도 않습니다.

변경 1 — 회원 등급 할인

은수 — 회원 등급을 도입합니다. 일반/실버/골드예요. 실버는 3%, 골드는 5% 할인. 그리고 골드는 금액 상관없이 무료배송입니다. 배송비 기준 3만 원도 골드는 안 봐요.

기존 코드에서 금액을 계산하는 부분은 두 군데입니다. 라인 소계를 더하는 곳과 배송비를 붙이는 곳. 거기에 끼워 넣습니다.

# ordering/views.py — 금액 계산 부분만            line_total = product["price"] * item["qty"]

        grade = conn.execute(
            "SELECT grade FROM customers WHERE id = %s", (customer_id,)
        ).scalar()

        discount = 0
        if grade == "실버":
            discount = int(total * 0.03)
        elif grade == "골드":
            discount = int(total * 0.05)
        total -= discount

        # 3만원 미만이면 배송비 3,000원

여기서 벌어진 일

버그는 아닙니다. 코드는 적힌 대로 정확히 동작합니다. 문제는 아무도 이 결정을 하지 않았다는 것입니다. "할인을 배송비 판정 전에 적용한다"는 업무 규칙이 total -= discount라는 한 줄의 위치로 결정되어 버렸습니다.

이런 결정은 코드 리뷰에서 보이지 않습니다. 리뷰어는 "총액에서 할인을 뺀다"는 것만 확인하고 통과시킵니다. 순서가 규칙이라는 사실을 코드가 말해주지 않기 때문입니다.

은수와 상의해서 "배송비는 할인 전 금액으로 판정한다"로 정했습니다. 이제 total 하나로는 안 됩니다. 할인 전 금액을 따로 들고 있어야 합니다. 변수 하나가 늘어납니다.

변경 3 — 주문 취소

지민 — 고객이 직접 주문을 취소할 수 있게 해주세요. 단, 이미 출고된 건은 안 됩니다. 출고된 다음에는 반품으로 처리해야 해요.

새 함수를 하나 만듭니다. place_order는 건드리지 않으니 안전해 보입니다.

# ordering/views.py — 새 함수def cancel_order(request, order_id):
    conn = db.connect()
    tx = conn.begin()
    try:
        order = conn.execute("SELECT * FROM orders WHERE id = %s", (order_id,)).one()

        if order["status"] == "출고됨":
            raise ValueError("이미 출고된 주문은 취소할 수 없습니다")

        lines = conn.execute(
            "SELECT * FROM order_lines WHERE order_id = %s", (order_id,)
        ).all()
        for line in lines:
            # 예약해 둔 재고를 풀어준다
            remain = line["qty"]
            batches = conn.execute(
                "SELECT * FROM stock_batches WHERE product_id = %s AND reserved > 0 "
                "ORDER BY expires_on", (line["product_id"],)
            ).all()
            for b in batches:
                if remain == 0:
                    break
                give_back = min(b["reserved"], remain)
                conn.execute(
                    "UPDATE stock_batches SET reserved = reserved - %s WHERE id = %s",
                    (give_back, b["id"]),
                )
                remain -= give_back

        if order["pg_tid"]:
            pg_client.cancel(tid=order["pg_tid"], amount=order["total"])

        conn.execute("UPDATE orders SET status = '취소됨' WHERE id = %s", (order_id,))
        tx.commit()
    except Exception as e:
        tx.rollback()
        return JsonResponse({"error": str(e)}, status=400)

    mailer.send(order["customer_id"], "주문이 취소되었습니다", render_cancel_mail(order_id))
    return JsonResponse({"ok": True})

도현

피킹까지 다 끝내고 포장하려는데 주문이 취소됐다고 나와요. 물건을 다시 갖다 놔야 하는데 로케이션이 어딘지 모르겠어요.

원인은 이렇습니다. 주문 상태에는 '출고준비'가 있고, 이 상태는 이미 창고 직원이 피킹을 시작한 상태입니다. 그런데 취소 조건은 status == "출고됨" 하나만 막고 있었습니다.

"취소 가능 여부" 규칙이 지금 몇 군데에 있나

  1. cancel_order() — status == "출고됨"이면 거부
  2. 관리자 화면의 취소 버튼 표시 조건 — status not in ("출고됨", "배송완료", "취소됨")
  3. 고객 앱의 취소 버튼 표시 조건 — status in ("결제대기", "결제완료") (모바일팀이 따로 짰습니다)
  4. CS 어드민의 강제 취소 — 조건 없음. 지민이 쓰는 화면입니다.

네 곳의 조건이 모두 다릅니다. 그리고 어느 것이 "맞는" 규칙인지 아무도 모릅니다. 문서에는 "출고 전까지 취소 가능"이라고만 적혀 있고, 출고가 무슨 뜻인지는 0장에서 봤듯이 사람마다 다릅니다.

고객 앱이 버튼을 숨기고 있어서 지금까지 사고가 안 났던 것입니다. 모바일팀이 조건을 조금만 바꾸면 언제든 같은 사고가 다시 납니다.

1장 · 화면 8

6개월 뒤: 무엇이 아픈가

요구사항 세 개를 반영했을 뿐인데, 지금 코드의 상태를 정리하면 이렇습니다. 막연히 "복잡해졌다"고 넘기지 않고 정확한 이름을 붙여 봅시다. 진단이 정확해야 처방이 나옵니다.

통증 1 — 규칙이 코드 위치로 결정된다

"할인을 배송비 판정 전에 적용한다"는 규칙은 total -= discount 한 줄의 위치였습니다. 누가 이 줄을 세 줄 아래로 옮기면 업무 규칙이 조용히 바뀝니다. 테스트가 그 케이스를 안 잡고 있으면 아무도 모릅니다.

통증 2 — 같은 규칙이 여러 곳에 복사된다

"팔 수 있는 재고"는 다섯 곳, "취소 가능 여부"는 네 곳에 있습니다. 그리고 조건이 서로 다릅니다. 규칙을 바꾸려면 먼저 규칙이 어디 있는지 찾는 조사부터 해야 하고, 그 조사는 절대 완벽하지 않습니다.

통증 3 — 업무 규칙을 테스트하려면 세상을 다 준비해야 한다

"골드 회원이 29,000원어치를 사면 배송비가 붙는가?"를 확인하려면 데이터베이스, 상품 데이터, 재고 배치, 회원 등급, PG 목(mock), 메일 목, 슬랙 목이 필요합니다. 금액 계산 규칙 하나 검증하는 데 인프라 전체가 필요합니다. 그래서 실제로는 이런 테스트를 안 씁니다.

통증 4 — 읽어도 업무를 알 수 없다

place_order는 이제 90줄이 넘습니다. 이 함수를 읽으면 SQL, JSON 파싱, 트랜잭션 관리, PG 응답 코드, 메일 발송이 보입니다. "한빛몰이 주문을 어떻게 처리하는가"는 보이지 않습니다. 업무를 알고 싶으면 코드가 아니라 은수에게 물어봐야 합니다.

통증 5 — 규칙을 어길 방법이 너무 많다

데이터베이스의 orders 테이블은 누구나 UPDATE할 수 있습니다. 배치 스크립트, 관리자 화면, 데이터 보정 쿼리, 다른 팀의 신규 기능 — 이 중 어느 것도 "출고된 주문은 취소할 수 없다"를 지킬 의무가 없습니다. 규칙은 cancel_order()라는 한 통로 안에만 있고, 통로는 여러 개입니다.

통증 5가 가장 중요합니다

1~4는 불편함이고, 5는 구조적 결함입니다. 규칙을 지키는 것이 "모든 개발자가 잊지 않고 그 함수를 호출하는 것"에 달려 있다면, 그 규칙은 이미 깨져 있는 것과 같습니다. 사람은 잊습니다. 신입은 그 함수의 존재를 모릅니다.

DDD의 핵심 아이디어를 한 문장으로 미리 말하면 이렇습니다 — 규칙을 지키는 유일한 통로를 만들고, 그 통로를 통하지 않으면 데이터를 바꿀 수 없게 한다. 3장에서 이걸 애그리게이트라는 이름으로 배웁니다.

1장 · 화면 9

이 상태에 붙은 이름

지금까지 본 코드 스타일에는 이름이 있습니다. 널리 쓰이는 이름이니 알아두면 대화가 짧아집니다.

트랜잭션 스크립트 (Transaction Script)

트랜잭션 스크립트는 하나의 요청을 처음부터 끝까지 절차적으로 처리하는 하나의 함수를 말합니다. "요청 하나 = 스크립트 하나"입니다. Martin Fowler가 Patterns of Enterprise Application Architecture(2002)에서 붙인 이름입니다.

place_order와 cancel_order가 정확히 이것입니다. 이 방식에서 업무 규칙은 함수의 실행 순서로 표현됩니다.

빈혈 도메인 모델 (Anemic Domain Model)

한빛몰 코드에도 "모델"은 있습니다. 다만 이렇게 생겼습니다.

# models.py — 있긴 있는 모델@dataclass
class Order:
    id: int
    customer_id: int
    status: str
    total: int
    pg_tid: str | None

@dataclass
class OrderLine:
    order_id: int
    product_id: int
    product_name: str
    unit_price: int
    qty: int
    line_total: int

데이터를 담는 상자입니다. 행동이 하나도 없습니다. Order는 자기가 취소될 수 있는지 모르고, 자기 총액을 계산할 줄도 모릅니다. 그 지식은 전부 views.py의 함수들에 있습니다.

이런 모델을 빈혈 도메인 모델이라고 부릅니다. Martin Fowler가 2003년에 안티패턴으로 지목하면서 붙인 이름입니다. 피(행동)가 빠진 껍데기라는 뜻입니다.

이 두 이름의 관계

둘은 항상 같이 나타납니다. 규칙이 스크립트에 있으면 모델은 비게 되고, 모델이 비어 있으면 규칙은 스크립트로 갈 수밖에 없습니다. ORM을 쓰면 "모델 클래스"가 생기니까 도메인 모델이 있다고 착각하기 쉽지만, 필드만 있는 클래스는 모델이 아니라 테이블의 그림자입니다.

더 깊이 — 왜 "빈혈"이 안티패턴인가, 반론까지

빈혈 모델을 옹호하는 주장도 있습니다. "데이터와 로직을 분리하면 각각 테스트하기 쉽고, 함수형 스타일에 가깝다"는 것입니다. 실제로 규칙이 단순하고 조합이 적은 시스템에서는 이 주장이 맞습니다.

문제는 규칙이 서로 얽힐 때 생깁니다. "결제 완료 후에는 라인을 못 바꾼다", "라인이 바뀌면 총액을 다시 계산한다", "총액이 바뀌면 배송비 판정을 다시 한다" — 이 세 규칙은 서로를 참조합니다. 데이터와 규칙이 떨어져 있으면 이 얽힘을 표현할 곳이 없어서, 결국 모든 스크립트가 세 규칙을 각자 알고 있어야 합니다.

Fowler 본인의 표현을 빌리면, 빈혈 모델은 "객체지향의 비용은 다 내고 이득은 하나도 못 받는" 상태입니다. 클래스와 매핑 코드는 다 쓰면서, 정작 객체가 자기 규칙을 지키는 이득은 못 얻습니다.

1장 · 화면 10

그런데 이게 정답인 경우

여기서 균형을 잡고 갑시다. 트랜잭션 스크립트는 안티패턴이 아닙니다. Fowler가 빈혈 모델을 안티패턴이라 부른 것과 달리, 트랜잭션 스크립트는 정당한 선택지로 소개된 패턴입니다.

트랜잭션 스크립트가 더 나은 경우

  • 규칙이 거의 없는 CRUD. 게시판, 설문, 관리자 화면. "저장하고 꺼내는 것"이 업무의 전부라면 도메인 모델을 만들 이유가 없습니다. 만들면 코드가 3배가 되고 얻는 게 없습니다.
  • 규칙이 한 번 정해지고 안 바뀌는 경우. 정산 배치, 데이터 마이그레이션, 리포트 생성. 규칙이 안 바뀌면 "규칙을 한 곳에 모으는" 이득이 작습니다.
  • 규칙이 데이터 집합 연산인 경우. "지난달 카테고리별 매출 상위 10개"는 객체 100만 개를 메모리에 올려 계산하는 것보다 SQL 한 방이 옳습니다. 13장에서 이 이야기를 다시 합니다.
  • 수명이 짧은 코드. 3개월 뒤 버릴 이벤트 페이지에 설계를 투자하는 것은 낭비입니다.

그럼 한빛몰의 주문 처리는 왜 다를까요? 세 가지 신호가 있습니다.

신호한빛몰에서 관찰된 것
규칙이 많다 주문 하나에 얽힌 규칙이 이미 20개가 넘습니다. 최소 수량, 금액 계산 순서, 판매 상태, 유통기한 여유, 등급 할인, 배송비 기준, 취소 가능 시점, 재고 예약 순서…
규칙이 자주 바뀐다 6개월에 세 번 바뀌었고, 앞으로 더 자주 바뀔 것입니다. 프로모션과 물류 정책은 회사가 살아 있는 동안 계속 바뀝니다.
규칙을 어기면 돈을 잃는다 유통기한 지난 식품 출고, 재고 초과 판매, 출고 후 취소. 전부 실제 손해와 고객 신뢰로 이어집니다.

판단 기준으로 정리하면

DDD는 규칙이 많고, 자주 바뀌고, 어기면 손해가 나는 영역에 씁니다. 셋 중 하나라도 아니라면 트랜잭션 스크립트로 짜고 그 시간을 다른 데 쓰는 것이 낫습니다.

그리고 한 시스템 안에서 두 방식을 섞는 것이 정상입니다. 한빛몰에서도 주문과 재고는 도메인 모델로 가고, 공지사항과 배너 관리는 끝까지 CRUD로 갑니다. 14장에서 이 전략을 다룹니다.

도메인, 도메인 모델, 도메인 로직

이 세 낱말은 앞으로 계속 나옵니다. 지금 정확히 구분해 둡시다.

낱말뜻한빛몰에서는
도메인 소프트웨어가 다루는 업무 영역 그 자체. 코드가 아닙니다. 회사에 소프트웨어가 없어도 도메인은 존재합니다. 온라인 판매와 창고 물류. 은수·도현·지민이 매일 하는 일.
도메인 모델 그 업무를 이해한 방식을 표현한 구조. 업무의 사진이 아니라 지금 풀려는 문제에 필요한 만큼만 추린 지도입니다. Order가 라인을 갖고, 총액을 계산하고, 취소 가능 여부를 판단한다는 구조.
도메인 로직 업무 규칙을 실제로 구현한 코드. 업무 담당자와 이야기할 수 있는 것만 도메인 로직입니다. "3만 원 미만이면 배송비 3,000원", "출고 후에는 취소 불가"

도메인 로직과 그 밖의 것을 가르는 질문

"이걸 은수에게 설명하면 알아들을까?"

"3만 원 미만이면 배송비 3,000원" — 알아듣습니다. 도메인 로직입니다.
"PG 응답의 resultCode가 0000이면 성공" — 못 알아듣습니다. 이건 기술적 세부사항입니다. 은수가 아는 것은 "결제가 됐는지 안 됐는지"뿐입니다.

이 구분이 10장의 ACL(부패 방지 계층)로 이어집니다.

class OrderingService:

    def place_order(self, cmd: PlaceOrderCommand) -> OrderNumber:
        with self.uow:
            items = self.catalog.snapshot(cmd.items)      # 상품명·가격 스냅샷

1장 마무리

핵심 요약

  1. 트랜잭션 스크립트는 요청 하나를 절차적으로 처리하는 함수입니다. 빠르게 만들 수 있고, 읽는 순서가 벌어지는 순서라 직관적입니다.
  2. 규칙이 많아지면 규칙이 코드 위치로 결정되고, 여러 곳에 복사되고, 테스트하려면 인프라 전체가 필요하고, 읽어도 업무를 알 수 없고, 규칙을 어길 통로가 여러 개가 됩니다.
  3. 필드만 있고 행동이 없는 모델을 빈혈 도메인 모델이라 부릅니다. 트랜잭션 스크립트와 항상 같이 나타납니다.
  4. DDD는 규칙이 많고, 자주 바뀌고, 어기면 손해가 나는 영역에 씁니다. 그렇지 않은 곳에는 쓰지 않는 것이 옳습니다.
  5. 도메인은 업무 영역 그 자체, 도메인 모델은 그것을 이해한 구조, 도메인 로직은 업무 담당자와 이야기할 수 있는 규칙의 코드입니다.

다음 중 도메인 로직이 아닌 것은 무엇일까요?

  1. 유통기한이 3일 미만 남은 재고는 주문에 할당하지 않는다
  2. PG사 응답이 타임아웃이면 3회까지 재시도한다
  3. 출고된 주문은 취소할 수 없고 반품으로 처리한다
  4. 골드 회원은 주문 금액과 무관하게 배송비가 없다

해설 판별 질문은 "업무 담당자와 이 규칙을 두고 대화할 수 있는가"입니다. 재시도 3회는 은수가 정할 일이 아니고, 정해도 업무에 영향이 없습니다. 반면 "골드는 무료배송"은 은수가 정하고, 바뀌면 매출이 바뀝니다.

다만 경계가 늘 뚜렷하지는 않습니다. "결제가 3회 실패하면 주문을 자동 취소한다"라면 이건 도메인 로직입니다. 고객이 겪는 결과가 달라지고, 은수가 결정할 문제이기 때문입니다. 같은 재시도 이야기라도 누가 결정하는지에 따라 갈립니다.

화면 8의 통증 다섯 개 중, 저자가 "구조적 결함"이라고 따로 지목한 것은 무엇이었나요? 그리고 그 이유는?

  1. 규칙이 여러 곳에 복사되는 것 — 유지보수 비용이 커지기 때문
  2. 테스트에 인프라 전체가 필요한 것 — 테스트를 안 쓰게 되기 때문
  3. 함수가 길어 업무를 알 수 없는 것 — 신규 입사자가 이해하지 못하기 때문
  4. 규칙을 어길 통로가 여러 개인 것 — 사람의 기억에 규칙 준수를 의존하기 때문

해설 1~4번 통증은 비용의 문제입니다. 고생하면 버틸 수 있습니다. 5번은 보장의 문제입니다. 아무리 고생해도 "이 규칙이 항상 지켜진다"고 말할 수 없습니다.

이 차이가 DDD의 여러 패턴이 존재하는 이유입니다. 애그리게이트(3장)는 규칙을 지키는 유일한 통로를 만들고, 리포지토리(4장)는 그 통로를 우회하는 데이터 접근을 막고, 계층 구조(5장)와 헥사고날 아키텍처(11장)는 그 통로가 기술 코드에 오염되지 않게 지킵니다.

팀에서 새 프로젝트를 시작합니다. 사내 공지사항 게시판입니다. 글 작성·수정·삭제, 첨부파일, 읽음 표시가 전부입니다. 어떻게 하는 것이 옳을까요?

  1. 트랜잭션 스크립트로 짠다. 도메인 모델을 만들지 않는다
  2. 지금은 단순하지만 나중을 대비해 애그리게이트로 설계한다
  3. 회사 표준이 DDD이므로 게시판도 같은 구조로 맞춘다
  4. 읽음 표시 규칙이 있으므로 그 부분만 도메인 모델로 만든다

해설 규칙이 많지도, 자주 바뀌지도, 어겨서 손해가 나지도 않습니다. 셋 다 아니므로 DDD를 쓸 이유가 없습니다.

이 판단을 못 하면 DDD는 비용만 내는 장식이 됩니다. 실무에서 "DDD 했는데 별로였다"는 이야기의 상당 부분이 이 판단 실패에서 나옵니다. 14장 전체가 이 주제입니다.

직접 해보기

화면 7에서 본 "취소 가능 여부" 규칙이 네 곳에 흩어져 있고 조건이 모두 다릅니다. 지금 배운 것 없이, 여러분이 아는 방법으로 이 문제를 고쳐 보세요. 코드를 쓰지 않고 3~5줄로 설명해도 됩니다.

그리고 여러분의 해법에 대해 이 질문에 답해 보세요 — "6개월 뒤 이 코드를 처음 보는 신입이 그 규칙을 우회할 수 있는가?"

모범답안 — 그리고 흔한 해법이 왜 부족한지

흔한 해법 1: 함수로 뽑는다

def can_cancel(order) -> bool:
    return order["status"] in ("결제대기", "결제완료")

네 곳이 이 함수를 부르면 조건은 하나가 됩니다. 좋은 개선입니다. 실제로 이것만 해도 이 장에서 본 사고는 막혔을 것입니다.

부족한 점: 부르지 않으면 아무 일도 일어나지 않습니다. 모바일팀은 이 함수의 존재를 모르고, 데이터 보정 쿼리는 함수를 부를 수 없습니다. UPDATE orders SET status='취소됨' WHERE id=123 한 줄이면 규칙은 통과됩니다. 통증 5가 그대로 남습니다.

흔한 해법 2: DB 제약으로 막는다

트리거나 CHECK 제약으로 상태 전이를 막는 방법입니다. 우회가 불가능해지므로 통증 5에는 강력합니다. 실제로 쓰이는 방법입니다.

부족한 점: 규칙이 업무 언어를 잃습니다. "출고된 주문은 취소할 수 없다"가 트리거의 SQL 조건으로 번역되면, 은수는 그것을 읽을 수 없고 개발자도 6개월 뒤에 왜 그 조건인지 모릅니다. 규칙이 여럿 얽히면(취소 + 라인 변경 + 총액 재계산) 트리거로는 표현이 급격히 어려워집니다.

이 교재가 가는 길

3장에서는 상태와 규칙을 같은 객체 안에 넣습니다.

class Order:
    def cancel(self) -> None:
        if self.status not in (OrderStatus.생성됨, OrderStatus.결제대기,
                               OrderStatus.결제완료):
            raise AlreadyShipped("출고가 시작된 주문은 취소할 수 없습니다")
        self.status = OrderStatus.취소됨

그리고 4장에서 status를 밖에서 대입할 수 없게 만듭니다. 주문 상태를 바꾸는 유일한 방법이 order.cancel()이 되면, 규칙을 우회하려면 일부러 노력해야 합니다. 잊어서 우회하는 일은 없어집니다.

핵심은 함수로 뽑는 것과 객체 안에 넣는 것의 차이입니다. 함수는 부를 수도 있고 안 부를 수도 있고, 객체의 메서드는 그 객체를 쓰는 한 반드시 거쳐야 합니다.

14장 · 화면 1

마무리
DDD를 쓰지 말아야 할 때

0장 화면 6은 이 문장으로 시작했습니다.

도메인 주도 설계(DDD)는 업무 규칙이 복잡한 소프트웨어를 만들 때, 업무 그 자체의 구조와 언어를 코드의 중심에 두는 설계 방식이다. 기술(데이터베이스, 프레임워크, API)은 그 중심을 감싸는 껍데기로 밀어낸다.

13개 장을 거치는 동안 이 문장 안의 낱말 하나하나에 코드가 붙었습니다 — "업무 그 자체의 구조"는 Order·InventoryItem 같은 애그리게이트가 됐고, "코드의 중심"은 헥사고날의 안쪽 원(11장)이 됐고, "껍데기"는 어댑터가 됐습니다. 그런데 이 문장은 처음부터 조건 하나를 이미 걸어 두고 있었습니다 — "업무 규칙이 복잡한 소프트웨어를 만들 때." 0장은 이 조건을 "미리 지워둘 오해 3 — DDD는 항상 옳다"에서 "아닙니다"라고 짧게만 반박하고 "14장이 다룬다"며 넘겼습니다. 이 장이 그 각주를 본문으로 끌어옵니다.

이 장은 이 교재의 마지막 장입니다

지금까지는 화면 끝마다 "다음 장에서 무엇을 다룹니다"라고 예고했습니다. 이 장에는 그 문장이 없습니다. 13장(CQRS· 이벤트 소싱)이 그랬듯, 이 장도 새 애그리게이트나 새 불변식을 만들지 않습니다 — 대신 지금까지 만든 것 전체를 한 걸음 물러나서 봅니다. 코드를 인용은 하지만, 그 코드에 무엇을 더 추가하기 위해서가 아니라 "이 복잡도가 정당했는가"를 따지기 위해서입니다.

이 장의 지도

  • 화면 2 · 도메인 복잡도 vs 기술 복잡도. 1장이 던진 판단 기준(규칙이 많고, 자주 바뀌고, 어기면 손해)을 한 프로젝트 전체로 확장합니다. CRUD에 DDD를 얹으면 정확히 무엇이 늘어나는지 봅니다.
  • 화면 3 · 핵심·지원·일반 하위 도메인. "쓸까 말까"를 프로젝트 단위가 아니라 하위 도메인 단위로 쪼갭니다. 그리고 어디를 사고 어디를 만들지를 판단합니다.
  • 화면 4 · 한빛몰 다시 보기. 9장이 나눈 일곱 컨텍스트를 이 기준으로 다시 분류하고, 이 교재가 실제로 만들지 않은 것들을 정직하게 짚습니다.
  • 화면 5 · 부분 도입 전략. 한 코드베이스 안에서 두 스타일이 공존하는 방법.
  • 화면 6 · 다음 걸음. 다음에 읽을 책 네 권과, 자기 프로젝트에 적용하는 첫 체크리스트.
  • 화면 7 · 마무리. 요약·퀴즈·과제, 그리고 교재를 닫는 글.

14장 · 화면 2

도메인 복잡도 vs 기술 복잡도

1장 화면 16은 트랜잭션 스크립트가 나은 경우를 이렇게 정리했습니다 — 규칙이 거의 없는 CRUD, 규칙이 한 번 정해지고 안 바뀌는 경우, 규칙이 데이터 집합 연산인 경우 (13장 화면 5의 읽기 전용 쿼리 객체가 실제로 이 판단을 실천해 보인 자리입니다), 수명이 짧은 코드. 그리고 화면 17 마지막 퀴즈는 "사내 공지사항 게시판"에 DDD를 얹으려는 팀원에게 뭐라고 답할지 물었습니다 — 정답은 "얹지 않는다"였습니다. 그 판단은 옳았지만, 화면 17의 해설은 짧은 한 문장으로 끝났습니다. "실무에서 'DDD 했는데 별로였다'는 이야기의 상당 부분이 이 판단 실패에서 나옵니다." 이 장이 그 실패가 실제로 어떤 모습인지 보여줄 차례입니다.

복잡도는 한 종류가 아니다

도메인 복잡도는 업무 규칙 그 자체의 얽힘입니다 — 한빛몰 주문의 "결제완료 이후 라인 변경 금지", "출고시작 이후 취소 불가", "골드는 배송비 무료" 같은 규칙들이 서로 참조하며 늘어나는 것입니다. 기술 복잡도는 그 규칙을 표현하려고 코드에 들이는 구조 — 애그리게이트, 리포지토리, 포트, 계층 — 그 자체의 부피입니다. DDD의 모든 패턴은 도메인 복잡도를 다루기 위해 기술 복잡도를 지불하는 거래입니다. 도메인 복잡도가 낮은 곳에 그 거래를 하면, 지불만 하고 돌려받는 것이 없습니다.

공지사항 게시판으로 이 거래를 실제로 해 보면 이렇게 됩니다(왼쪽 탭의 %s·RETURNING id·.scalar()는 1장 화면 6이 이미 설명한 그대로입니다).

def create_notice(db, title: str, body: str, author_id: int) -> int:
    return db.execute(
        "INSERT INTO notices (title, body, author_id) VALUES (%s, %s, %s) "
        "RETURNING id", (title, body, author_id)).scalar()

def update_notice(db, notice_id: int, title: str, body: str) -> None:
    db.execute("UPDATE notices SET title=%s, body=%s WHERE id=%s",
               (title, body, notice_id))

# domain: Notice(엔티티) + NoticeTitle·NoticeBody(값 객체)
# application: NoticeRepository(포트) + NoticeService
# infrastructure: SqlAlchemyNoticeRepository + ORM 매핑
# 규칙: "제목은 1자 이상 200자 이하" 하나뿐. 이걸 지키려고
#       클래스 5개, 매핑 코드, 포트 인터페이스가 새로 생긴다.
class Notice:                        # 엔티티 — 그런데 규칙이 하나뿐이다
    def __init__(self, title: "NoticeTitle", body: "NoticeBody") -> None:
        self.title, self.body = title, body

class NoticeRepository(Protocol):    # 포트 — 구현은 하나, 교체 계획 없음
    def get(self, notice_id: int) -> Notice: ...
    def add(self, notice: Notice) -> None: ...

오른쪽 코드가 왼쪽보다 "더 좋은 설계"가 아닙니다. 4장 화면 11~12의 기준을 그대로 다시 씁니다 — 리포지토리의 비용은 규칙 개수와 무관하게 고정이고, 이득은 규칙이 복잡할수록 커집니다. 규칙이 "제목 길이 하나"뿐인 곳에 포트·엔티티·값 객체를 얹으면, 비용은 그대로 내면서 이득은 거의 0입니다. 9장 화면 12가 컨텍스트 경계에 대해 했던 말이 여기도 그대로 적용됩니다 — "다른 팀의 정책이 바뀌었는데 내 코드를 고쳐야 한다"는 신호가 없으면, 경계도 계층도 정당화되지 않습니다.

DDD의 패턴은 전부 같은 저울 위에 있다

4장 화면 11~12가 리포지토리 하나를 두고 낸 판단("비용은 고정, 이득은 규칙 복잡도에 비례")은 이 교재가 만든 모든 패턴에 그대로 적용됩니다. 표로 정리하면 이렇습니다.

패턴고정 비용이득이 커지는 조건
애그리게이트(3장) 경계를 정하고 불변식을 메서드 뒤로 숨기는 설계 비용 불변식이 여럿이고, 어기면 실제 손해(재고 초과 판매 등)
리포지토리(4장) 인터페이스 + 구현 최소 두 벌 도메인 규칙이 복잡해 메모리 구현으로 빠르게 테스트해야 함
Unit of Work(5장) 커밋·롤백 경계를 관리하는 코드 한 켜 한 유스케이스가 애그리게이트 여러 개를 함께 바꿈
도메인 이벤트(7장) MessageBus, 구독·발행 배선 한 사실에 반응해야 하는 다른 애그리게이트·컨텍스트가 있음
바운디드 컨텍스트 분리(9장) 폴더 분리, 포트, 스냅샷 코드 여러 팀이 같은 낱말을 다른 뜻으로 쓰기 시작함(화면 4에서 계속)
부패 방지 계층(10장) 포트 + 값 객체 + 예외 한 벌 외부 모델의 응답 형식이 우리 코드 여러 곳에 흩어질 위험
헥사고날(11장) domain/application/infrastructure 계층 분리, 포트 개수만큼 DB·외부 API를 바꿀 가능성이 실제로 있고 팀이 여럿

10장 화면 12는 "PG사를 하나만 쓰고 바꿀 계획도 없다면 ACL 없이 직접 불러도 실무적으로 큰 문제가 없다"고 이미 인정했고, 11장 화면 11은 "포트 개수는 프로젝트 크기가 아니라 (DB·외부 API 교체 가능성, 업무 규칙 양, 팀 수라는) 세 신호가 얼마나 자주 나타나는가로 정해진다"고 못박았습니다. 이 장은 그 개별 판단들을 하나로 모읍니다 — 새 패턴을 볼 때마다 "이 표의 오른쪽 칸에 해당하는가?"를 먼저 묻는 것이 DDD를 쓸지 말지 판단하는 실제 방법입니다.

13장이 "이벤트 소싱 판단 기준을 더 넓은 범위로 다시 본다"고 남겨 둔 질문도 결국 이 저울 위에 있습니다 — 이벤트 소싱이 감당할 수 있는 복잡도를 더하는지는, 그게 적용되는 하위 도메인이 핵심인지 일반인지에 달려 있습니다 (다음 화면에서 이 구분을 봅니다).

14장 · 화면 3

핵심·지원·일반 하위 도메인

화면 2의 판단은 프로젝트 전체를 하나로 놓고 물었습니다. 그런데 실제 회사는 "전부 CRUD" 아니면 "전부 DDD"인 경우가 드뭅니다. 한빛몰 하나 안에도 주문·재고처럼 규칙이 복잡한 곳과, 공지사항·배너처럼 단순한 곳이 같이 있습니다. 그래서 판단의 단위를 프로젝트에서 하위 도메인 (subdomain)으로 한 단계 낮춥니다 — 하위 도메인은 업무 문제를 나눈 조각입니다. Evans의 원전(Blue Book)이 핵심 도메인과 일반 하위 도메인을 구분했고, 이후 DDD 문헌은 보통 그 사이에 지원 하위 도메인을 더해 세 가지로 나눕니다.

종류정의한빛몰이라면할 일
핵심 도메인
(Core Domain)		 이 회사가 다른 회사와 달라지는 지점. 잘하면 돈을 벌고 못하면 고객이 떠나는 곳 주문 + 재고 — 입고예정 판매·약속일·FEFO가 한빛몰의 차별점 애그리게이트·불변식·리포지토리 등 이 교재의 모든 패턴을 아낌없이 투자
지원 하위 도메인
(Supporting Subdomain)		 핵심을 돌아가게는 해야 하지만, 그 자체가 경쟁력은 아닌 곳 카탈로그, 회원 등급, 창고 로케이션 직접 만들되, 핵심만큼 정교한 설계를 들이지 않는다
일반 하위 도메인
(Generic Subdomain)		 어느 회사에나 있고, 이미 잘 만들어진 상용품이 있는 곳 결제 승인, 택배사 연동, 세금계산서 발행 직접 만들지 않는다 — 사거나 외부 서비스를 쓴다

"산다"가 곧 "포트도 필요 없다"는 아니다

10장이 이미 이 판단을 코드로 보여줬습니다 — 결제는 일반 하위 도메인이라 승인·환불 로직 자체는 PG사에서 삽니다. 그런데 "산다"가 "아무 코드도 안 짠다"는 뜻은 아닙니다. PG의 resultCode가 우리 도메인 언어로 새어 들어오지 않게 막을 경계(PaymentPort, 부패 방지 계층)는 직접 만듭니다. 일반 하위 도메인에서 직접 짓는 것은 "그 도메인의 로직"이 아니라 "그 도메인과 우리 도메인 사이의 국경"입니다.

8장 화면 8이 남긴 질문 — "모든 프로젝트가 이만큼 이름에 공들여야 하는가?" — 도 이 구분으로 답이 납니다. 유비쿼터스 언어·이벤트 스토밍 같은 투자는 핵심 도메인에서 값어치가 가장 큽니다. 규칙이 복잡하고 여러 팀이 같은 낱말을 다르게 쓰는 곳이 정확히 핵심 도메인이기 때문입니다. 일반 하위 도메인(결제)의 낱말은 이미 PG사의 API 문서가 정해 줍니다 — 거기에 우리 팀만의 유비쿼터스 언어를 새로 벼릴 이유가 작습니다.

흔한 오해 — 하위 도메인과 바운디드 컨텍스트는 다른 것이다

9장은 바운디드 컨텍스트를 "하나의 모델과 그 낱말들이 정확히 한 가지 뜻으로만 통하는 범위"라고 정의했습니다. 그건 모델(구현)의 경계입니다. 하위 도메인은 업무 문제 자체를 나눈 조각이고, 코드가 한 줄도 없어도 존재합니다. 화면 4의 표에서 한빛몰의 일곱 컨텍스트와 하위 도메인 분류가 거의 1:1로 겹치는 것은 9장이 애초에 그렇게 되도록 경계를 그었기 때문이지, 둘이 같은 개념이라서가 아닙니다. 실제로는 지원 하위 도메인 하나에 컨텍스트가 여럿 필요할 수도, 핵심 도메인 하나가 한동안 컨텍스트 분리 없이(9장 이전의 한빛몰처럼) 굴러갈 수도 있습니다.

14장 · 화면 4

한빛몰 다시 보기

9장 화면 12는 "컨텍스트를 나누는 비용은 여러 팀이 같은 낱말을 다른 뜻으로 쓰기 시작할 때부터 이익으로 바뀐다"고 했고, "14장에서 이 판단을 언제 내리는가를 더 다룬다"고 예고했습니다. 9장이 나눈 일곱 컨텍스트를 화면 3의 기준으로 다시 분류하면 이렇습니다.

배송일반 —(ShippingPolicy.lead_time 정책 값만) ShippingCarrierPort는 10장 화면 10에서 예시로만 등장, 구현 없음

이 교재가 코드로 만들지 않은 불변식 다섯 개 — 정직하게 기록

이 교재를 기획할 때 창고 컨텍스트에도 PickingOrder (피킹 지시서)라는 애그리게이트와 불변식 셋을 함께 정해 뒀습니다 — I11(모든 라인이 피킹 완료되기 전에는 출고 처리할 수 없다), I12(피킹수량 ≤ 지시수량), I13(결번 처리된 라인은 다른 로케이션으로 재지시해야 한다). 그런데 이 교재 어느 장도 PickingOrder를 실제 애그리게이트로 만들지 않았습니다. 창고 컨텍스트는 9장에서 StoredItem(로케이션 정보)까지만 들어왔습니다. 마찬가지로 결제 컨텍스트의 I14(환불 누계 ≤ 승인 금액)·I15(승인되지 않은 결제는 환불할 수 없다)도 10~12장이 거듭 "그 애그리게이트는 아직 이 교재 어디에도 없다"고 밝혔을 뿐, 실제로 만들지 않았습니다.

이건 실수로 빠뜨린 것이 아니라 범위를 정하며 뺀 것입니다. 창고팀의 결번·재지시까지 애그리게이트로 구현하면, 이 교재는 끝나지 않습니다. 결제도 마찬가지입니다 — 결제는 일반 하위 도메인이고, PG사가 이미 승인·거절·환불의 실제 판정을 갖고 있습니다. 우리 쪽에 Payment 애그리게이트를 따로 만드는 것은, "PG의 응답을 그대로 믿지 않고 우리 장부로도 한 번 더 검증하겠다"는 결정이고, 그 결정이 필요해지는 시점(환불 사고, 정산 감사 요구)이 오면 그때 가서 이 애그리게이트를 추가하면 됩니다. 지금은 그 시점이 아니라고 판단하고 미룬 것이며, 바로 이것이 이 장이 말하는 "범위를 정하는 판단"의 실물입니다.

이 분류가 유일한 정답은 아니다

만약 한빛몰이 "정확한 재고 예측"이 아니라 "업계에서 가장 빠른 당일 출고"로 차별화하는 회사였다면, 핵심 도메인은 주문·재고가 아니라 창고(피킹 동선 최적화) 쪽으로 옮겨 가고, 그때는 PickingOrder가 안 만든 쪽이 아니라 가장 공들여 만드는 애그리게이트가 됐을 것입니다. 핵심 도메인은 코드의 성질이 아니라 회사의 전략이 정합니다 — 같은 창고 시스템도 회사가 다르면 분류가 바뀝니다.

14장 · 화면 5

부분 도입 전략 — 한 코드베이스, 두 스타일

1장 화면 16은 이렇게 적어 뒀습니다 — "한 시스템 안에서 두 방식을 섞는 것이 정상입니다. 한빛몰에서도 주문과 재고는 도메인 모델로 가고, 공지사항과 배너 관리는 끝까지 CRUD로 갑니다. 14장에서 이 전략을 다룹니다." 화면 3~4가 "어디에"를 답했으니, 이제 "어떻게 한 코드베이스 안에 공존시키는가"를 봅니다.

11장 화면 6이 확정한 디렉터리 구조를 그대로 가져오면, 답은 이미 구조 안에 있습니다.

# 11장이 확정한 트리 + 지원 도메인 옆자리ordering/       domain/ application/ infrastructure/ web/   # 핵심 — 4계층 전부
inventory/      domain/ application/ infrastructure/ web/   # 핵심 — 4계층 전부
catalog/        domain/ application/ infrastructure/ web/   # 지원 — 규칙이 적어 domain/이 얇다
notices/        views.py  repository.py                      # CRUD — domain/ 자체가 없다

notices/에는 애초에 domain/ 폴더가 없습니다. 뷰 함수가 SQL을 직접 부르거나, 얇은 리포지토리 하나만 거칩니다 — 화면 2의 왼쪽 탭(create_notice)이 바로 이 모양입니다. 이것은 "아직 리팩터링을 못 한 부채"가 아니라 의도한 최종 상태입니다. catalog/는 그 중간입니다 — 9장에서 컨텍스트로는 분리했지만(폴더가 있다), 규칙이 "판매가 ≥ 0"(I16), "판매중지 상품은 담을 수 없다"(I17) 둘뿐이라 domain/ 안의 코드가 얇습니다.

판단 기준은 화면 2의 표를 그대로 다시 쓴다

새 기능을 어디에 넣을지 고민될 때마다, 화면 2의 저울("고정 비용 vs 규칙 복잡도")을 그 기능 하나에 대고 다시 재면 됩니다. 애그리게이트를 만들지, domain/ 폴더 자체를 만들지, 리포지토리를 인터페이스로 뺄지 — 세 질문 모두 같은 저울입니다. "우리 프로젝트는 DDD 프로젝트다/아니다"라고 프로젝트 전체에 한 번만 답하는 것이 아니라, 기능 단위로 계속 다시 묻는 것이 부분 도입의 실천입니다.

주의할 것 하나 — notices/가 커지기 시작하면(예: "공지사항에도 예약 발행·대상 회원 지정 규칙이 생긴다") 그 순간 다시 화면 2의 저울에 올려야 합니다. CRUD로 시작한 것을 나중에 도메인 모델로 옮기는 것은 부끄러운 일이 아니라 이 표를 제대로 쓰고 있다는 증거입니다. 반대로 "나중에 복잡해질 수도 있으니 미리 구조를 갖춰 두자"는 것은 1장 화면 17 퀴즈가 이미 틀렸다고 답한 선택지입니다.

자기 프로젝트에 적용하는 첫 스텝

  1. 하위 도메인을 나열한다. 지금 팀이 다루는 업무를 몇 개 덩어리로 쓸 수 있는가? (한빛몰이면: 주문, 재고, 카탈로그, 결제…)
  2. 각 덩어리에 화면 3의 표를 적용한다. "우리 회사가 이걸 잘해서 돈을 버는가, 아니면 이게 없으면 그냥 안 돌아가는가, 아니면 어느 회사나 똑같이 필요한가?"
  3. 핵심으로 분류된 것에만 화면 2의 저울을 다시 댄다. 규칙이 많고, 자주 바뀌고, 어기면 손해가 나는가? 그렇다면 애그리게이트부터 시작한다(3장) — 리포지토리·이벤트·컨텍스트 분리는 그다음이다.
  4. 지원·일반으로 분류된 것은 지금 스타일 그대로 둔다. 이미 트랜잭션 스크립트로 잘 돌아가고 있다면, "표준을 맞추자"는 이유만으로 건드리지 않는다(1장 화면 17 퀴즈).
  5. 포트 개수는 11장의 세 신호로만 늘린다. DB·외부 API를 바꿀 가능성, 업무 규칙의 양, 팀 수 — 이 셋이 자주 나타나지 않으면 포트를 추가하지 않는다.
  6. 컨텍스트 분리는 "다른 뜻으로 쓰는 팀이 생겼을 때"만 한다. 9장 화면 10의 세 질문(개념이 바뀌는 이유가 다른가, 같은 낱말인데 정의가 다른가, 누가 규칙을 책임지는가)을 그대로 쓴다.
  7. 다시 처음으로. 6개월 뒤 하위 도메인 분류를 다시 해 본다 — 지원이었던 것이 핵심으로 옮겨 가기도 한다(화면 4의 "분류가 유일한 정답은 아니다").

14장 · 화면 7

14장 마무리 — 그리고 이 교재를 마칩니다

핵심 요약

  1. DDD의 모든 패턴은 도메인 복잡도를 다루려고 기술 복잡도를 지불하는 거래입니다. 규칙이 적은 곳에 패턴을 얹으면 비용만 남고 이득이 없습니다.
  2. 판단은 프로젝트 전체가 아니라 하위 도메인 단위로 내립니다 — 핵심 도메인에는 아낌없이 투자하고, 지원 하위 도메인은 가볍게 직접 만들고, 일반 하위 도메인은 국경(포트)만 만들고 내부는 삽니다.
  3. 한 코드베이스 안에 여러 스타일이 공존하는 것이 정상입니다. notices/가 domain/ 폴더 없이 남아 있는 것은 부채가 아니라 설계입니다.
  4. 이 교재도 범위를 정하며 다섯 개의 불변식(PickingOrder의 I11~I13, 결제의 I14·I15)을 코드로 만들지 않았습니다 — 이것이 "범위를 정하는 판단"의 실제 사례입니다.
  5. 다음 걸음은 책 네 권(cosmic python → 『만들면서 배우는 클린 아키텍처』 → IDDD → Blue Book)과, 자기 프로젝트에 화면 6의 체크리스트를 적용해 보는 것입니다.

팀이 사내 "회의실 예약" 기능을 만듭니다. 규칙은 "같은 시간에 같은 회의실은 중복 예약 불가"뿐입니다. 한 개발자가 이렇게 제안합니다 — "예약도 도메인 객체니까 Reservation 애그리게이트와 ReservationRepository를 만들고, 나중에 화상회의 연동이 생길 걸 대비해 포트도 미리 빼 두자." 가장 적절한 반응은?

  1. 지원 하위 도메인이니 애그리게이트 없이 가볍게만 만들자고 절충한다
  2. 화상회의 연동은 확실히 올 변화이니 포트를 미리 만드는 것이 맞다
  3. 규칙이 하나뿐이니 DB 제약이나 간단한 함수로 처리하고, 포트는 지금 만들지 않는다
  4. 팀의 다른 코드가 전부 DDD 스타일이니 일관성을 위해 맞춘다

해설 "나중에 필요할 수도 있다"는 이유로 지금 구조를 갖추는 것은 1장 화면 17 퀴즈가 이미 오답으로 처리한 선택지입니다. 화상회의 연동이 실제 요구사항으로 확정되는 순간, 그때 포트를 추가해도 Reservation을 부르는 곳이 한두 곳뿐이라면 비용이 크지 않습니다.

한 쇼핑몰이 "세금계산서 자동 발행"과 "장바구니 추천 알고리즘"을 동시에 개발합니다. 화면 3의 기준으로 둘을 분류하면?

  1. 세금계산서 발행은 핵심 도메인, 추천 알고리즘은 일반 하위 도메인이다
  2. 세금계산서 발행은 일반 하위 도메인, 추천 알고리즘은 핵심 도메인이다
  3. 둘 다 핵심 도메인이다 — 둘 다 코드로 새로 만드는 기능이니까
  4. 둘 다 일반 하위 도메인이다 — 둘 다 상용 솔루션이 이미 있으니까

해설 화면 3의 표가 기준으로 삼은 것은 "코드로 새로 짜는가"가 아니라 "이 일을 잘하는 것이 이 회사만의 경쟁력인가"입니다. 세금계산서는 누가 발행하든 결과가 같아야 하는 일(오히려 다르면 문제)이고, 추천 알고리즘은 잘하면 매출이 바뀌는 일입니다.

이 교재가 PickingOrder(피킹 지시서, I11~I13)와 결제 애그리게이트(I14·I15)를 코드로 만들지 않은 이유로 가장 정확한 것은?

  1. 기획 단계에서 미처 생각하지 못했다가 뒤늦게 발견해서
  2. 피킹·환불에는 애초에 지켜야 할 규칙이 없어서
  3. 피킹·환불 로직은 Python으로 표현하기 어려운 규칙이라서
  4. 핵심 도메인(주문·재고)에 자원을 집중하고, 그 밖은 지금 당장 필요한 만큼만 만드는 판단을 이 교재도 실제로 내렸기 때문에

해설 화면 4가 정직하게 기록한 대로입니다. 실무에서도 "이 애그리게이트를 지금 만들지 말지"는 기술적으로 가능한가의 문제가 아니라, 그 하위 도메인이 지금 그 투자를 받을 만한가의 문제입니다.

직접 해보기

신선식품 정기배송 스타트업 "초록마트"에 합류했습니다. 지금 급한 개발 항목은 두 가지입니다.

  1. 구독 배송 규칙 — 주기(매주/격주), 건너뛰기, 일시정지, 다음 배송일 계산. 프로모션 시즌마다 규칙이 바뀌고, 잘못 계산하면 고객에게 이중 청구되거나 배송이 누락됩니다.
  2. 사내 공지사항 게시판 — 글 작성·수정·삭제뿐입니다.

화면 3~6의 기준으로 각각 어디에 DDD를 적용할지, 근거를 3줄로 적어 보세요.

모범답안
  • 구독 배송 규칙 — 핵심 도메인, DDD를 적용한다. "정기배송을 정확하고 유연하게 운영하는 것"이 이 회사의 경쟁력이고(화면 3의 정의 그대로), 규칙이 이미 여럿(주기·건너뛰기·일시정지)이며 앞으로도 바뀌고, 어기면 실제 손해(이중 청구, 배송 누락)가 납니다 — 화면 2의 저울(규칙 많고, 자주 바뀌고, 어기면 손해) 세 조건을 모두 만족합니다. Subscription 애그리게이트로 "다음 배송일" 계산과 "일시정지 중에는 청구하지 않는다" 같은 불변식을 메서드 뒤로 숨기는 것부터 시작합니다.
  • 공지사항 게시판 — CRUD로 남긴다. 규칙이 없고, 바뀔 것도 없고, 어겨도 손해가 나지 않습니다. 화면 2의 왼쪽 탭과 똑같은 모양의 함수 몇 개로 충분합니다.
  • 흔히 하는 실수 두 가지 — (1) "우리 회사 전체가 DDD로 간다"며 게시판에도 폴더 구조부터 갖추는 것(8장 화면 8·14장 화면 3이 반박한 논리 — 이름·구조에 공들일 값어치는 핵심 도메인에서 가장 크다). (2) 반대로 "아직 스타트업이라 다 나중에"라며 구독 배송까지 트랜잭션 스크립트로 미루는 것 — 1장이 보여준 대로, 규칙이 얽히기 시작한 뒤에 옮기는 리팩터링 비용이 처음부터 옮기는 것보다 훨씬 큽니다.

마지막으로 한 걸음 더

위 연습은 남이 만든 가상의 회사였습니다. 이 교재가 남기는 진짜 과제는 이것입니다 — "지금 내가 다니는 회사(또는 만들고 있는 프로젝트)에 DDD를 도입할까?"에 근거 있는 답을 3줄로 써 보세요. 정답을 확인해 줄 기준은 없습니다. 화면 2~6에서 배운 기준(도메인 복잡도, 하위 도메인 분류, 저울)을 실제로 써 보는 것 자체가 답입니다.

이 교재를 마치며

0장은 한빛몰의 은수·도현·지민이 같은 낱말을 다르게 쓰는 장면으로 시작했습니다. 그 뒤 13개 장을 거치며 그 낱말들은 OrderStatus의 값이 되고, Allocation이 되고, StoredItem이 됐습니다. 그리고 이 마지막 장은 그 모든 구조에 "항상 옳지는 않다"는 조건을 다시 걸었습니다 — 이 조건을 걸 수 있어야, 즉 언제 안 쓸지를 말할 수 있어야 비로소 DDD를 안다고 말할 수 있습니다. 0장 화면 6의 오해 3이 처음부터 가리키고 있던 자리가 여기였습니다.

부록으로 용어집도 준비돼 있습니다. 지금까지 만난 용어를 한자리에서 다시 찾아보고 싶다면 그쪽을 보세요. 각 장 본문의 밑줄 친 용어 툴팁과 같은 정의를, 교재에 등장한 순서대로 모아 뒀습니다.

여기까지 읽으셨다면, 3장 화면 6이 물었던 "왜 주문과 재고를 하나의 애그리게이트로 묶지 않는가"에 이제 스스로 답할 수 있을 것입니다 — 그리고 그보다 더 중요한 질문, "이걸 안 써도 되는 곳은 어디인가"에도 답할 수 있을 것입니다. 수고하셨습니다.

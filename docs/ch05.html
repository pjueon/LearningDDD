Application Service
계층 구조와 유스케이스 조립

4장에서 OrderRepository와 InventoryRepository를 만들었습니다. 그런데 아직 아무도 이 둘을 동시에 열지 않습니다. 주문 하나를 만들려면 카탈로그에서 가격을 묻고, 회원 등급을 묻고, 재고를 할당하고, 두 애그리게이트를 저장한 뒤 트랜잭션을 커밋해야 합니다. 이 장은 그 조립을 맡을 자리를 만듭니다.

3장 화면 14가 남긴 질문 — "이 조립 코드는 지금 어느 클래스에도 들어 있지 않다. 그럼 누가 하나?" — 에 이 장이 답합니다.

이 장의 지도

  • 화면 2~3 · 문제와 계층. 표현 계층이 조립까지 떠맡을 때 벌어지는 일, 그리고 도메인·응용·인프라·표현 네 계층과 의존 방향의 규칙.
  • 화면 4~6 · 트랜잭션 경계. Unit of Work를 정의하고 구현하고, 커밋을 잊거나 중간에 실패하면 무슨 일이 일어나는지 봅니다.
  • 화면 7~9 · 경계 넘기. 커맨드로 입력을 받고 DTO로 출력을 내보내고, 카탈로그·회원·배송 컨텍스트에 값을 묻습니다.
  • 화면 10~12 · 조립과 한계. place_order()를 완성하고, 이 설계의 약점과 cancel_order()·표현 계층 연결까지 봅니다.

5장 · 화면 2

표현 계층이 조립까지 떠맡으면

4장에서 만든 리포지토리를 실제로 써야 합니다. 가장 빠른 방법은 HTTP 요청을 받는 함수 안에서 바로 쓰는 것입니다.

# web/views.py — 하지 않는다def place_order_view(request):
    session = Session()
    order_repo = SqlAlchemyOrderRepository(session)                # 1
    inventory_repo = SqlAlchemyInventoryRepository(session)

    data = json.loads(request.body)
    order = Order(order_repo.next_order_number(date.today()),
                  request.user.id, Address(**data["address"]))
    for item in data["items"]:
        product = CatalogModel.objects.get(sku=item["sku"])        # 2
        order.add_line(item["sku"], product.name,
                       Money.won(product.price), Quantity(item["qty"]))
        inventory_repo.get(item["sku"]).allocate(item["qty"], date.today())

    order_repo.add(order)
    session.commit()                                                # 3
    return JsonResponse({"order_number": order.order_number.value})
  1. 3~4행 SqlAlchemyOrderRepository와 SqlAlchemyInventoryRepository를 표현 계층이 직접 조립합니다. 4장에서 도메인 밖으로 밀어낸 인프라 지식(세션, 구체적인 구현 클래스 이름)이 한 층 위에서 그대로 새어 들어왔습니다.
  2. 10행 뷰 함수가 카탈로그 조회 방법을 직접 압니다. CatalogModel이 우리 DB의 테이블인지, 다른 팀의 서비스인지도 여기서만 알 수 있습니다.
  3. 16행 이 커밋이 실패하면 무슨 일이 일어날까요? inventory_repo.get(...).allocate(...)는 이미 실행돼 배치의 reserved가 늘어난 채입니다. 4장 화면 2가 경고한 문제 — "상태와 저장된 값이 어긋날 수 있다" — 가 두 애그리게이트로 규모만 커져 돌아왔습니다. 이 문제는 화면 6에서 정면으로 다룹니다.

이 함수를 테스트하려면

request 객체 전체, JSON 본문 형식, 진짜 DB 세션, CatalogModel이 어디서 응답하는지까지 다 갖춰야 합니다. 1장 화면 13의 통증 3번이 형태를 바꿔 다시 나타났습니다. 4장이 리포지토리로 한 번 없앤 문제인데, 이번엔 리포지토리 자체가 아니라 그것을 조립하는 코드가 문제입니다.

더 근본적인 문제는 이름입니다. place_order_view가 실제로 하는 일은 "HTTP 요청을 처리하는 것"이 아니라 "주문하기 유스케이스를 조립하는 것"입니다. 서로 다른 두 책임이 한 함수 안에 있습니다. 이 둘을 가르는 것이 계층입니다.

응용 서비스는 규칙을 갖지 않는다

1장 화면 16에서 이미 이 문장을 스쳐 지나갔습니다 — "응용 서비스 — 유스케이스를 조립할 뿐, 규칙은 갖지 않는다." 화면 2의 코드가 문제였던 이유를 이 문장으로 다시 말할 수 있습니다: 규칙(카탈로그 조회 방법, 커밋 시점)이 응용도 아니고 도메인도 아닌, 표현 계층에 있었습니다. 이 장에서 그 문장의 의미를 실제 코드로 만듭니다.

화면 2의 문제를 이 표로 다시 보면, 문제는 명확합니다 — 모든 코드가 표현 계층 하나에 있었습니다. Order.add_line()과 InventoryItem.allocate()만 제자리(도메인)에 있었고, 나머지 전부가 뷰 함수 안에 뒤섞여 있었습니다.

5장 · 화면 4

트랜잭션 경계는 응용 계층에

유스케이스 하나는 트랜잭션 하나여야 합니다. 주문 저장과 재고 할당은 둘 다 성공하거나 둘 다 실패해야지, 하나만 반영되면 안 됩니다. 그런데 이 "하나로 묶기"는 누구의 일일까요?

  • 도메인이 할 수 없습니다. Order는 InventoryItem의 존재조차 모릅니다(3장의 규칙입니다).
  • 리포지토리도 할 수 없습니다. OrderRepository는 주문만, InventoryRepository는 재고만 압니다. 4장의 인터페이스 어디에도 "둘을 묶어라"는 메서드가 없습니다.

남는 곳은 응용 계층뿐입니다. 이 경계를 표현하는 장치에 이름이 있습니다 — Unit of Work(UoW)입니다.

# application/unit_of_work.pyclass UnitOfWork(Protocol):
    orders: OrderRepository
    inventory: InventoryRepository

    def __enter__(self) -> "UnitOfWork": ...
    def __exit__(self, *args: object) -> None: ...   # 1
    def commit(self) -> None: ...
    def rollback(self) -> None: ...
  1. 2~3행 화면 2의 코드가 흩어놓았던 두 리포지토리가 한 객체 안에 모입니다. 응용 서비스는 이제 uow.orders와 uow.inventory로 같은 트랜잭션 안에서 두 애그리게이트에 접근합니다.
  2. 6행 __enter__/__exit__는 파이썬의 컨텍스트 매니저 프로토콜입니다. 이 둘을 구현하면 with uow: 문을 쓸 수 있습니다. __exit__가 받는 세 인자(예외 타입·값·트레이스백)는 블록 안에서 예외가 났는지 알려 줍니다. 화면 6에서 이 값을 씁니다.

경계 안에는 무엇을 두는가 — 1장 화면 8을 기억하시나요

1장 화면 8에서 본 사고를 떠올려 보세요 — PG 승인 호출이 DB 트랜잭션 안에서 일어나서, 트랜잭션이 3초 동안 붙잡혀 있었고, 승인이 성공한 뒤 우리 DB가 실패하면 롤백이 카드 결제까지 되돌리지 못했습니다.

같은 원리로 규칙을 하나 세웁니다 — with uow: 블록 안에는 우리 DB에 대한 작업만 둔다. 카탈로그·회원처럼 다른 컨텍스트에 값을 묻는 호출은 트랜잭션을 열기 전에 끝냅니다. 오래 걸리거나 실패해도, 아직 시작하지 않은 트랜잭션은 되돌릴 것이 없습니다. 화면 10에서 이 규칙을 실제 코드로 지킵니다.

이 Protocol은 도메인이 아니라 응용 계층에 둡니다. 트랜잭션이라는 개념 자체가 업무 규칙이 아니라, 화면 3에서 정한 응용 계층의 책임이기 때문입니다.

5장 · 화면 5

Unit of Work 구현하기

인터페이스를 두 가지로 구현합니다. 4장과 같은 순서입니다 — 메모리로 규칙을 익히고, SQLAlchemy로 진짜 트랜잭션을 겁니다.

# infra/memory_uow.pyclass InMemoryUnitOfWork:
    def __init__(self) -> None:
        self.orders = InMemoryOrderRepository()
        self.inventory = InMemoryInventoryRepository()
        self.committed = False

    def __enter__(self) -> "InMemoryUnitOfWork":
        return self

    def __exit__(self, *args: object) -> None:
        pass

    def commit(self) -> None:
        self.committed = True

    def rollback(self) -> None:
        pass

# infra/sqlalchemy_uow.pyclass SqlAlchemyUnitOfWork:
    def __init__(self, session_factory: Callable[[], Session]) -> None:
        self._session_factory = session_factory

    def __enter__(self) -> "SqlAlchemyUnitOfWork":
        self.session = self._session_factory()               # 1
        self.orders = SqlAlchemyOrderRepository(self.session)
        self.inventory = SqlAlchemyInventoryRepository(self.session)
        return self

    def __exit__(self, *args: object) -> None:
        self.rollback()                                       # 2
        self.session.close()

    def commit(self) -> None:
        self.session.commit()                                 # 3

    def rollback(self) -> None:
        self.session.rollback()
  1. (메모리) 5행 committed 플래그는 테스트에서 "커밋을 실제로 불렀는지" 확인하는 용도입니다. 메모리 저장소는 4장 화면 7에서 봤듯 직렬화가 없어서, commit() 자체는 상태에 아무 영향을 주지 않습니다.
  2. (SQLAlchemy) 6행 세션은 with 블록에 들어갈 때마다 새로 만듭니다. 여러 요청이 세션 하나를 공유하면 안 됩니다 — 요청마다 독립된 트랜잭션이어야 합니다.
  3. (SQLAlchemy) 12행 블록을 나갈 때 기본값은 롤백입니다. 커밋을 명시적으로 부르지 않았다면 아무것도 저장되지 않습니다. 화면 6에서 이 한 줄이 왜 안전장치인지 봅니다.
  4. (SQLAlchemy) 16행 4장 화면 7의 5장에서 다시 볼 문제가 바로 이것입니다 — Identity Map입니다. session.get()으로 꺼내 온 Order나 InventoryItem을 세션이 계속 추적하다가, commit()이 불리는 순간 바뀐 속성을 스스로 찾아 UPDATE 문을 만듭니다. 이미 있는 애그리게이트를 다시 add()할 필요가 없는 이유가 이것입니다 — 세션이 이미 그 객체를 알고 있습니다.

정직하게 남겨두는 것 — 메모리 구현의 rollback()은 빈 껍데기다

InMemoryUnitOfWork.rollback()은 아무것도 되돌리지 못합니다. InMemoryInventoryRepository.get()이 애그리게이트를 직접 참조로 돌려주기 때문에(4장 화면 5), allocate()가 이미 바꾼 reserved 값은 롤백을 호출해도 그대로 남습니다. 진짜 DB에서는 세션이 커밋 전까지의 변경을 붙잡고 있다가 롤백 시 통째로 버리지만, 파이썬 객체 참조에는 그런 장치가 없습니다.

그래서 "부분 실패 시 정말 롤백되는가"를 검증하는 테스트는 메모리 구현으로 쓸 수 없습니다. 화면 9의 SqlAlchemyUnitOfWork를 쓰는 소수의 통합 테스트로 남겨 둡니다(4장 화면 5의 원칙과 같습니다).

5장 · 화면 6

커밋을 잊으면, 또는 중간에 실패하면

4장 화면 2는 원시 sqlite3 코드로 이 문제를 처음 보였습니다 — "conn.commit()이 실패하면 self.status는 이미 바뀌었는데 DB는 그대로다." with uow:가 이 문제를 어떻게 다루는지 두 시나리오로 확인합니다.

시나리오 1 — 취소 도중 커밋이 실패한다면

# application/ordering.py — cancel_order() 의 뼈대def cancel_order(self, order_number: OrderNumber) -> None:
    with self._uow as uow:
        order = uow.orders.get(order_number)
        order.cancel()                     # 1  메모리 안의 self.status 를 바꾼다
        uow.commit()                       # 2
  1. 4행 order.cancel()이 메모리 안의 status를 바꿉니다. 3장의 Order는 저장 방법을 모르므로 이 시점엔 DB가 전혀 바뀌지 않았습니다.
  2. 5행 commit()이 실패하면(DB 오류 등) 예외가 __exit__로 전달되고 rollback()이 불립니다. DB는 안전합니다. 다만 이 특정 order 객체는 메모리 안에서 이미 취소됨 상태로 남은 채 함수가 예외로 끝납니다.

4장의 사고와 다른 점

4장 화면 2의 사고는 같은 객체가 다음 요청에서도 계속 쓰였기 때문에 위험했습니다. 여기서는 다릅니다 — 이 order 인스턴스는 함수가 끝나면 버려지고, 다음 요청은 uow.orders.get()으로 DB에서 다시 읽어옵니다. DB가 진실을 담고 있는 한, 메모리에 잠깐 남은 어긋남은 아무에게도 보이지 않습니다. "저장되지 않은 변경은 다음 요청에 영향을 주지 않는다"가 4장 화면 2의 문제에 대한 실질적인 답입니다.

시나리오 2 — 여러 애그리게이트 중 하나가 실패한다면

더 중요한 경우는 주문 한 건이 SKU 두 개를 담고 있을 때입니다.

# 두 번째 SKU에서 재고가 모자란 경우with self._uow as uow:
    items = uow.inventory.get_many(["SKU-001", "SKU-002"])
    items["SKU-001"].allocate(3, today)      # 1  성공 — 배치의 reserved 가 늘어난다
    items["SKU-002"].allocate(100, today)    # 2  InsufficientStock 발생
    uow.commit()                              # 여기 도달하지 못한다
  1. 3행 SKU-001의 할당은 성공합니다. 세션은 이 변경을 추적하기 시작합니다(화면 5의 Identity Map).
  2. 4행 SKU-002에서 InsufficientStock이 납니다. 예외가 with 블록을 빠져나가며 __exit__를 부르고, rollback()이 실행됩니다. 3행에서 이미 성공한 SKU-001의 변경까지 함께 버려집니다 — commit()을 한 번도 부르지 않았으므로 세션에는 아직 아무것도 확정되지 않은 상태였기 때문입니다.

이것이 Unit of Work 가 사는 이유

두 애그리게이트에 걸친 변경이 전부 반영되거나, 전부 반영되지 않거나 둘 중 하나입니다. "SKU-001은 반영됐는데 SKU-002는 실패한" 어중간한 상태는 나오지 않습니다. 4장 화면 2가 하나의 애그리게이트로 보여준 문제를, 여기서는 두 애그리게이트로 일반화해서 해결했습니다.

5장 · 화면 7

커맨드로 입력 경계 정하기

표현 계층은 원시 데이터(JSON, 폼 값)를 받습니다. 응용 서비스는 이 원시 데이터를 그대로 받지 않습니다 — 커맨드라는 값 객체로 바꿔서 받습니다.

# application/commands.py@dataclass(frozen=True)
class OrderItemInput:
    sku: str
    quantity: int


@dataclass(frozen=True)
class PlaceOrderCommand:
    customer_id: UUID
    items: tuple[OrderItemInput, ...]
    shipping_address: Address
  1. 11행 Address는 2장에서 만든 값 객체입니다. zipcode 형식 검증이 생성자 안에서 이미 끝났습니다. PlaceOrderCommand가 존재한다는 사실 자체가 "이 주소는 형식을 통과했다"는 증명서입니다 — 2장 화면 8에서 본 그 원리 그대로입니다.

이 커맨드는 표현 계층이 만듭니다. 원시 JSON을 값 객체로 바꾸는 지점이 바로 2장 화면 8이 예고한 "시스템 경계 한 곳"입니다.

# web/parsing.pydef parse_place_order_command(data: dict) -> PlaceOrderCommand:
    return PlaceOrderCommand(
        customer_id=UUID(data["customer_id"]),
        items=tuple(OrderItemInput(i["sku"], i["quantity"])
                    for i in data["items"]),
        shipping_address=Address(**data["address"]))   # 1

왜 등급을 커맨드에 넣지 않는가

PlaceOrderCommand에 grade 필드가 없습니다. 등급은 클라이언트가 "저는 골드 회원입니다"라고 주장할 값이 아니라, 회원 컨텍스트에 물어봐야 할 값이기 때문입니다. 화면 9에서 MembershipPort로 묻습니다.

DTO로 출력 경계 정하기

반대 방향도 있습니다. 응용 서비스가 Order 객체를 그대로 표현 계층에 돌려주면 어떻게 될까요?

Order를 그대로 내보내면 안 되는 이유

  • Order.lines는 내부 엔티티 OrderLine의 튜플입니다. 이걸 JSON으로 직렬화하려는 순간, 표현 계층이 도메인 내부 구조를 알아야 합니다.
  • 3장에서 Order에 필드를 하나 추가하면(예: 6장의 events) 직렬화 코드가 덩달아 깨집니다. 도메인 모델과 API 응답 형식이 같은 속도로 바뀔 이유가 없습니다.
  • 3장 화면 5가 이미 경고했습니다 — "화면에 뿌릴 데이터는 4장의 리포지토리와 5장의 DTO가 따로 담당합니다." 애그리게이트는 쓰기 단위이지 화면 단위가 아닙니다.

그래서 응용 서비스는 DTO(Data Transfer Object) — 행동이 없는, 화면이 필요로 하는 모양 그대로의 데이터 뭉치 — 를 따로 만들어 돌려줍니다.

3장 화면 16의 마지막 퀴즈를 기억하시나요 — "주문 화면에 회원 이름을 보여줘야 한다"는 요구였습니다. 그 해설이 예고한 첫 번째 방법이 바로 이것입니다 — "응용 서비스가 두 리포지토리에서 각각 읽어 DTO로 조립한다."

3장 화면 14가 남긴 그 조립 코드입니다 — 재고를 할당하고, 그 결과를 주문에 약속으로 적어 넣는 코드입니다. 그때는 REPL에 친 예시였고, 이제 진짜 자리를 찾습니다.

# application/ordering.pyclass OrderingService:
    def __init__(self, uow: UnitOfWork, catalog: CatalogPort,
                 members: MembershipPort, shipping: ShippingPolicy) -> None:
        self._uow = uow
        self._catalog = catalog
        self._members = members
        self._shipping = shipping

    def place_order(self, cmd: PlaceOrderCommand) -> OrderNumber:
        snapshots = self._catalog.snapshot(cmd.items)              # 1
        grade = self._members.grade_of(cmd.customer_id)

        with self._uow as uow:
            order = Order(uow.orders.next_order_number(date.today()),
                          cmd.customer_id, cmd.shipping_address)
            for s in snapshots:
                order.add_line(s.sku, s.product_name, s.unit_price, s.quantity)

            order.discount = order.amounts.subtotal.percent(        # 2
                grade.discount_rate)
            order.shipping_fee = (Money.won(0) if grade.free_shipping
                                   else Money.won(3_000))            # 3

            items = uow.inventory.get_many([l.sku for l in order.lines])  # 4
            order.allocation = {                                    # 5
                l.sku: items[l.sku].allocate(l.quantity.value, date.today())
                for l in order.lines}
            ready_on = max(a.ready_on for a in order.allocation.values())  # 6
            order.promise_delivery(Promise(
                ship_on=ready_on,
                arrive_by=ready_on + self._shipping.lead_time,
                promised_at=datetime.now()))

            uow.orders.add(order)
            uow.commit()
            return order.order_number
  1. 10~11행 트랜잭션을 열기 전에 다른 컨텍스트에 묻습니다. 화면 4의 규칙 그대로입니다 — 카탈로그나 회원 컨텍스트가 느리거나 실패해도, 아직 시작하지 않은 uow 블록은 되돌릴 것이 없습니다.
  2. 19~22행 등급별 할인율과 배송비를 응용 서비스가 직접 계산합니다. 지금은 동작하지만, 이건 업무 규칙입니다 — 화면 11에서 이 문제로 다시 돌아옵니다. 6장에서 다시 볼 문제
  3. 24행 get_many로 한 번에 필요한 재고 애그리게이트를 가져옵니다(4장 화면 4). 라인마다 get()을 부르지 않습니다.
  4. 25~27행 allocate()는 SKU 하나(=재고 애그리게이트 하나)에 대한 결과만 돌려줍니다. 라인이 여러 SKU에 걸치면 Allocation이 여러 개 나오는데, SKU를 키로 하는 dict에 담습니다. 여러 Allocation을 하나로 합치고 싶어질 수 있지만, 하면 안 됩니다 — 3장 화면 16 모범답안의 InventoryItem.release()는 allocation.lines의 batch_id를 _find()로 찾다가 자기 배치가 아니면 DomainError를 던집니다. 합친 값을 다른 SKU의 release()에 넘기면 그대로 예외가 납니다. 같은 SKU가 두 라인에 나뉘어 있다면

Order.add_line()은 3장에서 항상 새 라인을 추가할 뿐, 같은 SKU를 합치지 않습니다(3장 화면 3). 그런데 위 코드는 {sku: ...}로 담으므로, 라인 두 개가 같은 SKU라면 나중 라인의 Allocation이 앞 라인의 것을 덮어씁니다. 지금은 "같은 상품은 라인 하나로 합쳐 수량만 늘린다"는 관례(용어집의 '주문 라인' 정의)에 기대 이 경우를 다루지 않습니다. 표현 계층이 이 관례를 지키지 않으면 조용히 재고가 어긋납니다 — 굳이 강제하려면 place_order() 앞단에서 같은 SKU 라인을 합치는 검증을 추가해야 합니다.

  3. 5행 3장 화면 4가 예고한 그 경계입니다 — except DomainError 한 줄로 "고객에게 사유를 보여줄 오류"를 잡고, 나머지(버그, 인프라 장애)는 여기서 잡지 않고 그대로 올려 보냅니다(프레임워크가 500으로 처리합니다).

5장 마무리

핵심 요약

  1. 애플리케이션은 표현·응용·도메인·인프라 네 계층으로 나뉩니다. 표현→응용→도메인은 의존 방향대로, 인프라는 의존성 역전으로 도메인을 향해 의존합니다. 응용 서비스는 유스케이스를 조립할 뿐, 업무 규칙을 갖지 않습니다.
  2. Unit of Work는 여러 애그리게이트에 걸친 변경을 하나의 트랜잭션으로 묶습니다. with uow: 블록을 나갈 때 기본값은 롤백이라, 커밋을 잊거나 중간에 실패해도 전부 반영되거나 전부 반영되지 않거나 둘 중 하나입니다.
  3. 커맨드는 표현 계층에서 응용 계층으로 들어가는 입력 경계, DTO는 응용 계층에서 표현 계층으로 나가는 출력 경계입니다. 둘 다 도메인 객체를 그대로 노출하지 않습니다.
  4. 포트(CatalogPort·MembershipPort· ShippingPolicy)는 다른 컨텍스트에 값을 묻는 인터페이스입니다. 리포지토리와 같은 원리(인터페이스는 쓰는 쪽이 정의)를 DB가 아니라 다른 컨텍스트에 적용한 것입니다.
  5. 코드가 응용 서비스 안에 있어도 되는지는 "업무 규칙을 담고 있는가, 순서만 정하는가"로 판별합니다. 규칙이면 도메인이나 도메인 서비스로 — 지금 응용 서비스에 남아 있는 할인·배송비 계산이 6장에서 그렇게 옮겨갑니다.

다음 중 OrderingService.place_order() 안에 있어도 괜찮은 코드는 무엇일까요?

  1. 회원 등급에 따라 할인율을 0%·3%·5%로 나누는 계산
  2. 주문 금액이 3만 원 미만이면 배송비 3,000원을 매기는 계산
  3. get_many로 재고를 한 번에 조회하고, SKU별 allocate() 결과를 dict에 모으는 코드
  4. 유통기한이 3일 미만 남은 배치는 할당에서 제외하는 판단

해설 판별 질문은 화면 11과 같습니다 — "업무 담당자가 바꿀 수 있는 규칙인가, 아니면 개발자만 아는 조립 순서인가?" 3번만 후자입니다.

흥미로운 점은, 이 넷 다 지금 실제로 어딘가에 있다는 것입니다. 1·2번은 지금 place_order() 안에 있고(화면 11에서 문제로 짚었습니다), 4번은 이미 3장에서 InventoryItem 안에 있습니다. 코드가 도는 것과 코드가 제자리에 있는 것은 다른 문제입니다.

with self._uow as uow: 블록 안에서 SKU 두 개를 차례로 할당하다가, 두 번째 SKU에서 InsufficientStock이 났습니다. 첫 번째 SKU의 할당(reserved 증가)은 최종적으로 어떻게 될까요? (SQLAlchemy 구현 기준)

  1. 이미 실행됐으므로 DB에 반영된 채로 남는다
  2. 예외로 블록을 빠져나가며 rollback()이 호출돼, 첫 번째 SKU의 변경까지 함께 버려진다
  3. 첫 번째 SKU만 반영되고 두 번째 SKU만 취소된다
  4. 메모리 구현과 마찬가지로 아무것도 되돌려지지 않는다

해설 이것이 화면 6의 시나리오 2입니다. Unit of Work의 핵심 가치는 "몇 개가 성공했든" 커밋 이전에는 전부 임시 상태라는 것입니다. 4번 선택지가 함정인 이유는, 메모리 구현이었다면 실제로 맞는 말이기 때문입니다 — 화면 5의 경고를 놓치면 이 둘을 헷갈리기 쉽습니다.

place_order_view가 except Exception으로 모든 예외를 잡아 {"error": str(e)}로 응답하도록 바꾸자는 제안이 나왔습니다. 무엇이 문제일까요?

  1. 문제없다 — 오히려 사용자에게 보여줄 오류를 놓치지 않는다
  2. 예외 처리 비용이 커져서 성능이 나빠진다
  3. DomainError가 더 이상 잡히지 않게 된다
  4. DB 연결 실패나 버그로 인한 예외까지 "정상적인 업무 응답"처럼 그대로 노출된다

해설 3장 화면 4가 DomainError를 만든 이유가 정확히 이것입니다 — 업무 규칙 위반과 프로그램 버그를 구분하기 위해서였습니다. except Exception은 이 구분을 지워 버립니다. 스택 트레이스나 내부 오류 메시지가 그대로 API 응답에 실리면, 보안 문제로도 이어질 수 있습니다.

규칙은 간단합니다 — 도메인이 이름 붙인 예외만 골라 잡고, 나머지는 그대로 올려 보낸다. 무엇을 잡을지 화이트리스트로 정하는 것이, 무엇을 잡을지 모른 채 전부 잡는 것보다 안전합니다.

  • 이 메서드는 무엇을 바꾸나요, 아니면 아무것도 바꾸지 않나요? 그렇다면 with self._uow:로 감쌀 필요가 있을까요, 아니면 uow.orders.get()만 불러도 될까요?
  • 주문이 없는 order_number가 들어오면 무슨 일이 일어나야 할까요? 4장에서 만든 어떤 예외가 이미 이 상황을 처리하고 있나요?
모범답안 
class OrderingService:
    ...
    def get_order_summary(self, order_number: OrderNumber) -> OrderSummary:
        order = self._uow.orders.get(order_number)     # 1
        return to_summary(order)
  1. 3~4행 with self._uow:로 감싸지 않아도 됩니다. 이 메서드는 아무것도 바꾸지 않는 읽기 전용 조회입니다 — 트랜잭션 경계는 "변경을 한 단위로 묶기" 위한 것이지, 읽기에는 필요 없습니다. (다만 리포지토리 구현이 세션을 통해서만 get()할 수 있다면, 세션을 얻기 위해 with를 쓰는 것 자체는 무방합니다 — 그 안에서 commit()을 부르지만 않으면 됩니다.)
  2. 4행 없는 order_number가 들어오면 uow.orders.get()이 4장에서 만든 OrderNotFound를 던집니다. 이 메서드가 별도로 처리할 필요가 없습니다 — 표현 계층의 except DomainError가 이미 잡습니다(화면 12).

다음 장 예고

화면 11에서 짚은 문제가 남아 있습니다 — 등급별 할인율과 배송비 계산이 아직 응용 서비스 안에 있습니다. Order.add_line()이나 InventoryItem.allocate()처럼 특정 엔티티 하나에 넣기는 애매하고, 그렇다고 응용 서비스에 두면 업무 규칙이 잘못된 층에 남습니다.

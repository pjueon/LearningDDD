도메인 모델의 최소 단위
Entity와 Value Object

1장에서 본 코드에는 도메인 모델이 없었습니다. 이제 만들기 시작합니다. 다만 Order부터 만들지 않습니다. 금액, 수량, 주소처럼 가장 작은 것부터 시작합니다.

이 순서가 이상하게 느껴질 수 있습니다. 주문이 핵심인데 왜 금액부터 만들까요? 두 가지 이유가 있습니다.

  • 큰 것은 작은 것으로 만들어집니다. Order를 잘 만들려면 그 안에 들어갈 금액과 수량이 먼저 튼튼해야 합니다. 3장에서 Order를 만들 때 이 장에서 만든 부품들을 그대로 씁니다.
  • 작은 것에서 효과가 가장 빨리 보입니다. 이 장이 끝나면 1장에서 봤던 버그 몇 개가 애초에 작성 불가능한 코드가 됩니다.

이 장에서 만들 것

  • Money — 금액. 이 장의 주인공입니다.
  • Quantity — 수량. 1 이상이라는 규칙을 타입이 지킵니다.
  • Address — 배송지. 왜 불변이어야 하는지가 핵심입니다.
  • OrderNumber — 주문번호. 문자열과 무엇이 다른지 봅니다.
  • SaleStatus, OrderStatus — 1장에서 남겨둔 "판매중" 문자열 비교 문제를 해결합니다.

그리고 이 장의 진짜 목표는 위 다섯 개를 만드는 것이 아닙니다. "이건 엔티티인가 값 객체인가"를 스스로 판단하는 것입니다. 화면 11이 그 훈련입니다.

2장 · 화면 2

사건: 2원이 사라졌다

1장에서 회원 등급 할인을 붙인 뒤 몇 주가 지났습니다. 정산팀에서 문의가 옵니다.

정산팀

주문 상세 화면의 라인별 할인액을 다 더하면 총 할인액과 안 맞는 건이 있습니다. 어제만 1,400건이에요. 대부분 1~3원 차이입니다.

개발팀

...금액이 안 맞는 건 아니고요? 결제는 총액으로 하니까 고객이 낸 돈은 맞습니다.

정산팀

고객이 낸 돈은 맞는데 영수증에 적힌 숫자들의 합이 안 맞습니다. 세금계산서를 이 숫자로 만들어야 하는데요.

재현해 봅시다. 골드 회원(5% 할인)이 10,000원어치 주문을 했고, 라인이 세 개입니다. 라인은 주문서의 한 줄, 즉 그 주문에 담은 상품 하나입니다 (1장 화면 3의 order_lines 테이블 한 행). 같은 상품을 3개 담으면 라인은 하나이고 수량이 3입니다.

아래 lines는 라인 객체가 아니라 세 줄의 금액(소계)만 뽑아 놓은 리스트입니다.

# 실제로 벌어진 일>>> total = 10000
>>> discount = int(total * 0.05)          # 총 할인액
>>> discount
500

>>> lines = [3333, 3333, 3334]            # 라인별 금액, 합계 10,000원
>>> per_line = [int(x * 0.05) for x in lines]   # 화면에 보여줄 라인별 할인액
>>> per_line
[166, 166, 166]
>>> sum(per_line)
498                                       # 총 할인액은 500원인데?

2원이 사라졌습니다. 원인은 명확합니다. 라인마다 166.65 → 166으로 버림했고, 그 손실이 세 번 쌓였습니다.

급하게 고치라는 요청이 옵니다. 개발팀은 반올림으로 바꿔봅니다.

# 반올림으로 바꿔도>>> per_line = [round(x * 0.05) for x in lines]
>>> per_line
[167, 167, 167]
>>> sum(per_line)
501                                       # 이번엔 1원이 늘었다

여기서 알아야 할 것

이건 반올림 방식을 고르는 문제가 아닙니다. 버림이든 반올림이든, 쪼갠 값을 다시 더하면 원본과 달라집니다. 필요한 것은 "나눌 때 1원도 잃거나 만들지 않는다"는 규칙이고, 그 규칙이 금액을 다루는 모든 곳에서 똑같이 적용되어야 합니다.

그런데 지금 금액은 그냥 int입니다. int에는 그런 규칙을 붙일 곳이 없습니다. 그래서 금액을 나누는 코드가 생길 때마다 개발자가 매번 기억해서 처리해야 합니다. 1장 화면 13의 통증 5번과 정확히 같은 구조입니다.

int로 돈을 다루면 생기는 일

2원 사건은 여러 문제 중 하나입니다. 금액을 원시 타입으로 두면 생기는 일을 정리해 봅시다.

1. 단위가 코드에 적혀 있지 않다

def refund(order_id: int, amount: int) -> None: ...

이 amount는 원일까요 전일까요? 한빛몰은 원 단위를 쓰지만, PG사 API 중에는 최소 단위(전, 센트)로 받는 것이 있습니다. 문서를 찾아봐야 알 수 있고, 단위를 착각하면 100배 환불이 나갑니다. 타입이 int이니 잘못 넘겨도 아무도 막지 않습니다.

2. 의미 없는 연산이 허용된다

>>> unit_price = 7000
>>> quantity = 3
>>> shipping_fee = 3000

>>> unit_price * quantity        # 21000  — 의미 있다 (금액 × 개수 = 금액)
>>> unit_price * shipping_fee    # 21000000 — 의미 없다. 그런데 잘 돌아간다
>>> quantity + shipping_fee      # 3003 — 개수와 금액을 더했다. 역시 잘 돌아간다

세 줄 다 정상 실행됩니다. 파이썬에게는 전부 그냥 정수 곱셈과 덧셈입니다. "금액에 금액을 곱하면 안 된다"는 것은 업무 지식이고, 코드에는 그 지식이 없습니다.

3. 소수점 연산이 정확하지 않다

>>> 0.1 + 0.2
0.30000000000000004
>>> 19990 * 0.05
999.5000000000001              # 999.5 가 아니다

float는 2진수로 소수를 표현하기 때문에 0.1 같은 값을 정확히 담지 못합니다. 금액 계산에 float를 쓰면 1원 차이가 무작위로 생깁니다. 파이썬 표준 라이브러리의 Decimal이 이 문제를 위해 있습니다.

4. 규칙을 붙일 곳이 없다

"금액은 음수가 될 수 없다", "원 단위 미만은 존재하지 않는다", "나눌 때 총합이 보존된다" — 이 세 규칙을 int에 붙일 방법이 없습니다. 그래서 검사 코드가 금액을 만지는 모든 함수에 복사됩니다.

이 네 가지를 한 번에 없애는 방법

금액을 담는 타입을 하나 만들고, 규칙을 그 안에 넣는 것입니다. 다음 화면에서 만듭니다. 만들고 나면 위의 나쁜 코드 세 줄은 실행되지 않고 예외를 던지거나, 애초에 타입 검사에서 걸립니다.

Money 만들기 ① — 값을 감싸고 규칙을 넣기

# domain/money.pyfrom dataclasses import dataclass
from decimal import Decimal
from typing import ClassVar


class DomainError(Exception):                                    # 1
    """도메인 규칙 위반. 기술적 오류(DB 접속 실패 등)와 구분한다."""


@dataclass(frozen=True, order=True)                              # 2
class Money:
    """한빛몰의 금액. 원(KRW) 단위 정수만 표현한다."""

    amount: Decimal                                              # 3

    ZERO: ClassVar["Money"]                                      # 4

    def __post_init__(self) -> None:                             # 5
        if self.amount != self.amount.to_integral_value():
            raise DomainError(f"금액은 원 단위여야 합니다: {self.amount}")
        if self.amount < 0:                                      # 6
            raise DomainError(f"금액은 음수가 될 수 없습니다: {self.amount}")

    @classmethod
    def won(cls, amount: int) -> "Money":                        # 7
        return cls(Decimal(amount))

    def __str__(self) -> str:                                    # 8
        return f"{int(self.amount):,}원"


Money.ZERO = Money.won(0)                                        # 9
  1. 6행 도메인 예외를 하나 만들어 둡니다. "금액이 음수"는 업무 규칙 위반이고, "데이터베이스가 죽었다"는 기술 장애입니다. 1장에서는 둘이 똑같이 except Exception에 잡혀 같은 400 응답으로 나갔습니다. 타입을 나눠두면 어디서 무엇을 어떻게 처리할지 구분할 수 있습니다. 3장에서 이것을 상속한 예외들(AlreadyShipped 등)이 나옵니다.
  2. 10행 @dataclass는 __init__, __eq__, __repr__을 자동으로 만들어 줍니다. frozen=True는 만든 뒤에 필드를 못 바꾸게 합니다 — 이게 값 객체의 핵심이라 화면 7에서 따로 다룹니다. order=True는 <, > 비교를 만들어 줍니다. 필드가 amount 하나뿐이라 "금액 비교"가 정확히 우리가 원하는 뜻이 됩니다.
  3. 14행 float가 아니라 Decimal입니다. 화면 3의 3번 문제 때문입니다. 주의할 점 하나 — Decimal(0.1)처럼 float에서 만들면 오차가 그대로 들어옵니다. 항상 int나 문자열에서 만들어야 합니다. 그래서 7번 항목의 won()이 필요합니다.
  4. 16행 ClassVar로 선언한 필드는 dataclass가 인스턴스 필드로 취급하지 않습니다. 즉 Money(...)를 만들 때 인수로 요구하지 않고, __eq__ 비교에도 끼지 않습니다. "0원"을 매번 만들지 않고 Money.ZERO로 쓰기 위한 장치입니다.
  5. 18~22행 __post_init__은 dataclass가 __init__ 마지막에 자동으로 불러주는 메서드입니다. 검증을 여기에 두면 규칙을 어긴 Money는 세상에 존재할 수 없습니다. to_integral_value()는 소수점을 버린 값을 주므로, 원본과 다르면 "1원 미만이 섞여 있다"는 뜻입니다.
  6. 21행 음수를 막는 것은 선택이었고, 이유가 있습니다. 음수를 허용하면 "할인 −3,000원"과 "환불 −3,000원"과 "계산 실수로 음수가 된 총액"이 모두 같은 값이 되어 구분할 수 없습니다. 한빛몰은 할인을 양수 Money로 두고 빼는 쪽에서 검증하기로 정했습니다(다음 화면).
  7. 24~26행 이름 있는 생성자입니다. Money(Decimal(3000))보다 Money.won(3000)이 읽기 쉽고, Decimal을 아는 것이 호출자의 일이 아니게 됩니다. 나중에 외화가 필요해지면 Money.usd(...)가 옆에 생길 자리이기도 합니다.
  8. 28~29행 로그와 화면에 찍힐 모양을 정해둡니다. str(money) → "21,000원". 이게 있으면 디버깅이 편하고, 무엇보다 템플릿에서 콤마 찍는 코드가 여러 곳에 복사되지 않습니다.
  9. 32행 클래스가 다 정의된 뒤에 ZERO를 채웁니다. 클래스 본문 안에서는 아직 Money가 완성되지 않아 자기 자신을 만들 수 없습니다.

이제 화면 3의 나쁜 코드가 어떻게 되는지 봅시다.

>>> unit_price = Money.won(7000)
>>> unit_price * Money.won(3000)
TypeError: unsupported operand type(s) for *: 'Money' and 'Money'

>>> Money.won(-500)
DomainError: 금액은 음수가 될 수 없습니다: -500

>>> Money(Decimal("0.5"))
DomainError: 금액은 원 단위여야 합니다: 0.5

돌아가던 나쁜 코드가 이제 돌아가지 않습니다. 이게 도메인 모델이 하는 일입니다.

Money 만들기 ② — 허용할 연산만 정의하기

금액끼리 더할 수는 있어야 합니다. 개수를 곱할 수도 있어야 합니다. 필요한 연산만 열어줍니다.

# domain/money.py — Money 클래스 안에 추가
# 추가 import: from decimal import ROUND_DOWN / from typing import Sequence    def __add__(self, other: "Money") -> "Money":                # 1
        if not isinstance(other, Money):
            return NotImplemented
        return Money(self.amount + other.amount)

    def __sub__(self, other: "Money") -> "Money":
        if not isinstance(other, Money):
            return NotImplemented
        if self.amount < other.amount:                           # 2
            raise DomainError(f"{self}에서 {other}를 뺄 수 없습니다")
        return Money(self.amount - other.amount)

    def __mul__(self, count: int) -> "Money":                    # 3
        if not isinstance(count, int):
            return NotImplemented
        return Money(self.amount * count)

    def percent(self, rate: Decimal) -> "Money":                 # 4
        """비율을 적용한다. 원 단위 미만은 버린다(고객에게 유리한 방향)."""
        return Money((self.amount * rate).to_integral_value(rounding=ROUND_DOWN))

    def distribute(self, weights: Sequence["Money"]) -> list["Money"]:   # 5
        """가중치 비율로 쪼갠다. 1원도 잃거나 만들지 않는다."""
        base = sum((w.amount for w in weights), Decimal(0))
        if base == 0:
            raise DomainError("가중치 합이 0이면 나눌 수 없습니다")

        shares = [
            (self.amount * w.amount / base).to_integral_value(rounding=ROUND_DOWN)
            for w in weights
        ]
        remainder = self.amount - sum(shares)                    # 6
        for i in range(int(remainder)):
            shares[i] += 1
        return [Money(s) for s in shares]
  1. 1~4행 __add__를 정의하면 a + b가 동작합니다. isinstance 검사에서 NotImplemented를 돌려주는 것은 파이썬의 관례입니다 — "나는 이 조합을 모른다"고 알리면 파이썬이 TypeError로 바꿔줍니다. raise하는 것보다 이쪽이 낫습니다.
  2. 9~10행 음수 금액을 만들지 않기로 했으니(화면 4의 6번), 뺄 수 없는 뺄셈은 여기서 막습니다. "3,000원에서 5,000원을 뺄 수 없다"는 것은 업무 규칙이므로 DomainError입니다. 참고로 이 검사가 있으면 "할인이 상품 금액보다 큰 쿠폰" 같은 사고가 계산 단계에서 드러납니다.
  3. 13~16행 곱셈은 int만 받습니다. Money * Money는 정의하지 않았으므로 TypeError가 납니다. 화면 3의 2번 문제가 이 세 줄로 사라집니다.
  4. 18~20행 할인율 적용입니다. 버림을 선택했고, 그 이유를 주석에 남겼습니다 — 할인액이 줄어드는 방향이 아니라 고객이 내는 금액이 줄어드는 방향이 되도록 정한 것입니다. 이런 결정은 은수와 합의해야 하는 업무 규칙이고, 합의한 결과가 코드 한 곳에 적혀 있는 것이 이 장의 성과입니다.
  5. 22~35행 화면 2의 2원 사건을 해결하는 메서드입니다. Martin Fowler가 Patterns of Enterprise Application Architecture에서 Money.allocate()라는 이름으로 소개한 방법입니다.
  6. 32~34행 핵심입니다. 먼저 전부 버림으로 나눈 다음, 남은 잔액을 앞에서부터 1원씩 나눠줍니다. 그래서 합이 항상 원본과 같습니다. "앞에서부터"는 임의의 선택이므로, 업무상 기준이 있다면(예: 금액이 큰 라인 우선) 거기를 고치면 됩니다. 고칠 곳이 한 군데라는 점이 중요합니다.

>>> lines = [Money.won(3333), Money.won(3333), Money.won(3334)]
>>> total = Money.won(10000)
>>> discount = total.percent(Decimal("0.05"))
>>> str(discount)
'500원'

True                                    # 1원도 사라지지 않았다

무엇이 달라졌나

"할인을 라인별로 나눌 때 총합이 보존된다"는 규칙이 이제 한 군데에만 있습니다. 주문 상세 화면, 세금계산서, 정산 배치, 부분 취소 계산 — 금액을 쪼개는 모든 코드가 distribute()를 부르는 한 같은 규칙을 따릅니다.

이름 붙이기 — 값 객체

지금 만든 Money에는 이름이 있습니다. 값 객체(Value Object)입니다. Eric Evans가 Domain-Driven Design(2003, 통칭 Blue Book)에서 정의한 개념입니다.

값 객체를 알아보는 방법은 간단합니다. 숫자나 문자열처럼 다뤄도 되는 개념이면 값 객체입니다. 3,000원과 3,000원은 "같은 금액"이고, 어느 쪽을 쓰든 상관없습니다. 성질 세 가지로 정리하면 이렇습니다.

"그럼 int도 값 객체 아닌가?"

맞습니다. int, str, date는 모두 위 세 성질을 갖고 있습니다. 값 객체는 새로운 종류의 물건이 아니라, "int처럼 다룰 수 있는 우리 도메인의 개념에 이름과 규칙을 붙인 것"입니다.

그래서 값 객체를 만드는 것은 어렵지 않습니다. 어려운 것은 무엇을 값 객체로 만들지 판단하는 일이고, 그게 화면 11과 12의 주제입니다.

더 깊이 — frozen=True가 주는 공짜 선물, __hash__

@dataclass(frozen=True)는 __hash__도 만들어 줍니다. 값이 바뀌지 않으니 해시값도 바뀌지 않기 때문입니다. 덕분에 값 객체를 딕셔너리의 키나 set의 원소로 쓸 수 있습니다.

>>> {Money.won(1000), Money.won(1000), Money.won(2000)}
{Money(amount=Decimal('1000')), Money(amount=Decimal('2000'))}   # 중복이 하나로

반대로, 가변 객체를 딕셔너리 키로 쓰면 재앙이 벌어집니다. 키로 넣은 뒤 내용을 바꾸면 해시값이 달라져서 딕셔너리에 넣어둔 값을 다시는 찾을 수 없습니다. 파이썬이 list를 키로 못 쓰게 막아둔 이유가 이것입니다.

검증을 타입 안으로 — Quantity와 OrderNumber

1장 코드 해설에서 이런 지적을 했습니다 — 수량이 -5여도 통과한다. 그 문제를 타입으로 막아봅시다.

# domain/quantity.py@dataclass(frozen=True, order=True)
class Quantity:
    """주문 수량. 1 이상이다. (불변식 I3)"""

    value: int

    def __post_init__(self) -> None:
        if not isinstance(self.value, int) or isinstance(self.value, bool):   # 1
            raise DomainError(f"수량은 정수여야 합니다: {self.value!r}")
        if self.value < 1:
            raise DomainError(f"수량은 1 이상이어야 합니다: {self.value}")

    def __add__(self, other: "Quantity") -> "Quantity":
        if not isinstance(other, Quantity):
            return NotImplemented
        return Quantity(self.value + other.value)
  1. 8~9행 bool을 따로 걸러내는 이유가 재미있습니다. 파이썬에서 bool은 int의 하위 클래스라 isinstance(True, int)가 True입니다. 즉 Quantity(True)는 수량 1로 통과합니다. JSON에서 {"qty": true}가 들어오는 일은 실제로 벌어집니다.

이제 "수량 0으로 주문" 같은 요청은 도메인에 도달하기 전에 걸립니다.

주문번호 — 문자열과 무엇이 다른가

# domain/order_number.py@dataclass(frozen=True)
class OrderNumber:
    """한빛몰 주문번호. 'YYYYMMDD-순번6자리' 형식이다."""

    value: str

    def __post_init__(self) -> None:
        if not re.fullmatch(r"\d{8}-\d{6}", self.value):
            raise DomainError(f"주문번호 형식이 아닙니다: {self.value}")

    @classmethod
    def issue(cls, today: date, seq: int) -> "OrderNumber":
        return cls(f"{today:%Y%m%d}-{seq:06d}")

    def __str__(self) -> str:
        return self.value

엔티티는 dataclass로 만들지 않는다

Order를 @dataclass로 만들면 어떻게 되는지 봅시다.

class Order:
    order_number: OrderNumber
    shipping_address: Address

dataclass가 만들어주는 __eq__는 모든 필드를 비교합니다. 그러면 이런 일이 벌어집니다.

# 같은 주문의 배송지를 고쳤다

같은 주문번호를 가진 같은 주문인데, 배송지 한 글자가 달라서 "다른 주문"이 됩니다. set에 넣으면 두 개가 되고, 리스트에서 in으로 찾으면 못 찾습니다. 그래서 엔티티는 __eq__를 직접 씁니다.

# domain/order.py — 3장에서 이어서 만든다class Order:
    def __init__(self, order_number: OrderNumber, customer_id: UUID,
                 shipping_address: Address) -> None:
        self._order_number = order_number                 # 1
        self.customer_id = customer_id
        self.shipping_address = shipping_address
        self.status = OrderStatus.생성됨

    @property
    def order_number(self) -> OrderNumber:                # 2
        return self._order_number

    def __eq__(self, other: object) -> bool:              # 3
        if not isinstance(other, Order):
            return NotImplemented
        return self._order_number == other._order_number

    def __hash__(self) -> int:                            # 4
        return hash(self._order_number)

    def __repr__(self) -> str:
        return f"<Order {self._order_number} {self.status.name}>"
  1. 4행 식별자를 _로 시작하는 이름에 넣고 @property로만 읽게 합니다. 식별자는 바뀌면 안 되기 때문입니다. 주문번호가 바뀌는 순간 그것은 다른 주문이 되고, 이미 그 번호로 처리된 결제·배송·정산이 전부 미아가 됩니다.
  2. 9~11행 읽기 전용으로만 노출합니다. 파이썬에는 진짜 private이 없으므로 order._order_number = ...를 물리적으로 막을 수는 없습니다. "이건 만지면 안 되는 것"이라는 의사 표시이고, 파이썬에서는 이 정도가 관례입니다.
  3. 13~16행 식별자만 비교합니다. 배송지가 바뀌어도, 상태가 바뀌어도 같은 주문입니다. 이게 엔티티의 정의를 코드로 옮긴 것입니다.
  4. 18~19행 파이썬에서 __eq__를 직접 정의하면 __hash__가 자동으로 None이 되어 그 객체는 해시할 수 없게 됩니다(set·딕셔너리 키로 못 씀). 그래서 짝으로 함께 정의합니다. __eq__와 같은 기준을 써야 합니다 — 식별자로 같다고 판정한 둘은 해시값도 같아야 합니다.

1. 주문에 적힌 배송지 주소

값 객체입니다.

주문 입장에서 배송지는 "이 주소로 보내달라"는 내용일 뿐입니다. 그 주소를 개별적으로 추적할 이유가 없고, 다른 주문의 같은 주소와 구별할 이유도 없습니다. 바꿀 때는 새 Address로 통째로 교체하면 됩니다.

그리고 화면 7에서 봤듯이 불변이어야만 과거 주문의 배송지가 안전합니다.

2. 회원 주소록에 저장된 주소 (같은 "주소"입니다)

엔티티입니다.

주소록의 주소는 개별적으로 관리됩니다. 고객이 "집" 주소를 수정하고, "회사" 주소를 삭제하고, 특정 주소를 기본 배송지로 지정합니다. "어떤 주소를 수정할지" 가리켜야 하므로 식별자가 필요합니다.

내용을 다 바꿔도(이사를 가서 우편번호부터 전부 달라져도) 고객에게는 여전히 "집"이라는 같은 항목입니다. 전형적인 엔티티입니다.

이 문항이 이 장에서 가장 중요합니다

같은 "주소"가 한쪽에서는 값 객체이고 다른 쪽에서는 엔티티입니다. 엔티티냐 값 객체냐는 그 물건의 본질이 아니라, 그것을 다루는 맥락이 결정합니다.

이 발견이 9장 바운디드 컨텍스트로 이어집니다. 주문 컨텍스트의 "주소"와 회원 컨텍스트의 "주소"는 이름만 같은 다른 것입니다. 하나로 합치려는 시도가 실패하는 이유가 여기 있습니다.

3. 주문 라인 (주문에 담긴 상품 한 줄)

엔티티입니다. 다만 논쟁의 여지가 있습니다.

엔티티인 이유: 라인의 수량을 변경할 수 있어야 하고("2개를 3개로"), 그러려면 어느 라인인지 가리킬 수 있어야 합니다. 같은 상품이 두 줄로 들어간 주문도 가능하므로 상품 ID로는 구별이 안 됩니다. 그래서 라인마다 line_id를 둡니다.

반대 의견도 성립합니다. "수량 변경"을 "그 라인을 지우고 새 라인을 넣는 것"으로 정의하면 주문 라인은 값 객체가 됩니다. 실제로 그렇게 설계한 시스템도 많습니다. 더 단순해지고, 라인의 변경 이력이 자연히 남습니다.

한빛몰은 엔티티로 갑니다. 이유는 창고 쪽 요구 때문입니다 — 피킹 지시서가 주문 라인 단위로 만들어지고, 라인별로 결번 처리와 부분 피킹이 기록되어야 합니다. 라인이 교체될 때마다 다른 것이 되면 그 기록을 이어붙일 수 없습니다.

이게 판단하는 방식입니다. "일반적으로 무엇인가"가 아니라 "우리 업무에서 개별 추적이 필요한가"로 정합니다.

4. 재고 배치 (StockBatch)

엔티티입니다.

reserved(예약 수량)가 계속 변합니다. 주문이 들어오면 늘고, 취소되면 줄고, 출고되면 quantity와 함께 줄어듭니다. 그리고 "101번 배치에서 5개를 예약했다"처럼 어느 배치인지 가리켜야 합니다.

반면 그 배치의 유통기한은 값 객체(date)입니다. 2026년 9월 1일은 어디에 적혀 있든 같은 날입니다.

엔티티 안에 값 객체가 들어 있는 이 구조가 도메인 모델의 일반적인 모습입니다.

5. 결제 (Payment)

엔티티입니다. 그리고 식별자를 무엇으로 할지가 실무 쟁점입니다.

결제는 승인 → 부분 환불 → 부분 환불 → 전액 환불처럼 상태가 변해가는 생애가 있고, 환불할 때 "어느 결제를 환불할지" 가리켜야 하므로 엔티티입니다.

식별자 후보가 둘입니다 — 우리가 만든 결제 ID와 PG사가 준 거래번호(tid). PG의 tid를 식별자로 쓰면 편해 보이지만, PG사를 바꾸는 순간(또는 두 개를 병행하는 순간) 식별자 체계가 무너집니다. 남의 시스템이 만든 값을 우리 엔티티의 식별자로 쓰지 않습니다. 우리 ID를 쓰고 tid는 속성으로 보관합니다. 10장에서 이 원칙을 다시 봅니다.

6. 상품 (Product) — 함정이 있습니다

엔티티입니다. 상품명과 가격이 바뀌어도 같은 상품이니까요.

함정은 여기입니다 — 그런데 주문 라인에 복사된 상품명과 가격은 값 객체입니다. 같은 정보인데 한쪽은 엔티티의 속성이고 한쪽은 값입니다.

구별하는 방법: 카탈로그의 Product.price는 "지금 이 상품을 얼마에 파는가"라는, 계속 변하는 현재 상태입니다. 주문 라인의 unit_price는 "그때 이 고객이 얼마를 냈는가"라는, 다시 변하지 않는 과거 사실입니다.

과거의 사실은 값 객체입니다. 이 문장이 6장 스냅샷의 한 줄 요약입니다.

어디까지 값 객체로 만들까

값 객체를 배우면 모든 것을 감싸고 싶어집니다. 그 충동을 조절하는 것이 이 화면의 목표입니다. 양쪽 끝에 각각 이름이 있습니다.

한쪽 끝 — 원시값 집착 (Primitive Obsession)

도메인 개념을 전부 int, str, dict로 다루는 것. Martin Fowler가 Refactoring에서 코드 냄새(code smell)로 지목했습니다. 1장의 코드가 이 상태였고, 결과는 화면 2·3에서 봤습니다.

다른 쪽 끝 — 값 객체 과용

모든 문자열에 타입을 만드는 것. ProductName, SlackChannel, LogMessage, Memo… 클래스가 50개 늘어나고, 각각에 대해 데이터베이스 변환 코드가 붙고, 정작 규칙은 하나도 없습니다. 비용은 다 내고 이득은 없는 상태입니다.

판단 기준 세 가지

셋 중 하나라도 해당하면 값 객체로 만들 가치가 있습니다. 하나도 없으면 원시 타입으로 둡니다.

  1. 규칙이 붙는가. "1 이상", "5자리 숫자", "원 단위", "이 형식" 같은 규칙이 있다면 그 규칙이 살 집이 필요합니다. → Quantity, OrderNumber
  2. 실수로 섞이면 손해가 나는가. 금액과 수량, 주문번호와 고객번호처럼 바꿔 넣어도 타입 검사가 통과되고 사고가 나는 조합이라면 타입을 나눕니다. → Money
  3. 여러 값이 항상 함께 움직이는가. 우편번호·도로명·상세주소·받는이·전화번호는 따로 존재할 이유가 없습니다. 함께 넘기고 함께 검증합니다. → Address
한빛몰의 결정판단근거
Money값 객체 ○ 기준 1·2 모두. 규칙도 많고 섞이면 돈이 걸린다
Quantity값 객체 ○ 기준 1. "1 이상"이 지켜져야 한다
Address값 객체 ○ 기준 3. 다섯 값이 늘 함께 움직인다
OrderNumber값 객체 ○ 기준 1·2. 형식이 있고, 다른 ID와 섞이면 위험하다
상품명그냥 str ✕ 규칙이 없고, 다른 문자열과 섞여도 손해가 없다
슬랙 채널명그냥 str ✕ 도메인 개념이 아니다. 알림 인프라의 설정값이다

Money에 통화(Currency)를 넣지 않은 이유

금액 값 객체를 소개하는 거의 모든 문헌이 Money(amount, currency)로 시작합니다. 이 교재는 일부러 넣지 않았습니다.

한빛몰은 원화만 씁니다. 통화 필드를 넣으면 모든 Money 생성에 인수가 하나 늘고, 모든 연산에 "통화가 같은지" 검사가 붙고, 데이터베이스에 컬럼이 하나 늘어납니다. 그 비용을 지불하고 얻는 것은 지금은 없습니다.

필요해지면 그때 넣습니다. 그리고 그때 고칠 곳은 Money 한 파일입니다 — 바로 이것이 값 객체를 만들어 둔 덕입니다. 값 객체는 "미래를 대비해 미리 복잡하게 만드는 것"이 아니라, "나중에 복잡해질 때 한 곳만 고치게 만드는 것"입니다.

FREE_SHIPPING_THRESHOLD = Money.won(30000)
SHIPPING_FEE = Money.won(3000)


@dataclass(frozen=True)
class Amounts:
    """세 금액을 함께 다니게 묶은 값 객체."""
    subtotal: Money
    discount: Money
    shipping_fee: Money

    @property
    def total(self) -> Money:                # 불변식 I2 가 여기 산다
        return self.subtotal - self.discount + self.shipping_fee


def calculate_amounts(lines: Sequence[OrderLine],
                      grade: MemberGrade) -> Amounts:
    subtotal = sum((line.subtotal for line in lines), Money.ZERO)
    discount = subtotal.percent(grade.discount_rate)

    if subtotal < FREE_SHIPPING_THRESHOLD and not grade.free_shipping:
        shipping_fee = SHIPPING_FEE
    else:
        shipping_fee = Money.ZERO

    return Amounts(subtotal=subtotal, discount=discount,
                   shipping_fee=shipping_fee)

2장 마무리

핵심 요약

  1. 값 객체는 불변이고, 내용이 같으면 같은 것이며, 바꿀 때는 새로 만들어 교체합니다. "int처럼 다뤄도 되는 도메인 개념"에 이름과 규칙을 붙인 것입니다.
  2. 엔티티는 식별자로 같음을 판단합니다. 내용이 다 바뀌어도 같은 것이고, 생애 주기가 있습니다. 엔티티는 dataclass로 만들지 않고 __eq__/__hash__를 식별자 기준으로 직접 씁니다.
  3. 규칙을 __post_init__에 넣으면 규칙을 어긴 값은 존재할 수 없습니다. 방어적 검사가 시스템 경계 한 곳으로 모입니다.
  4. 같은 것이 맥락에 따라 엔티티이기도 하고 값 객체이기도 합니다. 주문의 배송지는 값 객체, 주소록의 주소는 엔티티입니다. 이 발견이 9장으로 이어집니다.
  5. 값 객체는 규칙이 붙거나, 섞이면 손해가 나거나, 여러 값이 함께 움직일 때 만듭니다. 셋 다 아니면 원시 타입으로 두는 것이 옳습니다.

팀원이 Order를 이렇게 만들었습니다. 무엇이 문제일까요?

@dataclass(frozen=True)
class Order:
    order_number: OrderNumber
    shipping_address: Address
    status: OrderStatus
  1. frozen=True를 썼다 — 엔티티는 절대 불변이면 안 된다
  2. 동등성이 모든 필드로 정해진다 — 배송지가 바뀌면 다른 주문이 된다
  3. 필드가 너무 적다 — 주문 라인과 금액이 없다
  4. 타입 힌트가 부족하다

해설 엔티티의 동등성은 식별자 하나로 정해져야 합니다. dataclass가 만들어주는 __eq__는 그 반대입니다.

1번 선택지에 대해 조금 더 — frozen=True 엔티티는 실제로 유효한 설계입니다. 상태를 바꿀 때마다 새 Order를 반환하는 방식이고, 이력 추적과 동시성 처리에 유리합니다. 다만 __eq__는 여전히 식별자 기준으로 직접 써야 하고, ORM과 맞물릴 때 다루기 까다로워집니다. 이 교재는 가변 엔티티로 갑니다.

신규 요구사항입니다 — "쿠폰 기능을 추가한다. 쿠폰은 정액(3,000원 할인) 또는 정률(10% 할인)이고, 최대 할인 한도가 있다." 값 객체와 엔티티 중 어느 쪽으로 만들어야 할까요?

  1. 쿠폰은 규칙만 갖고 있으니 값 객체 하나로 충분하다
  2. 쿠폰은 사용 여부가 바뀌니 엔티티 하나로 충분하다
  3. 둘 다 필요하다 — 할인 규칙은 값 객체, 발급된 쿠폰은 엔티티
  4. 지금은 원시 타입으로 두고 나중에 판단한다

해설 두 가지가 섞여 있는 요구사항입니다.

할인 정책("3,000원 할인", "10% 할인, 최대 5,000원")은 규칙 덩어리이고, 같은 내용이면 같은 정책입니다. 값 객체입니다. 이걸 값 객체로 두면 policy.discount_for(subtotal) -> Money처럼 규칙이 자기 안에서 계산합니다.

발급된 쿠폰("김은수에게 발급된 쿠폰 A1B2C3, 사용됨, 만료일 12/31")은 개별 추적 대상입니다. 사용 여부가 바뀌고, "이 쿠폰"을 가리켜야 하므로 엔티티입니다.

이런 정책 값 객체는 6장 도메인 서비스에서 다시 등장합니다. 화면 13의 MemberGrade가 할인율을 스스로 아는 것과 같은 패턴입니다.

Money.percent()는 원 단위 미만을 버림합니다. 정산팀이 "회계 기준상 반올림이어야 한다"고 합니다. 무엇을 해야 할까요?

  1. Money.percent()를 고친다. 그리고 그 결정을 어디에 기록할지 정한다
  2. 정산 배치에서만 반올림으로 다시 계산한다
  3. percent(rate, rounding=...)로 인수를 추가해 호출자가 고르게 한다
  4. 고객에게 불리해지므로 반올림은 받아들이지 않는다

해설 이 퀴즈의 요점은 "고칠 곳이 한 군데"라는 상태의 가치입니다. 1장이라면 int(total * 0.05)가 흩어진 다섯 곳을 찾아다녀야 했고, 그중 하나를 놓쳤을 것입니다.

3번 선택지가 매력적으로 보이는 것을 경계하세요. "유연하게 만들자"는 충동은 결정을 호출자에게 미루는 것이고, 결정은 미룰수록 흩어집니다. 업무 규칙이 하나라면 코드도 하나여야 합니다.

한빛몰에 회원 등급을 값 객체로 만들어 보세요. 요구사항은 이렇습니다.

  • 등급은 일반·실버·골드 세 가지다.
  • 할인율은 각각 0%, 3%, 5%다.
  • 골드는 금액과 무관하게 무료배송이다.
  • 등급이 하나 추가될 때 고칠 파일이 하나여야 한다.

화면 13의 calculate_amounts()가 grade.discount_rate와 grade.free_shipping을 쓰고 있었습니다. 그게 동작하도록 만들면 됩니다.

모범답안 — 그리고 흔한 두 가지 접근

흔한 접근 1: Enum + 바깥의 딕셔너리

class MemberGrade(Enum):
    일반 = auto()
    실버 = auto()
    골드 = auto()

DISCOUNT_RATES = {                    # 규칙이 Enum 밖에 있다
    MemberGrade.일반: Decimal("0"),
    MemberGrade.실버: Decimal("0.03"),
    MemberGrade.골드: Decimal("0.05"),
}
FREE_SHIPPING_GRADES = {MemberGrade.골드}

동작합니다. 1장보다 훨씬 낫습니다. 부족한 점: 등급을 추가할 때 고칠 곳이 세 군데(Enum, 딕셔너리, 집합)이고, 딕셔너리에 넣는 것을 잊으면 KeyError가 실행 시점에 터집니다.

흔한 접근 2: 값을 가진 Enum

class MemberGrade(Enum):
    일반 = (Decimal("0"), False)
    실버 = (Decimal("0.03"), False)
    골드 = (Decimal("0.05"), True)

    def __init__(self, discount_rate: Decimal, free_shipping: bool) -> None:
        self.discount_rate = discount_rate
        self.free_shipping = free_shipping

이게 모범답안입니다. Enum 멤버가 자기 규칙을 들고 있어서 등급 추가는 한 줄입니다. 빠뜨릴 수 있는 딕셔너리가 없습니다. MemberGrade.골드.discount_rate처럼 읽히는 것도 업무 언어에 가깝습니다.

쓰는 쪽은 이렇게 됩니다.

>>> subtotal = Money.won(10000)
>>> subtotal.percent(MemberGrade.골드.discount_rate)
Money(amount=Decimal('500'))
>>> MemberGrade.골드.free_shipping
True

여기서 한 걸음 더 — 이 설계의 한계

할인율을 코드에 박아두면 프로모션 기간에 실버 할인을 5%로 올리는 일을 배포 없이 할 수 없습니다. 실무에서 이 요구는 반드시 옵니다.

그때는 등급을 Enum이 아니라 데이터베이스에서 읽어오는 정책 객체로 바꿔야 합니다. 다만 지금 그렇게 만들지는 않습니다. 요구가 오지 않은 유연성은 비용만 냅니다 (화면 12의 통화 이야기와 같습니다).

중요한 것은 그때 고칠 곳이 어디인지 지금 알 수 있다는 점입니다 — MemberGrade를 쓰는 곳은 calculate_amounts() 한 곳뿐입니다. 6장에서 이것을 DiscountPolicy라는 도메인 서비스로 바꿉니다.

상품 목록 100개가 느려지는 이유

은수

상품 목록에 "재고 있음/없음"만 나오니까 고객이 답답해해요. 몇 개 살 수 있는지랑, 지금 없으면 언제 들어오는지도 같이 보여주세요.

요구사항 자체는 낯설지 않습니다 — InventoryItem.sellable_quantity(I20, 판매가능수량)는 3장부터 있었습니다. 개발자는 자연스럽게 이렇게 짭니다.

# catalog/application/queries.py — 처음 떠오르는 방법class CatalogQueryService:
    def __init__(self, uow: UnitOfWork, inventory: InventoryRepository,
                 shipping: ShippingPolicy) -> None:
        self._uow, self._inventory, self._shipping = uow, inventory, shipping

    def list_products(self, offset: int, limit: int) -> list["ProductListingRow"]:
        with self._uow as uow:
            products = uow.products.list_page(offset, limit)   # 1  Product 애그리게이트 N개

        skus = [c.sku for p in products for c in p.composition]
        items = self._inventory.get_many(skus)                 # 2  한 번에 조회(4장 페이지 4)

        rows = []
        for p in products:
            atp = min(items[c.sku].sellable_quantity // c.quantity_per_product
                       for c in p.composition)                  # 3
            rows.append(ProductListingRow(p.product_id, p.name,
                        int(p.price.amount), atp, None, None))
        return rows
  1. 8행 카탈로그 쪽 리포지토리(uow.products)는 아직 이 교재에 없지만, 4장의 OrderRepository·InventoryRepository와 같은 모양으로 자연스럽게 하나 더 생긴다고 상상해 보세요 — 페이지 하나 분량의 Product 애그리게이트를 통째로 불러옵니다.
  2. 11행 get_many를 씁니다. 4장 페이지 4가 가르친 그대로 — SKU마다 get을 부르지 않고 한 번에 가져옵니다.
  3. 15~16행 9장의 ProductSku.quantity_per_product를 반영합니다 — 세트 상품이라면 구성 SKU 각각의 ATP를 세트 배수로 나눈 값 중 가장 작은 것이 그 세트를 몇 개 만들 수 있는지를 정합니다(분할 출고를 하지 않는다는 I21과 같은 성격의 논리 — 하나라도 모자라면 세트 전체가 묶입니다).

11행에서 get_many를 썼으니 왕복은 두 번뿐입니다 — 겉보기엔 4장의 교훈을 잘 지킨 코드입니다. 그런데 상품이 100개인 페이지에서 이 코드를 실제로 돌리면 목록이 뜨기까지 몇 초씩 걸립니다. 왜일까요?

관계 로딩에서 생기는 N+1

4장 페이지 4의 N+1은 InventoryItem 루트 행을 SKU마다 따로 조회하는 문제였고, get_many가 그걸 막았습니다. 그런데 위 매핑에는 relationship(StockBatch)에 로딩 방식을 지정하지 않았습니다 — SQLAlchemy의 기본값은 지연 로딩(lazy loading)입니다. 즉 item._batches는 처음 접근하는 순간에야 SELECT * FROM stock_batches WHERE sku = ?를 실행합니다. 그런데 item.sellable_quantity가 정확히 그 _batches를 순회합니다(9장 페이지 8의 그 프로퍼티). 루트 100개를 한 번에 가져와도, 그 뒤 100번의 .sellable_quantity 접근이 배치 조회 100번을 새로 만듭니다. 같은 N+1 문제가 이번에는 관계 로딩에서 다시 나타났습니다.

N+1을 selectinload 같은 즉시 로딩으로 없앤다고 해도 더 근본적인 문제가 남습니다 — InventoryItem을 완전히 복원하려면 그 SKU가 지금까지 받은 모든 배치(이미 소진되어 재고에 안 잡히는 옛 배치까지)를 파이썬 객체로 띄워야 합니다. 정작 화면에 필요한 건 정수 두 개(판매가능수량, 도착 예정일)뿐인데, 그 두 숫자를 얻으려고 애그리게이트 전체 — 나중에 쓸 allocate()· release() 같은 쓰기 행위까지 포함된 객체 — 를 매번 다시 조립하고 있습니다.

3장 페이지 5는 애그리게이트를 "데이터 변경의 목적으로 하나의 단위로 취급되는 연관 객체들의 묶음"이라고 정의했습니다. 그리고 "주문 목록 화면에 회원 이름도 같이 보여줘야 하니까 Order가 Customer를 갖고 있어야겠다"는 생각은 애그리게이트를 나누는 근거가 되지 못하며, "읽기는 13장 CQRS의 영역입니다"라고 적었습니다. 지금 우리가 맞닥뜨린 것이 정확히 그 문제입니다.

주문 목록의 반복 조회

5장 페이지 8은 이미 "애그리게이트에서 읽어 DTO로 조립"하는 방법을 보여준 적이 있습니다 — 주문 한 건의 상세 화면이었습니다.

# 5장 페이지 8 — 주문 한 건의 상세. 다시 가져옴def get_order_detail(self, order_number: OrderNumber) -> "OrderDetail":
    with self._uow as uow:                                  # 1
        order = uow.orders.get(order_number)                # 2  주문 컨텍스트
        number = order.order_number.value
        customer_id = order.customer_id
        total = int(order.total_amount.amount)
    name = self._members.name_of(customer_id)               # 3  회원 컨텍스트
    return OrderDetail(order_number=number, customer_name=name,
                       total_amount=total)

주문 한 건이라면 이 코드는 충분히 빠릅니다. 그런데 "내 주문 내역" 화면처럼 같은 고객의 주문 20건을 목록으로 보여줘야 한다면, 개발자는 자연스럽게 이 코드를 반복문에 넣습니다.

# ordering/application/queries.py — 목록으로 확장한 버전def list_my_orders(self, customer_id: UUID,
                    numbers: Sequence[OrderNumber]) -> list["OrderListingRow"]:
    rows = []
    with self._uow as uow:
        for number in numbers:                                # 1
            order = uow.orders.get(number)                     # 2  주문마다 애그리게이트 통째로
            name = self._members.name_of(order.customer_id)    # 3  주문마다 회원 컨텍스트 왕복
            rows.append(OrderListingRow(
                order.order_number.value, name, order.status.name,
                int(order.total_amount.amount), len(order.lines)))
    return rows
  1. 5행 numbers(주문번호 목록)를 하나씩 순회합니다 — 반복문 자체는 문제가 아닙니다. 문제는 그 안에서 무엇을 반복하느냐입니다.
  2. 6행 주문이 20건이면 uow.orders.get()이 20번 불립니다. 그때마다 Order와 그 안의 OrderLine 전체가 다시 조립됩니다(4장의 orders_table·order_lines_table 매핑도 관계 로딩을 따로 지정하지 않았으므로, 페이지 2와 같은 이유로 이 역시 지연 로딩입니다).
  3. 7행 더 눈에 띄는 낭비입니다 — "내 주문 내역"이므로 customer_id는 20건 내내 같은 값입니다. 그런데 name_of()를 20번 부릅니다. 같은 질문을 같은 답이 나올 걸 알면서도 스무 번 반복한 것입니다.

4장 페이지 12의 퀴즈가 이미 이 논리를 한 번 냈습니다 — InventoryItem을 위해 StockBatchRepository를 새로 만들자는 제안에 "애그리게이트는 쓰기 단위이지 읽기 단위가 아니다"라고 반대했습니다. 그 자리는 목록 조회가 아직 등장하기 전이라 대안을 "13장에서 정식으로 다룬다"고만 미뤄 뒀습니다.

13장 · 페이지 4

CQRS라는 이름

사실 이 교재는 5장부터 이미 이 방향으로 걷고 있었습니다 — place_order() (상태를 바꾸는 커맨드)와 get_order_detail()(상태를 읽기만 하는 쿼리)을 처음부터 다른 메서드로 나눠 왔습니다. 이 구분 자체는 버트런드 마이어의 CQS(Command-Query Separation, "메서드 하나는 무언가를 바꾸거나 무언가를 돌려주거나 둘 중 하나만 해야 한다") 원칙입니다.

그렉 영(Greg Young)은 2010년경 이 아이디어를 메서드 수준에서 모델 수준으로 끌어올렸습니다 — CQRS(Command Query Responsibility Segregation)는 "쓰기와 읽기는 같은 메서드뿐 아니라 같은 모델도 함께 쓸 필요가 없다"는 주장입니다. 페이지 2~3에서 본 문제의 정체가 이것입니다 — Order·InventoryItem은 불변식을 지키도록 설계된 쓰기 모델인데, 화면 표시는 그 설계가 지켜야 할 책임과 아무 상관이 없습니다.

CQRS는 "전부 아니면 전무"가 아니라 단계입니다. 이 교재가 이미 있는 자리부터 아직 안 간 자리까지 나열하면 이렇습니다.

단계모습이 교재
0. CQS만같은 모델, 메서드만 커맨드/쿼리로 구분 5장부터 — place_order() vs get_order_detail()
1. DTO 조립같은 DB, 애그리게이트를 읽어 DTO로 변환 5장 페이지 8 — 주문 한 건에는 충분
2. 쿼리 객체같은 DB, 도메인 모델을 거치지 않고 SQL로 직접 읽기 이 장 페이지 5 — 지금 만든다
3. 동기화 읽기 테이블미리 계산해 둔 별도 테이블. 쓰기와 별도로 갱신 페이지 6 — 언제 필요한지만 다룬다
4. 별도 DB/서비스읽기 모델이 물리적으로 다른 저장소 10~12장이 "다른 서비스로 분리"를 언급한 자리와 같은 방향. 코드로 만들지 않는다
5. 이벤트 소싱쓰기 모델 자체가 이벤트 로그. 읽기 모델은 그 재생(replay) 페이지 7~8 — 개념만. 코드로 만들지 않는다

CQRS와 이벤트 소싱의 관계

둘을 한 세트로 묶어 말하는 경우가 많지만, CQRS는 이벤트 소싱을 전제하지 않습니다. 페이지 5에서 만들 쿼리 객체는 이벤트를 하나도 쓰지 않는 CQRS입니다 — 같은 테이블을 도메인 모델 없이 다시 읽을 뿐입니다. 반대로 이벤트 소싱을 하면 (페이지 7) 현재 상태를 바로 읽을 방법이 없어서 사실상 CQRS가 강제됩니다 — 정리하면, 이벤트 소싱 없이 CQRS는 할 수 있지만 CQRS 없이 이벤트 소싱은 할 수 없습니다.

13장 · 페이지 5

최소 형태 — 읽기 전용 쿼리 객체

1장 페이지 5~7이 SQL을 직접 썼던 이유는 "그것 말고는 방법을 몰랐기 때문"이었고, 그게 이 교재가 지적한 문제였습니다. 이번엔 다릅니다 — 읽기 전용 조회로 한정한다는 조건 아래에서, 의도적으로 같은 방식으로 돌아갑니다. 도메인 객체를 하나도 만들지 않고, SQL이 직접 답을 계산하게 둡니다.

1장 페이지 16은 "지난달 카테고리별 매출 상위 10개" 같은 데이터 집합 연산은 객체보다 SQL이 맞다고 하고, 이 장에서 다시 다루겠다고 했습니다. 지금 보는 판매가능수량 집계가 바로 그런 연산입니다. 여러 행을 묶어 합하는 계산이라 SQL에 맡깁니다.

SKU별 판매가능수량부터 봅니다. 9장 페이지 8의 sellable_quantity 프로퍼티(sum(b.available for b in batches), 창고·입고예정 배치를 가리지 않고 모두 더함, I20)와 같은 규칙을 SQL로 계산합니다.

# reporting/queries.py — SKU 단위 판매가능수량SELECT sku,
       SUM(CASE WHEN kind = '창고' THEN quantity - reserved
                ELSE 0 END) AS on_hand_available,             -- 1
       SUM(quantity - reserved) AS atp,                        -- 2
       MIN(CASE WHEN kind = '입고예정' AND quantity - reserved > 0
                THEN eta END) AS earliest_eta                  -- 3
FROM stock_batches
GROUP BY sku
  1. 2~3행 CASE WHEN 조건 THEN 값 ELSE 값 END는 행마다 조건에 따라 다른 값을 골라 쓰는 SQL 문법입니다 — 파이썬의 값 if 조건 else 값과 같은 자리에 씁니다. 여기서는 "창고 배치일 때만 센다"는 조건을 SUM 안에 넣어, 파이썬으로 치면 sum(b.available for b in batches if b.kind == 창고)와 같은 일을 SQL 한 줄로 합니다(9장 페이지 8의 available_quantity, I7).
  2. 4행 SUM(quantity - reserved)는 배치 종류(창고·입고예정)를 가리지 않고 전부 더합니다 — I20이 정의하는 판매가능수량(atp, ATP) 그 자체입니다. 바로 위 on_hand_available이 창고 배치만 골라 더하는 것과 나란히 놓고 비교해 보세요.
  3. 5~6행 ELSE가 없는 CASE WHEN은 조건을 만족하는 행이 하나도 없으면 NULL을 돌려줍니다 — 입고예정 배치가 하나도 없는 SKU라면 earliest_eta는 NULL입니다. 1장에서 COALESCE로 감쌌던 것과 달리 여기서는 그냥 둡니다. NULL 자체가 "입고 예정이 없다"는 유효한 답이기 때문입니다(빈 합계를 0으로 바꿔야 했던 1장의 상황과는 다릅니다).
  4. 8행 GROUP BY는 "같은 sku 값끼리 묶어서, 그 묶음 전체에 대해 SUM·MIN 같은 집계 함수를 한 번씩만 계산하라"는 뜻입니다 — SKU마다 쿼리를 따로 날리지 않고 테이블 전체를 한 번 훑어서 SKU별 결과를 한 번에 뽑습니다.

이제 이 결과를 상품(Product) 단위로 접습니다. 9장이 정한 composition(상품 1개가 SKU 몇 개로 구성되는가)을 SQL의 하위 질의로 한 번 더 조인합니다.

# reporting/queries.py — 상품 목록 조회, sku_atp는 위 질의SELECT product_id, name, price,
       MIN(atp / quantity_per_product) AS sellable_quantity,   -- 1
       MAX(ready_date) AS ship_on                               -- 2
FROM (
    SELECT p.product_id, p.name, p.price, ps.quantity_per_product,
           sa.atp,
           CASE WHEN sa.on_hand_available >= ps.quantity_per_product
                THEN DATE('now')
                ELSE sa.earliest_eta END AS ready_date           -- 3
    FROM products p
    JOIN product_skus ps ON ps.product_id = p.product_id         -- 4
    JOIN (sku_atp) sa ON sa.sku = ps.sku
    WHERE p.status = '판매중'
) t
GROUP BY product_id, name, price
ORDER BY name
LIMIT ? OFFSET ?
  1. 2행 MIN(atp / quantity_per_product) — 상품 하나가 SKU 여러 개로 구성되면(9장의 세트 상품), 각 SKU가 몇 세트어치를 감당하는지 나눠 보고 가장 모자란 SKU가 전체를 정합니다. 페이지 2의 코드가 파이썬 min()으로 하던 일과 같습니다 — 여기서는 SQL이 합니다.
  2. 3행 페이지 2의 나머지 절반(도착 예정일)입니다. ship_on은 구성 SKU 중 가장 늦게 준비되는 날입니다 — 세트 상품은 하나라도 모자라면 전체를 나눠 보낼 수 없다는, I21과 같은 논리입니다.
  3. 7~9행 안쪽 CASE가 SKU별 ready_date를 정합니다 — 지금 창고 재고만으로 이 상품 한 개분을 채울 수 있으면 오늘(DATE('now')) 출고 가능, 모자라면 그 SKU의 earliest_eta(가장 이른 입고예정일)가 준비일이 됩니다. 페이지 2의 코드는 ship_on·arrival_estimate 자리를 None, None으로 비워 뒀었는데, 이 CASE가(3행의 MAX를 거쳐) ship_on을 채웁니다 — arrival_estimate는 list_page()가 그 값에 배송 리드타임을 더해 따로 채웁니다.
  4. 10~12행 JOIN은 두 테이블(또는 하위 질의)의 행을 공통 값이 같은 것끼리 짝지어 한 행으로 합칩니다 — 파이썬으로 치면 두 딕셔너리를 같은 키로 묶어 새 딕셔너리를 만드는 것과 비슷합니다. product_skus·SKU별 집계·products 세 곳에 흩어진 값을 한 번의 조회로 모읍니다.

다만 이 계산에는 놓치는 경우가 하나 있습니다 — 구성 SKU 중 하나가 영원히 입고 예정이 없다면(earliest_eta가 NULL), SQL의 MAX()는 NULL을 조용히 무시하고 다른 구성요소의 날짜를 대신 보여줍니다. sellable_quantity는 이 경우 정확히 0이 되어 품절임을 알리지만, ship_on 쪽은 그 사실을 반영하지 못합니다. 이런 경계 사례까지 다 잡으려면 SQL이 더 복잡해져야 하는데, 이 교재는 이 한계를 인정하는 선에서 넘어갑니다.

경계 사례가 하나 더 있습니다 — 페이지 앞쪽의 "같은 규칙을 계산"에도 조건이 붙습니다. 위 sku_atp 서브쿼리는 stock_batches를 GROUP BY sku한 결과라서, 배치가 한 건도 없던 신상품 SKU는 그 서브쿼리에 아예 행이 없습니다. 이 상품 목록 SQL이 그 결과와 JOIN (그냥 JOIN이라고 쓰면 INNER JOIN이며, 짝이 없는 행은 버립니다)하므로, 그런 SKU를 포함한 상품은 목록에서 통째로 빠집니다 — 9장의 sellable_quantity 프로퍼티(빈 배치 리스트에 sum(), 조용히 0)라면 일어나지 않을 누락입니다. 실무라면 LEFT JOIN(왼쪽 테이블의 행은 짝이 없어도 남기는 조인)과 COALESCE로 고쳐야 하는 대목이지만, 이 교재는 이 경계 사례도 인정하는 선에서 넘어갑니다.

컨텍스트 경계를 넘는 조인의 세 조건

11장의 import-linter 계약은 "재고가 카탈로그를 import하면 안 된다"고 정했습니다. 그런데 위 SQL은 products·product_skus (카탈로그)와 stock_batches(재고)를 한 질의 안에서 조인합니다 — 명백히 경계를 넘습니다. 그런데 이건 11~12장에서 본, 마지못해 감수하는 "위반"과는 다릅니다. 세 조건이 함께 지켜지기 때문입니다.

  1. 같은 DB. 물리적으로 다른 서비스라면 이 조인 자체가 불가능합니다.
  2. 도메인 클래스를 하나도 import하지 않습니다. 이 모듈은 Product·Sku·InventoryItem 어느 것도 모릅니다. 아는 것은 테이블 이름과 컬럼뿐입니다.
  3. DTO만 반환합니다. 반환값에는 행동이 없고, 이 값으로 무언가를 바꿀 수 없습니다.

그래서 이 코드는 ordering/·inventory/·catalog/ 어디에도 속하지 않는 reporting/이라는 네 번째 자리에 둡니다 — 어느 컨텍스트의 도메인·응용 계층에도 속하지 않는, 오직 화면을 위한 조회 전용 모듈입니다.

실제로 데이터를 넣고 돌려 본 결과입니다. 표는 이해하기 쉽도록 신라면부터 적었습니다(위 SQL의 ORDER BY name으로 정렬하면 생수가 먼저 나옵니다). 오늘은 2026-09-20이고, SKU-RAMEN(신라면)은 창고에 10개 중 8개가 이미 예약되어 2개만 가용하고 입고예정 50개(ETA 10/5)가 더 있습니다. SKU-WATER(생수)는 창고 재고가 0이고 입고예정 100개(ETA 9/30)뿐입니다.

도착 예정일에는 "근사"라는 단서가 붙어 있습니다. Order.promise_delivery()가 실제로 약속하는 날짜(I22)는 그 주문이 allocate()를 부르는 순간 FEFO· 입고예정 우선순위(I19)까지 반영해 정확히 계산됩니다. 지금 이 목록의 날짜는 "이 SKU의 가장 빠른 입고예정 하나"만 본 단순화된 값입니다 — 여러 주문이 동시에 같은 배치를 다투는 경우까지는 반영하지 않습니다. 목록 화면은 근사치로 충분하고, 진짜 약속은 주문 시점에 확정된다는 이 구분 자체가 CQRS가 던지는 질문입니다 — 모든 화면이 도메인 모델만큼 정확해야 하는 것은 아닙니다.

파이썬 쪽은 이 SQL을 감싸는 얇은 클래스 하나면 됩니다.

# reporting/queries.py@dataclass(frozen=True)
class ProductListingRow:
    product_id: str
    name: str
    price: int
    sellable_quantity: int
    ship_on: date | None            # None이면 입고 예정도 없다(품절)
    arrival_estimate: date | None   # ship_on + 배송 리드타임(근사)

class SqlProductListingQuery:
    def __init__(self, connection, shipping: ShippingPolicy) -> None:
        self._conn, self._shipping = connection, shipping

    def list_page(self, offset: int, limit: int) -> list[ProductListingRow]:
        rows = self._conn.execute(_LISTING_SQL, (limit, offset)).all()
        result = []
        for r in rows:
            ship = date.fromisoformat(r.ship_on) if r.ship_on else None
            arrival = ship + self._shipping.lead_time if ship else None
            result.append(ProductListingRow(
                r.product_id, r.name, r.price, r.sellable_quantity, ship, arrival))
        return result

SQLite는 날짜를 문자열로 돌려주므로 date.fromisoformat으로 date로 바꿉니다.

여기서도 배송 리드타임을 상수로 두지 않았습니다 — self._shipping.lead_time은 3장 페이지 14가 정한 그 규칙(정책 객체로 받는다)이 읽기 쪽에도 그대로 적용된다는 뜻입니다. ShippingPolicy는 5장이 이미 정의해 둔 포트를 재사용할 뿐, 새로 만들지 않습니다.

주문 목록도 같은 방법으로 풉니다. 3장 페이지 16의 퀴즈가 낸 그 상황 — "주문 목록에 회원 이름도 보여 달라" — 을 실제로 풀어 봅니다.

COALESCE를 여기 남겨 뒀지만, 사실 이 자리에서는 발동할 일이 없습니다 — WHERE만 있고 JOIN이 없었던 1장의 상황과 달리 이 쿼리는 order_lines와 INNER JOIN하고, 이 도메인은 EmptyOrder(I1)로 라인 없는 주문 자체를 허용하지 않습니다.   2. 6행 members 테이블과의 조인이 위 상자의 "경계를 넘는 조인" 원칙을 여기서도 그대로 따릅니다 — 도메인 클래스는 모르고 테이블만 압니다.

뷰와 동기화 테이블의 득실

페이지 5의 SQL을 CREATE VIEW product_listing AS SELECT ...로 감싸 두면 이름 하나로 재사용할 수 있습니다. 그런데 뷰는 계산을 저장해 두는 것이 아닙니다 — SELECT * FROM product_listing을 실행할 때마다 뒤에 숨은 JOIN·GROUP BY가 매번 다시 돌아갑니다(더구나 SQLite에는 실체화 뷰(materialized view) 자체가 없습니다 — 뷰는 언제나 그 순간의 계산입니다). 뷰는 "같은 SQL을 여러 곳에서 복사하지 않는다"는 편의일 뿐, 페이지 2가 겪은 "매번 다시 계산한다"는 근본 성격은 바뀌지 않습니다.

진짜 다음 단계는 미리 계산해서 저장해 둔 별도 테이블입니다 — product_listing_view 같은 테이블에 sellable_quantity· ship_on을 이미 계산된 값으로 넣어 두고, 읽기는 그 테이블 하나만 SELECT합니다. 그런데 이 값은 재고가 바뀔 때마다(입고, 할당, 취소) 누군가 다시 계산해 넣어야 합니다 — 7장부터 있는 DeliveryPromised 같은 실제 도메인 이벤트는 물론, 배치가 실제로 입고될 때 발행된다고 가정할 InboundArrived(지금 코드엔 없는 가상의 이벤트) 같은 것까지 구독하는 프로젝터를 새로 만드는 일입니다.

동기화 테이블의 비용

  • 프로젝터가 밀리거나 실패하면 화면의 숫자가 진짜 재고와 어긋납니다 — 12장이 "재고 반영은 5초 이내"로 합의했던 바로 그 결과적 일관성 문제가, 이번엔 재고 할당이 아니라 화면 표시를 두고 다시 열립니다.
  • 테이블이 하나 늘면 마이그레이션·백업·모니터링 대상도 하나 늘어납니다.
  • 프로젝터 코드에 버그가 있으면, 페이지 5의 SQL과 달리 DB를 직접 들여다봐도 원인을 못 찾습니다 — 저장된 값 자체가 이미 틀렸기 때문입니다. 진짜 원인은 "그 값을 왜 그렇게 계산해 넣었는가"라는 프로젝터의 과거 실행에 있습니다.

3장 페이지 16의 퀴즈는 별도 읽기 테이블이 왜 대부분에게 과한지를 13장에서 다루겠다고 예고했습니다. 답은 이렇습니다 — 페이지 5의 쿼리 객체가 이미 충분히 빠르다면, 동기화 테이블은 얻는 것 없이 위 세 가지 비용만 추가합니다. 한빛몰 규모(SKU 수천 개, 배치 수만 행)에서 GROUP BY 한 번은 인덱스만 잘 잡혀 있으면 수십 밀리초 안에 끝납니다. 동기화 테이블이 실제로 쓸모 있는 경우는 딱 하나입니다 — 페이지 5가 조인하던 테이블들이 더 이상 같은 DB에 있지 않을 때입니다. 재고와 카탈로그가 서로 다른 서비스로 쪼개지면(10~12장이 언급만 하고 코드로 만들지 않은 그 방향), 애초에 한 번의 SQL로 조인할 방법이 없으므로 그때는 동기화된 사본을 두는 것이 유일한 선택지가 됩니다. 그 전에는 페이지 5로 충분합니다.

13장 · 페이지 7

이벤트 소싱의 개념

7장부터 DomainEvent가 있었습니다 — OrderPlaced, DeliveryPromised, InboundDelayed. 그런데 이 이벤트들은 애그리게이트 사이의 통신 수단이었을 뿐입니다. 실제로 "지금 상태가 무엇인가"를 묻는 질문의 답은 여전히 stock_batches·orders 테이블의 현재 값(quantity, reserved, status)이 들고 있습니다. 이벤트는 발행되고 나면 버려집니다(구독자가 처리를 마치면 끝).

이벤트 소싱(Event Sourcing)은 이 관계를 뒤집습니다 — 현재 상태를 저장하는 대신, 그 상태에 이르기까지 일어난 사실 전부를 순서대로 저장합니다. InventoryItem의 "지금 reserved가 5"라는 값 자체를 테이블에 두지 않고, 대신 이런 로그를 둡니다.

순번이벤트내용
1배치입고됨batch_id=B1, quantity=10
2예약됨batch_id=B1, count=3, order=O-1
3예약됨batch_id=B1, count=5, order=O-2
4예약취소됨batch_id=B1, count=3, order=O-1(주문 취소)

"지금 reserved가 얼마인가?"는 저장된 값이 아니라 이 로그를 처음부터 재생(replay)한 결과입니다(0 + 3 + 5 − 3 = 5). 현재 상태는 로그의 파생값일 뿐, 진실은 로그 자체입니다.

이벤트 소싱의 장점

  • 완전한 감사 추적. "이 배치의 reserved가 왜 지금 5인지"를 정확히 누가, 언제, 무엇을 했는지까지 답할 수 있습니다. 지금 한빛몰의 stock_batches는 배치 자체는 지우지 않지만(9장), 그 배치의 예약 수량이 어떤 주문들 때문에 지금 값이 됐는지의 이력은 저장하지 않습니다 — 현재 값만 있고 경로는 없습니다.
  • 시간을 되돌린 질문. "지난주 화요일 오후 3시의 재고는 얼마였나"에 로그를 그 시점까지만 재생해서 답합니다.
  • 읽기 모델을 나중에 새로 만들 수 있다. 페이지 5·6에서 만든 읽기 모델에 없던 통계가 필요해지면, 처음부터 다시 재생해서 과거 데이터에도 소급 적용된 새 읽기 모델을 만들 수 있습니다 — 페이지 6의 동기화 테이블은 "지금부터"만 쌓이지만, 이벤트 로그는 "처음부터" 다시 계산할 수 있습니다.

다만 비용이 있습니다 — 이벤트 소싱을 하는 순간, "지금 상태"를 바로 읽는 길이 없어집니다. 페이지 6이 "선택"이라고 했던 동기화 읽기 모델이 이번에는 모든 화면에 대해 필수가 됩니다. 다음 페이지에서 이 비용을 자세히 봅니다.

13장 · 페이지 8

이벤트 소싱이 대부분의 프로젝트에 과한 이유

이벤트 소싱의 비용

  1. 모든 읽기에 프로젝터가 만든 읽기 테이블이 필요하다. 페이지 6에서는 "동기화 테이블이 필요한가"가 선택이었습니다. 이벤트 소싱에서는 SELECT quantity FROM stock_batches 같은 가장 단순한 질문에도 답할 테이블이 애초에 없습니다 — 시스템을 켜는 첫날부터 프로젝터 하나 이상을 만들어야 합니다.
  2. 이벤트 스키마도 버전을 관리해야 한다. InboundDelayed에 필드 하나를 추가하고 싶다고 합시다. 새 이벤트는 새 필드를 갖지만, 이미 저장된 옛날 이벤트들은 그 필드가 없는 채로 영원히 남습니다. 재생 코드는 옛 모양과 새 모양을 둘 다 이해해야 합니다 — 이런 이벤트 버전 관리 자체가 하나의 전문 분야입니다.
  3. 디버깅이 어려워진다. "왜 지금 이 값인가"에 답하려면 SELECT 한 줄이 아니라 로그를 처음부터, 또는 중간에 저장해 둔 상태(이벤트 소싱에서 "스냅샷"이라 부르며, 6장의 가격 스냅샷과는 다른 뜻입니다)부터 재생해야 합니다. 페이지 6의 "동기화 테이블은 값이 틀려도 원인을 못 찾는다"는 문제가, 이벤트 소싱에서는 모든 상태에 대해 근본적으로 그렇습니다.
  4. 팀 전체가 새 모델로 사고해야 한다. 이벤트 스토어(이벤트 로그를 저장하는 전용 저장소)를 운영해 본 팀이 드뭅니다. 학습 비용과 도구 투자가 본문 전체보다 클 수 있습니다.

그런데도 값어치가 있는 도메인이 있습니다 — 이력 그 자체가 업무 요구사항인 도메인입니다. 회계 원장(모든 분개가 영구히 남아야 함), 금융 거래, 보험 청구 처리처럼 "무슨 일이 있었는지"를 사후에 설명할 수 있어야 하는 게 법적·감사 요구인 경우입니다. 이때는 이벤트 소싱의 1~3번 비용을 기꺼이 감수합니다 — 감사 추적을 별도로 흉내 내는 것보다, 처음부터 그것을 저장 방식으로 삼는 편이 쌉니다.

한빛몰에 대한 판단

재고 불일치는 12장 페이지 7이 이미 "실사 주기 단위의 결과적 일관성"으로 답을 냈습니다 — 실물과 장부가 어긋나면 실사로 맞추면 됩니다. "이 배치가 왜 지금 이 수량인지 5년 전 이벤트까지 거슬러 설명해야 한다"는 요구가 한빛몰 어디에도 없습니다. 배치를 지우지 않고 남겨 두는 지금 방식(9장)만으로도 이 도메인이 필요로 하는 이력은 충분합니다 — 완전한 이벤트 소싱이 주는 나머지 가치는, 한빛몰이 비용을 감수할 만큼 필요로 하지 않는 가치입니다.

판단 기준을 한 문장으로 줄이면 이렇습니다 — "이력을 재구성할 수 있으면 좋겠다"가 아니라 "이력이 없으면 이 업무 자체가 성립하지 않는다"일 때만 이벤트 소싱을 고려합니다. 14장이 이 질문("DDD를 쓰지 말아야 할 때")을 더 넓은 범위로 다시 다룹니다.

13장 · 페이지 9

13장 마무리

핵심 요약

  1. 애그리게이트는 쓰기 단위이지 읽기 단위가 아닙니다. 화면에 필요한 숫자 두 개를 얻으려고 애그리게이트 전체(관계 로딩까지 포함)를 복원하면, 왕복 횟수를 줄여도(get_many) 화면은 계속 느립니다.
  2. CQRS는 "쓰기와 읽기가 같은 모델을 거칠 필요가 없다"는 아이디어이고, 전부-아니면-전무가 아니라 단계입니다 — DTO 조립(5장)도 이미 CQRS의 시작이고, 도메인 모델을 거치지 않는 읽기 전용 쿼리 객체(이 장)가 그 최소 형태입니다.
  3. 쿼리 객체는 같은 DB, 도메인 클래스 미참조, DTO만 반환이라는 세 조건 아래에서 컨텍스트 경계를 의도적으로 넘습니다 — 이건 11~12장의 "위반"과 달리, 원칙을 지키면서 만든 예외입니다.
  4. 별도로 동기화되는 읽기 테이블은 페이지 6의 세 가지 비용(지연·운영 부담·디버깅 난이도)이 듭니다 — 조인할 테이블들이 물리적으로 갈라질 때가 아니면 대부분 과합니다.
  5. 이벤트 소싱은 현재 상태 대신 사실의 로그를 저장 방식으로 삼는 것입니다. CQRS를 강제하고, 이벤트 버전 관리·디버깅 난이도라는 새 비용을 낳습니다 — 이력 자체가 업무 요구사항인 도메인(회계, 금융) 밖에서는 대체로 과합니다.

InventoryRepository.get_many(skus)로 SKU 100개를 한 번의 왕복으로 가져왔는데도 상품 목록 화면이 여전히 느립니다. 가장 유력한 원인은?

  1. get_many가 SKU를 한 번에 하나씩만 받아서
  2. _batches 관계가 지연 로딩이라, sellable_quantity에 접근할 때마다 배치 조회가 SKU별로 다시 나가서
  3. InventoryRepository가 Protocol이라 실행이 느려서
  4. quantity_per_product로 나누는 파이썬 계산 자체가 느려서

해설 페이지 2가 확인한 것입니다 — N+1은 루트 조회 (4장이 get_many로 막은 자리)뿐 아니라 관계 로딩에서도 똑같이 재발할 수 있습니다. 매핑에 로딩 전략을 명시하지 않으면 기본값이 조용히 적용됩니다.

페이지 5의 SQL에 있는 SUM(quantity - reserved)는 InventoryItem.sellable_quantity 프로퍼티와 같은 규칙을 계산합니다. 둘을 나란히 유지하는 것의 진짜 위험은?

  1. SQL의 SUM이 파이썬의 sum()보다 부정확해서
  2. 쿼리 객체가 도메인 메서드를 호출하지 않아 왕복이 늘어나서
  3. 업무 규칙(I20)이 도메인 코드와 SQL, 두 곳에 따로 존재하게 되어 나중에 한쪽만 고치고 다른 쪽을 잊을 수 있어서
  4. 쿼리 객체가 반환하는 타입이 InventoryItem과 달라서 타입 검사가 깨져서

해설 CQRS의 최소 형태에도 비용이 있습니다. 속도를 얻는 대신 업무 규칙 하나를 두 곳에서 손으로 맞춰야 합니다. 11장의 "위반"들이 그랬듯, 이것도 코드 리뷰가 메워야 하는 자리입니다.

다음 중 별도로 동기화되는 읽기 테이블(페이지 6) 또는 이벤트 소싱을 도입할 정당한 근거가 되는 것은?

  1. 화면 디자이너가 목록에 컬럼을 하나 더 보여달라고 요청했다
  2. 재고와 카탈로그가 서로 다른 서비스(다른 DB)로 분리되었다
  3. 지금 쿼리 객체의 SQL이 길고 복잡해 보인다
  4. 팀이 이벤트 소싱을 도입해 보고 싶어 한다

해설 페이지 6과 8은 같은 형태의 기준을 씁니다. "더 정교해 보인다"가 아니라 "지금 방법으로는 요구를 채울 수 없는가"를 먼저 확인합니다. 페이지 6은 테이블이 서로 다른 DB로 갈라질 때, 페이지 8은 이력이 없으면 업무가 성립하지 않을 때입니다. 그 지점에 아직 도달하지 않았다면, 더 단순한 단계(페이지 4의 표)로 충분합니다.

직접 해보기

창고팀이 "입고예정 배치가 실제로 도착하면 페이지 5의 상품 목록에 몇 초 안에 반영되어야 하는지 CS팀과 협상해 달라"고 요청했습니다(도착을 알리는 InboundArrived 같은 이벤트는 지금 코드엔 없습니다 — 있다고 가정합니다) — 12장 페이지 7이 재고 할당에 대해 "5초 안에"를 협상했던 것과 같은 방식입니다. 지금 페이지 5의 쿼리 객체를 그대로 쓴다면 이 협상이 필요할까요? 페이지 6의 동기화 테이블로 바꾼다면 무엇이 달라질까요? 3줄로 설명해 보세요.

모범답안
  • 페이지 5(쿼리 객체) 그대로라면: 협상이 필요 없습니다. 이 쿼리는 stock_batches를 매번 직접 읽으므로, (가상의) InboundArrived 이벤트가 나든 안 나든 상관없이 입고 트랜잭션의 커밋을 마치는 순간부터 다음 조회는 항상 최신 값을 봅니다. "지연"이라는 개념 자체가 없습니다 — 읽기와 쓰기가 같은 진실(같은 테이블)을 보기 때문입니다.
  • 페이지 6(동기화 테이블)으로 바꾸면: 협상이 반드시 필요해집니다. (가상의) InboundArrived 이벤트가 발행된 시점과 프로젝터가 그 값을 product_listing_view에 반영하는 시점 사이에 지연 창이 생기기 때문입니다 — 12장이 재고 할당에 대해 했던 것과 똑같은 종류의 협상을, 이번엔 "화면에 보이는 숫자"에 대해 다시 해야 합니다.
  • 결론: 페이지 6에서 동기화 테이블에 비용이 든다고 한 것이 바로 이 비용입니다 — 빠른 읽기를 얻는 대신, 이전에는 없던 결과적 일관성 협상 하나를 새로 만들어 냅니다. 이 협상 자체가 필요 없는 페이지 5가, 그 협상 비용을 감수할 이유가 생기기 전까지는 더 나은 선택인 이유이기도 합니다.

Bounded Context
하나의 모델은 어디까지 유효한가

8장 마지막 화면이 남긴 문제입니다 — 지민·도현·은수가 "출고"라는 낱말을 OrderStatus의 세 값으로 정확히 맞춰봤는데도, 그렇다고 세 사람이 같은 것에 관심을 갖게 되지는 않았습니다. 도현은 여전히 실물을, 은수는 여전히 판매 가능 여부를 봅니다. 그리고 3장 화면 13은 InventoryItem 하나가 세 팀의 관심사를 프로퍼티 세 개로 봉합하고 있다고 짚어 뒀습니다. 이 장은 용어를 더 맞추는 대신, 모델 자체를 쪼갭니다.

  • 화면 2~4 · 문제. 요구사항 두 개가 "상품 1개 = SKU 1개" 가정을 깨고, 억지로 구겨 넣어 봅니다. 그리고 이게 낯선 병이 아니라는 것도 확인합니다.

미리 말해 둘 것이 하나 있습니다. 이 장을 다 읽고 나면 Order와 InventoryItem의 코드는 거의 그대로일 것입니다. 3~7장에서 "애그리게이트는 ID로만 참조한다", "카탈로그 값은 스냅샷으로 복사한다"는 규칙을 지켜 온 대가가 바로 이 장에서 나옵니다 — 가정이 깨져도 규칙을 지킨 코드는 거의 손댈 필요가 없습니다. 반대로 손대야 하는 곳은 애초에 그 규칙이 없던 자리, Product입니다.

억지로 욱여넣기

지금 코드를 최대한 안 건드리고 풀 수 있을까요? OrderLine.sku를 콤마로 묶은 문자열로 만들어 보는 사람이 꼭 나옵니다. 왜 안 되는지 직접 겪어야 다음 화면의 해법이 설득력을 갖습니다.

# 이렇게 하면 안 된다 — 문자열로 여러 SKU를 욱여넣기class OrderItemInput:
    sku: str          # "SET-JEONGSEONG-3"? 아니면 "SHAMPOO,RINSE,BODYWASH"?
    quantity: int

세 가지가 한꺼번에 무너집니다

  • 재고 코드가 카탈로그 규칙을 알아야 합니다. InventoryRepository.get_many(skus)가 "SET-JEONGSEONG-3"이라는 문자열을 받으면, 이걸 세 개의 진짜 SKU로 풀어내는 로직이 재고 컨텍스트 어딘가에 있어야 합니다. 재고팀 코드가 "이 세트는 무엇으로 구성되는가"라는 카탈로그의 지식을 떠안게 됩니다.
  • 낱개/박스는 반대로 안 풀립니다. "SHAMPOO,RINSE,BODYWASH"처럼 여러 SKU를 한 문자열에 담는 방식은애초에 "SKU 하나를 배수로 파는" 경우(신라면 낱개/박스)에는 맞지도 않습니다. 한 방향의 임시방편이 반대 방향은 아예 처리하지 못합니다.
  • 어디에도 진짜 이름이 없습니다. "SET-JEONGSEONG-3"이 무엇인지는 이 문자열을 만든 사람의 머릿속에만 있습니다. 8장이 가르친 것과 정반대입니다 — 이름이 개념을 가리키지 못합니다.

문제는 코드 몇 줄이 아니라 모델입니다. "상품"과 "SKU"는 애초에 같은 것을 가리킨 적이 없었는데, 지금까지는 우연히 숫자가 같아서 하나로 써도 티가 안 났을 뿐입니다.

9장 · 화면 5

이름 붙이기 — 바운디드 컨텍스트

바운디드 컨텍스트(Bounded Context)는 하나의 모델과 그 모델이 쓰는 낱말들이 유효한 범위입니다. "유효하다"는 것은 그 안에서는 낱말 하나가 정확히 하나의 뜻만 가진다는 뜻입니다 — 8장의 유비쿼터스 언어는 사실 컨텍스트 하나 안에서만 성립하는 약속이었습니다. "출고"가 세 가지 뜻으로 갈라진 것도, 실은 지민·도현·은수가 서로 다른 컨텍스트에서 일하고 있었기 때문입니다.

경계 안에서 정확한 것과, 경계를 나누는 것은 다른 일이다

8장까지는 "출고"라는 한 낱말이 가리키는 세 시점을 한 애그리게이트 (Order) 안에서 정확히 구분했습니다 — 이건 경계를 나눈 게 아니라 한 모델 안에서 이름을 정리한 것입니다. 이 장에서 하는 일은 다릅니다 — 애초에 서로 다른 모델이어야 했던 것을 서로 다른 클래스로, 서로 다른 모듈로 갈라놓는 것입니다.

기준은 간단합니다 — 이 개념의 규칙이 바뀌는 이유가 다른가? 카탈로그의 "상품"은 마케팅이 판매 전략을 바꿀 때 규칙이 바뀝니다("세트로 묶어 팔자"). 재고의 "SKU"는 창고 운영 방식이 바뀔 때 규칙이 바뀝니다("유통기한 관리 대상을 늘리자"). 바뀌는 이유가 다르면, 바뀌는 시점도 다르고, 결국 같은 클래스에 있으면 안 됩니다 — 한쪽 변경이 다른 쪽 코드를 건드리기 시작하기 때문입니다.

중요: 컨텍스트는 지금 셋으로 "새로 생기는" 게 아니다

00-기획 단계에서 이미 일곱 개 컨텍스트(카탈로그·주문·재고·창고·배송·결제·회원)를 정해 뒀습니다. 1~8장은 그중 주문과 재고에만 집중했고, 나머지는 존재는 했지만 코드로 드러나지 않았을 뿐입니다. 이 장이 하는 일은 컨텍스트를 발명하는 것이 아니라, Product 하나에 숨어 있던 카탈로그·재고·창고 세 컨텍스트의 경계를 코드로 드러내는 것입니다.

9장 · 화면 6

카탈로그 쪼개기 — Product를 셋으로

지금까지 Product는 온전한 클래스로 코드에 등장한 적이 없습니다 (2장 화면 11에서 "엔티티다"라고만 판정했습니다). 정확히 그게 신호였습니다 — 모두가 안다고 생각했지만 아무도 제대로 정의한 적이 없는 클래스는 여러 컨텍스트의 관심사가 뒤섞여 있을 가능성이 높습니다. 이제 세 개로 나눠 정식으로 정의합니다.

# catalog/product.py — 카탈로그 컨텍스트: "무엇을 파는가"class Product:                              # 애그리게이트 루트
    product_id: UUID
    name: str
    price: Money                            # I16: 판매가 ≥ 0
    status: SaleStatus                      # 판매중 / 판매중지 (I17)
    composition: tuple["ProductSku", ...]   # 이 상품이 어떤 SKU로 구성되는가

@dataclass(frozen=True)
class ProductSku:
    sku: str
    quantity_per_product: int    # 이 상품 1개를 팔 때 이 SKU가 몇 개 빠지는가

# inventory/sku.py — 재고 컨텍스트: "몇 개 팔 수 있는가"class Sku:                       # 재고 컨텍스트가 아는 "품목". 판매가를 모른다
    sku: str
    name: str                    # 재고 담당자가 쓰는 이름. 상품명과 다를 수 있다
    manages_expiry: bool
# InventoryItem, StockBatch, Allocation은 체크포인트 1과 완전히 같다.

# warehouse/stored_item.py — 창고 컨텍스트: "어느 랙에 있는가"@dataclass(frozen=True)
class Location:
    code: str            # "A동-03-B-12"

class StoredItem:
    sku: str
    location: Location
    quantity: int         # 이 로케이션에 실사로 확인된 수량

이제 두 요구사항이 어떻게 풀리는지 보이나요?

요구사항composition
정성 3종 세트 [ProductSku("shampoo-01", 1), ProductSku("rinse-01", 1), ProductSku("bodywash-01", 1)] — 서로 다른 SKU 셋, 배수는 모두 1.
신라면 낱개 [ProductSku("ramen-shin", 1)]
신라면 1박스(30입) [ProductSku("ramen-shin", 30)] — 같은 SKU, 배수만 30.

방향이 정반대인 두 요구사항이 한 구조로 풀렸다

화면 2의 표에서 "1:3"과 "2:1"은 서로 반대 방향처럼 보였습니다. 그런데 composition은 "이 상품을 만드는 데 어떤 SKU가 몇 개씩 필요한가"라는 한 가지 질문일 뿐이고, 그 답이 세트에서는 여러 줄, 낱개/박스에서는 같은 SKU의 배수만 다른 한 줄로 나올 뿐입니다. 모델을 제대로 잡으면 "방향이 다른 요구사항"이 사실 같은 구조의 다른 사례였다는 것이 드러납니다.

9장 · 화면 7

컨텍스트를 잇는 통로 — CatalogPort

5장이 만든 CatalogPort.snapshot()을 기억하나요? 그때는 구현을 보여주지 않았습니다. 지금이 그 구현을 볼 차례입니다.

class SqlCatalogPort:
    def snapshot(self, items):
        rows = self._query_products([i.sku for i in items])
        return [
            OrderItemSnapshot(
                sku=row.id,                      # Product.id를 SKU로 그대로 씀
                product_name=row.name,
                unit_price=Money.won(row.price),
                quantity=Quantity(item.quantity))
            for item, row in zip(items, rows)
        ]

class SqlCatalogPort:
    def snapshot(self, items):
        result = []
        for item in items:
            product = self._load_product(item.sku)   # item.sku = product_id
            for comp in product.composition:
                result.append(OrderItemSnapshot(
                    sku=comp.sku,                      # 진짜 재고 SKU
                    product_name=product.name,
                    unit_price=product.price,
                    quantity=Quantity(
                        item.quantity * comp.quantity_per_product)))
        return result

세 곳이 바뀝니다. ① item.sku의 뜻이 바뀝니다 — 1~8장에서는 진짜 SKU였는데, 9장부터는 "고객이 장바구니에 담은 카탈로그 항목의 식별자"(=product_id)입니다. 단일 SKU 상품이라면 지금까지와 똑같이 SKU와 값이 같아 보이지만, 세트 상품이라면 다릅니다. ② 결과가 items와 1:1이 아닐 수 있습니다 — 세트 하나가 SKU 셋으로 펼쳐집니다. ③ 수량 계산에 quantity_per_product가 곱해집니다.

OrderItemInput.sku라는 이름은 바꾸지 않는다

5장에서 정한 필드 이름을 그대로 둡니다(정본을 고치지 않는 한 시그니처는 유지합니다 — 집필 절차 §1.2). 대신 그 문자열에 담기는 값의 뜻이 조용히 넓어졌습니다. 이것도 하나의 교훈입니다 — 문자열 타입 필드는 이름이 바뀌지 않아도 의미가 바뀔 수 있고, 그 변화는 타입 검사로 걸리지 않습니다. 2장이 원시값 집착을 경고했던 이유가 여기서도 나타납니다.

그럼 place_order()·allocate_stock()· InventoryRepository.get_many()는 어떻게 바뀔까요?

한 줄도 안 바뀐다

세 곳 다 OrderItemSnapshot.sku나 OrderLine.sku를 이미 있는 그대로의 문자열로만 다뤘습니다 — "이 값이 Product.id와 같다"는 가정을 코드로 심어 둔 곳은 어디에도 없었습니다(4장 화면 11의 표, 5장 화면 11의 표가 그 가정을 주석으로만 남겨 뒀던 이유가 이겁니다). 3장이 정한 "ID로만 참조"와 6장의 스냅샷 규칙을 지킨 대가가 이것입니다 — 가정이 깨져도 그 가정에 기대지 않은 코드는 흔들리지 않습니다. InventoryItem.sku도 마찬가지입니다 — 이 필드는 언제나 그냥 str이었을 뿐, Product를 참조한 적이 없습니다. 이제 이 값에 들어오는 문자열이 Product.id가 아니라 Sku.sku가 됐다는 것만 달라집니다.

9장 · 화면 8

재고 컨텍스트는 그대로 둔다

이제 3장 화면 13이 남긴 빚을 갚을 차례입니다. 그 화면은 이렇게 약속했습니다 — "지금은 프로퍼티 세 개로 봉합했다. 9장에서 이 봉합을 뜯고 창고 컨텍스트와 재고 컨텍스트로 나눈다." 그 화면의 코드를 다시 가져오겠습니다.

# domain/inventory.py — 3장 화면 13, 그대로    @property
    def on_hand_quantity(self) -> int:      # 실물재고
        return sum(b.quantity for b in self._batches
                   if b.kind is BatchKind.창고)

    @property
    def available_quantity(self) -> int:    # 가용재고 (I7)
        return sum(b.available for b in self._batches
                   if b.kind is BatchKind.창고)

    @property
    def sellable_quantity(self) -> int:     # 판매가능수량 (I20)
        return sum(b.available for b in self._batches)

봉합을 뜯어 보겠습니다 — 실제로 뜯어 보면, 뜯을 것이 없습니다. 3장 화면 13의 표를 다시 보세요.

낱말누가 쓰나왜 재고 컨텍스트 안에 있어도 되는가
실물재고 창고팀(도현), 재고 실사 _batches의 quantity 합입니다. 실사와 비교하는 기준값은 재고 컨텍스트가 쥐고 있어야 실사 차이를 계산할 수 있습니다.
가용재고 피킹 담당, 긴급 출고 판단 예약(reserved)은 재고 컨텍스트만 아는 장부입니다. 피킹 담당은 이 숫자를 물어보는 것이지, 자기 컨텍스트에 이 계산을 옮겨 와야 할 이유가 없습니다.
판매가능수량(ATP) 주문팀(은수) 가용재고 + 입고예정. 역시 재고 컨텍스트의 장부 두 가지를 더한 값입니다.

"누가 쓰는가"와 "누가 계산하는가"는 다른 질문이다

세 프로퍼티는 전부 같은 재료(배치의 quantity와 reserved)에서 나옵니다. 쓰는 사람이 창고 쪽(도현, 피킹 담당)이든 주문 쪽(은수)이든, 계산 자체의 주인은 하나여야 값이 어긋나지 않습니다. 화면 5가 세운 기준("규칙이 바뀌는 이유가 다른가")으로 다시 확인해도 같은 결론입니다 — 세 계산은 전부 "예약을 어떻게 셀 것인가"라는 재고팀의 규칙이 바뀔 때 함께 바뀝니다. 창고 운영 방식이 바뀐다고 이 계산식이 바뀌지는 않습니다.

그러면 3장 화면 13은 틀린 예고를 한 걸까요? 방향은 맞았는데 무엇을 뜯어야 하는지를 그 시점에는 정확히 몰랐던 것에 가깝습니다. 다음 화면에서 실제로 없던 것이 무엇인지 봅니다.

9장 · 화면 9

창고 컨텍스트를 새로 만든다

도현이 실제로 하는 일을 떠올려 보세요 — 피킹 지시서를 들고 어느 랙으로 가야 하는지를 압니다. on_hand_quantity는 이 질문에 답하지 못합니다. 그건 "전체 창고에 몇 개가 있는가"라는 합계일 뿐, "그중 몇 개가 A동-03-B-12에 있는가"는 처음부터 InventoryItem이 가진 적 없는 정보입니다. 8장 화면 7의 warn 상자가 "용어를 맞춰도 관심사 자체는 다르다"고 한 것이 정확히 이 지점입니다 — 도현에게 진짜 필요했던 데이터가 애초에 코드 어디에도 없었습니다.

화면 6에서 이미 정의한 StoredItem이 그 데이터입니다.

# warehouse/stored_item.py — 다시class StoredItem:
    sku: str
    location: Location
    quantity: int         # 이 로케이션에 실사로 확인된 수량

StoredItem.quantity는 on_hand_quantity에서 잘라 온 값이 아니다

둘은 서로 다른 방법으로 구해지는, 서로 다른 숫자입니다. on_hand_quantity는 재고 컨텍스트가 입고 처리(receive()· arrive())를 반영해 계산하는 장부상의 합입니다. StoredItem.quantity는 창고팀이 실사로 직접 세어 확인한 로케이션별 실물입니다. 정상적인 상황이라면 모든 로케이션의 StoredItem.quantity를 더한 값이 그 SKU의 on_hand_quantity와 같아야 하지만, 코드가 그 일치를 강제하지 않습니다. 도난·파손·전산 누락이 생기면 어긋나고, 그 어긋남을 맞추는 것 자체가 실사(재고 조정)의 일입니다 — 두 컨텍스트가 항상 정확히 같은 숫자를 보장하지 않는다는 것을 결과적 일관성이라고 부릅니다 (12장에서 더 다룹니다).

"출고" 다시 보기

8장이 세 사람의 "출고"를 OrderStatus의 세 값으로 정리했을 때, 그건 주문 컨텍스트 안의 시점 구분이었습니다. 그런데 도현이 실제로 처리하는 "출고 작업"은 어느 StoredItem에서 몇 개를 꺼내 피킹했는지를 다루는, 창고 컨텍스트만의 별도 절차입니다. Order.status가 출고됨으로 바뀌는 것과, 창고에서 실제로 특정 로케이션의 StoredItem.quantity가 줄어드는 것은 같은 사건의 두 표현이지 하나가 다른 하나의 원인은 아닙니다. 용어를 맞추고 나서도 남았던 9장에서 다시 볼 문제가 바로 이것이었습니다 — 도현과 은수는 낱말을 맞춘 뒤에도 서로 다른 컨텍스트에서, 서로 다른 이유로 바뀌는 서로 다른 모델을 보고 있었고, 이제 그 모델이 코드로 각각 존재합니다.

9장 · 화면 10

경계 긋는 기준

지금까지 나온 판단을 기준 세 개로 정리합니다.

경계를 나눌 때 던지는 세 가지 질문

  1. 이 개념이 바뀌는 이유가 다른가? (화면 5) 마케팅 전략 때문에 바뀌는 것과 창고 운영 때문에 바뀌는 것은 다른 컨텍스트에 둡니다.
  2. 같은 낱말인데 정의가 다른가? (화면 4) "상품", "재고", "주소", "출고" — 같은 말을 서로 다른 팀이 서로 다른 뜻으로 쓰고 있다면 후보입니다. 다만 정의가 다르다고 항상 나눠야 하는 건 아닙니다 (8장처럼 한 애그리게이트 안에서 이름만 정리해도 되는 경우와 구분해야 합니다 — 화면 5의 note 상자).
  3. 누가 이 규칙을 책임지는가? 3장 화면 6이 애그리게이트 경계에 썼던 질문("규칙의 주인이 누구인가")을 컨텍스트 단위로 다시 던집니다. SKU 구성을 결정하는 것은 재고팀이 아니라 상품 기획입니다.

Bounded Context ≠ 마이크로서비스

가장 흔한 오해입니다 — "컨텍스트를 나눴으니 서비스도 따로 배포해야 한다"는 결론은 따라오지 않습니다. 지금 만든 catalog/· inventory/·warehouse/는 같은 프로세스, 같은 배포 단위 안의 세 폴더일 뿐입니다. 마이크로서비스로 쪼갤지는 완전히 다른 결정이고(팀 규모, 배포 주기, 장애 격리 요구), 컨텍스트 경계가 분명하면 그 결정을 나중에 내려도 코드 구조를 크게 갈아엎지 않고 옮길 수 있습니다. 반대로 컨텍스트 경계 없이 마이크로서비스부터 여러 개 두면, 서비스 사이에서도 지금 봤던 "상품 1개 = SKU 1개" 같은 암묵적 가정이 네트워크 너머로 새어 나가 더 고치기 어렵습니다.

이 경계는 파이썬이 강제하지 않는다

catalog/·inventory/·warehouse/라는 폴더 구분은 관례입니다. inventory/ 코드가 from catalog.product import Product를 그대로 써도 파이썬은 막지 않습니다. 지금 규모에서는 폴더 구조와 코드 리뷰로 충분하다고 보지만, 팀이 커지면 import-linter 같은 도구를 CI에 넣어 "이 방향의 참조는 안 된다"는 규칙을 빌드 실패로 강제하기도 합니다. C++의 네임스페이스·링크 경계처럼 컴파일러가 지켜 주는 것과는 다르다는 점을 기억해 두세요.

9장 · 화면 11

경계를 잇는 법

나누는 기준을 세웠으니, 이제 나눈 뒤 다시 잇는 규칙이 필요합니다. 사실 이 규칙은 새로 만들 필요가 없습니다 — 3장이 애그리게이트 사이에 세운 두 규칙이 컨텍스트 사이에도 그대로 적용됩니다.

3장의 애그리게이트 규칙9장의 컨텍스트 규칙
다른 애그리게이트는 ID로만 참조한다(화면 7) 다른 컨텍스트는 SKU 문자열 같은 식별자로만 참조한다. InventoryItem은 Product를 몰라도 됩니다.
필요한 값은 스냅샷으로 복사한다(I6, 6장) 컨텍스트를 넘는 값도 복사해서 가져온다. CatalogPort.snapshot()이 상품명·단가를 복사해 오는 것과 같은 방법입니다.

무엇을 스냅샷할지 결정하는 기준도 6장과 같습니다 — "과거의 사실인가, 지금의 상태인가?" 주문 라인의 product_name· unit_price는 과거의 사실이라 스냅샷입니다. 반대로 InventoryItem이 재고를 확인할 때 쓰는 Sku.manages_expiry는 매번 다시 물어봐도 되는 지금의 상태라 스냅샷하지 않고 그때그때 조회합니다.

10장 예고

지금은 카탈로그 → 재고 방향의 통합(CatalogPort)만 봤습니다. 실제로는 컨텍스트 사이의 관계가 항상 이렇게 대등하지 않습니다 — 결제 컨텍스트(외부 PG사)처럼 우리가 상대의 모델을 바꿀 수 없는 경우도 있고, 이때는 이번 장과 다른 패턴(부패 방지 계층)이 필요합니다. 컨텍스트 사이의 이런 관계의 종류를 지도로 그리는 것이 10장 Context Map의 주제입니다.

9장 · 화면 12

한계와 반대의견

1. 경계를 잘못 그으면 신호가 보인다

3장 화면 14가 이 신호를 미리 알려 줬습니다 — "다른 컨텍스트의 정책이 바뀌었는데 내 코드를 고쳐야 한다"면 경계가 잘못된 것입니다. 배송 리드타임을 예로 들어 이미 이 원칙을 지켰습니다 — ShippingPolicy.lead_time을 재고·주문 코드에 상수로 박지 않고 밖에서 주입받게 했습니다. 만약 그때 timedelta(days=2)를 InventoryItem 안에 박아 뒀다면, 배송 컨텍스트가 택배사를 바꿀 때마다 재고 코드를 고쳐야 했을 것이고, 그게 바로 경계를 잘못 그은 신호였을 겁니다. 이번 장의 StoredItem도 같은 시험을 통과해야 합니다 — 창고가 랙 배치를 바꿔도 재고 컨텍스트의 코드는 한 줄도 안 바뀝니다.

2. 경계는 한 번에 완벽하게 그어지지 않는다

3장 화면 13은 "여기서 뜯는다"고 예고했지만, 실제로 뜯어 보니(화면 8) 뜯을 것은 예고했던 것과 달랐습니다. 이건 실패가 아니라 정상입니다. 코드를 실제로 나눠 보기 전에는 어디가 진짜 이음매인지 알기 어렵습니다. 처음 그은 경계가 며칠 안에 다시 움직이는 것은 흔한 일이고, 화면 10의 세 질문으로 다시 확인하는 습관이 그은 경계보다 중요합니다.

3. 작은 프로젝트에는 과하다

상품 종류가 몇 개 안 되고 창고도 하나뿐인 쇼핑몰이라면, 오늘 만든 세 폴더는 불필요한 간접 참조가 됩니다. Product 하나에 sku 필드를 그냥 두는 편이 코드를 읽기에도, 유지하기에도 쉽습니다. 컨텍스트를 나누는 비용(폴더·포트·스냅샷 코드)은 여러 팀이 같은 낱말을 다른 뜻으로 쓰기 시작할 때부터 이익으로 바뀝니다. 14장에서 "이 판단을 언제 내리는가"를 더 다룹니다.

9장 · 화면 13

9장 마무리

핵심 요약

  1. 바운디드 컨텍스트는 하나의 모델과 낱말이 유효한 범위입니다. "출고"·"재고"·"상품"이 여러 뜻으로 갈라진 것은 용어 문제가 아니라, 서로 다른 이유로 바뀌는 서로 다른 모델이 한 클래스에 뭉쳐 있었기 때문입니다.
  2. "상품 1개 = SKU 1개" 가정이 깨지자 Product는 카탈로그의 Product/재고의 Sku/창고의 StoredItem 셋으로 나뉘었습니다. 방향이 반대로 보였던 두 요구사항(세트 상품, 낱개·박스)이 composition 구조 하나로 풀렸습니다.
  3. InventoryItem은 바뀌지 않았습니다. 실물재고·가용재고· 판매가능수량은 전부 재고 컨텍스트 한 곳의 장부에서 나오는 값이라 나눌 이유가 없었습니다. 정말 없었던 것은 StoredItem의 로케이션 정보였습니다.
  4. 3~7장이 지킨 "ID로만 참조"·"스냅샷" 규칙 덕분에, 가정이 깨져도 Order·InventoryItem·place_order()· allocate_stock()은 거의 그대로였습니다. 바뀐 것은 그 규칙이 없던 Product 하나뿐입니다.
  5. Bounded Context는 마이크로서비스가 아닙니다. 한 배포 단위 안에 여러 컨텍스트가 있어도 되고, 폴더 경계는 파이썬이 아니라 관례(또는 import-linter 같은 도구)가 지킵니다.

3장 화면 13은 "9장에서 InventoryItem의 세 프로퍼티를 창고 컨텍스트와 재고 컨텍스트로 나눈다"고 예고했습니다. 실제로 9장이 한 일과 가장 가까운 것은?

  1. on_hand_quantity를 StoredItem으로, 나머지 둘을 InventoryItem에 남겼다
  2. 세 프로퍼티를 각각 다른 클래스 세 개로 나눠 계산하게 했다
  3. 세 프로퍼티는 그대로 두고, 대신 창고 컨텍스트에 없던 StoredItem(로케이션 정보)을 새로 만들었다
  4. InventoryItem을 완전히 삭제하고 Sku로 대체했다

해설 3장의 예고는 방향은 맞았지만 무엇을 뜯어야 하는지는 정확히 짚지 못했습니다(화면 12의 반대의견 2). 실제로 확인해 보니 진짜 빠져 있던 것은 계산식의 소유권이 아니라 창고가 필요로 하는, 이전에 없던 데이터였습니다.

CatalogPort.snapshot()의 구현이 바뀌었는데도 place_order()·allocate_stock()은 한 줄도 바뀌지 않은 이유로 가장 정확한 것은?

  1. 두 함수가 마침 SKU를 안 써서 우연히 영향을 안 받았다
  2. 두 함수가 sku 값의 출처에 대해 아무 가정도 하지 않고, 스냅샷으로 받은 값을 그대로만 사용했기 때문에
  3. sku의 타입 힌트가 이번에 str로 수정됐기 때문에
  4. 도메인 이벤트의 필드 이름을 이번 장에서 다시 맞췄기 때문에

해설 화면 7의 good 상자가 이 논지입니다. "ID로만 참조"·"스냅샷"은 단순히 좋은 습관이 아니라, 나중에 가정이 깨질 때 얼마나 많은 코드를 다시 써야 하는지를 결정하는 보험이었습니다.

다음 중 "이 프로젝트에 Bounded Context를 나눠야 한다"는 근거로 가장 부적절한 것은?

  1. 카탈로그 팀과 재고 팀이 서로 다른 이유로, 서로 다른 시점에 모델을 변경한다
  2. 여러 팀이 같은 낱말을 서로 다른 뜻으로 쓰고 있어서 의사소통 오류가 반복된다
  3. 상품 구성을 결정하는 책임이 재고팀이 아니라 상품기획팀에 있다
  4. 서버를 여러 대로 나눠 배포하고 싶어서

해설 Bounded Context는 모델의 경계를 정하는 개념이고, 마이크로서비스는 배포의 경계를 정하는 결정입니다. 둘은 자주 같이 다니지만 같은 질문이 아닙니다.

직접 해보기

한빛몰이 창고를 하나 더 엽니다(서울 창고, 부산 창고). 같은 SKU가 두 창고에 나뉘어 보관될 수 있습니다. 다음 두 안 중 하나를 고르고, 화면 10의 세 가지 질문으로 근거를 대 보세요.

  1. 안 A — StoredItem에 warehouse_id 필드를 추가한다.
  2. 안 B — Location.code 문자열 안에 창고 정보를 포함시킨다(예: "SEOUL-A동-03-B-12").
모범답안

안 A가 낫습니다. 화면 10의 질문으로 확인해 보면:

  • "이 개념이 바뀌는 이유가 다른가?" — 창고가 어디에 있는지(어느 물류센터인지)와 그 창고 안 어느 랙인지는 서로 다른 결정입니다. 새 창고를 여는 것과 기존 창고 안에서 랙을 재배치하는 것은 다른 팀, 다른 시점의 일입니다.
  • "같은 낱말인데 정의가 다른가?" — 안 B처럼 문자열에 정보를 욱여넣으면, "SEOUL-A동-03-B-12"를 파싱해서 창고를 가려내는 코드가 어딘가에 반드시 생깁니다. 이건 화면 3에서 이미 겪은 실수(문자열에 여러 개념 욱여넣기)의 재발입니다.
  • "누가 이 규칙을 책임지는가?" — "어느 창고에서 출고할지 정하는 규칙"(가까운 창고 우선? 재고 있는 곳 우선?)은 랙 배치 규칙과 다른 사람이 정합니다. 필드로 분리해 둬야 이 규칙을 독립적으로 바꿀 수 있습니다.

안 B가 매력적으로 보이는 이유는 "지금 당장 코드를 안 고쳐도 되기 때문"인데, 이건 화면 3의 "억지로 욱여넣기"와 같은 함정입니다. 값 하나에 개념 두 개를 담으면 지금은 편하고 나중에 비쌉니다.

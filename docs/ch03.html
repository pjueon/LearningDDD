Aggregate
불변식을 지키는 경계

2장에서 부품을 만들었습니다. Money, Quantity, Address. 이제 조립할 차례입니다. 그런데 조립은 필드를 한 클래스에 모으는 일이 아닙니다. 규칙을 지킬 경계를 긋는 일입니다.

2장 마지막에 이런 문장을 남겼습니다 — "이 함수는 여전히 주문 밖에 있는 계산기입니다. 누군가 이 함수를 부르지 않고 총액을 직접 계산해 저장하면 규칙은 무시됩니다."

이 장은 그 문장을 없애는 장입니다. 규칙을 어길 수 없게 만듭니다. 그리고 그 규칙을 지키는 울타리에 붙은 이름이 애그리게이트(Aggregate)입니다.

이 장의 지도 — 세 덩어리로 되어 있습니다

  • 화면 2~7 · 주문 애그리게이트. Order를 만들며 불변식 I1~I5를 코드로 강제합니다. 그 과정에서 "애그리게이트 루트", "경계", "ID 참조"라는 세 가지 규칙이 나옵니다.
  • 화면 8~9 · 재고 애그리게이트. InventoryItem과 배치를 만들고 FEFO 할당을 구현합니다(I7~I10).
  • 화면 10~14 · 새 요구사항이 들어옵니다. "입고 예정인 물건도 팔게 해주세요." 이 한 문장이 방금 만든 재고 모델을 갈라놓고, 마지막에는 애그리게이트 경계 자체를 찌르는 질문이 됩니다.

이 장은 무겁습니다

16화면 · 3시간으로, 이 교재에서 가장 긴 장입니다. 화면 9까지 읽고 하루 쉬는 것을 권합니다. 화면 10부터는 새 요구사항을 받아 앞의 코드를 고치는 내용이라, 앞부분이 머리에 남아 있어야 합니다.

그리고 이 장은 DDD의 허리입니다. 4장 이후는 대부분 "여기서 만든 애그리게이트를 어떻게 저장하고, 조립하고, 잇는가"에 대한 이야기입니다.

같은 주에 일어난 세 건의 사고

1장의 place_order()가 배포된 지 반년이 지났습니다. 그동안 CS팀이 쓰는 관리자 화면, 정산 배치, 재고 보정 스크립트가 하나씩 늘었습니다. 모두 같은 테이블을 씁니다.

CS팀

주문 상세 화면에 상품이 하나도 없는 주문이 있습니다. 금액은 3,000원이고요. 배송비만 남은 것 같은데 이게 뭔가요?

정산팀

어제 주문 중 열두 건이 라인 합계와 총액이 다릅니다. 2장에서 고쳤다고 하지 않았나요?

창고팀

피킹 지시서에 취소된 주문이 올라와 있습니다. 직원이 이미 물건을 꺼냈어요.

원인을 하나씩 찾아보면 이렇습니다.

사고원인
라인 0개 주문 CS 관리자 화면의 "라인 삭제" 버튼. 마지막 한 줄까지 지울 수 있었다. 지운 뒤 총액을 다시 계산하지도 않았다.
총액 불일치 프로모션 배치가 UPDATE orders SET discount = ...만 실행했다. total_amount 컬럼은 그대로 두었다.
취소 주문 출고 취소 처리 코드가 환불 API를 먼저 부르고 status를 나중에 바꾼다. 환불은 성공했는데 그 뒤에서 실패해 상태가 결제완료로 남았다. 피킹 지시 생성 배치는 WHERE status = '결제완료'로 뽑는다.

세 사고의 공통점은 코드가 틀렸다는 것이 아닙니다. 각 코드는 자기 자리에서 자기 일을 합니다. 문제는 지켜야 할 규칙이 코드 어디에도 적혀 있지 않다는 것입니다. 규칙은 개발자의 머릿속에만 있었고, 새 코드를 쓰는 사람은 그 규칙을 몰랐습니다.

불변식(invariant)

불변식이란 "언제 확인해도 반드시 참이어야 하는 규칙"입니다. "주문이 저장될 때 참"이 아니라 언제나 참이어야 합니다.

한빛몰의 주문에는 다섯 개가 있습니다. 이 교재는 기획 단계에서 번호를 붙여 관리합니다.

번호불변식어겨지면
I1주문 라인이 최소 1개 있어야 한다 빈 주문. 사고 1번
I2총액 = Σ(라인 소계) − 할인액 + 배송비 금액 불일치. 사고 2번
I3라인 수량은 1 이상이다 0개 주문, 음수 주문
I4결제완료 이후에는 라인을 추가·삭제·수량변경할 수 없다 결제한 금액과 다른 물건이 나감
I5주문 취소는 출고 시작 전까지만 가능하다 이미 나간 물건을 "취소". 사고 3번

I3은 2장에서 이미 해결했습니다. Quantity가 1 미만을 거부하므로 수량 0인 라인은 만들 수가 없습니다. 나머지 넷은 여러 값에 걸친 규칙이라 값 객체 하나로는 지킬 수 없습니다.

규칙이 걸치는 범위가 곧 경계다

I2를 지키려면 라인 전부와 할인액과 배송비를 동시에 봐야 합니다. I1을 지키려면 라인 목록 전체를 봐야 합니다. 즉 이 넷은 "주문 하나"라는 덩어리 안에서만 확인할 수 있습니다.

이 문장을 뒤집으면 이 장의 핵심이 나옵니다. 함께 확인해야 하는 것들이 곧 하나의 덩어리이고, 그 덩어리 밖에서는 안을 건드릴 수 없어야 규칙이 지켜집니다.

Order 만들기 ① — 라인과 금액

2장에서 Order의 껍데기(식별자와 __eq__)까지는 만들었습니다. 이제 안을 채웁니다. 먼저 라인부터.

# domain/order.py — 주문 라인 (내부 엔티티)class OrderLine:
    def __init__(self, sku: str, product_name: str,
                 unit_price: Money, quantity: Quantity) -> None:
        self.line_id = uuid4()                        # 1
        self.sku = sku                                # 2
        self.product_name = product_name              # 3
        self.unit_price = unit_price                  # 3
        self.quantity = quantity

    @property
    def subtotal(self) -> Money:                      # 4
        return self.unit_price * self.quantity.value

    def __eq__(self, other: object) -> bool:          # 5
        if not isinstance(other, OrderLine):
            return NotImplemented
        return self.line_id == other.line_id

    def __hash__(self) -> int:
        return hash(self.line_id)
  1. 4행 라인에도 식별자가 있습니다. 같은 상품을 두 줄로 담을 수 있고("사은품용 1개, 내 것 2개"), 그러면 두 줄은 내용이 같아도 다른 줄입니다. 식별자가 필요하다는 것은 라인이 값 객체가 아니라 엔티티라는 뜻입니다.
  2. 5행 SKU를 문자열로 들고 있습니다. Product 객체가 아닙니다. 왜 그런지는 화면 7에서 다룹니다. 지금은 "상품 1개 = SKU 1개"라고 가정합니다. 9장에서 다시 볼 문제
  3. 6~7행 상품명과 단가를 복사해서 보관합니다(I6). 카탈로그에서 가격이 바뀌어도 과거 주문 금액은 변하지 않습니다. 1장 화면 2의 8번 요구사항이 이것이었습니다. 왜 참조가 아니라 복사인지는 6장에서 정면으로 다룹니다.
  4. 10~12행 소계를 저장하지 않고 계산합니다. 저장하면 단가나 수량이 바뀔 때 같이 안 바뀔 위험이 생깁니다. "계산할 수 있는 값은 저장하지 않는다" — 사고 2번이 바로 저장해 둔 값이 낡아서 생긴 일이었습니다.
  5. 14~17행 2장에서 배운 대로 식별자 기준 동등성입니다. 수량이 바뀌어도 같은 라인입니다.

이제 Order가 라인을 품습니다.

# domain/order.py — Order (__eq__·__hash__ 는 2장에서 만든 것 그대로)class Order:
    def __init__(self, order_number: OrderNumber, customer_id: UUID,
                 shipping_address: Address,
                 discount: Money = Money.ZERO,
                 shipping_fee: Money = Money.ZERO) -> None:
        self._order_number = order_number
        self.customer_id = customer_id                    # 1
        self.shipping_address = shipping_address
        self.status = OrderStatus.생성됨
        self._lines: list[OrderLine] = []                 # 2
        self.discount = discount
        self.shipping_fee = shipping_fee

    @property
    def lines(self) -> tuple[OrderLine, ...]:             # 3
        return tuple(self._lines)

    def add_line(self, sku: str, product_name: str,
                 unit_price: Money, quantity: Quantity) -> None:
        self._lines.append(                               # 4
            OrderLine(sku, product_name, unit_price, quantity))

    @property
    def amounts(self) -> Amounts:                         # 5
        subtotal = sum((line.subtotal for line in self._lines), Money.ZERO)
        return Amounts(subtotal=subtotal, discount=self.discount,
                       shipping_fee=self.shipping_fee)

    @property
    def total_amount(self) -> Money:                      # 6
        return self.amounts.total
  1. 7행 회원을 Customer 객체가 아니라 UUID로 들고 있습니다. 라인의 SKU와 같은 이유이고, 화면 7의 주제입니다.
  2. 10행 라인 목록을 _lines라는 밑줄 이름의 리스트로 둡니다. 밖에서 이 리스트를 직접 얻지 못하게 하려는 것입니다.
  3. 14~16행 그래서 밖에는 tuple로 복사해서 줍니다. tuple은 append가 없으므로 order.lines.append(...)가 불가능해집니다. 라인을 넣는 길은 add_line() 하나뿐입니다.
    파이썬에는 진짜 private이 없어서 order._lines.append(...)는 여전히 됩니다. 하지만 그건 일부러 규칙을 깨는 코드이고, 리뷰에서 눈에 띕니다. 실수로 깨는 것과는 다릅니다.
  4. 18~21행 OrderLine을 Order가 만듭니다. 호출자는 완성된 라인 객체를 건네지 않습니다. 이렇게 하면 라인을 만드는 규칙(예: 앞으로 추가될 "같은 SKU는 한 줄로 합친다")을 넣을 자리가 한 곳으로 정해집니다.
  5. 23~27행 2장의 calculate_amounts()에서 조립 부분만 여기로 들어왔습니다. sum()의 두 번째 인수 Money.ZERO는 시작값입니다. 파이썬 sum()의 기본 시작값은 정수 0이라 0 + Money(...)에서 터집니다. 라인이 0개일 때 Money.ZERO가 나오게 하는 역할도 합니다.
  6. 29~31행 총액은 필드가 아니라 계산값입니다. order.total_amount = 5000은 파이썬이 거부합니다(setter 없는 property라 AttributeError). I2를 어길 방법이 없어졌습니다. 사고 2번 같은 UPDATE는 4장에서 리포지토리를 만들 때 다시 막습니다.

여기서 정직하게 남겨두는 문제

discount는 생성할 때 받아서 그대로 들고 있습니다. 그런데 add_line()으로 라인을 하나 더 담으면 소계가 늘어나는데 할인액은 그대로입니다. 등급 할인이 5%였다면 이제 5%가 아닌 값이 됩니다.

I2("총액 = 소계 − 할인 + 배송비")는 여전히 참입니다. 어긋난 것은 "할인액은 소계의 5%다"라는 다른 규칙이고, 그 규칙은 회원 등급과 프로모션을 알아야 계산할 수 있습니다. 등급은 주문 밖(회원 컨텍스트)에 있습니다. 주문이 알 수 없는 것으로 만든 규칙은 주문 안에 넣을 수 없습니다.

그래서 지금은 밖에서 받은 값을 그대로 둡니다. 이 계산을 누가 언제 하는가는 6장 도메인 서비스(DiscountPolicy)의 주제입니다. 6장에서 다시 볼 문제

Order 만들기 ② — 상태가 행동을 막는다

I4와 I5는 상태에 따라 할 수 있는 일이 달라진다는 규칙입니다. 먼저 규칙을 어겼을 때 낼 예외부터 만듭니다.

# domain/errors.pyclass DomainError(Exception):
    """도메인 규칙을 어겼을 때 나는 예외의 뿌리. (2장에서 정의)"""


class OrderCannotBeModified(DomainError): ...   # I4
class EmptyOrder(DomainError): ...              # I1
class LineNotFound(DomainError): ...
class AlreadyShipped(DomainError): ...          # I5
class InsufficientStock(DomainError): ...       # 화면 9에서 쓴다

왜 ValueError를 쓰지 않는가

DomainError를 뿌리로 두면 업무 규칙 위반과 프로그램 버그를 구분할 수 있습니다. 5장에서 응용 서비스를 만들 때 except DomainError 한 줄로 "고객에게 사유를 보여줄 오류"를 잡고, 나머지는 500 오류로 내보냅니다.

이름도 업무 언어입니다. AlreadyShipped는 CS팀이 쓰는 말이고, 로그에 찍혔을 때 개발자가 아닌 사람도 무슨 일인지 압니다. ValueError("invalid status")는 그렇지 않습니다.

이제 Order에 행동을 붙입니다.

# domain/order.py — Order 안에 이어서    MODIFIABLE = (OrderStatus.생성됨, OrderStatus.결제대기)      # 1
    CANCELLABLE = (OrderStatus.생성됨, OrderStatus.결제대기,
                   OrderStatus.결제완료)

    def _ensure_modifiable(self) -> None:                     # 2
        if self.status not in self.MODIFIABLE:
            raise OrderCannotBeModified(
                f"{self.status.name} 주문은 라인을 바꿀 수 없습니다")

    def add_line(self, sku: str, product_name: str,
                 unit_price: Money, quantity: Quantity) -> None:
        self._ensure_modifiable()                             # 3
        self._lines.append(
            OrderLine(sku, product_name, unit_price, quantity))

    def change_quantity(self, line_id: UUID, quantity: Quantity) -> None:
        self._ensure_modifiable()
        self._find(line_id).quantity = quantity               # 4

    def remove_line(self, line_id: UUID) -> None:
        self._ensure_modifiable()
        if len(self._lines) == 1:                             # 5
            raise EmptyOrder("주문에는 라인이 최소 한 개 있어야 합니다")
        self._lines.remove(self._find(line_id))

    def cancel(self) -> None:
        if self.status not in self.CANCELLABLE:               # 6
            raise AlreadyShipped(
                f"{self.status.name} 주문은 취소가 아니라 반품 대상입니다")
        self.status = OrderStatus.취소됨

    def _find(self, line_id: UUID) -> OrderLine:              # 7
        for line in self._lines:
            if line.line_id == line_id:
                return line
        raise LineNotFound(str(line_id))
  1. 1~3행 "바꿀 수 있는 상태"와 "취소할 수 있는 상태"를 목록으로 적어둡니다. 상태가 하나 늘어날 때 고칠 곳이 여기 두 줄입니다. 조건문이 메서드마다 흩어져 있으면 새 상태를 넣을 때 반드시 하나를 빠뜨립니다.
  2. 5~8행 검사를 한 곳에 모읍니다. I4는 "라인을 추가·삭제·수량변경할 수 없다"는 하나의 규칙인데 메서드는 셋입니다. 규칙이 하나면 코드도 하나여야 합니다(2장 화면 14 퀴즈 3의 논지와 같습니다).
  3. 12행 세 메서드가 모두 첫 줄에서 같은 검사를 부릅니다. 이 패턴을 가드(guard)라고 부릅니다. 상태를 바꾸기 전에 먼저 막습니다.
  4. 18행 수량 변경은 Quantity를 받습니다. int가 아닙니다. 그래서 0이나 음수는 여기까지 오지도 못합니다 — 2장의 Quantity가 생성 시점에 막습니다. 이것이 I3입니다. 이 메서드에는 수량 검사 코드가 한 줄도 없는데 I3이 지켜집니다.
  5. 22~23행 I1입니다. 마지막 한 줄은 지울 수 없습니다. CS 관리자 화면이 무엇을 하든 빈 주문은 만들 수 없습니다.
    "그럼 주문 전체를 없애고 싶을 때는?" — 그건 취소라는 다른 행위입니다. 업무에서 다른 일이면 코드에서도 다른 메서드여야 합니다.
  6. 26~30행 I5입니다. 출고준비부터는 목록에 없으므로 취소가 막힙니다. 출고준비는 창고 직원이 이미 피킹을 시작한 상태이고, 1장 화면 12에서 도현이 겪은 사고("피킹까지 다 끝내고 포장하려는데 주문이 취소됐다")가 정확히 이 상태의 주문을 취소한 것이었습니다. 예외 이름과 메시지가 대안을 알려줍니다 — "이건 취소가 아니라 반품이다". 좋은 도메인 예외는 무엇이 틀렸는지만 말하지 않고 업무적으로 무엇을 해야 하는지를 말합니다.

3장 · 화면 5

이 울타리에 붙은 이름 — 애그리게이트

지금까지 한 일을 정리하면 이렇습니다.

  • Order와 OrderLine을 한 덩어리로 묶었다.
  • 그 덩어리 안의 규칙(I1·I2·I4·I5)은 덩어리 안에서 지킨다.
  • 바깥에서는 Order만 만질 수 있다. OrderLine은 밖에서 만들지도, 목록에 직접 넣지도 못한다.

이 구조에 붙은 이름이 애그리게이트(Aggregate)이고, 바깥이 유일하게 참조하는 대표 객체를 애그리게이트 루트라고 부릅니다. 여기서는 Order가 루트, OrderLine이 내부 엔티티입니다.

그래서 왜 line_id로 지시하는가

화면 4의 change_quantity(line_id, quantity)가 라인 객체가 아니라 식별자를 받는 이유가 여기 있습니다. 만약 라인 객체를 밖으로 꺼내 쓰게 하면 이렇게 됩니다.

# 만약 라인을 밖에서 직접 만질 수 있다면>>> line = order.lines[0]
>>> line.quantity = Quantity(5)      # 상태 검사(I4)를 건너뛴다
>>> order.status
<OrderStatus.결제완료: 3>            # 결제까지 끝난 주문인데 수량이 바뀌었다

규칙은 Order에 있는데 변경은 OrderLine에서 일어났습니다. 규칙을 아는 객체를 거치지 않았으므로 규칙이 적용되지 않습니다.

파이썬에서는 이걸 완전히 막을 수 없습니다

order.lines[0].quantity = ...는 여전히 실행됩니다. tuple로 감싸도 안에 든 객체 자체는 가변이기 때문입니다. 자바나 C#이라면 인터페이스로 읽기 전용 뷰를 줄 수 있지만 파이썬은 그렇지 않습니다.

그래서 파이썬에서 애그리게이트는 강제가 아니라 설계 합의에 가깝습니다. 중요한 것은 "올바른 길이 가장 편한 길"이 되게 만드는 것입니다. order.change_quantity(line_id, qty)는 한 줄이고, 규칙을 우회하려면 리스트를 뒤져 객체를 꺼내는 부자연스러운 코드를 써야 합니다. 그런 코드는 리뷰에서 눈에 띕니다.

덧붙여, 라인을 밖으로 아예 안 주는 선택도 있습니다. "화면에 뿌릴 데이터"는 4장의 리포지토리와 5장의 DTO가 따로 담당합니다.

더 깊이 — 이 이름은 어디서 왔나

애그리게이트는 에릭 에반스(Eric Evans)의 『도메인 주도 설계』(2003, 통칭 Blue Book)에 나오는 용어입니다. 원문의 정의는 대략 이렇습니다 — "데이터 변경의 목적으로 하나의 단위로 취급되는 연관 객체들의 묶음."

여기서 "데이터 변경의 목적으로"가 핵심입니다. 읽기 위한 묶음이 아닙니다. "주문 목록 화면에 회원 이름도 같이 보여줘야 하니까 Order가 Customer를 갖고 있어야겠다"는 애그리게이트를 나누는 근거가 되지 못합니다. 읽기는 13장 CQRS의 영역입니다.

번역어로 "집합체"를 쓰기도 하지만, 이 교재는 원어 그대로 애그리게이트를 씁니다. "집합"이라는 말이 set이나 "여러 개 모음"으로 읽혀 오해를 부르기 때문입니다. 실무 대화에서도 대부분 원어를 씁니다.

경계는 어디까지인가

애그리게이트가 "함께 규칙을 지키는 묶음"이라면, 자연스러운 질문이 따라옵니다. 주문과 재고도 함께 지켜야 할 규칙이 있지 않나요?

개발팀 신입

"재고보다 많이 주문할 수 없다"도 불변식 아닌가요? 그러면 Order 안에 재고를 넣어야 항상 지켜지는 것 아닌가요?

좋은 질문이고, 논리적으로 일관됩니다. 실제로 해보면 이렇게 됩니다.

대가 1 — 저장 단위가 함께 커진다

애그리게이트는 통째로 읽고 통째로 저장합니다(4장에서 자세히 봅니다). 주문 하나를 읽으려면 그 주문이 참조하는 모든 SKU의 재고와 배치를 전부 읽어야 합니다. 주문 목록 화면은 이제 주문 20건 × 라인 3개 × 배치 10개를 읽습니다.

대가 2 — 동시성 지옥

이게 진짜 문제입니다. 12장에서 자세히 다루지만, 여기서 그림만 봐 두겠습니다.

큰 애그리게이트가 만드는 것

"한 번에 바꾸는 범위"가 곧 "동시에 못 하는 범위"입니다. 애그리게이트를 크게 잡으면 일관성은 쉬워지지만 동시 처리량이 그만큼 줄어듭니다. 그리고 이 비용은 처음에는 보이지 않습니다. 트래픽이 늘어야 보이고, 그때는 이미 코드가 그 구조에 얽혀 있습니다.

그럼 재고 초과 주문은 어떻게 막나

막지 않습니다. 정확히는, "주문을 저장하는 순간"에 막지 않습니다. 주문을 받은 뒤 재고 애그리게이트가 자기 트랜잭션에서 할당을 시도하고, 모자라면 그때 실패 처리합니다. 고객에게는 "품절되어 주문이 취소되었습니다"가 나갑니다.

업무적으로 이게 이상한가요? 아닙니다. 실제 쇼핑몰이 그렇게 동작합니다. 주문 완료 메일을 받은 뒤 품절 안내를 받아본 적이 있을 겁니다. 그건 버그가 아니라 설계된 동작입니다. 이것을 결과적 일관성이라고 부르고, 12장의 주제입니다.

경계를 그을 때 던지는 세 가지 질문

  1. 이 규칙은 정말 "즉시" 지켜져야 하는가? 1초 뒤에 지켜져도 되는 규칙이라면 한 애그리게이트에 넣을 이유가 없습니다. 대부분의 규칙이 여기에 해당합니다.
  2. 규칙을 어겼을 때 업무적으로 되돌릴 수 있는가? 재고 초과 주문은 취소·환불로 되돌릴 수 있습니다(비용은 들지만 가능합니다). 되돌릴 수 없는 것만 즉시 막아야 합니다.
  3. 누가 이 규칙의 주인인가? "재고보다 많이 팔지 않는다"의 주인은 재고팀이지 주문팀이 아닙니다. 규칙은 주인의 애그리게이트에 둡니다.

세 질문을 통과하면 애그리게이트는 작아집니다. 그래서 흔히 "애그리게이트는 작게 유지하라"고 말합니다. 다만 이 규칙이 언제 틀리는지는 화면 15에서 따로 다룹니다.

애그리게이트끼리는 ID로만 참조한다

경계를 나눴으면, 그 경계를 넘는 방법도 정해야 합니다. 규칙은 한 줄입니다 — 다른 애그리게이트는 객체가 아니라 식별자로 참조한다.

class Order:
    customer: Customer          # 회원 애그리게이트 통째로
    ...

class OrderLine:
    product: Product            # 상품 애그리게이트 통째로
    quantity: Quantity

    @property
    def subtotal(self) -> Money:
        return self.product.price * self.quantity.value

class Order:
    customer_id: UUID           # 식별자만
    ...

class OrderLine:
    sku: str                    # 식별자만
    product_name: str           # 주문 시점 스냅샷 (I6)
    unit_price: Money           # 주문 시점 스냅샷 (I6)
    quantity: Quantity

    @property
    def subtotal(self) -> Money:
        return self.unit_price * self.quantity.value

왼쪽이 훨씬 자연스러워 보입니다. ORM도 이런 모양을 권합니다. 그런데 왼쪽에는 세 가지 문제가 있습니다.

문제무슨 일이 벌어지나
과거가 바뀐다 self.product.price는 지금 가격입니다. 상품 가격이 오르면 작년 주문의 총액도 같이 오릅니다. 1장 화면 2의 8번 요구사항이 정확히 이걸 금지했습니다.
경계가 새어나간다 order.customer.grade = MemberGrade.골드라고 쓸 수 있습니다. 주문 코드가 회원을 바꿉니다. 문법적으로 막을 수 없고, 이런 줄은 반드시 생깁니다.
읽는 범위가 커진다 주문 하나를 읽으면 회원과 상품이 딸려 옵니다. ORM의 지연 로딩으로 미루면 나중에 예상 못 한 곳에서 쿼리가 터집니다(N+1).

ID 참조가 주는 것

주문 애그리게이트를 테스트하는 데 회원도 상품도 필요 없습니다. uuid4()와 문자열 "SKU-001"이면 충분합니다. 데이터베이스도, 픽스처도 없이 Order의 모든 규칙을 테스트할 수 있습니다. 1장 화면 13의 통증 3번(테스트에 DB가 필요하다)이 여기서 사라집니다.

그리고 나중에 회원 서비스가 별도 프로세스로 떨어져 나가도 주문 코드는 한 줄도 바뀌지 않습니다. UUID는 프로세스 경계를 넘어도 똑같이 UUID입니다.

그럼 상품명은 어디서 오나

OrderLine은 product_name과 unit_price를 들고 있습니다. 이 값은 주문을 만들 때 카탈로그에서 한 번 복사해 옵니다. 누가 복사해 오는가는 5장(응용 서비스)과 6장(스냅샷)의 주제입니다.

두 번째 애그리게이트 — 재고

이제 경계 반대편입니다. 재고는 이 교재에서 가장 여러 번 다시 등장하는 모델입니다. 동시성(12장), 이벤트(7장), 컨텍스트 분리(9장)가 모두 여기서 출발합니다.

용어뜻
배치 한 번에 들어온 물건 묶음. 같은 생수라도 3월 5일 입고분과 3월 20일 입고분은 다른 배치입니다. 유통기한이 다르기 때문에 나눠 관리합니다.

할당 특정 주문을 위해 재고를 잡는 행위. 물건이 움직인 게 아닙니다. 숫자만 바뀝니다. 실제로 꺼내는 것은 피킹입니다.
FEFO 유통기한이 이른 것부터 내보내는 규칙. 입고 순서인 FIFO와 다릅니다. 나중에 들어온 물건의 유통기한이 더 이를 수 있습니다.

# domain/inventory.py — InventoryItem 안에    def allocate(self, quantity: int, as_of: date) -> None:
        candidates = [b for b in self._batches                       # 1
                      if b.available > 0
                      and (b.expires_on is None or b.expires_on > as_of)]
        candidates.sort(key=lambda b: b.expires_on or date.max)      # 2

        total = sum(b.available for b in candidates)
        if total < quantity:                                         # 3
            raise InsufficientStock(
                f"{self.sku}: 요청 {quantity}, 가용 {total}")

        remaining = quantity
        for batch in candidates:                                     # 4
            take = min(remaining, batch.available)
            batch.reserve(take)
            remaining -= take
            if remaining == 0:
                return

    왜 date.today()를 안 쓰는가: 함수 안에서 현재 시각을 읽으면 테스트에서 "내일이면 만료되는 배치"를 만들 수 없습니다. 시간을 밖에서 넣으면 어떤 날짜든 시험해 볼 수 있습니다. 도메인 코드는 시계를 갖지 않는다는 원칙입니다.
  2. 5행 FEFO 정렬입니다. b.expires_on or date.max는 "유통기한이 없으면 아주 먼 미래로 친다"는 뜻입니다. None은 다른 날짜와 비교할 수 없어서 sort()가 터지므로, 정렬할 수 있는 값으로 바꿔 줍니다. 결과적으로 유통기한 없는 물건은 맨 뒤로 갑니다. 상하는 것부터 내보내는 것이 업무적으로도 맞습니다.
  3. 7~10행 먼저 전체를 확인하고, 그다음에 예약합니다. 이 순서가 중요합니다. 순서를 뒤집어 배치를 돌면서 예약하다가 중간에 모자라면, 이미 예약한 것들이 남습니다. 예외가 났는데 상태는 반쯤 바뀐 상태가 되고, 이것이 불변식을 깨는 가장 흔한 방식입니다.
  4. 13~18행 앞에서부터 채웁니다. 한 배치로 모자라면 다음 배치로 넘어갑니다. 이렇게 한 주문이 여러 배치에 걸쳐 할당될 수 있습니다. 이 사실이 화면 14에서 중요해집니다.

B가 나중에 들어왔지만 유통기한이 이르므로 먼저 나갔습니다. FIFO였다면 A부터 나갔을 것이고, B는 10월 15일에 폐기됐을 것입니다. 이 한 줄의 정렬 규칙이 연간 폐기 손실을 좌우합니다. 도메인 규칙이 돈이 되는 전형적인 예입니다.

더 깊이 — 유통기한 지난 재고는 왜 가용수량에서 안 빠지나

날카로운 독자라면 눈치챘을 것입니다. allocate()는 만료 배치를 빼는데 available_quantity는 안 뺍니다. 만료된 배치가 10개 남아 있으면 가용수량은 10인데 할당은 실패합니다.

이유는 단순합니다. available_quantity는 프로퍼티라 기준일을 받을 수 없습니다. available_quantity(as_of)처럼 메서드로 바꾸면 해결되지만, 그러면 이 값을 읽는 모든 곳이 날짜를 알아야 합니다.

한빛몰은 다른 선택을 했습니다 — 창고에서 매일 아침 만료 배치를 폐기 처리해 재고에서 없애는 업무 절차가 이미 있습니다. 그래서 만료 배치는 애초에 오래 남아 있지 않습니다. allocate()의 만료 검사는 그 절차가 늦어진 하루치를 막는 안전망입니다.

1장 화면 11에서 도현이 요청한 여유 규칙(신선식품은 유통기한 3일 전, 가공식품은 1일 전부터 주문에 잡지 않는다)도 아직 allocate()에 없습니다. 여유 일수가 상품 분류마다 다른데, 분류는 재고가 아니라 카탈로그가 아는 값입니다. 재고 안에 상수로 넣으면 화면 7의 규칙이 깨지므로 밖에서 정책으로 받아야 하고, 그 방법은 6장에서 배웁니다.

여기서 얻을 것: 코드로 완벽하게 막는 것만이 답이 아닙니다. 업무 절차가 이미 막고 있는 것을 코드가 또 막으면, 코드는 복잡해지는데 얻는 것은 없습니다. "이 규칙은 누가 지키고 있나"를 먼저 묻는 것이 DDD에서 도메인 전문가와 대화해야 하는 이유입니다.

    def __init__(self, kind: BatchKind, quantity: int,
                 received_on: date | None, eta: date | None,
                 expires_on: date | None) -> None:
        if kind is BatchKind.창고:                              # 1
            if received_on is None or eta is not None:
                raise DomainError("창고 배치는 입고일만 가진다")
        else:
            if eta is None or received_on is not None:
                raise DomainError("입고예정 배치는 ETA만 가진다")

        self.kind = kind
        self.received_on = received_on
        self.eta = eta
        self.expires_on = expires_on
        self.quantity = quantity
        self.reserved = 0

    @property
    def available(self) -> int:                                # 2

    def reserve(self, count: int) -> None:

            raise InsufficientStock(
                f"배치 {self.batch_id}: 가용 {self.available}, 요청 {count}")
        self.reserved += count

            raise DomainError("이미 입고된 배치입니다")
        self.kind = BatchKind.창고
        self.received_on = received_on

I19. 할당 우선순위는 창고 배치 전체가 입고예정 배치보다 앞선다. 창고 배치끼리는 FEFO, 입고예정 배치끼리는 ETA가 이른 순.

정렬 규칙을 코드로 옮깁니다.

# domain/inventory.py — InventoryItem 안에    def _candidates(self, as_of: date) -> list[StockBatch]:

    def allocate(self, quantity: int, as_of: date) -> None:
        candidates = [b for b in self._batches
                      if b.available > 0
                      and (b.expires_on is None or b.expires_on > as_of)]
        candidates.sort(key=lambda b: b.expires_on or date.max)

        total = sum(b.available for b in candidates)
        if total < quantity:
            raise InsufficientStock(
                f"{self.sku}: 요청 {quantity}, 가용 {total}")

        remaining = quantity
        for batch in candidates:
            take = min(remaining, batch.available)
            batch.reserve(take)
            remaining -= take
            if remaining == 0:
                return

    def allocate(self, quantity: int, as_of: date) -> "Allocation":
        candidates = self._candidates(as_of)

        total = sum(b.available for b in candidates)
        if total < quantity:
            raise InsufficientStock(
                f"{self.sku}: 요청 {quantity}, 판매가능 {total}")

        lines: list[AllocationLine] = []
        ready_on = as_of
        remaining = quantity
        for batch in candidates:
            take = min(remaining, batch.available)
            batch.reserve(take)
            lines.append(AllocationLine(batch.batch_id, take))
            ready_on = max(ready_on, batch.eta or as_of)
            remaining -= take
            if remaining == 0:
                break

        return Allocation(lines=tuple(lines), ready_on=ready_on)

경계를 찌르는 질문 — 출고 예정일

요구사항 3번이 남았습니다. "고객에게 출고 예정일을 알려준다." 이게 이 장에서 가장 까다로운 부분입니다.

출고 예정일을 계산하려면 어느 배치에서 할당됐는지 알아야 합니다. 창고 3개 + 입고예정 2개로 할당됐다면, 한빛몰은 분할 출고를 하지 않으므로 입고예정분이 도착하는 날이 출고일입니다.

I21. 할당 결과에는 출고 준비 완료일이 함께 나온다. 분할 출고를 하지 않으므로 이 날짜는 할당된 배치들의 ETA 중 가장 늦은 날이다 (창고 배치는 오늘로 본다).

여기서 화면 7의 규칙과 충돌이 생깁니다.

개발팀

주문이 출고일을 알려면 어느 배치에서 할당됐는지를 알아야 합니다. 그럼 Order가 StockBatch를 참조해야 하는 것 아닌가요? 방금 "애그리게이트끼리는 ID로만"이라고 배웠는데요.

참조하면 안 됩니다. StockBatch는 재고 애그리게이트의 내부 엔티티입니다. 루트도 아닌 내부 엔티티를 밖에서 가리키는 것은 화면 5에서 금지한 바로 그것입니다. 게다가 배치는 계속 변합니다 — 입고되면 종류가 바뀌고, 다 나가면 사라집니다.

답: 엔티티가 아니라 값을 돌려준다

allocate()가 그 순간의 할당 결과를 찍은 값 객체를 반환합니다.

반대 의견 — "애그리게이트는 작게"가 틀릴 때

이 장은 계속 "작게 나눠라"고 말했습니다. 그런데 이 규칙에도 대가가 있습니다.

작게 나눈 대가

  • 즉시 일관성을 포기합니다. 재고 초과 주문이 잠깐 존재하고, 나중에 취소됩니다. CS 문의가 늘고, 사과 쿠폰 비용이 듭니다.
  • 조립 코드가 필요합니다. 응용 서비스(5장), 도메인 이벤트(7장), 보상 트랜잭션(12장)이 전부 "쪼개 놓은 것을 다시 잇는" 장치입니다. 쪼개지 않았다면 필요 없었을 코드입니다.
  • 추적이 어려워집니다. 하나의 업무 흐름이 여러 트랜잭션에 흩어지면 "지금 이 주문이 어디까지 갔나"를 알기 위해 로그를 여러 개 봐야 합니다.

그래서 다음 조건이면 크게 묶는 것이 옳습니다.

  • 동시 접근이 사실상 없다. 사내 관리 도구, 하루 수십 건짜리 업무. 큰 애그리게이트의 유일한 실질적 비용이 동시성인데, 그게 없으면 비용이 0입니다.
  • 규칙 위반을 되돌릴 수 없다. 회계 전표, 의료 처방, 정산 마감처럼 "잠깐 어긋났다가 나중에 맞추면 됨"이 허용되지 않는 도메인이 있습니다.
  • 함께 안 바뀌는 경우가 없다. 항상 같이 읽고 같이 쓰는 두 덩어리를 억지로 나누면 조립 코드만 늘고 얻는 게 없습니다. 경계를 잘못 그었다는 신호이기도 합니다.

규칙보다 먼저 오는 것

"애그리게이트는 작게"는 결론이지 근거가 아닙니다. 근거는 화면 6의 세 질문 (즉시성 / 되돌릴 수 있는가 / 규칙의 주인이 누구인가)입니다. 세 질문에 답하면 크기는 결과로 나옵니다.

면접이나 설계 리뷰에서 "왜 이렇게 나눴나요?"라는 질문에 "작게 유지하는 게 좋다고 해서"라고 답하면 안 됩니다. "이 규칙은 1초 뒤에 지켜져도 되고, 어겨도 취소로 되돌릴 수 있으며, 규칙의 주인이 재고팀이라서"가 답입니다.

3장 마무리

핵심 요약

  1. 불변식은 언제 확인해도 참이어야 하는 규칙입니다. 규칙이 걸치는 범위가 곧 애그리게이트의 경계입니다. 여러 값에 걸친 규칙은 값 객체 하나로 지킬 수 없습니다.
  2. 애그리게이트는 함께 일관성을 지키는 묶음이고, 바깥은 루트만 만집니다. 내부 엔티티는 루트가 만들고, 밖에서는 line_id·batch_id 같은 식별자로 지시합니다.
  3. 경계는 세 질문으로 긋습니다 — 이 규칙은 즉시 지켜져야 하는가, 어겼을 때 업무적으로 되돌릴 수 있는가, 규칙의 주인이 누구인가. "작게 유지하라"는 이 셋의 결론이지 근거가 아닙니다.
  4. 다른 애그리게이트는 ID로만 참조하고, 경계를 넘어 나가는 것은 값 객체여야 합니다. Allocation이 그 예입니다 — 주문은 배치를 만지지 못한 채 출고일만 받아 갑니다.
  5. 요구사항 하나가 낱말을 갈라놓습니다. "재고"는 실물재고·가용재고· 판매가능수량 셋이 되었습니다. 업무에서 다른 것이면 코드에서도 다른 이름이어야 하고, 낱말이 갈라지는 자리가 곧 컨텍스트 경계의 흔적입니다.

팀원이 "주문 목록 화면에 회원 이름을 보여줘야 하니 Order가 Customer를 참조하게 하자"고 제안합니다. 어떻게 답해야 할까요?

  1. 화면에 필요하니 참조를 추가한다. 실용이 원칙보다 중요하다
  2. 회원 이름을 Order에 스냅샷으로 복사해 둔다
  3. 읽기는 애그리게이트로 풀 문제가 아니다. 조회 전용 방법을 따로 쓴다
  4. 주문 화면에 회원 이름을 넣지 않기로 한다

해설 에반스의 정의에 "데이터 변경의 목적으로"라는 단서가 붙어 있는 이유가 이것입니다(화면 5의 접힌 상자). 애그리게이트는 쓰기 모델이고, 화면은 읽기입니다. 읽기 요구로 쓰기 모델을 바꾸면 쓰기 모델이 화면 수만큼 뚱뚱해집니다.

구체적인 수단은 세 가지가 있고, 이 교재에서 순서대로 나옵니다. (1) 응용 서비스가 두 리포지토리에서 각각 읽어 DTO로 조립한다(5장). (2) 조회 전용 쿼리 객체를 만들어 조인 한 번으로 읽는다 — 도메인 모델을 거치지 않습니다(13장 CQRS의 최소 형태). (3) 읽기 전용 테이블을 따로 유지한다(13장).

대부분의 프로젝트는 (1)이나 (2)로 충분합니다. 13장에서 (3)이 왜 대부분에게 과한지도 함께 다룹니다.

창고에 5개(유통기한 2026-12-31), 입고예정 10개(ETA 2026-09-20)가 있고, 이 중 창고 배치에 이미 2개가 예약되어 있습니다. 오늘은 2026-09-07입니다. item.allocate(6, as_of=date(2026, 9, 7))의 결과는?

  1. 입고예정 배치에서 6개. ready_on은 09-20
  2. 창고 3개 + 입고예정 3개. ready_on은 09-20
  3. 창고 5개 + 입고예정 1개. ready_on은 09-20
  4. InsufficientStock 예외. 창고 가용이 3개뿐이므로

해설 세 가지가 한꺼번에 걸린 문제입니다 — I7(가용 = 실물 − 예약), I19(창고 우선), I21(ready_on은 가장 늦은 날).

4번 선택지를 고르셨다면 가용재고와 판매가능수량을 혼동한 것입니다. 화면 13의 도현·은수 대화가 정확히 이 혼동이었고, allocate()의 실패 판정 기준은 ATP입니다.

여기서 한 걸음 더 — ready_on이 09-20이라는 사실이 업무적으로 불편하다는 것을 눈치채셨나요? 창고에 3개가 이미 있는데 고객은 13일을 기다립니다. 3개를 먼저 보내면 고객이 더 만족할 수 있습니다. 한빛몰이 분할 출고를 안 하기로 한 것은 포장·배송비가 두 배이기 때문입니다. 이 결정을 뒤집으면 I21이 바뀌고, 그 변경이 코드에 어디까지 번지는지를 12장에서 실제로 해 봅니다.

동료가 InventoryItem에 이런 메서드를 추가하자고 합니다. def allocate_for(self, order: Order) -> None — 주문을 통째로 받아 라인별로 알아서 할당하는 메서드입니다. 무엇이 문제일까요?

  1. 재고 애그리게이트가 주문 애그리게이트를 객체로 알게 된다
  2. allocate_for라는 이름이 업무 용어가 아니다
  3. 반환값이 None이라 출고 예정일을 알 수 없다
  4. 한 주문에 여러 SKU가 있어서 InventoryItem 하나로는 처리할 수 없다

해설 4번도 사실이지만, 진짜 문제는 의존 방향입니다. inventory.py가 order.py를 import 하게 되고, 주문 모델이 바뀔 때마다 재고 코드가 영향을 받습니다.

이걸 알아채는 실전 신호: 도메인 모듈의 import 문을 보세요. 한 애그리게이트 파일이 다른 애그리게이트 파일을 import 하고 있다면 경계가 새고 있는 것입니다. uuid·datetime 같은 표준 라이브러리와 공용 값 객체(Money) 외에는 들어오지 않아야 합니다. 11장에서 이 규칙을 디렉터리 구조와 자동 검사로 굳힙니다.

덧붙여 — 그럼 여러 SKU를 가진 주문 하나의 ready_on은 어떻게 구할까요? SKU마다 allocate()를 부르고, 돌려받은 ready_on 중 가장 늦은 날을 고르면 됩니다. 그 조립을 하는 곳이 응용 서비스(5장)입니다.

모범답안 — 그리고 흔한 두 가지 접근

흔한 접근 1: 수량만 받는다

def release(self, quantity: int) -> None:
    remaining = quantity
    for batch in self._batches:
        back = min(remaining, batch.reserved)
        batch.reserved -= back
        remaining -= back

동작은 합니다. 문제는 어느 배치의 예약을 푸는지 아무도 모른다는 것입니다. A 주문이 배치 1에서 3개를 잡았고 B 주문이 배치 2에서 3개를 잡았는데, A를 취소하면서 배치 2의 예약이 풀릴 수 있습니다. 합계는 맞으니 테스트도 통과합니다. 그리고 배치 2가 출고될 때 물건이 비어 있는 것을 창고에서 발견합니다.

합계가 맞는다고 상태가 맞는 것이 아닙니다. 예약은 "누가 무엇을 잡았는가"이고, 수량만으로는 그 정보가 사라집니다.

흔한 접근 2: 주문번호를 배치에 적어둔다

class StockBatch:
    reservations: dict[str, int]     # {주문번호: 수량}

정확해집니다. 그런데 재고가 주문번호를 알게 됩니다. 화면 7의 규칙(ID 참조)까지는 지켰지만, 재고 애그리게이트가 주문의 생애 주기를 신경 쓰기 시작합니다 — "취소된 주문의 예약은 언제 정리하나", "주문번호가 없는 예약(안전재고 확보)은 어떻게 표현하나". 재고의 관심사가 아닌 것이 재고 안으로 들어왔습니다.

다만 이 설계가 항상 틀린 것은 아닙니다. 12장에서 동시성을 다룰 때, "누가 무엇을 예약했는지"를 재고가 알아야 하는 요구가 실제로 생기면 그때 도입할 수 있습니다. 지금은 그 요구가 없습니다.

누가 부르는가 — 이게 진짜 문제입니다

Order.cancel() 안에서 부르고 싶어집니다. 하지만 Order는 InventoryItem을 알지 못합니다(화면 7). 알게 만들면 이 장에서 그은 경계가 무너집니다.

그리고 더 근본적으로, 취소와 예약 해제는 다른 애그리게이트의 일입니다. 한 트랜잭션에서 둘 다 바꾸면 화면 6에서 본 잠금 문제가 그대로 돌아옵니다.

정답은 "주문이 취소됐다"는 사실을 알리고, 재고가 그 사실을 듣고 스스로 해제하는 것입니다. 그 장치가 도메인 이벤트이고 7장의 주제입니다. 이 과제의 진짜 답은 "3장의 도구만으로는 깔끔하게 풀 수 없다"이고, 그 불편함이 7장을 읽을 이유가 됩니다.

참고로 Allocation을 어디에 보관해 뒀다가 취소 때 꺼내는지도 아직 정하지 않았습니다. 그건 4장(리포지토리)의 문제입니다.

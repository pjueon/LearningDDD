8장 · 화면 1

유비쿼터스 언어
코드와 대화가 같은 말을 쓸 때

7장 마지막 화면이 예고한 문제입니다 — 우리는 지난 일곱 장 동안 InventoryItem, available_quantity, sellable_quantity처럼 이름을 골라 왔지만, 그 이름을 실제로 쓰는 사람들(은수·도현·지민)이 같은 낱말로 다른 것을 가리키는 장면을 0장에서 이미 봤습니다. 이 장은 그 대화를 다시 꺼내는 것으로 시작합니다.

이 장의 지도

  • 화면 2~3 · 문제. 0장의 그 대화를 다시 펴고, 코드에도 같은 병이 있다는 것을 직접 봅니다.
  • 화면 4~5 · 이름 붙이기. 유비쿼터스 언어가 무엇이고, 용어집을 어떻게 쓰는지.
  • 화면 6~7 · 실천. 코드 리뷰에서 이름을 지적하는 법, 그리고 이벤트 스토밍으로 팀 전체가 함께 용어를 맞춰보는 법.
  • 화면 8 · 한계. 유비쿼터스 언어에도 비용이 있고, 모든 코드에 적용되는 것도 아닙니다.
  • 화면 9 · 마무리. 요약, 퀴즈, 과제.

이 장에서는 Order나 InventoryItem에 새 메서드를 붙이지 않습니다. 대신 이미 있는 이름이 얼마나 정확한지, 그리고 그 정확함이 왜 사람들에게 전달되지 않았는지를 봅니다.

8장 · 화면 2

그 대화, 다시 꺼낸다

0장에서 지민·도현·은수가 나눈 대화를 그대로 다시 옮깁니다.

지민

고객이 어제 주문한 게 아직 출고 안 됐다고 하시는데, 취소해 드려도 되나요?

도현

어제 건은 새벽에 다 출고했어요. 지금 못 막습니다.

지민

그런데 화면에는 아직 "배송 준비 중"이라고 나와요.

도현

그건 택배사가 스캔을 안 찍어서 그래요. 물건은 이미 나갔어요.

은수

잠깐만요. 개발팀에서는 결제 완료된 주문을 "출고 대상"이라고 부르던데 그건 또 다른 뜻인가요?

0장에서는 "세 사람이 같은 낱말을 세 가지 뜻으로 쓰고 있다"는 사실만 확인하고 넘어갔습니다. 이번에는 각자의 "출고"가 코드의 어느 상태와 대응하는지 정확히 짚습니다. 3장에서 이미 OrderStatus를 이렇게 정의해 뒀습니다.

코드가 이미 사람보다 정확했다

OrderStatus에는 이미 세 상태가 따로 있습니다. 결제완료·출고준비·출고됨은 서로 다른 시점이고, 3장의 cancel()은 이 중 결제완료까지만 취소를 허용합니다(I5). 문제는 코드가 부정확했던 게 아니라, 세 사람이 이 정확한 구분을 "출고"라는 한 낱말로 뭉개서 대화하고 있었다는 것입니다.

"출고 대상"이라는 표현이 특히 위험합니다 — 이것도 사실 개발팀이 붙인 이름인데(은수는 그렇게 부른다고 전해 듣고 되묻습니다), 정작 개발팀 자신의 코드에는 결제완료라는 이름만 있을 뿐 "출고 대상"이라는 이름은 어디에도 없습니다. 결제완료 상태의 주문은 전부 아직 출고준비에도 들어가지 않았는데, "출고 대상"이라는 이름은 마치 곧 출고될 것처럼 들립니다. 개발자 자신도 자기가 입으로 붙인 이름과 자기가 짠 코드가 어긋나 있었던 셈입니다. 화면 5에서 이 표현을 정리합니다.

8장 · 화면 3

코드에도 같은 병이 있다

말에서 일어나는 혼동은 코드에서도 똑같이 일어납니다. 다만 코드에서는 낱말이 아니라 식별자 이름이 그 역할을 합니다. 7장 화면 8의 allocate_stock 핸들러를 가져와, 로직은 한 글자도 바꾸지 않고 이름만 기술자 언어로 바꿔 보겠습니다.

class ProcessManager:
    def process(self, data: EventData, ctx: Context,
                policy1: Policy, policy2: Policy,
                bus: Bus) -> None:
        with ctx:
            obj: OrderData = ctx.repo1.get(Key(data.ref))
            items = ctx.repo2.get_many([k for k, _ in data.items])
            result: dict[str, Result] = {}
            flag: str | None = None

            for k, v in data.items:
                try:
                    result[k] = items[k].do(
                        v, date.today(), option=policy1.get(k))
                except CustomError:
                    flag = k
                    break

            if flag is not None:
                ctx.rollback()
                events = [Signal(occurred_at=datetime.now(),
                                  ref=data.ref, code=flag)]
            else:
                obj.result = result
                x = max(r.value for r in result.values())
                obj.update(Info(
                    a=x, b=x + policy2.value, c=datetime.now()))
                ctx.commit()
                events = obj.pull_events()

        bus.send(events)

def allocate_stock(event: OrderPlaced, uow: UnitOfWork,
                    expiry: ExpiryBufferPolicy,
                    shipping: ShippingPolicy,
                    bus: MessageBus) -> None:
    with uow:
        order = uow.orders.get(OrderNumber(event.order_number))
        items = uow.inventory.get_many(
            [sku for sku, _ in event.items])
        allocation: dict[str, Allocation] = {}
        out_of_stock: str | None = None

        for sku, qty in event.items:
            try:
                allocation[sku] = items[sku].allocate(
                    qty, date.today(),
                    buffer_days=expiry.buffer_days(sku))
            except InsufficientStock:
                out_of_stock = sku
                break

        if out_of_stock is not None:
            uow.rollback()
            events = [OutOfStock(occurred_at=datetime.now(),
                                  order_number=event.order_number,
                                  sku=out_of_stock)]
        else:
            order.allocation = allocation
            ready_on = max(a.ready_on for a in allocation.values())
            order.promise_delivery(Promise(
                ship_on=ready_on, arrive_by=ready_on + shipping.lead_time,
                promised_at=datetime.now()))
            uow.commit()
            events = order.pull_events()

    bus.publish(events)

두 코드는 줄 단위로 완전히 같은 일을 합니다. 분기 구조, 예외 처리 위치, 커밋·발행 순서까지 하나도 다르지 않습니다. OrderData· ProcessManager 같은 이름을 실제로 붙였다면 나왔을 코드가 왼쪽입니다. 바뀐 것은 오직 이름인데, 잃어버린 것은 이렇습니다.

  • EventData는 무엇이 일어났다는 신호인지 말하지 않습니다. OrderPlaced는 "주문이 접수됐다"는 사실을 이름으로 압니다.
  • items[k].do(...)의 do가 무엇을 하는지는 본문을 다 읽어야 압니다. allocate는 "재고를 잡아 둔다"는 행위를 이름이 이미 말해 줍니다.
  • CustomError는 어떤 업무적 실패인지 지웁니다. InsufficientStock은 "재고가 모자라다"는 사실 자체입니다.
  • Info(a=x, b=x + policy2.value, c=...)는 a· b·c가 무엇인지 타입 정의까지 따라가야 합니다. Promise(ship_on=..., arrive_by=..., promised_at=...)는 필드 이름 자체가 "무엇을 약속했는지"입니다.

왜 위험한가 — 컴파일러는 속지 않지만 사람은 속는다

왼쪽 코드는 완벽하게 동작합니다. 테스트도 통과하고 타입 검사도 통과합니다. 문제는 실행이 아니라 읽기에서 생깁니다. 은수에게 이 코드를 보여줘도 무슨 일을 하는지 짐작조차 할 수 없고, 6개월 뒤의 개발자 자신도 repo1이 주문인지 재고인지부터 타입을 뒤져야 합니다. 3장 화면 12가 "업무 담당자에게 읽어 줄 수 있는 코드가 유비쿼터스 언어의 목표"라고 한 말의 정반대 지점이 이것입니다.

8장 · 화면 4

이름 붙이기 — 유비쿼터스 언어

유비쿼터스 언어(Ubiquitous Language)는 업무 담당자와 개발자, 그리고 코드가 모두 같은 뜻으로 쓰는 낱말들을 말합니다. Evans의 원전(Blue Book)이 붙인 이름인데, "어디에나(ubiquitous)"라는 말이 핵심입니다 — 회의실에서 쓰는 말, 기획서에 적는 말, 코드에 쓰는 이름이 모두 같은 낱말이어야 합니다.

이 원칙은 양방향입니다.

  1. 업무 언어 → 코드. 도현이 "FEFO로 할당한다"고 말하면 코드에도 _candidates()의 정렬 기준이 그 규칙 그대로 있어야 합니다 (3장 화면 12에서 이미 했습니다).
  2. 코드 → 업무 언어. 코드를 만들다 보면 업무 담당자도 몰랐던 구분이 드러날 때가 있습니다. 3장 화면 13에서 available_quantity와 sellable_quantity를 나누기 전까지, 도현과 은수는 자신들이 "재고"라는 낱말로 서로 다른 것을 가리킨다는 사실 자체를 몰랐습니다. 코드가 먼저 정확해지고, 그 정확함이 대화로 역수출됩니다.

화면 2에서 이미 본 사례

화면 2의 표가 정확히 이 두 번째 방향입니다. OrderStatus의 세 값은 이미 정확했는데, 그 정확함이 지민·도현·은수의 대화로 옮겨지지 않았습니다. 유비쿼터스 언어를 만드는 일은 새 낱말을 발명하는 일이 아니라, 이미 코드에 있는 구분을 사람들의 말에도 옮기는 일인 경우가 많습니다.

화면 2·3이 보여준 두 가지 실패를 정리하면 이렇습니다.

실패원인이 장에서 하는 일
사람들의 대화가 부정확코드에 있는 구분을 모르고 씀 용어집 (화면 5)

8장 · 화면 5

용어집 만들기

용어집 한 줄은 세 칸이 있어야 쓸모가 있습니다 — 정의, 혼동하기 쉬운 것, 그리고 코드에서의 이름. 정의만 있으면 "그래서 코드 어디를 보면 되나요?"라는 질문에 답을 못 합니다.

낱말정의혼동하기 쉬운 것코드에서의 이름
출고 대상 (폐기) 결제가 끝나 앞으로 내보내야 할 주문 전체를 가리키던 개발팀의 구두 표현. 정작 코드에는 이 이름이 없었다 말 그대로 "출고"가 임박했다는 뜻이 아니다 — 아직 피킹도 시작 전일 수 있다 OrderStatus.결제완료를 그대로 부른다
출고시작 창고가 피킹에 착수해, 이후로는 취소 대신 반품으로만 처리되는 시점(I5) 실제로 물건이 나간 시각(도현의 "출고")과는 다르다 OrderStatus.출고준비 진입
출고 물건이 실제로 창고 문을 나서는 것 배송완료와 다르다. 택배사 스캔 지연 때문에 화면 반영이 늦을 수 있다 OrderStatus.출고됨

이 표에서 "출고 대상"은 폐기했습니다. 정의를 명확히 적는 것만큼 중요한 일이 혼동을 부르는 표현을 없애기로 합의하는 것입니다. 앞으로는 "결제완료 상태의 주문"이라고 상태 이름을 그대로 말하기로 했습니다 — 새 낱말을 만드는 대신 이미 코드에 있는 이름을 대화로 가져왔습니다.

3장 화면 13에서 만든 세 프로퍼티도 같은 방식으로 정리하면 이렇습니다 (이미 있던 용어집 항목에 코드 열만 채운 것입니다).

낱말누가 쓰나코드에서의 이름
실물재고 도현(창고팀)InventoryItem.on_hand_quantity
가용재고 피킹 담당InventoryItem.available_quantity
판매가능수량 은수(주문팀)InventoryItem.sellable_quantity

용어집은 한 번 쓰고 끝나는 문서가 아니다

용어집에 "코드에서의 이름" 칸을 넣어 두면, 코드 리뷰에서 새 이름이 나올 때마다 "이거 용어집에 있는 개념인가, 새 개념인가"를 바로 확인할 수 있습니다. 이 교재의 부록 용어집도 book.js의 TERMS가 초안이고, 장을 쓸 때마다 갱신됩니다.

8장 · 화면 6

코드 리뷰에서 이름을 지적하는 기술

7장 과제의 모범답안으로 나온 retry_allocation을, 신입 개발자가 처음 짰다면 이런 모습이었을 수 있습니다.

# 리뷰 전 — 신입 개발자의 첫 초안def handler(e, uow, p1, p2, bus):
    with uow:
        os_ = uow.orders.find_waiting_for(e.sku)
        for o in os_:
            if o.promise:
                continue
            # ... 나머지 로직

실제 코드 리뷰라면 이런 대화가 오갔을 것입니다.

리뷰어

handler라는 이름만 보면 어떤 이벤트를 처리하는지 알 수 없어요. StockReplenished를 받는다는 걸 이름에 넣어 주세요 — retry_allocation 정도가 어떨까요.

작성자

아, 그리고 os_도 그냥 orders로 바꿀게요. os가 운영체제 약자처럼 보여서 밑줄을 붙였는데, 그냥 이름이 겹치지 않게 하는 게 낫겠네요.

리뷰어

p1, p2는요? 타입을 안 보면 뭔지 전혀 모르겠어요.

작성자

expiry, shipping이었어요. 줄이려고 한 건데, 줄인 값어치보다 잃은 게 커 보이네요.

이 대화에서 리뷰어가 실제로 쓴 질문은 넷으로 정리됩니다. 코드 리뷰 중 이름이 의심스러울 때 이 질문들을 순서대로 던져 보세요.

이름을 검사하는 네 가지 질문

  1. 소리 내어 읽었을 때, 업무 담당자가 알아들을 수 있는가? (handler 탈락, retry_allocation 통과)
  2. 줄임말이 타이핑을 줄이는 것 말고 다른 이유가 있는가? (os_, p1 탈락)
  3. 이 이름이 "무엇을(what)"이 아니라 "어떻게(how)"나 "무엇으로 구현했나"를 말하고 있지 않은가? (process, handle, manage, Data, Info, Manager 같은 이름이 이 함정입니다 — 화면 3의 ProcessManager가 정확히 이 실패입니다)
  4. 이 이름과 옆에 있는 다른 함수·클래스의 이름을 서로 바꿔도 뜻이 통하는가? 통한다면 둘 다 아무 의미가 없다는 신호입니다. (화면 3의 process와 do는 서로 바꿔도 전혀 이상하지 않습니다 — 그래서 위험합니다)

넷 다 통과한 이름이 업무 담당자에게 그대로 읽어 줄 수 있는 이름입니다. 이것이 코드 리뷰가 유비쿼터스 언어를 지키는 자리이고, 린트 도구가 대신할 수 없는 부분입니다 — 문법은 맞지만 뜻이 빈 이름을 잡아내는 것은 사람만 할 수 있습니다.

8장 · 화면 7

이벤트 스토밍 아주 얕게

용어집과 코드 리뷰는 개발자가 주도하는 방법입니다. 은수·도현· 지민을 한자리에 모아 업무 흐름 전체를 함께 그리는 방법도 있습니다. 이벤트 스토밍(Event Storming)이 그것입니다 — 큰 벽에 색깔이 다른 포스트잇을 붙여, 업무에서 일어나는 일을 시간 순서로 늘어놓습니다.

  • 주황 — 도메인 이벤트. "이미 일어난 사실." 7장에서 배운 그대로 과거형으로 씁니다.
  • 파랑 — 커맨드. 누군가 하려는 행위. "주문하기"처럼 아직 성공할지 모르는 요청입니다.
  • 노랑 — 액터. 그 행위를 하는 사람이나 역할. "고객", "창고 직원."
  • 분홍 — 핫스팟. 참가자들의 말이 갈리거나, 아무도 확신하지 못하는 지점. 지금 우리가 화면 2에서 겪은 것이 바로 핫스팟입니다.

한빛몰의 주문 흐름 일부를 이 방식으로 늘어놓으면 이렇습니다.

이 중 실제로 코드에 있는 것은 둘뿐이다

7장은 "이벤트는 없으면 못 푸는 문제가 있을 때만 만든다"고 정했습니다 (7장 화면 12). 이 다섯 개 중 OrderPlaced(주문됨)와 DeliveryPromised(약속됨)만 실제 DomainEvent 클래스로 존재합니다. 결제승인됨·피킹지시생성됨·출고됨은 아직 후보입니다 — 벽에 붙일 때는 코드에 있는지 없는지 신경 쓰지 않습니다. 이벤트 스토밍은 업무 흐름 전체를 먼저 보는 것이 목적이고, 그중 무엇을 실제 이벤트로 구현할지는 7장의 판단 기준으로 나중에 가립니다.

벽 위 순서와 지금 코드는 이미 다릅니다 — 7장의 allocate_stock은 결제 확인을 기다리지 않고 OrderPlaced 직후 곧장 할당을 시작합니다(한빛몰에는 아직 결제 컨텍스트가 없습니다). 결제가 실패하면 이미 잡아 둔 재고는 어떻게 되는가 — 10장·12장에서 다시 볼 문제입니다.

포스트잇을 벽에 붙이는 이유는 그림을 남기기 위해서가 아닙니다. 같은 시간선 위에 놓았을 때 비로소 어긋남이 보이기 때문입니다. 대화만으로는 지민과 도현이 서로 다른 순간을 말하고 있다는 것을 알아채기 어렵지만, 포스트잇을 시간순으로 늘어놓으면 위치 차이가 눈에 보입니다.

용어를 맞춰도 안 풀리는 경우가 있다

화면 5에서 "출고 대상"이라는 말을 없애고 상태 이름을 그대로 쓰기로 했지만, 그렇다고 은수·도현·지민이 같은 것에 관심을 갖게 되는 것은 아닙니다. 도현은 여전히 실물을, 은수는 여전히 판매 가능 여부를 봅니다. 낱말을 통일하는 것과 관심사 자체가 다르다는 사실은 별개의 문제입니다. 9장에서 다시 볼 문제

8장 · 화면 8

한계와 반대의견

유비쿼터스 언어는 공짜가 아닙니다. 세 가지를 짚습니다.

1. 계층이 아니라 무엇을 가리키는지로 가른다

"모든 코드가 업무 용어를 써야 한다"는 말이 아닙니다. 기준은 어느 계층에 있는가가 아니라 그 이름이 무엇을 가리키는가입니다. UnitOfWork는 application/unit_of_work.py에 정의돼 있지만(5장), commit()·rollback()이라는 이름은 여전히 기술 용어입니다 — 이 이름이 가리키는 것은 "트랜잭션을 어떻게 관리하는가"라는 기술적 메커니즘이지 업무 행위가 아니기 때문입니다. 반대로 같은 application/ 아래 있는 allocate_stock·place_order는 이름 자체가 업무 행위입니다. 계층이 같아도 가리키는 대상이 다르면 이름의 언어도 다릅니다. 순수하게 기술적인 장치(트랜잭션, 메시지 발행 그 자체, DB 커넥션)까지 억지로 업무 용어를 붙이면 오히려 "이게 트랜잭션 얘기인지 주문 얘기인지" 헷갈리는 반대의 혼란이 생깁니다.

2. 합의에는 시간이 든다

은수·도현·지민을 한 시간 모으는 것 자체가 비용입니다. 조직이 크고 업무 담당자가 바쁠수록 이벤트 스토밍 같은 워크숍을 자주 열기 어렵습니다. 매 스프린트마다 이름 하나로 30분씩 토론하면, 그 자체가 새로운 종류의 낭비가 됩니다. 핫스팟을 표시해 두고 넘어가는 것도 정당한 선택입니다 — 모든 낱말을 그 자리에서 확정할 필요는 없습니다.

3. "그냥 주석을 달면 되지 않나?"

흔한 반론입니다. 하지만 주석은 코드가 바뀌어도 저절로 따라오지 않습니다. allocate()의 동작이 바뀌어도 그 위의 주석은 그대로 남을 수 있습니다. 반면 이름은 코드 자체입니다 — allocate를 reserve_or_wait로 바꾸는 리팩터링은 호출부를 다 고쳐야 하므로 낡은 이름이 조용히 남는 사고가 구조적으로 적습니다. 주석은 이름을 보완할 수는 있어도 대신할 수는 없습니다.

그리고 14장에서 다시 다루는 질문 — 모든 프로젝트가 이만큼 이름에 공들여야 하는가? CRUD에 가까운 관리자 화면 하나를 만드는 데 용어집과 이벤트 스토밍을 동원하면 오히려 과합니다. 업무 규칙이 복잡하고, 여러 팀이 같은 낱말을 다르게 쓰는 핵심 도메인에서 값어치가 가장 큽니다.

8장 · 화면 9

8장 마무리

핵심 요약

  1. 유비쿼터스 언어는 업무 담당자·개발자·코드가 모두 같은 뜻으로 쓰는 낱말입니다. 방향은 양쪽입니다 — 업무 언어가 코드로 가기도 하고(3장 FEFO), 코드의 구분이 대화로 역수출되기도 합니다(3장의 세 가지 "재고").
  2. 지민·도현·은수의 "출고"는 사실 OrderStatus의 세 값(결제완료·출고준비·출고됨)에 각각 대응했습니다. 코드는 이미 정확했지만, 그 정확함이 대화로 전달되지 않았습니다.
  3. OrderData·ProcessManager 같은 기술자 언어는 로직을 하나도 바꾸지 않고도 도메인 지식을 지웁니다. "무엇을(what)" 대신 "어떻게(how)"를 말하는 이름이 신호입니다.
  4. 용어집 한 줄에는 정의·혼동하기 쉬운 것·코드에서의 이름 세 칸이 필요합니다. 정의만으로는 코드와 연결되지 않습니다.
  5. 이벤트 스토밍은 팀 전체가 같은 시간선 위에서 업무 흐름을 보게 해, 대화만으로는 안 보이던 어긋남(핫스팟)을 드러냅니다.
  6. 유비쿼터스 언어는 이름이 업무 개념을 가리킬 때 적용되는 원칙입니다. 같은 application/ 안에 있어도 UnitOfWork.commit()처럼 기술적 메커니즘을 가리키는 이름은 기술 용어가 맞습니다. 합의에는 비용이 들고, 모든 낱말을 그 자리에서 확정할 필요는 없습니다.

화면 3에서 allocate_stock의 이름을 process로, InsufficientStock을 CustomError로 바꿔도 테스트는 그대로 통과합니다. 그런데도 이 변경이 문제인 근본적인 이유는 무엇일까요?

  1. 이름이 길어지면 실행 속도가 느려지기 때문에
  2. 타입 힌트가 사라져 타입 검사를 통과하지 못하기 때문에
  3. 실행은 똑같이 되지만, 사람이 코드를 읽고 의미를 재구성하는 비용이 커지기 때문에
  4. 예외를 어디서도 처리하지 않게 되어 프로그램이 항상 죽기 때문에

해설 화면 3의 두 코드는 동작이 완전히 같습니다. 차이는 오직 "읽는 사람이 무슨 일이 일어나는지 알 수 있는가"입니다. 이 경우에는 유비쿼터스 언어가 성능이나 정확성이 아니라 커뮤니케이션 비용의 문제입니다 — 다만 3장 화면 13처럼 이름이 모호해서 엉뚱한 프로퍼티를 잘못 부르는 사고로 이어지면 커뮤니케이션 비용이 곧 정확성 버그가 되기도 합니다.

화면 2에서 지민·도현·은수의 "출고"가 실제로 코드와 맞춰봤을 때 드러난 사실은 무엇이었나요?

  1. 코드도 세 가지 뜻을 하나의 상태 값으로 뭉쳐서 관리하고 있었다
  2. 코드는 이미 세 시점을 구분하고 있었지만, 그 구분이 대화에는 반영되지 않았다
  3. 세 사람 모두 코드와 다른 뜻으로 "출고"를 쓰고 있어서, 셋 다 틀렸다
  4. "출고 대상"이 가리키던 개념은 코드에 대응하는 것이 없어 전부 폐기해야 했다

해설 화면 4의 "코드 → 업무 언어" 방향이 바로 이것입니다. 새 개념을 코드에 만든 것이 아니라, 이미 있던 코드의 정확함을 사람의 말로 옮긴 것입니다.

UnitOfWork는 5장에서 application/unit_of_work.py에 정의됩니다 — allocate_stock·place_order와 같은 응용 계층입니다. 그런데도 commit()·rollback()은 업무 용어가 아니라 기술 용어를 씁니다. 왜 이것이 유비쿼터스 언어 원칙에 어긋나지 않을까요?

  1. 응용 계층 코드는 원래 유비쿼터스 언어의 적용 대상이 아니기 때문에
  2. 유비쿼터스 언어는 이름이 가리키는 대상이 업무 개념일 때 적용되는데, commit·rollback이 가리키는 것은 업무 행위가 아니라 기술적 메커니즘이기 때문에
  3. UnitOfWork는 인프라 계층에서만 쓰이는 이름이라서
  4. commit·rollback은 파이썬 표준 라이브러리의 예약어라 바꿀 수 없어서

해설 화면 8의 논지가 이것입니다 — 같은 파일, 같은 계층 안에서도 allocate_stock은 업무 행위를 가리키고 commit은 기술적 메커니즘을 가리킵니다. 유비쿼터스 언어가 지우려는 것은 도메인 지식이 기술 용어에 가려지는 것이지, 기술적 장치의 이름까지 업무 언어로 바꾸는 것이 아닙니다.

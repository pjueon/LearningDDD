6장 · 페이지 1

Domain Service, Factory
그리고 스냅샷

5장 페이지 11에서 남긴 문제가 있습니다 — 등급별 할인율과 배송비 계산이 OrderingService.place_order() 안에 그대로 있습니다. 업무 규칙인데 응용 계층에 있습니다. 그런데 이 규칙은 Order 안에도, MemberGrade 안에도 자연스럽게 넣을 수 없습니다. 이 장은 그 규칙이 살 세 번째 자리를 만듭니다.

그리고 Order를 만드는 코드도 다시 봅니다. 생성자를 부르고, 라인을 하나씩 추가하고, 할인과 배송비를 나중에 끼워 넣는 지금 방식은 순서를 하나라도 빠뜨리면 조용히 잘못된 주문을 만듭니다. 이걸 한 번의 호출로 바꾸는 것이 팩토리입니다.

이 장의 지도

  • 페이지 2~4 · 어디에도 안 맞는 규칙. 5장이 남긴 문제를 다시 보고, Order·MemberGrade·응용 서비스가 왜 이 규칙의 자리가 아닌지 확인한 뒤 이름을 붙입니다.
  • 페이지 5~6 · 리팩터와 판별. place_order()를 다시 조립하고, 도메인 서비스와 응용 서비스를 가르는 질문 3개를 봅니다.
  • 페이지 7~9 · 팩토리와 재구성. 생성자 직접 호출의 위험을 보고 Order.place()를 만든 뒤, 리포지토리가 왜 이 팩토리를 쓰지 않는지를 봅니다.
  • 페이지 10~12 · 스냅샷. 기획서 I6과 I22에 이름을 붙이고 마무리합니다.

6장 · 페이지 2

5장이 남긴 문제, 다시 보기

5장 페이지 11의 표를 한 줄로 요약하면 이렇습니다 — place_order() 안의 네 가지 코드 중 두 개는 업무 규칙이고 두 개는 조립 순서입니다.

# application/ordering.py — 5장 페이지 10 그대로, 문제의 두 줄            order.discount = order.amounts.subtotal.percent(
                grade.discount_rate)                              # 1
            order.shipping_fee = (Money.won(0) if grade.free_shipping
                                   else Money.won(3_000))          # 2
  1. 1~2행 등급별 할인율입니다. 은수가 "실버도 5%로 올리자"고 하면 이 두 줄이 바뀌어야 합니다. 업무 규칙입니다.
  2. 3~4행 배송비 산정입니다. "골드는 무료배송"이라는 규칙이 여기 있습니다. 역시 업무 규칙입니다.

왜 여기 있으면 안 되는가

이 두 줄을 테스트하려면 OrderingService 전체를 세워야 합니다 — 가짜 UnitOfWork, 가짜 CatalogPort, 가짜 MembershipPort까지 준비해야 "할인율 3%가 맞게 계산되는가"라는 간단한 질문에 답할 수 있습니다. 그리고 이 규칙이 필요한 곳이 생길 때마다 (예: 주문 상세 화면에서 "이 주문이 얼마나 할인됐는지" 미리 보여주기) 이 두 줄을 복사하거나, OrderingService를 통째로 다시 부르게 됩니다.

이 규칙을 어디로 옮겨야 할지, 후보를 하나씩 살펴봅니다.

6장 · 페이지 3

후보 셋을 검토한다

후보왜 안 맞는가
Order 안에 메서드로 Order는 customer_id: UUID만 알 뿐, 회원의 등급을 모릅니다(3장 페이지 7 — 애그리게이트는 ID로만 참조). 등급을 알아야 계산되는 규칙을 Order에 넣으려면 Order가 회원 애그리게이트를 통째로 참조해야 하는데, 그건 3장이 막은 바로 그 문제입니다.
MemberGrade 안에 메서드로 2장에서 MemberGrade는 discount_rate· free_shipping이라는 값을 스스로 들고 있게 만들었습니다. 그런데 "몇 %를 적용할지"가 아니라 "이 주문 전체에 얼마를 할인할지"를 계산하려면 라인 여러 개(다른 애그리게이트인 Order의 내부 상태)를 알아야 합니다. 값 객체 하나가 자기 필드만으로 답할 수 있는 범위를 넘어섭니다.
응용 서비스(OrderingService)에 그대로 지금 상태입니다. 페이지 2에서 본 문제 그대로입니다 — 재사용도 단위 테스트도 어렵고, 업무 규칙이 조립 코드와 뒤섞입니다.

공통점을 뽑아보면

이 규칙은 특정 엔티티나 값 객체 하나에 속하지 않지만, 그렇다고 트랜잭션을 열거나 다른 컨텍스트를 조율하는 일도 아닙니다. 입력(주문 라인들, 등급)과 출력(Money)이 전부 도메인 개념이고, 계산 자체는 Money.percent()처럼 상태 없이 값만 주고받으면 끝납니다.

도메인 모델에는 있는데 엔티티도 값 객체도 아닌 자리가 하나 더 필요하다는 뜻입니다.

6장 · 페이지 4

이름 붙이기 — 도메인 서비스

어느 엔티티·값 객체에도 속하지 않지만 업무 규칙인 계산을 위한 자리를 도메인 서비스(Domain Service)라고 부릅니다. 5장의 OrderingService (응용 서비스)와 이름이 비슷해 헷갈리기 쉬운데, 계층이 다릅니다.

# domain/services.pyclass ShippingFeePolicy(Protocol):
    def calculate(self, items: Sequence[OrderItemSnapshot],
                  address: Address, grade: MemberGrade) -> Money: ...    # 1


class DiscountPolicy(Protocol):
    def calculate(self, items: Sequence[OrderItemSnapshot],
                  grade: MemberGrade) -> Money: ...                      # 2


class GradeShippingFeePolicy:              # ShippingFeePolicy 구현        # 3
    FEE = Money.won(3_000)

    def calculate(self, items: Sequence[OrderItemSnapshot],
                  address: Address, grade: MemberGrade) -> Money:
        return Money.ZERO if grade.free_shipping else self.FEE


class GradeDiscountPolicy:                 # DiscountPolicy 구현           # 4
    def calculate(self, items: Sequence[OrderItemSnapshot],
                  grade: MemberGrade) -> Money:
        subtotal = sum(
            (i.unit_price * i.quantity.value for i in items), Money.ZERO)
        return subtotal.percent(grade.discount_rate)
  1. 2~3행, 7~8행 두 프로토콜 모두 인자가 Sequence[OrderItemSnapshot]인 것에 주의하십시오. Sequence[OrderLine]이 아닙니다. 이 정책은 Order.place()(페이지 8)가 호출되기 전에 값을 만들어 넘겨야 하는데, 그 시점에는 아직 OrderLine이 없습니다 — 있는 것은 5장에서 CatalogPort.snapshot()이 돌려준 스냅샷뿐입니다.
  2. 7~8행 DiscountPolicy에는 address가 없습니다. 할인율은 배송지와 무관합니다. 필요 없는 인자를 넣지 않는 것도 인터페이스 설계입니다.
  3. 11~16행 address를 받지만 지금은 쓰지 않습니다. 한빛몰은 아직 지역별 배송비가 없기 때문입니다. 그래도 인터페이스에 남겨두는 이유는, 나중에 도서산간 추가요금이 생기면 이 구현만 교체하면 되게 하기 위해서입니다 — 호출하는 쪽(응용 서비스)의 코드는 한 줄도 안 바뀝니다.
  4. 19~24행 2장 페이지 13~14에서 MemberGrade가 스스로 갖고 있던 discount_rate를, 이제 여러 라인에 걸쳐 적용하는 자리입니다. MemberGrade는 "몇 %인지"만 알고, "몇 %를 무엇에" 적용할지는 이 도메인 서비스가 압니다.

이름이 비슷한 것 — ShippingPolicy와 헷갈리지 마십시오

5장 페이지 9의 ShippingPolicy(lead_time을 갖고 있던 그것)는 포트입니다 — 배송이라는 다른 컨텍스트에 값을 묻는 창구이고, 응용 계층이 소유합니다. 반면 ShippingFeePolicy는 도메인 서비스입니다 — 주문 컨텍스트 자신의 규칙(배송비를 얼마로 매길지)이고, 도메인 계층이 소유합니다. 이름이 "Shipping"으로 시작하는 것은 우연이 아니라 둘 다 배송과 관련이 있어서인데, 묻는 대상이 다릅니다 — 하나는 배송 컨텍스트에게, 하나는 우리 자신의 업무 규칙에게.

def __init__(self, uow: UnitOfWork, catalog: CatalogPort,
             members: MembershipPort, shipping: ShippingPolicy,
             fee_policy: ShippingFeePolicy,
             discount_policy: DiscountPolicy) -> None:

    self._shipping = shipping
    self._fee_policy = fee_policy
    self._discount_policy = discount_policy

def place_order(self, cmd: PlaceOrderCommand) -> OrderNumber:

            order_number=uow.orders.next_order_number(date.today()),
            customer_id=cmd.customer_id,
            address=cmd.shipping_address,
            items=snapshots,
            shipping_fee=self._fee_policy.calculate(
                snapshots, cmd.shipping_address, grade),
            discount=self._discount_policy.calculate(snapshots, grade))

5장이 남긴 빚 — 갚았습니다

5장 페이지 11의 표: "6장 — 할인·배송비 계산이 응용 서비스 안에 있습니다. 어느 엔티티에도 넣기 애매한 이 규칙을 도메인 서비스로 뽑아냅니다." — GradeShippingFeePolicy·GradeDiscountPolicy가 그 답입니다. 3장 페이지 3이 남긴 문제("할인 계산을 누가 언제 하는가")도 같은 답으로 갚았습니다 — 누가는 도메인 서비스, 언제는 주문을 만드는 바로 그 순간(페이지 8의 Order.place() 안)입니다.

6장 · 페이지 6

도메인 서비스 vs 응용 서비스 — 판별 질문 3개

둘 다 "서비스"라는 이름이 붙어서 가장 헷갈리는 지점입니다. 질문 세 개로 가릅니다.

  1. 이 계산이 특정 엔티티나 값 객체 하나에 자연스럽게 속하는가? 아니라면(여러 개에 걸쳐 있거나 어느 것도 아니라면) 도메인 서비스 후보입니다.
  2. 입력과 출력이 전부 도메인 개념인가? Money· MemberGrade처럼 도메인 타입만 오간다면 도메인 서비스입니다. DB 세션·HTTP 요청·리포지토리처럼 인프라가 섞이면 응용 서비스입니다.
  3. 상태 없이, 같은 입력이면 항상 같은 결과를 돌려주는가? 그렇다면 도메인 서비스입니다. 트랜잭션을 열어야 하거나, 여러 애그리게이트를 순서대로 불러야 하거나, 부수 효과(저장·커밋·이벤트 발행)가 있다면 응용 서비스입니다.

헷갈리는 순간은 따로 있다

세 질문이 갈리지 않는 경우가 실제로 헷갈리는 순간입니다. 예를 들어 "재고가 있는지 확인하고 없으면 예외"는 ①(InventoryItem 하나에 속함)은 "엔티티에 속한다"고 답하지만, 그 판단이 여러 SKU에 걸쳐 있다면 다시 애매해집니다. 규칙이 하나로 안 갈리면, 지금 가장 자연스러운 자리에 두고 다음에 옮기면 됩니다. 처음부터 완벽하게 나누는 것보다, "지금은 응용 서비스에 있지만 이유는 안다"는 상태가 낫습니다.

6장 · 페이지 7

생성자를 직접 부르는 위험

페이지 5의 "5장" 탭 코드를 다시 보십시오. Order 하나를 만드는 데 세 단계를 거칩니다 — 생성자 호출, 라인 추가 반복, 할인·배송비 대입. 세 단계가 항상 이 순서로, 전부 실행돼야 유효한 주문이 됩니다.

order = Order(order_number, customer_id, address)   # 1단계: 껍데기
for s in snapshots:
    order.add_line(...)                              # 2단계: 라인
order.discount = ...
order.shipping_fee = ...                              # 3단계: 금액

이 코드를 두 번째로 쓰는 곳이 생기면

지금은 place_order()가 이 세 단계를 쓰는 유일한 곳입니다. 그런데 "관리자가 수동으로 주문을 등록하는" 기능이 생겼다고 해봅시다. 누군가 이 코드를 복사하다가 3단계를 빠뜨리면 어떻게 될까요? Order의 __init__은 discount·shipping_fee에 Money.ZERO 기본값을 주므로(3장), 에러 없이 할인 0원, 배송비 0원인 주문이 만들어집니다. 컴파일도 타입 검사도 이 실수를 잡지 못합니다 — 유효하지 않은 상태를 표현할 수 있는 API이기 때문입니다.

더 흔한 실수: 라인을 하나도 안 넣고 저장하는 것. I1("주문 라인이 최소 1개")을 어기는 주문이 지금 이 경로로는 아무 예외 없이 통과합니다. remove_line()은 I1을 지키지만(3장), Order를 처음 만드는 이 경로는 아무도 지키지 않습니다.

공통점은, 이 세 단계가 "주문을 만든다"는 하나의 개념인데 코드는 그것을 세 개의 독립된 호출로 표현하고 있다는 것입니다. 호출하는 쪽이 그 사실(세 단계가 하나라는 것)을 기억하고 있어야만 안전합니다.

6장 · 페이지 8

이름 붙이기 — 팩토리

여러 단계를 거쳐야 완성되는 객체를, 한 번의 호출로 항상 유효한 상태로만 만들어 돌려주는 자리를 팩토리(Factory)라고 부릅니다. 3장의 생성자 호출을 대체합니다.

# domain/order.py — Order 안에 이어서class Order:
    ...
    @classmethod
    def place(cls, order_number: OrderNumber, customer_id: UUID,
              address: Address, items: Sequence[OrderItemSnapshot],
              shipping_fee: Money, discount: Money) -> "Order":
        if not items:                                          # 1
            raise EmptyOrder("주문에는 라인이 최소 한 개 있어야 합니다")

        order = cls(order_number, customer_id, address,
                    discount=discount, shipping_fee=shipping_fee)  # 2
        for item in items:
            order.add_line(item.sku, item.product_name,
                           item.unit_price, item.quantity)         # 3
        return order
  1. 7~8행 I1이 마침내 생성 시점에 지켜집니다. EmptyOrder는 3장에서 이미 정의됐지만, remove_line() 한 곳만 지키고 있었습니다(페이지 7의 문제). 이제 "주문이 태어나는 단 하나의 문"에서도 지킵니다.
  2. 10~11행 __init__이 이미 갖고 있던 discount·shipping_fee 키워드 인자를 그대로 씁니다. 새 생성 경로를 만든 게 아니라, 생성자를 부르는 방법을 한 곳으로 모았을 뿐입니다.
  3. 12~14행 페이지 7의 2단계(라인 추가 반복)를 그대로 가져왔습니다. 호출하는 쪽(OrderingService)은 이제 이 반복문을 볼 필요가 없습니다.

팩토리가 주는 것

Order.place(...) 한 줄은 성공하면 항상 유효한 주문이고, 실패하면 아예 주문이 생기지 않습니다. "3단계 중 2단계까지만 실행된" 중간 상태가 코드로 표현될 방법 자체가 없어졌습니다. 페이지 5의 "6장" 탭 코드가 이미 이 팩토리를 쓰고 있었습니다.

6장 · 페이지 9

재구성(reconstitution)은 다른 문제다

질문 하나를 던져 봅니다 — 4장에서 만든 SqlAlchemyOrderRepository.get()은 왜 Order.place()를 안 쓸까요? 답을 이미 알고 있습니다. 4장 페이지 9로 돌아가 보십시오.

# infra/sqlalchemy_repository.py — 4장 페이지 9 그대로def get(self, order_number: OrderNumber) -> Order:
    order = self._session.get(Order, order_number.value)   # 1
    if order is None:
        raise OrderNotFound(order_number.value)
    return order
  1. 2행 session.get()은 Order(...)도 Order.place(...)도 부르지 않습니다. 4장 페이지 9가 "임퍼러티브 매핑"이라고 부른 방식은 __new__로 빈 객체를 만들고 컬럼 값을 속성에 직접 채워 넣습니다. 파이썬 생성자를 거치지 않습니다.

이름 붙이기 — 재구성

이미 존재하는 주문을 저장소에서 그대로 복원하는 것을 재구성이라고 부릅니다. 생성(팩토리)과 재구성은 서로 다른 일입니다. 생성은 "아직 없던 것을 규칙에 맞게 처음 만드는 것"이고, 재구성은 "이미 규칙을 통과해 저장된 것을 그대로 되살리는 것"입니다.

SQLAlchemy가 우연히 생성자를 건너뛴 게 아닙니다. 건너뛰어야만 합니다. 이유를 두 가지 들어 봅니다.

이유place()를 썼다면 벌어질 일
과거 상태를 재현해야 한다 DB에 저장된 주문은 결제완료·취소됨 같은 상태일 수 있습니다. place()는 항상 생성됨 상태의 새 주문만 만듭니다 — 상태를 강제로 되돌린 새 주문을 반환할 방법이 없습니다.
계산된 값이 아니라 확정된 값을 복원해야 한다 place()의 discount·shipping_fee는 정책이 그 순간 계산해 준 값입니다. 재구성 시점에 정책을 다시 불러 재계산하면, 할인율이 그 사이 바뀐 경우 과거 주문의 금액이 조용히 바뀌는 사고가 납니다 — 페이지 10에서 다룰 문제와 정확히 같은 유형입니다.

그래서 discount_amount는 DB 컬럼이다

4장 페이지 9의 orders 테이블에 discount_amount 컬럼이 있었습니다. 계산식이 아니라 이미 계산된 값 그 자체를 저장합니다. 재구성은 이 컬럼값을 order.discount에 그대로 옮겨 담을 뿐, DiscountPolicy를 다시 부르지 않습니다. 정책은 새 주문을 만들 때만 쓰입니다.

6장 · 페이지 10

I6 — 이 패턴에 이름을 붙인다: 스냅샷

3장 페이지 7이 "왜 Order가 Product를 참조하지 않고 product_name·unit_price를 복사하는가"에 이미 답했습니다 — 참조하면 과거 주문 금액이 상품 가격을 따라 바뀝니다. 5장 페이지 9~10이 "누가 언제 복사하는가"(CatalogPort.snapshot(), 트랜잭션을 열기 전)에 답했습니다. 이 장이 붙이는 것은 이름뿐입니다 — 이 패턴을 스냅샷이라고 부릅니다.

그리고 페이지 9에서 세 번째 스냅샷을 하나 더 찾았습니다 — order.discount와 order.shipping_fee도 스냅샷입니다. 가격만 스냅샷이 아니라, 정책이 계산해 준 결과값 전부가 스냅샷입니다.

판별 기준 — 언제 스냅샷이고 언제 참조인가

2장의 한 문장이 기준입니다 — "과거의 사실은 값 객체다." 질문은 하나입니다: "이 값이 바뀌면, 이미 확정된 과거 주문도 따라 바뀌어야 하는가?"

아니라면(가격, 할인액, 배송비 — 전부 "그 순간 그렇게 계산됐다"는 사실) 스냅샷입니다. 그렇다면(예: 회원 이름 — 3장 페이지 16 퀴즈에서 이미 확인했듯, 개명하면 주문 내역도 최신 이름으로 보여도 무방한 값) 스냅샷하지 않고 그때그때 조회합니다. 5장 페이지 9의 MembershipPort.name_of()가 그 조회 창구입니다.

값스냅샷인가근거
상품명·단가예 (I6) 가격 인상이 과거 주문에 번지면 안 됨
할인액·배송비예 정책이 바뀌어도 이미 계산된 금액은 그대로여야 함(페이지 9)
회원 이름아니오 개명해도 과거 주문에 옛 이름이 남을 이유가 없음

6장 · 페이지 11

I22 — 출고 예정일도 같은 이유로 스냅샷이다

3장 페이지 14가 이미 Promise 값 객체와 promise_delivery()를 만들었습니다 — 최초 약속은 한 번뿐이고, InventoryItem의 배치 ETA가 나중에 바뀌어도 Order.promise는 조용히 따라 바뀌지 않습니다. 페이지 10과 같은 원리인데, 이번에는 가격이 아니라 "약속"이라는 업무 개념이 하나 더 붙습니다.

가격 스냅샷과 무엇이 다른가

가격 스냅샷이 안 바뀌는 이유는 단순합니다 — 지난 계산을 건드리지 않기 위해서입니다. 약속일 스냅샷이 안 바뀌는 이유는 그보다 하나 더 있습니다 — 고객에게 이미 말을 했기 때문입니다. CS팀이 "9월 15일에 도착합니다"라고 안내한 뒤, 창고 사정으로 ETA가 밀렸다고 시스템이 말없이 그 날짜를 당겨 버리면, 정작 고객은 여전히 9월 15일을 기다립니다.

그래서 3장이 이미 답을 준비해 뒀습니다 — 재조정은 promise_delivery()를 다시 부르는 게 아니라 repromise(promise, reason)라는 다른 이름의 행위입니다. 이름이 다른 이유는, 이 행위가 반드시 고객 통지를 동반해야 하기 때문입니다. 같은 메서드를 재사용하면 통지를 빠뜨리는 경로가 생깁니다.

repromise()는 아직 만들지 않았습니다

이 메서드의 몸통은 7장에서 만듭니다 — 재고 컨텍스트가 "입고지연됨" 이벤트를 내보내고, 그 이벤트를 받은 핸들러가 영향받는 주문들을 찾아 repromise()를 부르는 흐름입니다. 지금은 왜 다른 이름이어야 하는지만 확인했습니다 — 도메인 이벤트가 아직 없어서, "누가 이 메서드를 부르는가"에 답할 수 없기 때문입니다.

정리하면: I6과 I22는 같은 원리(스냅샷)의 두 적용입니다. 차이는 I22에는 "약속을 어겼다는 사실을 조용히 지울 수 없다"는 조건이 하나 더 붙는다는 것뿐입니다.

6장 · 페이지 12

6장 마무리

핵심 요약

  1. 도메인 서비스는 특정 엔티티·값 객체 하나에 속하지 않는 업무 규칙의 자리입니다. 판별 질문은 셋 — ① 하나의 대상에 속하지 않는가, ② 입출력이 도메인 개념뿐인가, ③ 무상태이고 부수효과가 없는가. 셋 다 그렇다면 도메인 서비스, 아니라면 응용 서비스입니다.
  2. 팩토리는 여러 단계로 구성되는 객체를 한 번의 호출로 항상 유효하게 만듭니다. Order.place()가 생성자 직접 호출 + 라인 추가 반복 + 금액 대입이라는 3단계를 하나로 묶었고, 그 과정에서 3장부터 정의만 됐던 EmptyOrder(I1)를 마침내 생성 시점에 지킵니다.
  3. 재구성은 생성과 다릅니다. 이미 저장된 애그리게이트를 되살릴 때는 팩토리를 거치지 않습니다 — SQLAlchemy는 생성자조차 부르지 않고 컬럼 값을 직접 채웁니다. 과거 상태(상태값·확정된 금액)를 다시 계산하면 안 되기 때문입니다.
  4. 스냅샷은 "과거의 사실은 값으로 고정한다"는 원칙입니다. 상품명·단가(I6)뿐 아니라 정책이 계산한 할인액·배송비, 그리고 고객에게 한 약속(I22)까지 — 전부 "그 시점의 사실"이라 나중에 원인(가격, 정책, ETA)이 바뀌어도 조용히 따라 바뀌지 않습니다.

신규 요구사항 — "프로모션 기간에는 배송비를 DB에 저장된 이벤트 값으로 결정한다"가 들어왔습니다. 이 조회 로직을 어디에 둬야 할까요?

  1. ShippingFeePolicy 구현 안에 DB 세션을 주입해 직접 조회한다
  2. 조회는 응용 서비스(또는 포트)가 먼저 하고, 결과 값을 ShippingFeePolicy.calculate()의 인자로 넘긴다
  3. OrderingService 안에 if로 프로모션 규칙을 직접 구현한다
  4. Order 안에 프로모션 배송비 메서드를 추가한다

해설 도메인 서비스가 "무상태"라는 것은 "아무것도 몰라도 된다"는 뜻이 아니라, 계산에 필요한 값은 전부 인자로 받는다는 뜻입니다. 값을 어디서 구해오는지(DB, 다른 컨텍스트, 캐시)는 응용 서비스나 포트의 일이고, 도메인 서비스는 그 값으로 무엇을 계산할지만 압니다.

Order.place()의 if not items: raise EmptyOrder(...) 검사를 지우고 배포했다고 합시다. 무슨 일이 벌어질까요?

  1. add_line()이 이미 개수를 검사하므로 문제없다
  2. remove_line()의 검사가 대신 막아준다
  3. 라인이 0개인 Order가 예외 없이 만들어질 수 있다
  4. discount·shipping_fee 계산이 실패한다

해설 페이지 7에서 본 문제 그대로입니다 — EmptyOrder는 3장에서 정의는 됐지만 "주문이 태어나는 자리"를 지키고 있지 않았습니다. 팩토리가 그 자리를 만들어 준 뒤에야 비로소 I1이 생성 시점부터 지켜집니다.

SqlAlchemyOrderRepository.get()이 Order.place()를 부르지 않는 가장 근본적인 이유는 무엇일까요?

  1. place()는 새로 계산하고 새 상태로 만드는 생성 로직이라, 이미 확정된 과거 상태를 그대로 복원해야 하는 재구성과 목적이 다르다
  2. @classmethod는 ORM이 인식하지 못하는 문법이라서
  3. place()를 거치면 조회가 느려지기 때문에
  4. place()의 EmptyOrder 검사가 항상 실패하기 때문에

해설 4번 선택지가 함정인 이유 — EmptyOrder 검사 자체는 이미 라인이 있는 주문에는 걸리지 않습니다. 진짜 이유는 페이지 9의 표에 있는 두 가지, 특히 "계산된 값이 아니라 확정된 값을 복원해야 한다"는 것입니다. 이것이 이 장 전체(도메인 서비스·팩토리·스냅샷)를 잇는 하나의 줄기입니다 — "지금 계산할 것"과 "예전에 확정된 것"을 구분하는 것.

새 요구사항 — "6~8월 여름 성수기에는 등급과 무관하게 배송비를 무료로 한다." ShippingFeePolicy를 구현하는 새 클래스를 만들어 보세요.

  • "지금이 몇 월인가"를 이 클래스가 datetime.now()를 직접 불러 알아내면 무엇이 문제가 될까요? (힌트: 이 클래스를 테스트할 때 매번 실제 오늘 날짜에 의존하게 됩니다)
  • 기존 GradeShippingFeePolicy를 재사용하면서 이 규칙만 얹으려면 어떻게 구성해야 할까요?
모범답안 
class SummerFreeShippingPolicy:            # ShippingFeePolicy 구현
    def __init__(self, base: ShippingFeePolicy,
                 today_source: Callable[[], date] = date.today) -> None:
        self._base = base                                     # 1
        self._today_source = today_source

    def calculate(self, items: Sequence[OrderItemSnapshot],
                  address: Address, grade: MemberGrade) -> Money:  # 2
        if self._today_source().month in (6, 7, 8):             # 3
            return Money.ZERO
        return self._base.calculate(items, address, grade)
  1. 1~5행 새 규칙을 처음부터 다시 쓰지 않고, 기존 GradeShippingFeePolicy를 감쌉니다. 여름이 아니면 그대로 위임합니다.
  2. 7~9행 calculate()는 여전히 ShippingFeePolicy 프로토콜(페이지 4)과 똑같이 items·address·grade 세 인자만 받습니다 — today를 여기에 추가하면 페이지 5의 place_order()가 부르는 self._fee_policy.calculate(snapshots, address, grade)와 더 이상 맞지 않습니다. 대신 "지금이 몇 월인가"를 알아내는 방법 (today_source, "인자 없이 date 하나를 돌려주는 함수")을 생성자가 주입받습니다. calculate() 안에서 date.today()를 직접 부르면, 테스트가 실행되는 그날그날에 따라 통과하거나 실패합니다 — 7월에 짠 테스트가 1월에는 다르게 동작합니다. 도메인 서비스는 같은 입력이면 항상 같은 출력이어야 합니다(페이지 6의 판별 질문 ③).

흔히 이렇게도 풀지만 — 이 클래스 안에 직접 if grade.free_shipping or date.today().month in (6,7,8):처럼 규칙을 새로 다 쓰는 방법도 있습니다. 동작은 하지만 GradeShippingFeePolicy의 로직을 그대로 복사하게 되고, 등급 규칙이 바뀌면 두 곳을 함께 고쳐야 합니다.

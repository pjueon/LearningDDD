4장 · 화면 1

Repository
도메인에서 DB를 밀어내기

3장에서 Order와 InventoryItem을 만들었습니다. 그런데 3장의 코드 어디에도 INSERT도 SELECT도 없었습니다. 지금까지 만든 애그리게이트는 메모리에만 있고, 프로세스가 끝나면 사라집니다.

이 장은 그 객체들을 저장하고 꺼내는 방법을 만듭니다. 그런데 목표는 "저장 코드를 짜는 것"이 아닙니다. 도메인 코드가 저장 방법을 몰라도 되게 만드는 것입니다.

이 장의 지도

  • 화면 2~4 · 문제와 원칙. 도메인 안에 SQL이 들어가면 벌어지는 일, 영속성 무지와 의존성 역전 원칙, 그리고 리포지토리 인터페이스를 정의합니다.
  • 화면 5~8 · 메모리 구현으로 규칙을 다진다. 테스트가 쉬워지는 순간, 애그리게이트 단위로만 저장하는 규칙, 그리고 3장이 남긴 빚 — Allocation을 어디에 보관하는가.
  • 화면 9~10 · 진짜 저장소. SQLAlchemy로 실제 구현을 만들고, 1장의 생 SQL이 매핑 코드로 어떻게 바뀌는지 나란히 봅니다.
  • 화면 11~12 · 반대 의견과 마무리. "ORM 세션이 이미 리포지토리 아닌가?"라는 질문에 답하고, 이 장이 다음 장들에 남기는 것을 정리합니다.

4장 · 화면 2

도메인 안에 SQL이 있으면 벌어지는 일

3장에서 만든 Order.cancel()은 메모리 안의 status만 바꿉니다. 실제로 저장하려면 누군가 DB에 반영해야 합니다. 가장 빠른 방법은 이렇게 메서드 안에 저장 코드를 넣는 것입니다.

# domain/order.py — 하지 않는다class Order:
    def cancel(self) -> None:
        if self.status not in self.CANCELLABLE:
            raise AlreadyShipped("이미 출고된 주문입니다")
        self.status = OrderStatus.취소됨

        conn = sqlite3.connect("hanbit.db")             # 1
        conn.execute(                                   # 2
            "UPDATE orders SET status = ? WHERE order_number = ?",
            (self.status.name, self._order_number.value))
        conn.commit()                                   # 3
  1. 7행 sqlite3는 표준 라이브러리라 정본의 "도메인은 표준 라이브러리만 쓴다"는 규칙을 문법적으로는 어기지 않습니다. 그런데도 문제입니다 — Order가 이제 파일 경로, 테이블 이름, SQL 문법을 알아야 합니다. 이것들은 업무 규칙이 아니라 저장 방식에 대한 지식입니다.
  2. 8~10행 취소라는 업무 행위 하나가 SQL 문자열과 엮였습니다. 내일 누군가 "관리자 강제 취소" 배치를 만들면서 이 메서드를 부르지 않고 비슷한 SQL을 또 짜면, 두 코드가 같은 규칙을 두 번 유지하게 됩니다. 테이블 이름이 바뀌면 두 곳을 다 고쳐야 합니다.
  3. 11행 conn.commit()이 실패하면 어떻게 될까요? self.status는 이미 취소됨인데 DB는 그대로입니다. 객체의 상태와 저장된 값이 어긋날 수 있는 통로가 하나 더 생겼습니다. 5장에서 다시 볼 문제

이 코드로 테스트를 짜 보면

Order.cancel()을 테스트하려면 이제 hanbit.db 파일이 있어야 하고, orders 테이블이 그 안에 있어야 하고, 테스트가 끝나면 지운 행을 되돌려야 합니다. 불변식 하나(I5)를 확인하려고 DB 전체가 필요해졌습니다. 1장 화면 13의 통증 3번이 3장에서 사라졌다가 여기서 도로 생깁니다.

그런데 애초에 왜 저장 코드가 도메인 메서드 안에 있으면 안 될까요? 다음 화면에서 이름을 붙여 봅니다.

4장 · 화면 3

영속성 무지, 그리고 의존성의 방향을 뒤집기

화면 2의 문제를 한 문장으로 줄이면 — Order가 자신이 어떻게 저장되는지 알고 있다는 것입니다. 이 앎을 없애는 성질에 이름이 있습니다.

영속성 무지 (Persistence Ignorance)

도메인 객체는 자신이 SQLite에 저장되는지, PostgreSQL에 저장되는지, 아니면 그냥 메모리에 있다가 사라지는지 전혀 몰라야 합니다. Order는 cancel()이 호출되면 규칙을 검사하고 상태를 바꿀 뿐, 그 변화를 누가 어떻게 영구히 남기는지는 관심 밖입니다.

그런데 저장은 누군가 해야 합니다. 그 "누군가"를 어디에 둘지가 문제입니다. 1장~3장의 코드는 전부 이런 그림이었습니다 — 도메인이 DB를 안다.

오른쪽 그림에 붙은 이름이 의존성 역전 원칙(Dependency Inversion Principle)입니다. 인터페이스는 도메인이 정의하고, 구현은 인프라가 도메인 쪽을 보고 만듭니다. 화살표의 방향이 뒤집혔다는 것이 핵심입니다 — 누가 어느 코드를 import하는지가 바뀝니다.

이 인터페이스에 붙는 이름

도메인이 "나는 이런 모양의 저장소가 있으면 된다"고 정의해 두는 이 인터페이스가 리포지토리(Repository)입니다. 다음 화면에서 정의합니다.

4장 · 화면 4

리포지토리 인터페이스 정의하기

파이썬에는 자바의 interface가 없습니다. 대신 typing.Protocol을 씁니다 — 이 모양(메서드 이름과 시그니처)을 가진 것이면 무엇이든 통과시키는 구조적 타입입니다. 명시적으로 상속받지 않아도 됩니다.

# domain/repository.pyclass OrderRepository(Protocol):
    def get(self, order_number: OrderNumber) -> Order: ...   # 1
    def add(self, order: Order) -> None: ...                 # 2
    def next_order_number(self, today: date) -> OrderNumber: ...  # 3


class InventoryRepository(Protocol):
    def get(self, sku: str) -> InventoryItem: ...
    def get_many(self, skus: Sequence[str]) -> dict[str, InventoryItem]: ...  # 4
  1. 2행 없는 주문을 찾으면 OrderNotFound를 던집니다. 3장의 다섯 예외에 여섯 번째 도메인 예외가 추가됩니다 — 리포지토리도 도메인의 일부이므로(정의는 도메인 계층에 있습니다) 예외도 도메인 예외입니다.
  2. 3행 새 주문 하나만 받습니다. 이미 있는 주문을 바꾼 뒤 다시 "저장"하는 메서드가 없습니다. 왜 없는지는 화면 7의 주제입니다.
  3. 4행 주문 번호 생성이 왜 리포지토리에 있을까요? 번호는 "오늘 날짜 + 그날의 순번"이라 동시에 여러 요청이 주문을 만들 때 순번이 겹치면 안 됩니다. 겹치지 않게 보장하려면 결국 DB의 시퀀스나 잠금이 필요합니다 — 이건 업무 규칙이 아니라 인프라의 문제입니다. 그래서 번호의 형식 (OrderNumber, 2장)은 도메인이 정의하고, 번호를 발급하는 행위는 포트 뒤로 넘깁니다.
  4. 9행 get_many가 따로 있는 이유는 3장 화면 9의 그 문장 때문입니다 — "SKU마다 allocate()를 부르고, 가장 늦은 ready_on을 고른다." 라인이 5개인 주문은 SKU를 5번 조회해야 하는데, get을 5번 부르면 왕복이 5번입니다. get_many는 한 번의 왕복으로 5개를 가져옵니다. 이런 문제를 흔히 N+1 문제라고 부릅니다.

왜 OrderLineRepository는 없는가

지금 눈치채셨을 수 있습니다 — OrderLine에는 리포지토리가 없습니다. 이건 실수가 아닙니다. 화면 6에서 이유를 정면으로 다룹니다.

4장 · 화면 5

메모리 구현 — 그리고 갑자기 쉬워지는 테스트

인터페이스를 만들었으니 가장 단순한 구현부터 봅니다. 딕셔너리 하나면 됩니다.

# infra/memory_repository.pyclass InMemoryOrderRepository:
    def __init__(self) -> None:
        self._orders: dict[str, Order] = {}

    def get(self, order_number: OrderNumber) -> Order:
        try:
            return self._orders[order_number.value]        # 1
        except KeyError:
            raise OrderNotFound(order_number.value) from None

    def add(self, order: Order) -> None:
        self._orders[order.order_number.value] = order      # 2

    def next_order_number(self, today: date) -> OrderNumber:
        seq = sum(1 for k in self._orders
                  if k.startswith(today.strftime("%Y%m%d")))
        return OrderNumber.issue(today, seq + 1)
  1. 7행 키를 문자열로 씁니다. OrderNumber는 2장에서 frozen=True로 만들었으니 dict 키로 직접 써도 되지만, .value로 풀어 쓰면 나중에 SQLAlchemy 구현(화면 9)의 기본 키 컬럼과 모양이 맞습니다.
  2. 12행 order.order_number를 씁니다. 3장에서는 self._order_number로만 저장하고 밖으로 내주는 길이 없었습니다 — 3장까지는 그 값을 읽을 일이 없었기 때문입니다. 이제 리포지토리가 저장 키로 써야 하므로, Order에 읽기 전용 프로퍼티를 하나 추가합니다.
# domain/order.py — Order 안에 추가    @property
    def order_number(self) -> OrderNumber:
        return self._order_number

이제 이 리포지토리로 Order를 테스트합니다. DB도, 세션도, 픽스처도 없습니다.

# tests/test_ordering.pydef test_저장한_주문을_다시_꺼내면_같은_객체다() -> None:
    repo = InMemoryOrderRepository()
    order = Order(repo.next_order_number(date(2026, 9, 7)),
                  customer_id=uuid4(), shipping_address=배송지())
    order.add_line("SKU-001", "생수 2L", Money.won(1_000), Quantity(2))
    repo.add(order)

    again = repo.get(order.order_number)
    again.cancel()

    assert order.status is OrderStatus.취소됨    # 1
  1. 11행 같은 객체이므로 이미 반영돼 있습니다. again과 order는 파이썬 메모리 안에서 같은 객체를 가리키는 두 이름입니다. again.cancel()이 바꾼 것은 order가 보는 것과 같은 상태입니다. repo.add(order) 뒤에 "다시 저장"하는 코드가 한 줄도 없다는 점에 주목하세요.

1장 화면 13의 통증 3번이 다시 사라졌습니다

이 테스트는 1밀리초 안에 끝납니다. DB 컨테이너를 띄울 필요도, 테스트 뒤 데이터를 정리할 필요도 없습니다. Order의 모든 불변식(I1~I5)을 이런 식으로 빠르게, 격리된 채로 테스트할 수 있습니다. 진짜 DB를 쓰는 테스트는 화면 9의 구현을 검증하는 소수의 통합 테스트로 남겨 둡니다.

4장 · 화면 6

애그리게이트 단위로만 저장한다

화면 4에서 미뤄둔 질문 — 왜 OrderLineRepository는 없어야 할까요? 있다면 이런 모양일 것입니다.

# 만들지 않는다class OrderLineRepository:
    def update_quantity(self, line_id: UUID, quantity: Quantity) -> None: ...

이걸 만들면 이런 코드가 가능해집니다.

# 이 코드가 가능해진다면line_repo.update_quantity(line_id, Quantity(5))

낯익은 문제입니다. 3장 화면 5에서 정확히 같은 모양의 문제를 봤습니다 — order.lines[0].quantity = ...가 Order._ensure_modifiable()를 건너뛰던 그 코드입니다. OrderLineRepository는 그 우회로를 코드 수준에서 다시 열어 줍니다. 결제완료된 주문의 라인 수량을 이 메서드로 바꾸면 I4를 확인하는 코드는 아예 호출되지 않습니다.

규칙 — 리포지토리는 애그리게이트 루트에만 만든다

3장의 규칙("바깥은 루트만 참조한다")이 저장 계층에도 그대로 적용됩니다. 내부 엔티티로 가는 저장/조회 경로 자체를 만들지 않으면, 그 경로를 통한 우회는 구조적으로 불가능해집니다. "리뷰에서 눈에 띄겠지"에 기대지 않아도 됩니다 — 애초에 그런 클래스가 없습니다.

이제 3장의 마지막 질문에 답할 수 있습니다

1장 화면 6과 3장 화면 2의 사고 2번을 기억하시나요 — 프로모션 배치가 UPDATE orders SET discount = ...만 실행하고 total 컬럼은 그대로 둬서 금액이 어긋난 사고입니다. 이 사고가 4장 이후에는 구조적으로 불가능합니다. 이유가 셋 겹쳐 있습니다.

막는 장치어떻게 막는가
계산값은 컬럼이 아니다 total_amount는 3장에서 이미 @property가 됐습니다 (저장되는 값이 아니라 계산되는 값). 화면 9에서 매핑할 때 이 값은 테이블에 컬럼조차 없습니다. 어긋날 곳 자체가 없습니다.
저장 경로가 하나뿐이다 OrderRepository에는 get과 add만 있습니다. "컬럼 하나만 바꾸는" 메서드가 없으니, 프로모션 배치도 주문 전체를 get()으로 꺼내 도메인 메서드를 부르는 것 외에는 할 수 있는 일이 없습니다.
SQL을 쓸 길이 없다 배치 스크립트가 OrderRepository를 거치는 한, 원시 SQL을 쓸 일이 없습니다. 화면 2에서 본 것과 반대로, 이제는 SQL을 쓰려면 일부러 리포지토리를 건너뛰어야 합니다.

3장이 남긴 빚 — 갚았습니다

3장 화면 15의 "이 장이 남긴 빚" 표는 4장 몫으로 "애그리게이트를 통째로 저장하고 꺼내는 방법"과 "UPDATE orders SET ...를 막는 마지막 통로"를 남겼습니다. 위 표가 그 답입니다.

4장 · 화면 7

그런데 "저장"하는 메서드가 왜 없을까

화면 5의 테스트를 다시 보면 이상한 점이 있습니다. again.cancel()을 부른 뒤 "다시 저장해라"는 코드가 없습니다. 그런데도 order.status가 바뀌어 있었습니다. 이유는 단순합니다 — InMemoryOrderRepository는 객체를 직렬화하지 않습니다. 파이썬 참조를 그대로 들고 있을 뿐이라, 객체를 바꾸면 "저장된 것"도 그냥 바뀝니다.

진짜 DB는 다릅니다

진짜 DB는 객체가 아니라 행(row)을 저장합니다. Order 객체를 바꾼다고 orders 테이블의 행이 저절로 바뀌지 않습니다. 객체와 행 사이에는 직렬화 경계가 있고, 그 경계를 넘는 순간이 명시적으로 필요합니다.

그렇다고 OrderRepository에 update(order)를 추가하지는 않습니다. 대신 5장에서 Unit of Work라는 것을 만듭니다. 미리 살짝 보면 이렇게 씁니다.

# 5장에서 만드는 것의 미리보기order = uow.orders.get(order_number)      # 1
order.cancel()
uow.commit()                              # 2
  1. 1행 uow.orders가 곧 OrderRepository입니다.
  2. 3행 order.update()나 repo.save(order)가 없습니다. SQLAlchemy의 세션은 get()으로 꺼내 온 객체를 추적하고 있다가, commit() 시점에 바뀐 값을 찾아 스스로 UPDATE 문을 만듭니다(Identity Map이라는 장치입니다). 5장에서 다시 볼 문제

메모리 구현과 SQLAlchemy — "저장 코드가 안 보인다"는 같지만 이유는 다르다

둘 다 명시적인 "저장" 호출이 없다는 점은 같습니다. 그런데 메커니즘은 전혀 다릅니다. 메모리 구현은 애초에 직렬화가 없어서 저장이라는 개념 자체가 없습니다. SQLAlchemy는 세션이 변경을 추적했다가 커밋 시점에 실제로 SQL을 만들어 냅니다. 이 차이를 헷갈리면 5장의 Unit of Work가 왜 필요한지 이해하기 어렵습니다.

4장 · 화면 8

3장의 마지막 과제 — Allocation을 어디에 보관하는가

3장 화면 16의 과제 답에 이런 문장이 있었습니다 — "Allocation을 어디에 보관해 뒀다가 취소 때 꺼내는지도 아직 정하지 않았습니다. 그건 4장의 문제입니다." 저장 단위를 정하고 나니 이제 답할 수 있습니다.

InventoryItem.allocate()는 Allocation이라는 값을 돌려줍니다. 이 값에는 어느 배치에서 몇 개를 가져왔는지가 들어 있고, 나중에 주문이 취소되면 release(allocation)에 그대로 돌려줘야 합니다. 그런데 지금까지는 이 값이 응용 코드의 지역 변수로만 존재했습니다 — 요청이 끝나면 사라집니다.

재고 애그리게이트에 보관하면 안 되는 이유

"그럼 InventoryItem이 자기가 어느 주문에 할당했는지 기억하면 되지 않나요?" — 3장 화면 16의 모범답안이 이미 이 길을 막았습니다. 배치에 {주문번호: 수량}을 적어 두면 재고가 주문의 생애주기를 알아야 합니다("이 주문이 취소됐나, 아직 살아있나"). 재고의 관심사가 아닌 것이 재고 안으로 들어옵니다.

남은 자리는 하나뿐입니다. Order가 들고 있는 것입니다. 3장에서 Promise를 이렇게 다뤘던 것과 같은 논리입니다 — Order는 배치를 참조하지 않고, Allocation이라는 불변 값만 보관합니다.

SQLAlchemy의 클래식 매핑은 보통 "엔티티 하나 = 테이블 하나"를 가정하는데, AllocationLine은 엔티티가 아니라 식별자 없는 값이 여러 개 모인 것이라 표준적인 관계 매핑과 잘 맞지 않습니다. 실전에서는 커스텀 컬렉션이나 composite(), 혹은 그냥 JSON 컬럼에 직렬화하는 방법을 씁니다. 여기서는 스키마와 저장 위치까지만 정하고, 매핑 코드의 세부 구현은 이 교재의 범위 밖으로 남겨 둡니다 — 어느 쪽을 고르든 화면 6의 규칙(애그리게이트 루트를 통해서만 접근)은 지켜집니다.

4장 · 화면 9

SQLAlchemy로 진짜 저장소 만들기

메모리 구현과 정확히 같은 인터페이스를 진짜 DB로 구현합니다. 방법은 "임퍼러티브 매핑"(classical mapping)입니다 — 도메인 클래스에 SQLAlchemy 코드를 한 줄도 넣지 않고, 테이블과 클래스를 인프라 쪽에서 연결합니다.

# infra/orm.py — 도메인 코드는 이 파일의 존재를 모른다mapper_registry = registry()

orders_table = Table(
    "orders", mapper_registry.metadata,
    Column("order_number", String(15), primary_key=True),   # 1
    Column("customer_id", String(36)),
    Column("status", Enum(OrderStatus)),
    Column("discount_amount", Integer),
    Column("shipping_fee_amount", Integer),
    Column("zipcode", String(5)), Column("road", String),
    Column("promise_ship_on", Date, nullable=True),          # 2
)

order_lines_table = Table(
    "order_lines", mapper_registry.metadata,
    Column("line_id", String(36), primary_key=True),
    Column("order_number", ForeignKey("orders.order_number")),
    Column("sku", String), Column("product_name", String),
    Column("unit_price_amount", Integer), Column("qty", Integer),
)

def start_mappers() -> None:
    lines_mapper = mapper_registry.map_imperatively(
        OrderLine, order_lines_table)
    mapper_registry.map_imperatively(
        Order, orders_table,                                 # 3
        properties={"_order_number": orders_table.c.order_number,
                    "_lines": relationship(
                        lines_mapper, collection_class=list)})
  1. 5행 orders 테이블 정의는 1장 화면 3에서 본 그 테이블과 컬럼이 거의 같습니다 — customer_id, zipcode·road 같은 배송지 컬럼들입니다. 다른 점은 기본 키가 정수 id가 아니라 order_number 문자열이라는 것, 그리고 total 컬럼이 없다는 것입니다.
  2. 11행 promise_ship_on처럼 3장에서 추가된 필드도 그냥 컬럼입니다. Money·Address 같은 값 객체는 자기 테이블 없이 부모 테이블의 컬럼으로 펼쳐진다고 2장 화면 13에서 이미 다뤘습니다. discount_amount가 그 예입니다 — Money 하나가 정수 컬럼 하나가 됩니다.
  3. 25~29행 이것이 임퍼러티브 매핑의 핵심입니다. Order 클래스 정의에는 SQLAlchemy를 import하는 줄이 단 한 줄도 없습니다(2~3장을 다시 봐도 확인할 수 있습니다). 대신 이 infra/orm.py 파일이 바깥에서 "이 클래스의 이 속성은 이 테이블의 이 컬럼과 대응한다"고 선언합니다. _lines라는 밑줄 이름 속성까지 지정할 수 있는 것도 이 방식의 특징입니다 — Order가 캡슐화를 위해 만든 "private처럼 보이는" 속성을 인프라가 그대로 씁니다. _order_number도 같은 이유로 명시합니다 — 이렇게 두지 않으면 SQLAlchemy 가 읽기 전용 프로퍼티 order_number 자리를 덮으려 들기 때문입니다.

리포지토리 구현은 이제 짧습니다. 세션 하나만 감싸면 됩니다.

# infra/sqlalchemy_repository.pyclass SqlAlchemyOrderRepository:
    def __init__(self, session: Session) -> None:
        self._session = session

    def get(self, order_number: OrderNumber) -> Order:
        order = self._session.get(Order, order_number.value)
        if order is None:
            raise OrderNotFound(order_number.value)
        return order

    def add(self, order: Order) -> None:
        self._session.add(order)

InventoryRepository의 SQLAlchemy 구현도 같은 방식입니다 — StockBatch가 Order의 _lines와 똑같이 InventoryItem에 relationship으로 매달립니다. 코드가 거의 반복이라 여기서는 생략합니다.

4장 · 화면 11

반대 의견 — "ORM 세션이 이미 리포지토리 아닌가?"

시니어 개발자

SQLAlchemy의 Session도 session.get(Order, id), session.add(order)를 이미 제공합니다. OrderRepository를 또 만드는 건 같은 일을 두 번 감싸는 것 아닌가요?

일리 있는 지적입니다. 실제로 Session은 Unit of Work와 Identity Map을 이미 구현하고 있어서, 화면 9의 SqlAlchemyOrderRepository는 얇은 래퍼에 가깝습니다. 그래서 이 추상화가 정당화되는 경우와 과할 수 있는 경우를 나눠 봅니다.

리포지토리가 갚는 것대가로 치르는 것
테스트가 DB 없이 돈다(화면 5) 인터페이스와 두 가지 구현(메모리·SQLAlchemy)을 유지해야 한다
ORM을 나중에 바꿔도 도메인이 안 바뀐다 (예: SQLAlchemy → 원시 SQL, 또는 다른 ORM) 그런 교체가 실제로 일어날 일이 거의 없다면, 이 이득은 실현되지 않는 보험료다
도메인에 SQL/세션 코드가 새지 않는다(화면 6) 작은 프로젝트에서는 Session을 응용 서비스에서 직접 써도 같은 규율을 지킬 수 있다

리포지토리를 만들지 않아도 되는 경우

  • ORM을 바꿀 계획이 전혀 없고, 팀 전체가 SQLAlchemy에 익숙하다. 추상화의 가장 큰 이득(교체 가능성)이 애초에 필요 없다.
  • 애그리게이트가 단순하고 적다. 조회 화면이 대부분이고 쓰기 규칙이 거의 없는 CRUD 근처 도메인이라면(1장 화면 16의 판단 기준과 같습니다), Session을 바로 쓰는 편이 코드가 짧다.
  • 혼자 또는 아주 작은 팀. 인터페이스를 유지하는 비용을 나눠 낼 사람이 적으면 그 비용이 상대적으로 커진다.

한빛몰은 반대입니다 — 애그리게이트가 계속 늘어나고(5장 이후로도 계속 나옵니다), 도메인 테스트를 빠르게 돌리는 것이 3장부터 계속 강조된 가치였습니다. 그래서 이 교재는 리포지토리를 만드는 쪽을 택합니다. 이것이 언제나 옳다는 뜻은 아닙니다.

4장 · 화면 12

4장 마무리

핵심 요약

  1. 영속성 무지는 도메인 객체가 자신이 어떻게 저장되는지 몰라야 한다는 성질입니다. 의존성 역전 원칙으로 이걸 만듭니다 — 인터페이스는 도메인이 정의하고, 구현은 인프라가 그 인터페이스를 향해 만듭니다.
  2. 리포지토리는 애그리게이트 단위로만 존재합니다. OrderLineRepository가 없는 이유는 "바깥은 루트만 참조한다"는 3장의 규칙을 저장 계층에서도 지키기 위해서입니다.
  3. 메모리 구현은 테스트를 극적으로 빠르게 만듭니다. 다만 "저장 호출이 안 보이는" 이유가 메모리와 진짜 DB(SQLAlchemy Identity Map)에서 서로 다르다는 점을 구분해야 합니다.
  4. total_amount가 계산값이라 컬럼조차 없다는 사실과, 저장 경로가 get/add 뿐이라는 사실이 겹쳐 1장의 "총액 불일치" 사고를 구조적으로 막습니다.
  5. 애그리게이트 경계를 넘어 나가는 값(Allocation)은, 저장 단위가 정해지자 보관할 곳도 함께 정해집니다 — 값을 만든 애그리게이트가 아니라 그 값을 나중에 다시 써야 하는 애그리게이트가 보관합니다.

팀원이 "InventoryItem도 필요하니 StockBatchRepository를 따로 만들어 배치 하나만 빠르게 조회하자"고 제안합니다. 어떻게 답해야 할까요?

  1. 조회가 빨라지므로 찬성한다
  2. 반대한다 — StockBatch는 내부 엔티티이고, 별도 리포지토리는 InventoryItem의 불변식을 우회하는 통로가 된다
  3. 이름만 BatchQuery로 바꾸면 괜찮다
  4. 읽기 전용이라면 허용해도 된다

해설 "성능이 필요하다"는 요구는 정당하지만, 그 해법이 애그리게이트 경계를 뚫는 것이면 안 됩니다. 화면 6의 논리가 재고에도 그대로 적용됩니다.

정말 배치 단위 조회가 필요하다면(예: 창고 대시보드), 그건 쓰기 모델을 위한 리포지토리가 아니라 읽기 전용 쿼리로 풀어야 합니다. 3장 화면 16의 퀴즈에서 이미 나온 논리입니다 — 애그리게이트는 쓰기 단위이지 읽기 단위가 아닙니다. 13장에서 이 읽기 전용 경로를 정식으로 다룹니다.

InMemoryOrderRepository로 테스트를 통과시킨 코드를 그대로 SQLAlchemy 구현으로 바꿨더니, order.cancel() 뒤에 DB를 확인해도 상태가 결제완료 그대로였습니다. 가장 가능성 높은 원인은?

  1. OrderRepository 인터페이스 자체가 잘못됐다
  2. Order.cancel()의 상태 검사 로직에 버그가 있다
  3. session.commit()을 부르지 않았다
  4. order_number를 기본 키로 쓴 것이 문제다

해설 이 문제가 바로 화면 7의 경고입니다 — 메모리 구현에서는 "저장을 잊는다"는 실수가 애초에 존재하지 않습니다(직렬화가 없으니까요). SQLAlchemy로 바꾸는 순간 새로운 실수 종류가 생깁니다. 두 구현이 "저장 호출이 안 보인다"는 점에서 비슷해 보이지만, 그 이유가 다르다는 것을 몰랐다면 이 버그의 원인을 찾는 데 오래 걸렸을 것입니다.

이 실수를 막는 장치가 5장의 Unit of Work입니다 — with uow: 블록이 끝날 때 commit을 잊으면 자동으로 rollback되게 만들어, "커밋을 깜빡했는데 알아채지 못하는" 상황 자체를 줄입니다.

화면 11의 반대 의견 논의에서, 리포지토리를 만드는 비용이 이득보다 큰 상황으로 가장 적절한 것은?

  1. 혼자 만드는 사내 재고 확인용 CRUD 도구. 화면 세 개, 규칙은 "로그인한 사람만 수정 가능"뿐
  2. 한빛몰처럼 애그리게이트가 여러 개이고 팀이 계속 기능을 추가하는 상황
  3. 도메인 규칙이 복잡해서 테스트를 자주 돌려야 하는 상황
  4. 2년 안에 다른 데이터베이스로 옮길 계획이 있는 상황

class InventoryNotFound(DomainError): ...


class InMemoryInventoryRepository:
    def __init__(self) -> None:
        self._items: dict[str, InventoryItem] = {}

    def get(self, sku: str) -> InventoryItem:      # 1
        try:
            return self._items[sku]
        except KeyError:
            raise InventoryNotFound(sku) from None

    def get_many(
        self, skus: Sequence[str],
    ) -> dict[str, InventoryItem]:                   # 2
        return {sku: self.get(sku) for sku in skus}

    def add(self, item: InventoryItem) -> None:
        self._items[item.sku] = item
  1. 8행 OrderRepository.get과 같은 패턴을 그대로 재사용했습니다. 두 리포지토리가 같은 실패 방식을 쓰면, 응용 서비스(5장)에서 예외 처리 코드를 공통으로 쓸 수 있습니다.
  2. 14~17행 메모리 구현에서는 get을 여러 번 불러도 실질적인 비용 차이가 없습니다 — 딕셔너리 조회는 어차피 빠릅니다. 하지만 이렇게 짜 두면 SQLAlchemy 구현으로 바꿀 때 그대로 복사하면 N+1 문제가 재발합니다. 진짜 구현에서는 session.query(InventoryItem).filter(sku.in_(skus))처럼 한 번의 쿼리로 바꿔야 합니다. 인터페이스가 같다고 구현 전략까지 그대로 옮겨도 되는 것은 아닙니다 — 이것이 화면 4에서 get_many를 처음부터 별도 메서드로 정의해 둔 이유이기도 합니다. 시그니처를 미리 분리해 두면, 나중에 최적화할 때 호출하는 쪽의 코드를 바꿀 필요가 없습니다.

애그리게이트 사이를 잇기

6장 마지막 화면이 남긴 문제입니다 — place_order()가 주문을 만드는 것과 재고를 할당하는 것을 여전히 한 함수, 한 트랜잭션 안에서 처리합니다. Order와 InventoryItem은 3장에서 서로 ID로만 참조하기로 했는데, 응용 서비스 안에서는 결국 둘 다 동시에 손에 쥐고 있습니다.

그리고 갚지 못한 빚이 둘 더 있습니다. 3장이 만든 repromise()는 아직 몸통이 없고(화면 11), 1장의 83줄짜리 함수에 있던 메일 발송은 5장부터 코드 예제에서 조용히 빠져 있었습니다(화면 9). 이 장은 그 자리를 만듭니다 — 도메인 이벤트입니다.

  • 화면 10~11 · 실패와 재조정. 품절과 입고 지연, 두 실패 시나리오.
  • 화면 12~13 · 대가와 마무리. 이벤트가 공짜가 아닌 이유.

7장 · 화면 2

place_order()가 지금 하는 일

6장 화면 5가 만든 모양 그대로, 5장 화면 10의 할당 코드가 이어 붙어 있습니다.

# application/ordering.py — 지금(6장 시점)class OrderingService:
    def __init__(self, uow: UnitOfWork, catalog: CatalogPort,
                 members: MembershipPort, shipping: ShippingPolicy,
                 fee_policy: ShippingFeePolicy,
                 discount_policy: DiscountPolicy) -> None:
        self._uow, self._catalog, self._members = uow, catalog, members
        self._shipping = shipping
        self._fee_policy = fee_policy
        self._discount_policy = discount_policy

    def place_order(self, cmd: PlaceOrderCommand) -> OrderNumber:
        snapshots = self._catalog.snapshot(cmd.items)
        grade = self._members.grade_of(cmd.customer_id)

        with self._uow as uow:
            order = Order.place(
                order_number=uow.orders.next_order_number(date.today()),
                customer_id=cmd.customer_id,
                address=cmd.shipping_address,
                items=snapshots,
                shipping_fee=self._fee_policy.calculate(
                    snapshots, cmd.shipping_address, grade),
                discount=self._discount_policy.calculate(snapshots, grade))

            items = uow.inventory.get_many([l.sku for l in order.lines])
            order.allocation = {
                l.sku: items[l.sku].allocate(l.quantity.value, date.today())
                for l in order.lines}
            ready_on = max(a.ready_on for a in order.allocation.values())
            order.promise_delivery(Promise(
                ship_on=ready_on,
                arrive_by=ready_on + self._shipping.lead_time,
                promised_at=datetime.now()))

            uow.orders.add(order)
            uow.commit()
            return order.order_number
  1. 25~33행 Order.place()로 막 태어난 주문 바로 다음 줄에서, 다른 애그리게이트(InventoryItem)를 꺼내 직접 조작합니다. 한 함수가 두 애그리게이트의 트랜잭션을 동시에 쥐고 있습니다 — 3장이 애그리게이트 경계를 그은 이유(동시성, 각자의 규칙 주인)가 여기서 흐려집니다.

이 코드가 숨기고 있는 문제 둘

  1. Order와 InventoryItem이 한 트랜잭션 안에서 얽혀 있습니다. 재고 할당이 느리거나 실패하면 주문 생성 전체가 영향을 받습니다.
  2. 1장에 있던 메일 발송이 이 코드에는 없습니다. 5장부터 응용 서비스 예제가 핵심 흐름(할인·배송비·할당)에 집중하려고 잠시 빼 뒀습니다. 지금 이대로 메일을 추가하려면 또 place_order() 안에 줄을 보태야 하는데, 그러면 1장의 문제로 되돌아갑니다.

7장 · 화면 3

"그냥 Order 안에서 InventoryItem을 부르면 안 되나?"

자연스러운 생각입니다. Order.place() 안에서 재고까지 확인하고 할당해 버리면 응용 서비스가 훨씬 간결해질 것 같습니다. 안 되는 이유를 하나씩 짚어 봅시다.

  • ID로만 참조한다는 규칙(3장)이 깨집니다. Order가 InventoryItem을 직접 부르려면 리포지토리를 알아야 하는데, 도메인 계층이 인프라를 아는 순간 4장이 막았던 문제(영속성 무지 위반)가 재발합니다.
  • 두 애그리게이트가 한 트랜잭션에 더 단단히 묶입니다. 지금도 응용 서비스 수준에서 얽혀 있는 문제(화면 2)가, 도메인 계층까지 내려가면 더 풀기 어려워집니다. 동시성 문제는 12장에서 본격적으로 다룹니다.
  • 실패의 의미가 뒤섞입니다. "라인이 비었다"(I1)와 "재고가 모자라다"는 전혀 다른 종류의 실패인데, 한 메서드 안에서 나면 호출자는 둘을 구분하기 어려워집니다.

그럼 지금처럼 응용 서비스가 순서대로 다 부르면 되지 않을까요? 지금은 됩니다. 문제는 "지금 당장" 이후입니다.

은수

왜 지금 방식이 안 된다는 거예요? 지금도 잘 동작하잖아요.

도현

이건 "지금 이 순간 순서대로 조립하기"만 해결해요. 그런데 창고에서 배치 입고가 3일 늦어지면, 이미 그 배치로 할당받아 약속일을 받은 주문들을 다시 찾아서 약속을 고쳐야 해요. 그건 주문을 만드는 그 순간이 아니라 나중에, 재고 쪽에서 일어나는 사건이에요. place_order() 안에는 그 사건을 처리할 자리가 없어요.

필요한 것은 "순서대로 부르기"가 아니라, "이 애그리게이트에 이런 일이 일어났다"는 사실을 남겨 두고, 그 사실에 관심 있는 다른 코드가 (지금이든 나중이든) 반응하게 만드는 방법입니다. 그 사실에 이름을 붙이면 도메인 이벤트입니다.

7장 · 화면 4

이름 붙이기 — 도메인 이벤트

도메인 이벤트는 애그리게이트 안에서 일어난, 업무적으로 의미 있는 "이미 벌어진 사실"입니다. 그 모양을 코드로 옮기면 이렇습니다.

# domain/events.py@dataclass(frozen=True)
class DomainEvent:
    occurred_at: datetime

@dataclass(frozen=True)
class OrderPlaced(DomainEvent):
    order_number: str
    customer_id: UUID
    items: tuple[tuple[str, int], ...]   # (sku, quantity)

PlaceOrderCommand(5장)와 이름도 비슷하고 둘 다 frozen=True 불변 데이터지만, 뜻은 정반대입니다.

커맨드이벤트
이름 시제 현재형·명령형 — PlaceOrderCommand 과거형 — OrderPlaced
받는 대상 정확히 하나(그 일을 해야 할 서비스) 0개 이상. 누가 구독하는지 몰라도 됨
거부할 수 있나 할 수 있다(재고 없음 등으로 거절) 없다. 이미 일어난 사실이라, 구독자는 "할지 말지"가 아니라 "이 사실에 어떻게 반응할지"만 정한다

왜 과거형이어야 하는가

AllocateStock이라는 이름이었다면, 그 이벤트를 받은 핸들러가 "지금 재고가 없으니 안 하겠다"고 거부할 수 있다는 뜻처럼 읽힙니다. 하지만 OrderPlaced는 이미 커밋된 사실입니다 — 주문은 이미 생성됐습니다. 핸들러가 재고 할당에 실패할 수는 있어도, "주문이 생성된 사실 자체"를 되돌릴 권한은 없습니다. 이름이 그 권한 관계를 드러냅니다.

7장 · 화면 5

애그리게이트는 이벤트를 모아만 둔다

Order는 자기 안에서 일어난 일을 리스트에 적어 두기만 합니다. 누가 구독하는지, 언제 발행되는지는 전혀 모릅니다.

# domain/order.py — Order 안에 추가class Order:
    def __init__(self, order_number, customer_id, address) -> None:
        ...
        self.events: list[DomainEvent] = []             # 1

    def pull_events(self) -> list[DomainEvent]:
        events, self.events = self.events, []            # 2
        return events

    @classmethod
    def place(cls, order_number, customer_id, address, items,
              shipping_fee, discount) -> "Order":
        if not items:
            raise EmptyOrder(order_number.value)
        order = cls(order_number, customer_id, address)
        for item in items:
            order.add_line(item.sku, item.product_name,
                           item.unit_price, item.quantity)
        order.discount = discount
        order.shipping_fee = shipping_fee
        order.events.append(OrderPlaced(                 # 3
            occurred_at=datetime.now(),
            order_number=order_number.value,
            customer_id=customer_id,
            items=tuple((l.sku, l.quantity.value) for l in order.lines)))
        return order

    def promise_delivery(self, promise: "Promise") -> None:
        self.promise = promise
        self.events.append(DeliveryPromised(             # 4
            occurred_at=datetime.now(),
            order_number=self.order_number.value))
  1. 4행 빈 리스트로 시작합니다. 아직 아무 일도 없었습니다.
    5장 화면 8이 "Order에 필드를 하나 추가하면(예: 7장의 events) 직렬화 코드가 덩달아 깨진다"고 경고했던 그 필드입니다. 그런데 events는 저장하지 않습니다 — 4장 화면 9의 임퍼러티브 매핑은 Table에 적은 컬럼만 다루므로, 이 필드를 추가해도 orders 테이블은 그대로입니다. 리포지토리가 되살린 Order는 항상 빈 events로 시작합니다. 저장된 주문을 꺼냈다고 옛날 이벤트가 다시 나가면 안 되니까요.
  2. 7~8행 pull_events()는 이벤트를 돌려주면서 동시에 자기 리스트를 비웁니다. 한 번 꺼낸 이벤트를 다시 꺼내 발행하는 실수를 구조적으로 막습니다.
  3. 21~25행 6장의 Order.place()가 라인· 할인·배송비를 다 채운 맨 마지막에 이벤트를 적습니다. 아직 불완전한 상태에서 이벤트가 나가는 일이 없습니다.
  4. 30~32행 3장의 promise_delivery()에 한 줄이 늘었습니다. 약속이 정해졌다는 사실도 이벤트입니다 — 그래서 이름도 DeliveryPromised입니다. 이 메서드가 하는 일이 곧 이벤트의 이름이어야, 나중에 "이 이벤트는 언제 나오나"를 코드에서 되짚을 수 있습니다.
    이 이벤트에는 이 교재 안에서 구독자가 하나도 없습니다. 그래도 괜찮습니다 — 화면 4의 표대로 이벤트의 구독자는 "0개 이상"이고, 3장 화면 14가 "최초 약속은 조용히 해도 된다"고 이미 정해 뒀기 때문입니다. 반대로 재조정은 반드시 통지를 동반해야 하는데, 그 이야기는 화면 11입니다.

왜 이 자리에서 바로 발행하지 않는가

여기서 바로 bus.publish()를 부르면 어떻게 될까요? place() 이후 트랜잭션이 어떤 이유로든 롤백되면, 이미 나간 이벤트는 취소할 수 없습니다 — 존재하지 않는 주문의 확인 메일이 고객에게 갑니다. 그래서 애그리게이트는 "사실을 적어만" 두고, 커밋에 성공한 뒤 응용 계층이 꺼내 발행합니다(화면 7).

7장 · 화면 6

MessageBus — 구독과 발행

이벤트를 모아 뒀으면, 그걸 필요한 곳까지 배달하는 장치가 있어야 합니다.

# infra/message_bus.pyclass MessageBus:
    def __init__(self) -> None:
        self._handlers: dict[type, list[Callable]] = defaultdict(list)

    def subscribe(self, event_type: type[DomainEvent],
                  handler: Callable[[DomainEvent], None]) -> None:
        self._handlers[event_type].append(handler)          # 1

    def publish(self, events: Sequence[DomainEvent]) -> None:
        for event in events:
            for handler in self._handlers[type(event)]:      # 2
                try:
                    handler(event)                            # 3
                except Exception:
                    logging.exception("핸들러 실패: %s", handler)

# 부팅 코드 — 구독을 한 곳에 모아 둔다from functools import partial

bus = MessageBus()
bus.subscribe(OrderPlaced,
              partial(allocate_stock, uow=uow, expiry=expiry,
                      shipping=shipping, bus=bus))
bus.subscribe(OrderPlaced, partial(notify_customer, mailer=mailer))
bus.subscribe(OrderPlaced, partial(notify_warehouse, slack=slack))
bus.subscribe(InboundDelayed,
              partial(repromise_delayed_orders, uow=uow,
                      shipping=shipping, bus=bus))
  1. 7행 이벤트 타입을 키로 핸들러 함수를 쌓아 둡니다. 한 타입에 핸들러가 여러 개 붙을 수 있습니다.
  2. 11행 type(event)로 정확히 그 타입을 구독한 핸들러만 찾습니다.
  3. 12~15행 핸들러 하나가 실패해도 다른 핸들러는 계속 실행됩니다. 메일 서버가 죽었다고 재고 할당까지 멈추면 안 되기 때문입니다(화면 9에서 다시 봅니다).
  4. 4~11행(부팅 코드) publish()는 handler(event)로 인자를 하나만 넘깁니다(위 코드 13행). 그런데 실제 핸들러들(화면 8·9·11)은 uow·expiry· shipping·bus 같은 의존성이 더 필요합니다. functools.partial로 그 의존성을 미리 묶어 두면, MessageBus 입장에서는 여전히 "이벤트 하나만 받는 함수"로 보입니다.
  5. 4~8행(부팅 코드) OrderPlaced 하나에 핸들러 셋이 구독합니다 — 재고 할당, 고객 메일, 창고 슬랙 알림(1장 화면 1의 요구사항 "메일 보내고 슬랙 알린다"가 여기 자리 잡습니다). 셋은 서로의 존재를 모릅니다.

지금은 동기, 나중엔 큐

publish()는 지금 그 자리에서 핸들러를 바로 호출합니다 (같은 프로세스, 같은 트랜잭션 밖). 실무에서 부하가 커지면 이 안을 메시지 큐(SQS, Kafka 등)에 넣는 코드로 바꿉니다 — subscribe/ publish 인터페이스는 그대로 두고 구현만 바뀝니다. 핸들러 쪽 코드는 한 줄도 안 바뀝니다. 이것도 리포지토리(4장)와 같은 모양의 이점입니다 — 인터페이스 뒤에서 구현을 바꿉니다.

6장이 남긴 빚 — 갚았습니다

6장 화면 12 "다음 장 예고": "place_order()가 재고를 할당하고 약속일을 정하는 것까지 한 번에 처리합니다." — 이제 place_order()는 주문을 만들고 이벤트를 발행할 뿐, 재고에 대해 아무것도 모릅니다. shipping 인자가 빠진 이유도 이것입니다 — 배송 리드타임이 필요한 코드(약속일 계산)가 통째로 핸들러로 옮겨 갔습니다(화면 8).

여유 일수는 어디서 오나요? ExpiryBufferPolicy는 6장 화면 6의 판별 질문 셋을 그대로 통과합니다 — ① 어느 엔티티 하나에 속한 규칙이 아니고 (여러 SKU에 걸친 표 하나), ② 오가는 값이 sku와 일수뿐이라 인프라가 섞이지 않고, ③ 같은 SKU를 몇 번 물어도 같은 답이 나오며 부수 효과가 없습니다. 도메인 서비스입니다.

6장의 ShippingFeePolicy·DiscountPolicy와 "같은 모양"이라는 말은 자리가 나뉘는 방식까지 같다는 뜻입니다 — Protocol(무엇을 묻는가)은 도메인이 정의하고, "어느 SKU가 며칠인지" 라는 표를 실제로 들고 있는 구현은 인프라에 둡니다. 표를 들고 있는 것은 상태가 아니라 설정이라 ③을 깨지 않습니다. 그래서 InventoryItem은 "며칠 여유를 둘지"만 알고 "왜 그 SKU가 그만큼인지"(상품 분류)는 몰라도 됩니다.

이제 핸들러입니다. 응용 서비스와 모양이 같습니다 — 조회하고, 도메인 메서드를 부르고, 커밋합니다.

# application/handlers.pydef allocate_stock(event: OrderPlaced, uow: UnitOfWork,
                    expiry: ExpiryBufferPolicy, shipping: ShippingPolicy,
                    bus: MessageBus) -> None:
    with uow:
        order = uow.orders.get(OrderNumber(event.order_number))      # 1
        items = uow.inventory.get_many([sku for sku, _ in event.items])
        allocation: dict[str, Allocation] = {}
        out_of_stock: str | None = None

        for sku, qty in event.items:                                 # 2
            try:
                allocation[sku] = items[sku].allocate(
                    qty, date.today(), buffer_days=expiry.buffer_days(sku))
            except InsufficientStock:
                out_of_stock = sku                                   # 3
                break

        if out_of_stock is not None:
            uow.rollback()                                           # 4
            events = [OutOfStock(occurred_at=datetime.now(),
                                  order_number=event.order_number,
                                  sku=out_of_stock)]
        else:
            order.allocation = allocation
            ready_on = max(a.ready_on for a in allocation.values())  # 5
            order.promise_delivery(Promise(
                ship_on=ready_on, arrive_by=ready_on + shipping.lead_time,
                promised_at=datetime.now()))
            uow.commit()
            events = order.pull_events()

    bus.publish(events)                                              # 6
  1. 5행 이벤트는 order_number: str만 갖고 있어서(값 객체를 그대로 담지 않습니다 — 이벤트는 최대한 단순한 데이터여야 다른 프로세스로도 보낼 수 있습니다), OrderNumber로 다시 감싸 리포지토리에 넘깁니다.
  2. 10~13행 SKU마다 따로 여유 일수를 물어보고 allocate()를 부릅니다. 라인마다 분류가 다를 수 있기 때문입니다.
  3. 14~16행 하나라도 모자라면 실패한 SKU만 적어 두고 루프를 빠져나옵니다. 여기서 이벤트를 발행하지 않는 것이 중요합니다 — 아직 with uow: 안이기 때문입니다.
  4. 18~22행 롤백합니다. 이미 확보한 다른 SKU의 예약도 함께 풀립니다. 그리고 내보낼 이벤트를 만들어 두기만 합니다. 품절 뒤에 주문이 어떻게 되는지는 화면 10입니다.
  5. 24~30행 성공 경로입니다. 5장 화면 10에 있던 계산과 똑같습니다 — 이제 이 핸들러 안에 있을 뿐입니다.
  6. 32행 성공이든 실패든 with uow: 블록을 나온 뒤 한 자리에서 발행합니다. 화면 5의 규칙 그대로 — 커밋(또는 롤백)이 실제로 끝난 뒤에만 이벤트가 나갑니다.
    이벤트를 만드는 곳과 보내는 곳을 나눠 두면, 두 갈래 중 어느 쪽으로 가든 발행은 반드시 블록 밖에서 일어납니다 — 규칙을 어길 자리가 코드에 아예 없습니다. "조심해서 지키는 규칙"보다 "어길 수 없게 만든 구조"가 낫다는 것은 3장부터 계속 같은 이야기입니다.

① 메일이 안 가도 아무도 모른다. notify_customer가 실패하면 그 사실은 로그에만 남고 아무도 재시도하지 않습니다(지금 구현 기준). 달라진 것은 이제 이 트레이드오프를 의도적으로 골랐다는 점입니다 — 주문 성공이 메일 성공에 발목 잡히는 것보다는 낫다고 판단했기 때문입니다.

InventoryItem.delay()는 3장에 이미 있던 메서드입니다. 7장에서 한 줄이 늘었습니다 — 지연됐다는 사실을 이벤트로 남깁니다.

InventoryItem도 Order와 같은 방식(화면 5)으로 이벤트를 모읍니다. 창고팀의 "입고 지연 등록" 화면이 이 메서드를 부르고 커밋한 뒤 발행한다고만 해 두고, 자세한 응용 서비스는 이 교재에서 다루지 않습니다 — 초점은 그다음입니다.

InboundDelayed를 받은 핸들러가 할 일은 명확합니다 — "이 배치로 이미 약속을 받은 주문들을 찾아 약속을 고친다." 그런데 재고는 3장에서 정한 규칙대로 어느 주문이 자기를 기다리는지 모릅니다. 참조가 ID로만, 한 방향(주문 → 재고)이기 때문입니다.

답은 응용 계층의 조회입니다. Allocation.lines의 각 AllocationLine에는 batch_id가 들어 있고(3장 화면 14), Order.allocation은 그것을 SKU별로 담은 dict[str, Allocation]입니다(5장 화면 10). 그러니 "이 SKU, 이 배치로 할당받은 주문들"을 리포지토리에 물어볼 수 있습니다.

class OrderRepository(Protocol):

4장 화면 6이 OrderLineRepository를 만들지 말라고 한 것과 같은 규칙을 건드리는 것처럼 보일 수 있습니다. 그렇지 않습니다. OrderLineRepository가 위험했던 이유는 내부 엔티티에 직접 쓰는 경로를 열어서였습니다(line_repo.update_quantity(...)가 Order._ensure_modifiable()를 건너뛰던 것). find_by_allocation은 조건으로 걸러 찾을 뿐, 돌려주는 것은 항상 Order 전체입니다. 변경은 반드시 order.repromise()를 통해서만 일어납니다 — 내부를 우회하는 길이 없습니다.

# application/handlers.pydef repromise_delayed_orders(event: InboundDelayed, uow: UnitOfWork,
                              shipping: ShippingPolicy, bus: MessageBus) -> None:
    with uow:
        orders = uow.orders.find_by_allocation(event.sku, event.batch_id)  # 1
        changed: list[Order] = []

        for order in orders:
            other = [a.ready_on for sku, a in order.allocation.items()      # 2
                     if sku != event.sku]
            new_ship_on = max([event.new_eta] + other)
            if new_ship_on == order.promise.ship_on:                        # 3
                continue
            order.repromise(
                Promise(ship_on=new_ship_on,
                        arrive_by=new_ship_on + shipping.lead_time,
                        promised_at=datetime.now()),
                reason=f"{event.sku} 배치 입고 지연"
                       f"({event.old_eta}→{event.new_eta})")                 # 4
            changed.append(order)

        uow.commit()
        events = [e for o in changed for e in o.pull_events()]
    bus.publish(events)                                                     # 5
  1. 4행 영향받는 주문 전부를 한 번에 가져옵니다 — 배치 하나가 늦어지면 그 배치로 할당받은 주문이 여러 건일 수 있습니다.
  2. 8~9행 이 주문의 다른 SKU 라인들이 이미 확보한 날짜도 함께 봅니다. 지연된 배치가 이 주문의 유일한 병목이 아닐 수도 있기 때문입니다.
    단순화한 부분: 실제로는 이 배치가 그 SKU 라인의 유일한 근거가 아닐 수도 있습니다(다른 배치와 나눠 할당됐을 수 있음). 여기서는 "이 배치가 그 라인의 유일한 근거"라고 가정합니다 — 완전한 재계산은 재할당 로직 자체를 다시 돌려야 하고, 그러면서 생기는 동시성 문제는 12장의 몫입니다.
  3. 10~12행 다른 SKU가 이미 더 늦은 날짜로 잡혀 있었다면, 이번 지연이 주문 전체의 약속일을 바꾸지 않을 수도 있습니다. 그럴 때는 continue로 재조정하지 않습니다 — 안 바뀐 사실을 이벤트로 낼 이유가 없습니다.
  4. 13~18행 reason에 무엇이, 왜 바뀌었는지 사람이 읽을 수 있는 문장을 남깁니다. 3장 화면 14가 못박고 6장 화면 11이 다시 미뤄 둔 "재조정은 통지를 동반해야 한다"는 요구가 여기서 시작됩니다 — 통지문에 들어갈 문장을 도메인이 직접 만들어 이벤트에 실어 보냅니다.

3장·6장이 남긴 빚 — 갚았습니다

3장 화면 14: "repromise()는 7장에서 만듭니다." 6장 화면 11: "이 메서드의 몸통은 7장에서 만듭니다." 그런데 몸통보다 중요한 것은 왜 이름을 나눴는가였습니다. 3장 화면 14의 답은 이랬습니다 — "최초 약속은 조용히 해도 되지만 재조정은 반드시 고객 통지를 동반한다. 같은 메서드를 쓰면 통지를 빠뜨린다."

그 약속이 이제 구조로 지켜집니다. promise_delivery()는 DeliveryPromised를 내고 아무도 구독하지 않습니다(화면 5). repromise()는 PromisedDateChanged를 내고 notify_promise_change가 반드시 구독합니다. 두 행위가 다른 이벤트를 내기 때문에 "재조정했는데 통지를 안 하는" 경로가 아예 없습니다 — 통지를 빠뜨리려면 부팅 코드의 subscribe 줄을 일부러 지워야 합니다.

이것이 이벤트 연쇄입니다 — InboundDelayed → repromise_delayed_orders → PromisedDateChanged → notify_promise_change. 재고 컨텍스트에서 시작한 사건이 주문을 거쳐 고객에게 닿는데, 이 넷은 서로를 모릅니다. 그 편함의 청구서가 다음 화면입니다.

이벤트는 공짜가 아니다

화면 11의 연쇄를 다시 보면, "입고가 지연됐다"에서 "고객에게 알림이 간다"까지 코드를 눈으로 따라갈 방법이 없습니다. 어떤 핸들러가 무엇을 구독하는지는 화면 6의 부팅 코드에만 있고, 각 핸들러는 서로를 모릅니다. 이것이 이벤트의 장점(화면 6)이자 동시에 대가입니다.

부분 실행 화면 6의 try/except가 핸들러를 격리해 주는 것은 장점이지만(화면 9), 동시에 일부 핸들러만 조용히 실패하고 넘어갈 수 있다는 뜻이기도 합니다. 로그를 보지 않으면 아무도 모릅니다.

언제 이벤트가 과한가

같은 애그리게이트 안에서, 지금 당장 끝나야 하는 일이라면 그냥 메서드를 부르세요. Order.add_line()을 이벤트로 만들 이유는 없습니다 — 다른 애그리게이트도, 다른 트랜잭션도, "나중"도 없기 때문입니다. 이벤트가 필요한 조건은 오히려 명확합니다 — 다른 애그리게이트가 관련되거나, 트랜잭션 경계를 넘거나, "지금 당장"이 아니어도 되는 일일 때입니다. 이 장의 두 시나리오(재고 할당, 입고 지연)가 모두 이 조건을 만족했습니다.

만족하지 못한 예도 하나 있습니다. 4장 화면 11의 빚 표는 "재고가 '주문이 취소됐다'는 사실을 알아야 release()를 부를 수 있고, 그 전달 장치가 도메인 이벤트"라며 7장을 가리켰습니다. 그런데 이 장은 OrderCancelled를 만들지 않았습니다. 5장 화면 12에서 이미 확인했기 때문입니다 — cancel_order()는 한 응용 서비스가 두 리포지토리를 같은 트랜잭션에서 쥐고 "지금 당장" 끝내는 일이라, 이벤트가 풀어 줄 문제가 없습니다. 만들었다면 위 표의 대가 셋을 치르기만 하고 얻는 것은 없었을 것입니다.

4장이 미룬 답은 "이벤트를 만든다"가 아니라 "이 자리에는 이벤트가 필요 없다"였습니다. 빚을 갚는 방법에는 이런 것도 있습니다.

7장 마무리

핵심 요약

  1. 도메인 이벤트는 애그리게이트 안에서 일어난 이미 확정된 사실입니다. 이름은 과거형이고, 구독자는 "할지 말지"가 아니라 "어떻게 반응할지"만 정합니다.
  2. 애그리게이트는 이벤트를 events에 모으기만 합니다. 발행은 응용 계층이 커밋에 성공한 뒤 pull_events()로 꺼내 bus.publish()로 합니다 — 롤백된 트랜잭션의 이벤트가 나가는 사고를 막습니다.
  3. MessageBus는 이벤트 타입마다 핸들러 여러 개를 구독시키고, 발행 시 각각을 예외 격리해 호출합니다. 재고 할당·메일·슬랙 알림이 서로 몰라도 되게 만듭니다.
  4. 실패도 다루는 방식이 다릅니다 — 품절은 사람에게 넘기고(12장에서 본격적으로), 입고 지연은 리포지토리 조회로 영향받는 주문을 찾아 repromise()로 이어집니다.
  5. 이벤트는 흐름 추적 불가·순서 미보장·부분 실행이라는 대가가 있습니다. 같은 애그리게이트 안에서 지금 끝나는 일에는 그냥 메서드를 부릅니다 — 4장이 7장 몫으로 미뤄 둔 OrderCancelled를 끝내 만들지 않은 이유입니다(화면 12).
  6. 이 장이 바꾼 것은 구조이지 타이밍이 아닙니다. publish()가 아직 동기라, 1장이 말한 "메일 서버가 느리면 응답도 느리다"는 그대로 남아 있습니다 — 이벤트로 쪼개는 것과 비동기로 만드는 것은 다른 일입니다(화면 9).

이벤트 이름을 PromiseDelivery가 아니라 DeliveryPromised처럼 과거형으로 짓는 가장 근본적인 이유는 무엇일까요?

  1. 이미 일어난 사실임을 드러내, 구독자가 "할지 말지"를 판단할 권한이 없다는 것을 이름으로 표현하기 위해서
  2. 파이썬 命명 관례상 이벤트 클래스는 과거형으로 쓰는 것이 표준이라서
  3. MessageBus가 과거형 이름만 구독을 허용하도록 구현돼 있어서
  4. 이벤트는 커맨드보다 필드 수가 적어야 하기 때문에

해설 화면 4의 표에서 본 "받는 대상"·"거부할 수 있나"의 차이가 이름에 그대로 반영됩니다. OrderPlaced를 받은 allocate_stock이 재고가 없어 실패할 수는 있어도, "그 주문이 생성됐다는 사실 자체"를 되돌릴 수는 없습니다.

place_order()가 with uow: 블록 밖에서 bus.publish(events)를 호출하는 이유는 무엇일까요?

  1. 블록 밖에서 호출해야 실행 속도가 더 빠르기 때문에
  2. 커밋 전에 발행하면, 트랜잭션이 롤백돼도 이미 나간 이벤트는 취소할 수 없기 때문에
  3. with uow: 블록 안에서는 이벤트 객체 자체가 아직 생성되지 않았기 때문에
  4. MessageBus는 UnitOfWork 블록 안에서 호출할 수 없게 구현돼 있어서

해설 화면 5에서 세운 규칙 — "애그리게이트는 모으기만, 발행은 커밋 후" — 이 여기서 실제로 지켜지는 자리입니다. 화면 8의 allocate_stock도 같은 자리(with uow: 블록 밖)에서 발행합니다.

OrderRepository.find_by_allocation(sku, batch_id)이 4장 화면 6이 금지한 OrderLineRepository와 근본적으로 다른 이유는 무엇일까요?

  1. 어떤 조건으로 찾든 항상 애그리게이트 루트 전체를 돌려주고, 변경은 그 루트의 메서드를 통해서만 일어나기 때문에
  2. SQL 인덱스를 타서 OrderLineRepository보다 조회 성능이 항상 더 좋기 때문에
  3. 사실상 같은 위험을 갖고 있고, 이름만 더 안전하게 지은 것일 뿐이다
  4. 조회 전용 메서드라서, 어떤 기준으로 찾아 오든 리포지토리에 추가해도 항상 안전하기 때문에

해설 "쓰기 경로를 내부 엔티티로 열지 않는다"는 4장의 규칙은 조회에도 그대로 적용됩니다 — 다만 기준은 "조회냐 아니냐"가 아니라 "돌려주는 것이 루트 전체이고, 바꾸는 길이 루트의 메서드뿐이냐"입니다. 화면 11의 상자 "누가 대신 아는가 — 리포지토리 조회"를 다시 보면 이 구분이 명확합니다.

새 요구사항 — "품절됐던 주문도, 나중에 재고가 다시 들어오면 자동으로 재할당을 시도한다." 재고 컨텍스트에 StockReplenished(sku)라는 이벤트가 이미 있다고 가정하고, 이 이벤트를 구독해 재시도하는 핸들러 retry_allocation을 설계해 보세요.

  • StockReplenished에는 sku만 있습니다. "어느 주문을 다시 시도할지"는 어떻게 찾을 건가요?
  • 이 핸들러가 같은 이벤트를 두 번 받아도(메시지 큐는 중복 전달을 완전히 막지 못합니다) 안전하려면 무엇을 먼저 확인해야 할까요?
모범답안 
def retry_allocation(event: "StockReplenished", uow: UnitOfWork,
                      expiry: ExpiryBufferPolicy, shipping: ShippingPolicy,
                      bus: MessageBus) -> None:
    with uow:
        waiting = uow.orders.find_waiting_for(event.sku)          # 1
        changed: list[Order] = []

        for order in waiting:
            if order.promise is not None:                          # 2
                continue
            item = uow.inventory.get(event.sku)
            qty = next(l.quantity.value for l in order.lines
                       if l.sku == event.sku)
            try:
                allocation = item.allocate(
                    qty, date.today(), buffer_days=expiry.buffer_days(event.sku))
            except InsufficientStock:
                continue                                            # 3
            order.allocation = {**order.allocation, event.sku: allocation}
            if len(order.allocation) < len(order.lines):             # 4
                continue
            ready_on = max(a.ready_on for a in order.allocation.values())
            order.promise_delivery(Promise(
                ship_on=ready_on, arrive_by=ready_on + shipping.lead_time,
                promised_at=datetime.now()))
            changed.append(order)

        uow.commit()
        events = [e for o in changed for e in o.pull_events()]
    bus.publish(events)
  1. 5행 find_by_allocation과 같은 모양의 새 조회 메서드가 하나 더 필요합니다 — "이 SKU를 주문했지만 아직 할당받지 못한 주문들." OrderRepository에 목적별 조회 메서드가 늘어나는 것은 자연스럽습니다. 다만 항상 루트 전체를 돌려준다는 원칙은 그대로입니다.
  2. 9~10행 이게 멱등성의 핵심입니다. 이미 promise가 있다는 것은 다른 경로(예: 다른 StockReplenished 메시지의 중복 전달)로 이미 처리됐다는 뜻입니다. 이 확인이 없으면 같은 이벤트가 두 번 오는 순간 같은 수량을 두 번 예약하려 듭니다.
  3. 17~18행 재시도해도 여전히 모자라면 조용히 넘어갑니다 — 다음 StockReplenished를 기다립니다. 여기서 실패를 다시 이벤트로 낼지는 판단이 필요합니다 (매번 OutOfStock을 또 내면 화면 10의 CS 알림이 반복되어 소음이 될 수 있습니다).
  4. 19~21행 아직 못 채운 라인이 남았으면 약속을 미룹니다. 화면 8에서 품절로 롤백된 주문은 allocation이 통째로 비어 있습니다. SKU가 셋인 주문에 그중 하나만 다시 들어오면 나머지 둘은 여전히 할당이 없는데, 이 검사가 없으면 채우지도 못한 주문에 출고일을 약속하게 됩니다 — I21("전량이 확보되는 날")이 깨집니다.
    확보한 예약 자체는 커밋해 둡니다(다음 입고를 기다리는 동안 남이 가져가면 안 되니까). 미루는 것은 약속뿐입니다.

흔히 놓치는 것 — StockReplenished 하나가 오면 그 SKU를 기다리는 주문이 여러 건일 수 있는데, 재고가 그 전부를 채우기에 부족할 수 있습니다. 위 코드는 find_waiting_for가 돌려준 순서대로(보통 오래 기다린 주문부터) 처리하므로 먼저 온 주문이 먼저 재할당받습니다 — 이 자체가 업무 규칙(선입선출)이라는 점을 의식하고 있어야 합니다.

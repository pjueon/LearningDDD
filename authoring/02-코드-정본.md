# 코드 정본 (저자용)

교재 본문에 나오는 클래스·메서드 시그니처의 **단일 진실 원천**. 각 장을 쓸 때 이 파일을 기준으로
쓰고, 장을 쓰다가 시그니처를 바꿔야 한다면 **먼저 이 파일을 고친 뒤** 앞장의 해당 페이지도 함께
수정한다. 독자용 문서가 아니다.

체크포인트: 3장 후 / 5장 후 / 7장 후 / 9장 후.

공통 규칙
- 값 객체는 `@dataclass(frozen=True)`, 엔티티는 일반 클래스 + 명시적 `__eq__`(식별자 기준).
- 도메인 코드는 표준 라이브러리만 쓴다(`dataclasses`, `datetime`, `decimal`, `enum`, `uuid`, `typing`).
- 예외는 도메인 예외를 만든다: `DomainError` 를 루트로 3장에서 다섯 개를 정의한다 —
  `OrderCannotBeModified`(I4), `EmptyOrder`(I1), `LineNotFound`, `AlreadyShipped`(I5),
  `InsufficientStock`(할당 실패).
- **1~8장 전제(9장에서 깨짐)**: 상품 1개 = SKU 1개. 따라서 `InventoryItem.sku` 는
  `Product.id` 와 같은 값을 쓴다. 이 전제를 쓰는 페이지에는 "9장에서 다시 볼 문제" 표시.
- 통화는 KRW 고정, 소수점 없음. `Decimal` 로 보관하되 원 단위 정수만 허용.
- 배송 리드타임은 **출고 다음날부터 2일**로 고정한다(도착예정일 = 출고예정일 + 2일).
  이 값은 배송 컨텍스트의 것이므로 재고/주문 코드에 상수로 박지 않고 정책 객체로 받는다.

## 체크포인트 1 — 3장 후 (Entity / VO / Aggregate)

```python
# --- 값 객체 (2장) ---
class DomainError(Exception): ...       # 모든 도메인 예외의 루트

@dataclass(frozen=True, order=True)     # order=True: 필드가 amount 하나라 금액 비교가 된다
class Money:
    amount: Decimal                     # 원 단위, 음수 허용 안 함(할인은 별도 표현)
    ZERO: ClassVar["Money"]             # 클래스 정의 후 Money.ZERO = Money.won(0)

    def __add__(self, other: "Money") -> "Money": ...
    def __sub__(self, other: "Money") -> "Money": ...   # 음수가 되면 DomainError
    def __mul__(self, count: int) -> "Money": ...       # int 만. Money * Money 는 TypeError
    def percent(self, rate: Decimal) -> "Money": ...    # 원 단위 미만 버림(ROUND_DOWN)
    def distribute(self, weights: Sequence["Money"]) -> list["Money"]: ...
    def __str__(self) -> str: ...                       # "21,000원"
    @classmethod
    def won(cls, amount: int) -> "Money": ...

# distribute: 버림으로 나눈 뒤 잔액을 앞에서부터 1원씩 배분한다. 합이 항상 보존된다.
# 반올림 정책(percent)과 배분 정책(distribute)은 여기 한 곳에만 있어야 한다.

@dataclass(frozen=True)
class Amounts:                          # 세 금액을 함께 다니게 묶은 값 객체
    subtotal: Money
    discount: Money
    shipping_fee: Money
    @property
    def total(self) -> Money: ...       # subtotal - discount + shipping_fee (I2)

@dataclass(frozen=True, order=True)
class Quantity:
    value: int                          # 1 이상 (I3). bool 은 거부한다
    def __add__(self, other: "Quantity") -> "Quantity": ...

@dataclass(frozen=True)
class Address:
    zipcode: str                        # 5자리 숫자만 허용
    road: str
    detail: str
    receiver: str
    phone: str                          # 지금은 검증하지 않는다(요구가 오면 값 객체로 분리)

@dataclass(frozen=True)
class OrderNumber:
    value: str                          # "20260907-000123" (r"\d{8}-\d{6}")
    @classmethod
    def issue(cls, today: date, seq: int) -> "OrderNumber": ...

# --- 열거형 (2장). 값 객체의 특별한 형태 ---
class SaleStatus(Enum):                 # 카탈로그 컨텍스트 (I17)
    판매중 = auto(); 판매중지 = auto()

class MemberGrade(Enum):                # 멤버가 자기 규칙을 들고 있다
    일반 = (Decimal("0"), False)
    실버 = (Decimal("0.03"), False)
    골드 = (Decimal("0.05"), True)
    def __init__(self, discount_rate: Decimal, free_shipping: bool) -> None: ...

# 할인율을 코드에 박아둔 상태. 프로모션 요구가 오면 6장 DiscountPolicy 로 옮긴다.

# --- 주문 애그리게이트 (3장) ---
class OrderStatus(Enum):
    생성됨 = auto(); 결제대기 = auto(); 결제완료 = auto()
    출고준비 = auto(); 출고됨 = auto(); 배송완료 = auto(); 취소됨 = auto()

class OrderLine:                        # 내부 엔티티. 외부에서 직접 생성하지 않는다
    line_id: UUID
    sku: str                            # 1~8장: Product.id 와 동일 (9장에서 분리)
    product_name: str                   # 주문 시점 스냅샷 (I6)
    unit_price: Money                   # 주문 시점 스냅샷 (I6)
    quantity: Quantity
    @property
    def subtotal(self) -> Money: ...

# 약속일은 라인이 아니라 주문 단위다. 분할 출고를 하지 않으므로 주문 전체가 한 날짜를 약속한다.
@dataclass(frozen=True)
class Promise:                          # 값 객체 (I22)
    ship_on: date                       # 출고 예정일 = 할당 결과의 ready_on
    arrive_by: date                     # 도착 예정일 = ship_on + 배송 리드타임
    promised_at: datetime               # 언제 약속했는지. 재조정 이력의 기준

class Order:                            # 애그리게이트 루트
    order_number: OrderNumber
    customer_id: UUID
    shipping_address: Address
    status: OrderStatus
    lines: tuple[OrderLine, ...]        # 외부에는 읽기 전용으로만 노출
    discount: Money
    shipping_fee: Money

    # 3장에서 노출하는 행위
    def add_line(self, sku: str, product_name: str,
                 unit_price: Money, quantity: Quantity) -> None: ...   # I4 검사
    def change_quantity(self, line_id: UUID, quantity: Quantity) -> None: ...
    def remove_line(self, line_id: UUID) -> None: ...                  # I1 검사
    def cancel(self) -> None: ...                                      # I5 검사
    @property
    def amounts(self) -> Amounts: ...   # 라인에서 subtotal 을 계산해 Amounts 로 묶는다
    @property
    def total_amount(self) -> Money: ...                               # I2 (= amounts.total)

    # 약속일 (3장 후반에 추가)
    promise: Promise | None             # 할당 전에는 None
    def promise_delivery(self, promise: Promise) -> None: ...          # I22. 최초 약속
    def repromise(self, promise: Promise, reason: str) -> None: ...    # 7장. 명시적 재조정

# --- 재고 애그리게이트 (3장) ---
class BatchKind(Enum):
    창고 = auto()        # 입고 완료. received_on 있음, eta 없음 (I18)
    입고예정 = auto()     # 아직 안 들어옴. eta 있음, received_on 없음 (I18)

class StockBatch:                       # 내부 엔티티
    batch_id: UUID
    kind: BatchKind
    received_on: date | None            # 창고 배치만 값이 있다
    eta: date | None                    # 입고예정 배치만 값이 있다
    expires_on: date | None
    quantity: int
    reserved: int                       # 이 배치에서 예약된 수량
    @property
    def available(self) -> int: ...     # quantity - reserved (I7, I8)

class InventoryItem:                    # 애그리게이트 루트, SKU 단위
    sku: str
    batches: tuple[StockBatch, ...]

    # 입고 흐름
    def expect(self, quantity: int, eta: date,
               expires_on: date | None) -> None: ...        # 입고예정 등록
    def arrive(self, batch_id: UUID, received_on: date) -> None: ...  # 예정 → 창고
    def delay(self, batch_id: UUID, new_eta: date) -> None: ...       # 입고 지연
    def receive(self, quantity: int, received_on: date,
                expires_on: date | None) -> None: ...        # 예정 없이 바로 입고

    # 할당
    def allocate(self, quantity: int, as_of: date) -> "Allocation": ...  # I19~I21
    def release(self, allocation: "Allocation") -> None: ...  # 취소 시 예약 해제

    @property
    def on_hand_quantity(self) -> int: ...      # 실물재고: 창고 배치의 quantity 합
    @property
    def available_quantity(self) -> int: ...    # 가용재고: 창고 배치만 (I7)
    @property
    def sellable_quantity(self) -> int: ...     # 판매가능수량 ATP: 가용 + 입고예정 잔량 (I20)

@dataclass(frozen=True)
class Allocation:                       # allocate() 의 반환값. 값 객체다
    lines: tuple["AllocationLine", ...]
    ready_on: date                      # 전량 확보되는 날 (I21). 분할 출고 안 함

@dataclass(frozen=True)
class AllocationLine:
    batch_id: UUID
    quantity: int
```

**`allocate` 는 값을 돌려준다.** 3장의 첫 판에서는 반환값이 없었지만, "입고 예정 물건도 판다"는
요구사항이 들어오면 호출자가 **언제 출고할 수 있는지** 알아야 한다. 그렇다고 주문이 `StockBatch` 를
참조하게 두면 "애그리게이트 간 참조는 ID로만" 규칙이 깨진다. 그래서 **엔티티가 아니라 값 객체
`Allocation` 을 반환**한다. 주문은 이 값에서 `ready_on` 만 꺼내 자기 안에 적어둔다.

`ready_on` 계산: 할당된 배치들의 기준일 중 가장 늦은 날. 창고 배치의 기준일은 `as_of`(오늘),
입고예정 배치의 기준일은 `eta`. 실패는 `InsufficientStock` 예외 — **ATP 기준으로도 모자랄 때만**
실패다.

## 체크포인트 2 — 5장 후 (Repository / Application Service)

```python
# --- 4장: Order 에 추가되는 것 ---
class Order:
    @property
    def order_number(self) -> OrderNumber: ...   # 3장은 self._order_number 로만 저장, 읽기 전용 접근자가 없었다
    allocation: dict[str, Allocation]             # __init__ 에서 {}. SKU 를 키로 담는다(5장) —
                                                   # release() 에 되돌려줄 때 각 SKU 의 InventoryItem 에
                                                   # 그 SKU의 할당분만 넘겨야 한다(release() 는 자기 배치가
                                                   # 아닌 batch_id 를 만나면 DomainError 를 던진다)

# --- 4장: 도메인 예외 추가 ---
class OrderNotFound(DomainError): ...       # OrderRepository.get()
class InventoryNotFound(DomainError): ...   # InventoryRepository.get()

# --- 4장: 포트(인터페이스) ---
class OrderRepository(Protocol):
    def get(self, order_number: OrderNumber) -> Order: ...      # 없으면 OrderNotFound
    def add(self, order: Order) -> None: ...
    def next_order_number(self, today: date) -> OrderNumber: ...

class InventoryRepository(Protocol):
    def get(self, sku: str) -> InventoryItem: ...        # 없으면 InventoryNotFound
    def get_many(self, skus: Sequence[str]) -> dict[str, InventoryItem]: ...

# 이미 있는 애그리게이트의 변경은 save() 를 부르지 않고 UoW 커밋으로 반영한다.
# (4장에서 메모리 구현으로 먼저 보여주고, 5장 UoW에서 근거를 설명)

# --- 5장: Unit of Work ---
class UnitOfWork(Protocol):
    orders: OrderRepository
    inventory: InventoryRepository
    def __enter__(self) -> "UnitOfWork": ...
    def __exit__(self, *args) -> None: ...       # 예외 시 rollback
    def commit(self) -> None: ...
    def rollback(self) -> None: ...

# --- 5장: 커맨드 / DTO ---
@dataclass(frozen=True)
class PlaceOrderCommand:
    customer_id: UUID
    items: tuple["OrderItemInput", ...]
    shipping_address: Address

@dataclass(frozen=True)
class OrderItemInput:
    sku: str
    quantity: int

@dataclass(frozen=True)
class OrderSummary:                # 표현 계층으로 나가는 읽기 전용 DTO
    order_number: str
    status: str
    total_amount: int
    line_count: int

# --- 5장: 다른 컨텍스트를 향한 포트 (10장에서 이 관계의 이름을 정한다) ---
@dataclass(frozen=True)
class OrderItemSnapshot:            # 카탈로그에서 복사해 온 값 (I6)
    sku: str
    product_name: str
    unit_price: Money
    quantity: Quantity

class CatalogPort(Protocol):
    # 여러 항목을 한 번에 스냅샷한다. 항목마다 왕복하지 않는다.
    def snapshot(self, items: Sequence[OrderItemInput]) -> Sequence[OrderItemSnapshot]: ...

class MembershipPort(Protocol):
    def grade_of(self, customer_id: UUID) -> "MemberGrade": ...
    def name_of(self, customer_id: UUID) -> str: ...   # 5장 페이지 8, 회원 이름 조회(DTO 조립용)

# --- 5장: 배송 컨텍스트를 향한 포트 ---
class ShippingPolicy(Protocol):
    lead_time: timedelta            # 출고 후 도착까지. 3장 페이지 14가 "정책 객체로 받는다"고
                                     # 못박은 값 — 주문/재고 코드에 상수로 두지 않는다

# --- 5장: 응용 서비스 ---
class OrderingService:
    def __init__(self, uow: UnitOfWork, catalog: CatalogPort,
                 members: MembershipPort, shipping: ShippingPolicy) -> None: ...
    def place_order(self, cmd: PlaceOrderCommand) -> OrderNumber: ...
    def cancel_order(self, order_number: OrderNumber) -> None: ...
```

`PlaceOrderCommand` 에는 **등급을 넣지 않는다.** 등급은 클라이언트가 보내는 값이 아니라
회원 컨텍스트에 물어볼 값이다. 응용 서비스가 `members.grade_of()` 로 조회한다.

`shipping: ShippingPolicy`는 5장에서만 이 자리에 있다. 7장에서 재고 할당이 이벤트
핸들러로 옮겨가면 `lead_time`이 필요한 코드도 함께 옮겨가고, 이 생성자에서는 빠진다
(체크포인트 3의 6개 인자 — `uow`·`catalog`·`members`·`fee_policy`·`discount_policy`·`bus` —
에 `shipping`이 없는 이유다).

## 체크포인트 3 — 7장 후 (Domain Service / Factory / Domain Event)

```python
# --- 6장: 도메인 서비스 ---
class ShippingFeePolicy(Protocol):
    def calculate(self, items: Sequence[OrderItemSnapshot],
                  address: Address, grade: "MemberGrade") -> Money: ...

class DiscountPolicy(Protocol):
    def calculate(self, items: Sequence[OrderItemSnapshot],
                  grade: "MemberGrade") -> Money: ...

# --- 6장: 팩토리. 3장의 생성자 직접 호출을 이걸로 대체한다 ---
# OrderItemSnapshot 은 5장에서 이미 정의됨 (체크포인트 2). 여기서는 재사용만 한다.
class Order:
    @classmethod
    def place(cls, order_number: OrderNumber, customer_id: UUID,
              address: Address, items: Sequence[OrderItemSnapshot],
              shipping_fee: Money, discount: Money) -> "Order": ...
    # items 가 비어 있으면 EmptyOrder(I1). 생성 시점에 지킬 불변식을 한 자리에 모은다

# --- 7장: 도메인 이벤트 ---
@dataclass(frozen=True)
class DomainEvent:
    occurred_at: datetime

@dataclass(frozen=True)
class OrderPlaced(DomainEvent):
    order_number: str
    customer_id: UUID
    items: tuple[tuple[str, int], ...]   # (sku, quantity)

@dataclass(frozen=True)
class DeliveryPromised(DomainEvent):    # Order.promise_delivery() 가 낸다.
    order_number: str                   # 7장 시점엔 구독자가 없었다. 12장부터 approve_payment가 구독한다

@dataclass(frozen=True)
class OutOfStock(DomainEvent):
    order_number: str
    sku: str

@dataclass(frozen=True)
class InboundDelayed(DomainEvent):      # 재고 컨텍스트가 발생시킨다
    sku: str
    batch_id: UUID
    old_eta: date
    new_eta: date

@dataclass(frozen=True)
class PromisedDateChanged(DomainEvent): # 주문이 발생시킨다. 고객 통지로 이어진다
    order_number: str
    old_ship_on: date
    new_ship_on: date
    reason: str

# 애그리게이트는 이벤트를 모아만 둔다. 발행은 응용 계층(UoW 커밋 후).
class Order:
    events: list[DomainEvent]            # 7장에서 추가되는 필드
    def pull_events(self) -> list[DomainEvent]: ...

# InventoryItem도 같은 방식으로 이벤트를 모은다 — InboundDelayed는 재고 컨텍스트가
# 발생시키므로(체크포인트 3 상단 주석), 재고도 Order와 동일한 모양의 events/pull_events()가 있어야 한다
class InventoryItem:
    events: list[DomainEvent]            # 7장에서 추가되는 필드
    def pull_events(self) -> list[DomainEvent]: ...
    def delay(self, batch_id: UUID, new_eta: date) -> None: ...
    # delay() 는 배치의 eta 를 바꾼 뒤 InboundDelayed 를 events 에 append 한다(3장 시점엔 없던 동작)

class MessageBus:
    def subscribe(self, event_type: type[DomainEvent],
                  handler: Callable[[DomainEvent], None]) -> None: ...
    def publish(self, events: Sequence[DomainEvent]) -> None: ...

# --- 7장 시점의 응용 서비스 완성형. 1장 페이지 16의 미리보기가 이 코드다 ---
class OrderingService:
    def __init__(self, uow: UnitOfWork, catalog: CatalogPort,
                 members: MembershipPort, fee_policy: ShippingFeePolicy,
                 discount_policy: DiscountPolicy, bus: MessageBus) -> None: ...

    def place_order(self, cmd: PlaceOrderCommand) -> OrderNumber:
        # 1) 스냅샷/등급 조회  2) Order.place()  3) add + commit  4) 이벤트 발행
        ...
```

7장에서 `place_order` 는 커밋 후 `events = order.pull_events()` 로 꺼내 두고, `with` 블록을 나온 뒤
`bus.publish(events)` 를 호출하는 형태로 바뀐다(발행은 언제나 블록 밖 한 자리에서).
**5장 코드가 7장에서 어떻게 바뀌는지 diff를 화면으로 보여준다.**

```python
# --- 7장: 유통기한 여유 규칙을 정책으로 (3장 페이지 9가 미룬 문제) ---
class ExpiryBufferPolicy(Protocol):
    def buffer_days(self, sku: str) -> int: ...

class CategoryExpiryBufferPolicy:           # 구현. SKU→분류→여유일수는 인프라가 안다
    def __init__(self, days_by_sku: dict[str, int], default: int = 0) -> None: ...
    def buffer_days(self, sku: str) -> int: ...

# InventoryItem.allocate 시그니처 확장. 3장의 호출부(allocate(quantity, as_of))는
# 그대로 둔다 — buffer_days 는 기본값 0이라, 3장 시점 코드는 고치지 않아도 계속 유효하다.
class InventoryItem:
    def _candidates(self, as_of: date,
                    buffer_days: int = 0) -> list[StockBatch]: ...
    def allocate(self, quantity: int, as_of: date,
                 buffer_days: int = 0) -> "Allocation": ...
    # 조건이 붙는 자리는 _candidates 다(3장 페이지 12가 후보 선정을 그리로 모아 뒀다).
    #   expires_on is None or expires_on > as_of + timedelta(days=buffer_days)
    # 정렬(I19: 창고 배치 먼저 → FEFO, 그다음 입고예정을 ETA 순)은 건드리지 않는다.
    # allocate 는 buffer_days 를 _candidates 로 넘기기만 한다.

# --- 7장: 재고 컨텍스트가 주문 컨텍스트에 "누가 나를 기다리는가"를 되묻는 통로 ---
class OrderRepository(Protocol):
    def get(self, order_number: OrderNumber) -> Order: ...
    def add(self, order: Order) -> None: ...
    def next_order_number(self, today: date) -> OrderNumber: ...
    def find_by_allocation(self, sku: str, batch_id: UUID) -> Sequence[Order]: ...  # 7장
```

`find_by_allocation`은 애그리게이트 **단위**(전체 `Order`)를 돌려준다 — 4장 페이지 6이 금지한
것은 `OrderLineRepository`처럼 내부 엔티티에 **직접 쓰기 경로**를 여는 것이지, 조건으로
루트를 찾아오는 조회가 아니다. 핸들러는 돌려받은 `Order`의 `repromise()`(루트의 메서드)만
부른다 — 내부를 우회해 고치지 않는다.

## 체크포인트 4 — 9장 후 (Bounded Context 분리)

`Product` 가 세 개로 쪼개지고, 모듈 구조가 컨텍스트별로 재편된다.

```python
# catalog/  — 무엇을 파는가
class Product:                     # 애그리게이트 루트
    product_id: UUID
    name: str
    price: Money                   # I16
    status: SaleStatus             # 판매중 / 판매중지 (I17)
    composition: tuple["ProductSku", ...]   # 상품 1개가 여러 SKU로 구성될 수 있다

@dataclass(frozen=True)
class ProductSku:
    sku: str
    quantity_per_product: int      # 3개 묶음 세트면 3
    unit_price: Money              # 이 상품 안에서 SKU 1개를 얼마로 치는가 (수량 × 단가의 합 = Product.price)

# inventory/  — 몇 개 팔 수 있는가
class Sku:                         # 재고 컨텍스트가 아는 "품목". 판매가를 모른다
    sku: str
    name: str                      # 재고 담당자가 쓰는 이름(카탈로그 상품명과 다를 수 있다)
    manages_expiry: bool
class InventoryItem: ...           # 체크포인트 1과 동일

# warehouse/  — 어느 랙에 있는가
class StoredItem:
    sku: str
    location: "Location"
    quantity: int

# ordering/  — 카탈로그를 직접 참조하지 않는다.
# CatalogPort 시그니처는 체크포인트 2와 같다. 달라지는 것은 구현이다:
# 9장 이후의 구현은 Product.composition 을 펼쳐 SKU 라인들로 변환하며, 각 라인의 단가는
# ProductSku.unit_price(카탈로그가 상품 판매가를 SKU별로 나눠 둔 값, 수량 × 단가의 합 = 판매가)를 쓴다.
# 상품은 _load_products 로 한 번에 조회한다.
```

`OrderLine.sku` 는 9장 이후에도 `sku` 문자열을 그대로 쓴다(주문은 SKU 단위로 기록).
바뀌는 것은 **"그 sku를 어디서 얻는가"** — 이전에는 `Product.id`, 이후에는
`CatalogPort.snapshot()` 이 상품 구성을 펼쳐 SKU 라인들로 변환해 준다.

**`InventoryItem`은 체크포인트 1과 완전히 동일하다 — 필드도, `on_hand_quantity`/
`available_quantity`/`sellable_quantity` 세 프로퍼티도 하나도 옮기지 않는다.**
3장 페이지 13이 "9장에서 이 임시 구분을 뜯는다"고 예고했지만, 실제로 뜯을 것은 이 세 계산이
아니다 — 셋 다 재고 컨텍스트 **한 곳**의 장부(배치의 수량·예약)에서 나오는 값이라
쪼갤 이유가 없다(가용재고는 도현 팀 안에서도 피킹 담당이 쓰고, 실물재고는 실사 담당이
쓴다 — 사용자가 창고 쪽 사람이라고 해서 그 계산의 소유권이 창고 컨텍스트로 넘어가는
것은 아니다). 9장이 실제로 뜯는 것은 **애초에 `InventoryItem`에 없었던 것** —
도현이 피킹하려면 필요한 "그 수량이 어느 랙에 있는가"라는 위치 정보다. 그건 세
프로퍼티 중 어느 것도 답하지 못했다. 그래서 창고 컨텍스트에 `StoredItem`을
**새로** 둔다. `StoredItem.quantity`는 `InventoryItem.on_hand_quantity`에서
잘라 옮긴 값이 아니라 **로케이션별 실사로 얻는, 별도로 관리되는 숫자**다 —
정상 운영 중엔 두 숫자의 합이 같아야 하지만 그 일치를 코드가 강제하지 않는다
(실사 오차가 나면 달라질 수 있고, 그 어긋남을 맞추는 것 자체가 `재고조정됨` 이벤트의
일이다 — 12장 결과적 일관성의 예고편).

`catalog/`·`inventory/`·`warehouse/`라는 폴더 구분은 **관례일 뿐 파이썬이 강제하지
않는다.** `inventory/` 코드가 `from catalog.product import Product`를 그냥 써도
문법 에러는 나지 않는다. import-linter 같은 도구를 CI에 넣어야 "카탈로그가 재고를
알아도 되지만 그 반대는 안 된다" 같은 규칙이 실제로 깨졌을 때 빌드가 실패한다.
9장 시점에는 그 도구를 넣지 않는다 — 폴더 구조와 코드 리뷰로 충분하다고 보되,
이 경계가 관례로만 지켜진다는 것은 명시해 둔다.

## 체크포인트 5 — 10장 후 (Context Map: PaymentPort와 ACL)

결제 컨텍스트에 처음으로 경계가 생긴다. 애그리게이트는 아니다 — 포트 하나와 그
구현(부패 방지 계층)뿐이다. `place_order()`·`OrderingService.__init__`에는
**아직 연결하지 않는다**(체크포인트 3의 6개 인자 그대로). 연결·롤백은 12장.

```python
# domain/payment.py
class PaymentDeclined(DomainError): ...      # PG가 승인을 거절했다
class PaymentGatewayError(DomainError): ...  # PG 자체가 응답하지 못했다(장애·타임아웃)

@dataclass(frozen=True)
class PaymentApproval:
    tid: str              # 환불 요청 때 PG에 되돌려줘야 하는 참조 키라 그대로 보관한다.
                           # 2장 페이지 11의 규칙대로 우리 쪽 무언가의 식별자로는 쓰지 않는다.
    approved_amount: Money

class PaymentPort(Protocol):    # 5장의 CatalogPort·MembershipPort와 같은 자리
    def approve(self, order_number: OrderNumber, customer_id: UUID,
                amount: Money) -> PaymentApproval: ...
    def refund(self, tid: str, amount: Money) -> None: ...

# infrastructure/payment_gateway.py
class PgPaymentAdapter:         # PaymentPort 구현. 부패 방지 계층(ACL)
    def __init__(self, client) -> None: ...
    def approve(self, order_number: OrderNumber, customer_id: UUID,
                amount: Money) -> PaymentApproval: ...
        # raw["resultCode"] == "0000" 이면 성공. 그 밖의 문자열은 raw["resultMsg"]만
        # PaymentDeclined 로 옮기고 코드 자체는 버린다. resultCode 가 아예 없으면
        # (타임아웃 등) PaymentGatewayError.
    def refund(self, tid: str, amount: Money) -> None: ...
```

`PaymentApproval`에는 `resultCode` 같은 PG 고유 필드가 없다 — 성공은 값의 존재로,
실패는 예외로 표현한다(3장이 `DomainError`를 실패 신호로 쓴 것과 같은 결).
`PgPaymentAdapter`가 이 국경의 전부다 — `resultCode`·`"0000"`이라는 리터럴은 이
클래스 밖으로 나가지 않는다.

**이 계층이 안 하는 일**: 환불 누계가 승인 금액을 넘지 않는가(I14), 애초에 승인된
결제인가(I15)를 지키는 것은 이 어댑터가 아니라 결제 애그리게이트의 일이다 — 그런데
그 애그리게이트는 아직 이 교재 어디에도 없다. 만들 때가 오면 이 체크포인트를
확장한다.

`ShippingCarrierPort`(배송→택배사 ACL)는 10장 페이지 10에서 같은 모양의 예시로만
등장하고, 배송 컨텍스트가 실제로 구현되지 않아 정본에는 추가하지 않는다.

**11장 후 — 자리 정리(시그니처 변경 없음)**: 11장이 디렉터리 구조를 확정하며 위
네 클래스를 둘로 나눠 정리했다. `PaymentPort`(포트)와 `PaymentApproval`(다른
컨텍스트에서 받아 오는 값)은 `CatalogPort`·`MembershipPort`·`OrderItemSnapshot`
(체크포인트 2)과 같은 기준 — "다른 컨텍스트에 묻거나 요청하는 포트·그 값은 응용
계층" — 으로 `application/ports.py` 자리로 간다. `PaymentDeclined`·
`PaymentGatewayError`(예외)는 그와 달리 주문 쪽 예외들(3장 다섯 개 중
`InsufficientStock`을 뺀 네 개, 4장 `OrderNotFound`)이 모이는
`ordering/domain/errors.py`로 간다 — 실패를 예외로 알리는 것은 값이 아니라
도메인 예외 계층의 일이기 때문이다. `InsufficientStock`(애그리게이트가 직접
던진다)·`InventoryNotFound`(`InventoryRepository.get()`이 던진다)는 함께
옮기지 않는다 — 재고 쪽 예외라 `inventory/domain/inventory.py`로 간다
(11장 페이지 6). 11장이 함께 확정한 `shared/`(`Money`·`DomainError`·
`DomainEvent`)와 컨텍스트별 `errors.py`·`events.py` 분리도 시그니처 변경은
없다 — 12장 이후의 코드 위치는 이 트리를 기준으로 삼는다.
클래스 이름·메서드 시그니처는 위 코드 그대로이고, 위 코드 블록의
`domain/payment.py`·`infrastructure/payment_gateway.py` 캡션도 고치지 않는다 —
바뀐 것은 "이 챕터가 어느 파일에 있다고 설명하는가"뿐이다.

## 체크포인트 6 — 12장 후 (동시성 제어와 결제 사가)

`PaymentPort`가 처음으로 `MessageBus`에 연결된다. `OrderingService.__init__`은
바뀌지 않는다 — 결제는 응용 서비스가 아니라 새 이벤트 핸들러가 담당한다.

```python
# inventory/domain/inventory.py — InventoryItem에 필드 추가
class InventoryItem:
    version: int    # __init__에서 1. allocate()·release()가 배치를 바꿀 때마다

#     version_id_col=inventory_table.c.version, version_id_generator=False)
# version_id_generator=False: SQLAlchemy가 값을 자동 생성하지 않고, 도메인이 올린
# self.version 값을 그대로 쓰고 확인만 한다.

# shared/errors.py
class ConcurrentUpdateError(DomainError):
    """다른 트랜잭션이 먼저 이 애그리게이트를 바꿨다. UnitOfWork.commit()이
    SQLAlchemy의 StaleDataError를 이 예외로 번역해 던진다. 도메인 규칙이 아니라
    포트(UnitOfWork)의 계약이 알리는 신호라, 이름은 도메인 예외 계층에 있지만

# ordering/domain/order.py — Order에 추가

    def mark_paid(self, tid: str) -> None: ...

# ordering/domain/events.py — 신설
@dataclass(frozen=True)
class PaymentFailed(DomainEvent):       # PG가 확실히 거절했다 — 보상(재고 해제 +
    order_number: str                   # 주문 취소)까지 끝난 뒤 발행한다
    reason: str

@dataclass(frozen=True)
class PaymentUncertain(DomainEvent):    # PG 장애 — 승인 여부를 모른다. 재고도
    order_number: str                   # 주문도 자동으로 건드리지 않는다
    reason: str

# ordering/application/handlers.py — 신설
def approve_payment(event: DeliveryPromised, uow: UnitOfWork,
                     payment: PaymentPort, bus: MessageBus) -> None: ...
    # DeliveryPromised를 구독. 주문을 읽어 uow 밖에서 payment.approve()를 부른다.
    #   성공 -> 새 uow에서 order.mark_paid(approval.tid)
    #   PaymentDeclined -> _compensate() 호출 (아래)
    #   PaymentGatewayError -> PaymentUncertain 발행, 아무것도 건드리지 않는다

def _compensate(uow: UnitOfWork, order_number: OrderNumber,
                 reason: str) -> list[DomainEvent]: ...
    # cancel_order()(5장 페이지 12)와 같은 모양: 한 uow 안에서 order.allocation의
    # 각 SKU를 release()하고 order.cancel()한 뒤 커밋, PaymentFailed를 돌려준다
```

`DeliveryPromised`(체크포인트 3)의 "최초 약속은 통지를 동반하지 않으므로 구독자가
없다"는 주석은 12장부터 더 이상 맞지 않는다 — `approve_payment`가 구독한다.

`OrderRepository`·`InventoryRepository`·`UnitOfWork` Protocol 자체의 메서드
시그니처는 바뀌지 않는다. `commit()`이 이제 `ConcurrentUpdateError`를 던질 수
있다는 사실만 계약에 추가된다(타입 시그니처상의 변화는 없음 — 문서화된 동작만
늘어난다).

**이 장이 코드로 만들지 않는 것**: 재시도 루프(`allocate_stock`·`_compensate`가
`ConcurrentUpdateError`를 만나면 다시 시도하는 것)는 정본에 시그니처로 남길
정도의 새 타입이 아니라 각 핸들러 본문 안의 제어 흐름이라 여기 신설 목록에는
없다 — 12장 본문 페이지 4·9 참고. `next_order_number`의 동시성은 낙관적 락이
아니라 DB 시퀀스/`UNIQUE` 제약으로 푼다는 **결정**만 남기고, 새 타입은 만들지
않는다. I21(분할 출고 불허)은 **바꾸지 않기로 결정**했으므로 `Allocation`·
`Promise`의 시그니처도 그대로다.

## 체크포인트 7 — 13장 후 (선택) — 읽기 모델

13장은 커리큘럼이 명시한 **선택 장**이다. 아래는 전부 **순수 추가**다 —
`Order`·`InventoryItem`·`Product`·`Sku`·`StoredItem` 등 기존 쓰기 모델의 필드·
메서드는 단 하나도 바뀌지 않는다. **14장은 이 체크포인트를 전제하지 않는다** —
14장을 쓸 때 이 장을 읽지 않았다고 가정하고 써도 된다.

```python
# reporting/ — 어느 컨텍스트의 domain/application 계층에도 속하지 않는,
# 오직 읽기 전용 조회만을 위한 자리. Order·InventoryItem·Product·Sku 같은
# 도메인 클래스를 import하지 않는다. 아는 것은 테이블 이름과 컬럼뿐이다.

@dataclass(frozen=True)
class ProductListingRow:            # 상품 목록 화면의 한 행
    product_id: str
    name: str
    price: int                      # 5장의 DTO 관례: Money가 아니라 원 단위 정수
    sellable_quantity: int          # I20과 같은 계산(세트 상품은 구성 SKU의 최솟값)
    ship_on: date | None            # None이면 입고 예정도 없음(품절)
    arrival_estimate: date | None   # ship_on + ShippingPolicy.lead_time. 근사치 —
                                     # 실제 약속(I22, Order.promise)과 다를 수 있다

class ProductListingQuery(Protocol):
    def list_page(self, offset: int, limit: int) -> Sequence[ProductListingRow]: ...

class SqlProductListingQuery:       # 구현. 도메인 모델을 거치지 않고 SQL로 직접 읽는다
    def __init__(self, connection, shipping: ShippingPolicy) -> None: ...
    def list_page(self, offset: int, limit: int) -> Sequence[ProductListingRow]: ...

@dataclass(frozen=True)
class OrderListingRow:              # 주문 목록 화면의 한 행. OrderSummary(5장)와
    order_number: str               # 필드가 겹치지만 합치지 않는다 — OrderSummary는
    customer_name: str               # Order 하나를 그대로 옮긴 DTO(to_summary)이고, 이 타입은
    status: str                     # 목록 조회 전용 쿼리 객체의 산출물이다
    total_amount: int
    line_count: int

class OrderListingQuery(Protocol):
    def list_for_customer(self, customer_id: UUID, offset: int,
                           limit: int) -> Sequence[OrderListingRow]: ...

class SqlOrderListingQuery:
    def __init__(self, connection) -> None: ...
    def list_for_customer(self, customer_id: UUID, offset: int,
                           limit: int) -> Sequence[OrderListingRow]: ...
```

`ShippingPolicy`(5장 정의)는 재사용만 한다 — 새로 만들지 않는다. 배송 리드타임을
상수로 박지 않는다는 3장 페이지 14의 규칙이 읽기 쪽에도 그대로 적용된다는 것을
보여주기 위해서다.

**이 장이 코드로 만들지 않는 것**: SQL 뷰(`CREATE VIEW`), 동기화되는 별도 읽기
테이블, 그 테이블을 채우는 프로젝터(이벤트 핸들러), 이벤트 저장소 — 전부 13장
페이지 6·7~8에서 "어떤 조건일 때 필요한가"만 논의하고 실제 타입·코드로 만들지
않는다. 상품 단위 판매가능수량(구성 SKU의 `atp // quantity_per_product`의
최솟값)은 어느 애그리게이트에도 없는 **새 계산**이다 — 지금은 목록 화면 표시
전용이라 읽기 쪽에 둔 것이고, 이 계산이 실제 재고 확정(쓰기)에도 쓰이게 되면
그때는 카탈로그 또는 재고 애그리게이트로 승격을 검토해야 한다(지금은 미뤄 둔 문제가
아니라 판단이다).

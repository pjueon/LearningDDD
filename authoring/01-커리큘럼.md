# DDD 학습 교재 커리큘럼 · 학습 스케줄

전제: `00-기획.md` 의 도메인 시나리오("한빛몰")와 애그리게이트/불변식 정의를 따른다.

## 1. 장 구성 원칙 — 전술적 설계를 먼저

일반적인 DDD 책(특히 Vernon의 IDDD)은 **전략적 설계(Bounded Context, 유비쿼터스 언어)를 먼저**
다룬다. 이 교재는 **거꾸로 간다.** 아키텍처를 처음 공부하는 독자에게 1장부터
"컨텍스트 경계를 나눠라"라고 하면, 나눠본 적이 없어서 왜 나누는지 알 수 없다.

그래서 순서를 이렇게 잡는다.

```
나쁜 코드의 고통 (1장)
  → 작은 객체부터 (2장 Entity/VO)
  → 객체 묶음의 경계와 규칙 (3장 Aggregate)
  → 저장하고 꺼내기 (4장 Repository)
  → 유스케이스 조립 (5장 Application Service)
  → 모델이 커질 때 (6장 Domain Service/Factory)
  → 애그리게이트끼리 대화 (7장 Domain Event)
  ↑ 여기까지 "코드를 어떻게 쓰나" = 전술적 설계
  ↓ 여기부터 "시스템을 어떻게 쪼개나" = 전략적 설계
  → 말이 안 맞는 문제 (8장 유비쿼터스 언어)
  → 모델이 통하는 범위 (9장 Bounded Context)
  → 경계를 넘는 통합 (10장 Context Map)
  → 코드 구조로 옮기기 (11장 헥사고날)
  → 트랜잭션과 일관성의 비용 (12장)
  → 곁가지 (13장 CQRS) / 판단력 (14장)
```

**이 순서의 비용**: 3~7장에서 애그리게이트를 만들 때 "이 모델이 어디까지 유효한가"라는
질문이 미뤄진다. 그래서 각 장에 "9장에서 다시 볼 문제" 라는 표시를 남겨 두고,
9장에서 앞장의 코드를 실제로 다시 쪼갠다. 미뤘던 문제를 해결하는 구조.

## 2. 장별 상세

각 장의 형식은 동일하다: **문제 상황 → 코드로 겪기 → 개념과 이름 → 리팩터링 → 한계와 반대의견 →
요약 → 퀴즈 → 직접 해보기.**

### 0장 — 이 교재를 읽는 방법과 한빛몰 이야기
- 교재 사용법(페이지 넘김, 접힌 상자, 퀴즈), 학습 트랙 선택
- 한빛몰의 사업/창고 구조, 등장인물(주문팀·창고팀·CS팀), 초기 용어집
- DDD가 한 문장으로 무엇인지. 이 시점에 정의를 외우려 하지 말라는 안내
- **페이지 6 · 0.5시간**

### 1장 — 왜 DDD인가: 잘 돌아가는 나쁜 코드
- `place_order()` 함수 하나에 83줄: 재고 확인, 금액 계산, 결제 호출, 메일 발송이 뒤섞인 코드
- 요구사항 3개를 순차로 추가해 보며 그 함수가 어떻게 썩는지 직접 관찰
- 빈혈 도메인 모델(anemic model), 트랜잭션 스크립트라는 이름 붙이기
- "그런데 트랜잭션 스크립트가 정답인 경우도 있다" — 언제인지 명시
- 도메인 / 도메인 모델 / 도메인 로직의 정의
- **코드 해설에 4페이지를 쓴다**(§5.1 원칙): 데이터베이스 구조와 관계도 → '배치'와 예약수량 개념
  → 83줄 코드를 세 덩어리로 나눠 행별 해설(트랜잭션, `%s` 바인딩, `COALESCE`,
  `SET x = x + n`, 트랜잭션 안의 외부 호출 위험)
- **페이지 17 · 3.0시간**

### 2장 — 도메인 모델의 최소 단위: Entity와 Value Object
- `int` 로 표현한 금액이 만드는 버그(원/센트 혼용, 반올림, 통화). `Money` 값 객체 도입
- 값 객체의 3특성: 불변, 값 동등성, 교체 가능. `@dataclass(frozen=True)` 로 구현
- `Address`, `Quantity`, `OrderNumber` — 어디까지 값 객체로 만들 것인가
- 엔티티: 식별자로 동등성을 판단. `Order`, `OrderLine`
- **판단 훈련**: 배송지 주소는 값 객체인가 엔티티인가? 회원 주소록의 주소는?
- 원시값 집착(primitive obsession)과 값 객체 과용, 둘 다의 비용
- **페이지 14 · 2.5시간**

### 3장 — Aggregate: 불변식을 지키는 경계
- 불변식(invariant)이란 무엇인가. 기획서 I1~I5를 코드로 강제하기
- `Order.add_line()`, `Order.cancel()` — 규칙이 객체 안에 있을 때 생기는 안전함
- 애그리게이트 루트, 외부에서 내부 엔티티를 직접 만지면 안 되는 이유
- 경계 긋는 기준: **한 트랜잭션에서 함께 일관돼야 하는 것만 한 애그리게이트로**
- `InventoryItem` + `StockBatch` 를 만들며 I7~I10(FEFO, 예약 수량) 구현
- **요구사항 추가: "입고 예정인 물건도 팔게 해주세요"** (은수). 이 장의 후반 축이다
  - 배치가 두 종류로 나뉜다(창고 / 입고예정). I18·I19 할당 우선순위 구현
  - "재고"라는 낱말이 셋으로 나뉜다: 실물재고 / 가용재고 / 판매가능수량(ATP). I20
  - 도현과 은수가 각자 다른 것을 "재고"라고 부르고 있었다는 사실 발견 → 9장 예고
- **경계에 걸리는 질문**: 출고 예정일을 계산하려면 어느 배치에서 할당됐는지 알아야 한다.
  그러면 주문이 재고 배치를 참조해야 하나? 방금 배운 "ID로만 참조" 규칙과 충돌한다
  - 해결: 할당 결과를 **값(출고 준비 완료일)으로 돌려받는다.** I21
- "주문 안에 재고를 넣으면 안 되나?" — 큰 애그리게이트가 만드는 동시성 충돌 문제
- 애그리게이트 간 참조는 **ID로만**
- **페이지 16 · 3.0시간** ← 가장 무거운 장. 이틀에 나눠 읽어도 된다

### 4장 — Repository: 도메인에서 DB를 밀어내기
- 도메인 객체 안에 `INSERT INTO` 가 있을 때 벌어지는 일
- 영속성 무지(persistence ignorance), 의존성 역전 원칙을 여기서 처음 설명
- `OrderRepository` 인터페이스(`Protocol`) → 메모리 구현 → SQLAlchemy 구현
- **애그리게이트 단위로 저장하고 꺼낸다.** 왜 `OrderLineRepository` 는 없어야 하는가
- 테스트가 갑자기 쉬워지는 순간(메모리 저장소로 도메인 테스트)
- 반대의견: "ORM 리포지토리가 이미 리포지토리 아닌가?" / 리포지토리를 만들지 않아도 되는 경우
- ORM(SQLAlchemy) 매핑 해설 1페이지 — 1장에서 본 생 SQL이 매핑 코드로 바뀌는 대응 관계
- **페이지 12 · 2.5시간**

### 5장 — Application Service와 계층 구조
- 유스케이스 `주문하기` 를 조립: 리포지토리에서 꺼내고 → 도메인 메서드 호출 → 저장 → 커밋
- 도메인 계층 / 응용 계층 / 인프라 계층 / 표현 계층. 의존 방향의 규칙
- **트랜잭션 경계는 응용 계층에.** Unit of Work 패턴 소개
- DTO와 커맨드 객체. 도메인 객체를 API 응답으로 그대로 내보내면 안 되는 이유
- 응용 서비스가 다시 뚱뚱해지는 안티패턴(1장의 재발) 식별법
- **페이지 13 · 2.5시간**

### 6장 — Domain Service, Factory, 그리고 스냅샷
- 어느 엔티티에도 넣기 어려운 규칙: `배송비계산기`, `등급별할인정책` → 도메인 서비스
- 도메인 서비스와 응용 서비스의 차이(가장 많이 헷갈리는 지점, 판별 질문 3개 제공)
- 복잡한 생성 로직: `Order.place()` 팩토리, 재구성(reconstitution)과 생성의 차이
- 기획서 I6: **주문은 왜 `Product` 를 참조하지 않고 이름·가격을 복사하는가**
- 기획서 I22: **고객에게 약속한 출고 예정일도 같은 이유로 스냅샷이다.**
  가격 스냅샷과 똑같은 논리인데, 이번에는 "약속"이라는 업무 개념이 붙는다.
  입고예정일이 바뀌면 약속일도 자동으로 바뀌어야 하나? — 아니다. 왜 아닌지가 이 절의 핵심
- **페이지 12 · 2.5시간**

### 7장 — Domain Event: 애그리게이트 사이를 잇기
- 문제: 주문이 확정되면 재고를 할당해야 한다. 두 애그리게이트를 한 트랜잭션에서 바꿔야 하나?
- 도메인 이벤트 정의, 애그리게이트가 이벤트를 모아두고 응용 계층이 발행하는 구조
- 핸들러 등록, 동기 처리 → 메시지 큐로 넘길 때의 차이
- 이벤트 이름은 **과거형**이어야 하는 이유. 명령(Command)과 이벤트의 차이
- 실패 시나리오: 재고 부족 이벤트가 나면 주문은 어떻게 되나(보상 트랜잭션 소개)
- **입고가 3일 지연됐다.** `입고지연됨` 이벤트 하나가 이미 약속을 받은 주문 수십 건의
  예정일을 흔든다. 재고 애그리게이트는 어느 주문이 자기를 기다리는지 모르는데 어떻게 알리나
  - 핸들러가 영향받는 주문을 찾아 `약속일_재조정()` 을 호출하고, 그 결과로
    `약속일변경됨` 이벤트가 다시 나와 고객 통지로 이어진다(이벤트 연쇄)
  - 이 장에서 이벤트가 "있으면 좋은 것"이 아니라 **없으면 못 만드는 것**이 된다
- 이벤트를 남용할 때의 비용: 흐름 추적 불가, 디버깅 난이도
- **페이지 13 · 2.5시간**

### 8장 — 유비쿼터스 언어: 코드와 대화가 같은 말을 쓸 때
- 창고팀의 "출고"와 CS팀의 "출고"가 다른 것을 뜻하는 실제 대화 재현
- `OrderData`, `ProcessManager` 같은 기술자 언어가 도메인 지식을 지우는 과정
- 용어집 만들기, 코드 리뷰에서 이름을 지적하는 기술
- 이벤트 스토밍 아주 얕게: 한빛몰 주문 흐름을 포스트잇으로 늘어놓기(SVG로 재현)
- **페이지 9 · 1.5시간**

### 9장 — Bounded Context: 하나의 모델은 어디까지 유효한가
- 8장의 "출고" 충돌을 해결하는 방법은 용어 통일이 아니라 **경계 나누기**
- **미뤄둔 문제 해결**: 요구사항 두 개가 들어온다 — "3개 묶음 세트를 판다", "같은 라면을
  낱개와 박스로 판다". 1~8장이 깔고 있던 "상품 1개 = SKU 1개" 가정이 깨진다
- 카탈로그·재고·창고 관심사가 다 들어 있던 `Product` 를 쪼개기 → 카탈로그 `Product` /
  재고 `Sku` / 창고 보관품목. 같은 단어가 컨텍스트마다 다른 것을 뜻함을 코드로 체험
- **`재고`도 마찬가지다.** 창고는 실물재고를, 재고 팀은 가용재고를, 주문은 판매가능수량(ATP)을
  "재고"라고 부른다. 3장에서 나눠 둔 세 개념이 사실 컨텍스트 경계의 흔적이었다
- 쪼갠 뒤 세 컨텍스트를 ID로 잇는 방법과, 무엇을 복사(스냅샷)할지 결정하기
- Bounded Context ≠ 마이크로서비스. 하나의 배포 단위 안에 여러 컨텍스트가 있어도 된다
- 경계를 잘못 그었을 때의 신호(양쪽을 항상 같이 고쳐야 함)
- **페이지 13 · 2.5시간**

### 10장 — Context Map과 통합 패턴
- 컨텍스트 맵 그리기(SVG): 한빛몰 7개 컨텍스트와 화살표의 의미
- 조직 관계 패턴: 파트너십, 고객/공급자, 순응자, 분리된 방법
- 기술 통합 패턴: 공유 커널, 개방 호스트 서비스, 발행된 언어, **ACL(부패 방지 계층)**
- PG사 API의 이상한 응답 코드를 우리 언어로 번역하는 ACL을 Python으로 구현
- 카탈로그↔주문에 공유 커널을 쓰지 **않기로** 한 결정의 근거
- **페이지 13 · 2.5시간**

### 11장 — 아키텍처: 계층형에서 헥사고날로
- 계층형 아키텍처의 한계(DB가 최하층에 있으면 도메인이 DB에 의존한다)
- 의존성 역전으로 층을 뒤집기 → 포트와 어댑터(헥사고날)
- 한빛몰 주문 컨텍스트의 디렉터리 구조를 실제로 제시
- 어니언/클린 아키텍처와의 관계(같은 아이디어의 다른 그림)
- 얼마나 지킬 것인가: 포트를 3개 만들 프로젝트와 안 만들 프로젝트
- **페이지 13 · 2.5시간**

### 12장 — 트랜잭션 경계와 결과적 일관성
- **한 트랜잭션에 하나의 애그리게이트** 규칙과 그 근거
- 동시성: 두 주문이 마지막 1개를 동시에 잡을 때. 낙관적 락(버전 컬럼) 구현
- **입고 예정 수량을 두 주문이 동시에 잡으면?** 실물이 없는 수량을 파는 것이라 초과판매의
  결과가 더 나쁘다(고객은 이미 날짜를 약속받았다). 예약 경합을 어디서 막을지 결정
- 분할 출고를 허용할지 결정하기: 창고에 3개, 입고예정 2개인 주문을 지금 3개만 보낼까
  (I21을 바꾸는 결정이다. 업무 규칙 변경이 코드 구조에 어떻게 번지는지 관찰)
- 결과적 일관성을 업무 규칙으로 승격시키기("재고 반영은 5초 내" 를 기획과 합의)
- 사가(Saga)/프로세스 매니저 소개: 주문–결제–출고 흐름의 실패 보상
- 규칙을 깨야 할 때: 한 트랜잭션에서 두 애그리게이트를 바꿔도 되는 조건
- **페이지 11 · 2.0시간**

### 13장 — (선택) CQRS와 이벤트 소싱 입문
- 상품 목록 100개에 **판매가능수량과 도착 예정일**을 표시해야 한다. 애그리게이트를 100개
  로딩해서 계산하는 순간 화면이 죽는다 → 읽기 모델이 필요한 가장 현실적인 이유
- 주문 목록 화면이 애그리게이트 로딩으로 느려지는 문제 → 읽기 모델 분리
- CQRS를 도입하는 최소 형태(같은 DB, 읽기 전용 쿼리 객체)부터
- 이벤트 소싱은 무엇이고 왜 대부분의 프로젝트에 과한가
- **이 장은 건너뛰어도 나머지에 영향이 없다.**
- **페이지 9 · 1.5시간**

### 14장 — 마무리: DDD를 쓰지 말아야 할 때
- 도메인 복잡도 vs 기술 복잡도. CRUD 앱에 DDD를 얹으면 벌어지는 일
- 부분 도입 전략: 핵심 도메인(Core Domain)에만 쓰고 나머지는 단순하게
- 핵심/지원/일반 하위 도메인 구분, 무엇을 직접 만들고 무엇을 사올 것인가
- 다음 읽을 책 순서와 각 책의 성격
- 자기 프로젝트에 적용하는 첫 스텝 체크리스트
- **페이지 7 · 1.0시간**

## 4. 학습 스케줄

시간 산정 기준: 본문 읽기 + 코드 따라 읽기 + 퀴즈 + "직접 해보기" 과제. 코드를 직접 타이핑해
돌려보면 장당 30~60분이 더 든다(권장한다. 아래 트랙에 이미 반영).

### 트랙 B — 표준 (추천)
**평일 하루 1시간, 주 5시간 → 7주**

| 주 | 진행 | 이 주가 끝나면 |
|---|---|---|
| 1주 | 0장, 1장, 2장(전반) | 나쁜 코드의 문제를 말로 설명할 수 있다. `Money` 를 만들 수 있다 |
| 2주 | 2장(후반), 3장(전반) | Entity와 Value Object를 구분하고, 불변식을 코드로 강제할 수 있다 |
| 3주 | 3장(후반), 4장 | 애그리게이트 경계를 근거와 함께 그을 수 있다 ← **가장 중요한 주** |
| 4주 | 5장, 6장 | 유스케이스를 조립하고, 무엇을 스냅샷할지 판단할 수 있다 |
| 5주 | 7장, 8장 | 도메인 이벤트로 애그리게이트를 잇고 트레이드오프를 말할 수 있다 |
| 6주 | 9장, 10장 | 시스템을 컨텍스트로 쪼개고 맵을 그릴 수 있다 |
| 7주 | 11장, 12장, 14장 | 아키텍처 구조를 잡고, 쓸지 말지 판단할 수 있다 |

13장(CQRS)은 8주차 또는 나중에 필요할 때.

### 트랙 A — 여유 (부담 없이)
**하루 30분, 주 7일 = 주 3.5시간 → 10주**
- 페이지 단위로 끊어 읽기 좋게 설계했으므로 30분에 4~6페이지가 적당하다.
- 주말 중 하루는 **복습만** 하는 날로 쓴다(퀴즈 다시 풀기).

### 트랙 C — 주말 집중
**토·일 각 3시간, 주 6시간 → 6주**
- 한 번에 한 장을 통째로 끝내는 방식. 애그리게이트(3장)·이벤트(7장)처럼 호흡이 긴 장에 유리하다.
- 단점: 평일에 잊는다. 주말 시작 시 앞장 요약 페이지를 먼저 읽는 습관 필요.

### 트랙 D — 단기 몰입
**하루 2~3시간, 주 12시간 → 3주**
- 업무에 곧 적용해야 할 때. 단, 3장·7장·9장은 시간을 줄이지 말 것.
- 1차 완독 후 **반드시** 자기 프로젝트에 한 컨텍스트를 적용해 보는 2차 학습이 필요하다.

### 어떤 트랙이든 지킬 것

1. **3장·7장·9장에서는 속도를 늦춘다.** 이 세 장이 DDD에서 가장 중요한 파트다. 나머지는 이 셋을 응용한다.
2. **퀴즈를 건너뛰지 않는다.** 해설에 본문에 없는 내용이 들어 있다.
3. **"직접 해보기"는 최소 절반은 실제로 한다.** 읽기만 하면 3주 뒤 남는 게 없다.
4. **막히면 표시하고 넘어간다.** DDD는 뒷장이 앞장을 다시 설명하는 구조라
   9장까지 가면 3장의 의문이 풀리는 일이 흔하다.

### 이해도 체크포인트

각 지점에서 아래 질문에 스스로 답해 보고, 못 하면 그 구간을 다시 읽는다.

- **3장 후**: "왜 주문과 재고를 하나의 애그리게이트로 묶지 않는가?" 그리고
  "실물재고·가용재고·판매가능수량의 차이를 도현과 은수에게 각각 설명할 수 있는가?"
- **5장 후**: "이 로직은 도메인에 둬야 하나 응용 서비스에 둬야 하나?" 를 판단 기준으로 답하기
- **7장 후**: "이벤트로 처리하면 무엇을 잃는가?"
- **10장 후**: 내가 지금 다니는 회사 시스템의 컨텍스트 맵을 손으로 그려 보기
- **14장 후**: "지금 우리 프로젝트에 DDD를 도입할까?" 에 근거 있는 답 3줄
